## §1 原則

1. **認可・公開の可否・処置は固定の規則表と人が決める**
   - 認可はロールと規則表（§4）で判断し、LLM に委ねない。
   - コンテンツの公開可否はポリシールール表との突合と、必要に応じてモデレーターの判断で決める。
   - 掲示板の投稿の取り下げは、モデレーターの判断で行う。
   - 違反した住民への処置の内容はマスターが後で決める（OQ-037 → 決定、ADR-0032。内容は OQ-048、持ち越し）。決まるまで、処置を実行する手段は作らない。

2. **LLM は掲示板の審査で補助ラベルを付け、新聞では記事の文字を作るだけ**
   - 審査の LLM が返せるのは `ok` / `review` / `block` の 3 種のラベルだけ（ADR-0005）。
   - 新聞の LLM（J16）は、承認済みの素材から記事の文字を作るだけで、公開してよいかは決めない。出力は検査とルール表に当て、外れたら記事を決まった形で組む（OQ-051 → 決定、ADR-0055 の D8）。
   - LLM の出力がどのような値であっても、公開されてはならない物が公開されることはない。
   - LLM の出力によって、権限が与えられることも、処置が確定することもない。
   - LLM が失敗したとき・決められた値以外を返したときは、公開しない側（人の審査）に倒す。

3. **API の経路では LLM を呼ばない**（ADR-0014、api.md §1）
   - 認証・認可のパスに LLM は関与しない。
   - LLM の呼び出しはすべて worker（非同期バッチ）で行う（async.md §2。審査の J2 と新聞の記事の文字の J16 だけ、ADR-0039）。

4. **手紙の本文は LLM に渡さない**（ADR-0006・ADR-0072）
   - クローズドな手紙も配達の前に審査するが、ルール表だけで照合する（OQ-003 → 決定、ADR-0072、§5）。照合は投函のときに API が行う（OQ-052 → 決定、ADR-0069）。
   - 本文（一部や要約も）を LLM に渡さない。手紙の審査の経路には LLM のアダプタを渡さない。
   - 本文に触れてよい場面は §2.3 の 4 つに限る。通報された手紙（§5.4。OQ-043 → 決定、ADR-0078）と、送った人が確認を頼んだ確認待ちの手紙（§5.2。ADR-0069）は、モデレーターが 1 通ずつ確かめる。

5. **住民を守る制限は、住民が自分で外せる設定にしない**（OQ-043 → 決定、2026-11-19、ADR-0078 の D3）
   - 手紙と掲示板の審査（§5）・送信の上限・マッチングに街の外の連絡先の欄を設けないこと（FR-101）などを、住民の設定で外したり緩めたりできる形にしない。
   - ブロック（住民が自分で掛ける守り）を掛ける・外すのは住民のまま。
   - 方針は、老若男女・少年少女が使える、開かれていて安全な街（ADR-0078 の D1）。
   - 年齢で守り方を変えない（OQ-063 → 決定、2026-11-20、ADR-0057）。手紙と掲示板で止める基準（§5.1）と使える機能・権限（§4.2）は年齢に関係なく全員に同じで、年齢の区切りを置かない。
     詐欺と事件の防止も、年齢での制限でなく全員に同じ共通のルール（スパム検知・不審な挙動への対処、FR-120）で行う。不審な挙動への対処の中身は OQ-075（持ち越し、M4 の前に決める）。
   - 年齢は住民の設定をそのまま使い、確かめない（ADR-0041）。どの年齢にも危険な機能は設けない。年齢で守りが変わらないので、年齢を変えても守りは外れない。
     年齢と誕生日は登録で必須にし、あとから変えられない（OQ-064・OQ-077 → 決定、ADR-0093。§2.1）。変える経路がないので、年齢で何かを外すこともできない。

### §2.2 収集しないもの

以下の情報は収集しない。
例外は 1 つだけで、商店（段階 3）が公開するお店の実在の情報（お店の名前など）は「実名・氏名」の項目に当てない（ADR-0043 の D6）。
ほかの項目（電話番号・顔写真・位置情報・決済情報など）は、OQ-068・OQ-069 で決めるまで商店にも当てる。
担当者・経営者など個人の情報をどこまで出すかは公開の範囲にかかわるので、決めず、S3-2 の前にマスターに聞く（OQ-069 (3)）。
商店が出す実在の情報の項目と持ち方は OQ-069 で、契約と決済の情報（LP・問い合わせで受ける情報を含む）の扱いは OQ-068 で決める。
レポジトリ・テスト・シードに実在の名前を入れないこと（ADR-0038 の D5）は変えない。

- 実名・氏名
- 電話番号
- 年を含む生年月日（年齢は住民が設定した値をそのまま使うので要らない。ADR-0041 の D4）。誕生日（月日）は町の中の設定として集め（架空でよい）、年齢と同じに扱う（ADR-0093 の D5・D8）
- 年齢を確かめるための情報（本人確認の書類・外部の年齢確認の結果。年齢は確かめない、ADR-0041 の D2）。恋愛のための年齢確認も要らない（ADR-0024）
- 住民どうしの街の外の連絡先（マッチングの登録と提案に欄を設けない。FR-101。禁止は全ての書き込みに及び、ルール表の `real_info` で止める、ADR-0071。マッチングの中の守り方の細部は OQ-050）
- 顔写真・外見を識別できる画像（P-3 より）。段階 2 で住民がアップロードする画像は新聞用に加工し、元の画像は持たない。元の画像は加工が終わるか失敗した時点で消し、取りこぼしもアップロードから 24 時間 [assumed] を過ぎたあとの次の J14 で消す（最長で約 48 時間）。元の画像は住民にもモデレーターにも返さない（ADR-0074 の D5、FR-118）
- 位置情報（架空の住所のみ）
- 決済情報

### §2.3 手紙の暗号化

- 本文は AES-256-GCM で保存時に暗号化する（ADR-0006）。
- 鍵はサーバー側（KMS 相当）が管理し、鍵に版番号を付けて入れ替えられるようにする（ADR-0021）。
- 暗号化の付加データ（AAD）には手紙の ID を含め、別の手紙のデータを当てはめる攻撃を防ぐ（ADR-0021）。
- 本文に触れてよい場面は次の 4 つに限る（ADR-0072 の D4・ADR-0069、マスターの答え「厳格なアクセス制御」）。
  - (a) 送った人と受け取った人が、自分の手紙を読む（web）。
  - (b) 投函のときのルール表との照合（web の API の中、ADR-0069 の D2）。暗号化の前の平文を使い、復号はしない。平文はメモリの中だけに置き、DB・ログ・ジョブのペイロード・例外のメッセージに書かない。
    残すのはルール表の版と、当たったときの規則の ID だけ。当たって送った人が n を選んだ本文は保存しない。
    （もとは worker の J2 の照合で、OQ-052 → 決定、2026-11-20、ADR-0069 で置き換えた。worker は手紙を復号して照合しない）
  - (c) **決定**（OQ-043 の答え、2026-11-19、ADR-0078 の D2）: 通報された手紙を、モデレーターが確かめる（`GET /api/v1/admin/reports/{id}/letter`、api.md §7 F-08）。
    条件は、通報が `open`・当事者でない・二要素認証済み・1 回の操作で 1 通だけ。毎回 `moderation_actions` に `view_letter` を記録し（書けなければ本文を返さない）、
    応答は `Cache-Control: no-store`。条件に合わなければ 404。
    通報の行ができるのは、受取人が自分の郵便受けの行（`mailbox_item_id`）で通報した `delivered` の手紙だけ（ADR-0078 の D8・D9、§5.4）。送った人・ほかの住民は手紙を通報できないので、届いていない手紙（`pending`・`held`・`blocked`）や他人の手紙は (c) の経路に入らない。
  - (d) **決定**（OQ-052 の答え、2026-11-20、ADR-0069 の D5）: 送った人が確認を頼んだ確認待ちの手紙（`held`）を、モデレーターが確かめる（`GET /api/v1/admin/held-letters/{id}`、api.md §7 F-08）。
    条件は (c) と同じ（手紙が `held`・当事者（送った人・宛先の住民）でない・二要素認証済み・1 通だけ・毎回 `view_letter` を記録・`no-store`・合わなければ 404）。
- (a)・(b) は OQ-003 の答え（対象とする・LLM には渡さない）と OQ-052 の答え（送信時点でチェック）で決まった審査と配達に要る場面。人が手紙を読む (c) は OQ-043 の答え（「厳しい閲覧はプラスに働く」「ある程度の秘匿性は担保しないと」）で、(d) は OQ-052 の答え（「送った人の異議は有用」「モデレーター確認」）で決まった。
- 本文の一覧・検索の経路は作らない。通報されていない手紙は、送った人が確認を頼んだ `held` の手紙のほかは、モデレーターも読めない。`blocked`（却下した手紙）を見る経路もない（ADR-0069 の D5）。
- 手紙の本文は LLM に渡さない（§1 原則 4）。

### §2.4 保持期間と削除

ADR-0091 の退去の表と保持期間の表が正本（`staff_roles`・`auth_tokens`・`rate_limit_buckets`・メールの確認が済まない登録の行を含む、ADR-0091 の D8・D13・D14）。退去時の処理:

1. `residents.deleted_at` を現在時刻に設定（同期）。
2. 有効なセッションをすべて無効にし（`sessions.invalidated_at`）、その通知の購読を消す（同期、1 と同じトランザクション、ADR-0091 の D7・ADR-0090・ADR-0076）。
3. `account.erase` ジョブを積む（同期、1 と同じトランザクション、ID のみ）。
4. worker が J7 の最初の手順（手順 0）で、通知の購読の残り・セッションの行すべて（無効にした行も含む）・確認と再設定のトークン（`auth_tokens`。変更中の新しいメールアドレスを含む、ADR-0089 の D6）・認証情報（`credentials`。メール暗号化値・HMAC・パスワードハッシュ・TOTP の秘密）の行をこの順に消し、消したセッション・トークン・認証情報の行を `erasure_log` に記録する（非同期、ADR-0091 の D8）。
5. worker がブロックとロール（`staff_roles`、モデレーターだけ行がある。`erasure_log` に記録しない）を消し（J7 の手順 5、ADR-0091 の D13）、興味（`resident_interests`）と推し量った興味（`inferred_interests`、段階 2、ADR-0045）を消し、その住民の投稿から作った記事（`newspaper_articles`）を消して版を組み直す（非同期、J7・J8、ADR-0039）。新聞の誕生日の欄に載った行（`newspaper_birthday_entries`、組 1・2 を作る段階から）も消し、載った版を組み直す（ADR-0074 の D9）。
6. worker が、住所を `vacant_deleted` にするのと同じトランザクションで今の居住記録を終わらせ（`ended_at`・`is_current = false`、ADR-0091 の D10）、その住民の郵便受けの行を消したあと、`residents` を消す前に、その住民を指す列（`letters.sender_id`・`board_posts.author_id`・`reports.reporter_id`・`moderation_actions.moderator_id`・`images.uploader_id`・`tenancies.resident_id`）を 1 つのトランザクションで NULL にする（非同期、J7 の手順 7〜9、ADR-0091 の D9・D11）。行は残し、退去した住民の ID だけを外す。最後に `residents` を消して `erasure_log` に記録する（J7 の手順 10）。

### §2.5 ログに残さないもの

以下はログに記録しない。

- 手紙の本文・掲示板の投稿本文（操作ログ・アクセスログには含めない）。投函のときの照合で使った手紙の平文と、422 になった手紙の本文も、ログ・例外のメッセージに出さない（ADR-0072・ADR-0069）
- 手紙の照合で当たった規則の ID（`letters.matched_rule_id` と §7.1 の集計にだけ置き、アクセスログ・応答には出さない。ADR-0069 の D4）
- パスワード・セッションのトークン（DB にも平文を持たず、`sessions.token_hash` の SHA-256 だけを持つ、ADR-0089 の D1）・TOTP の秘密とコード
- メールアドレスの平文（ハッシュ・暗号化値のみ）
- 通報の詳細内容（通報 ID の参照のみ記録する）
- 通知の購読の `endpoint`・端末の鍵（`p256dh`・`auth`）・通知の中身（件数を含む）（ADR-0076）
- 住民の興味（選んだものも推し量ったものも）・住所録の検索語と過去の新聞の検索語（`?q=`。アクセスログのクエリ文字列も伏せる）。住所録の検索から興味を集めない（ADR-0045 の D1）。過去の新聞の検索語は、照合のあとメモリの外に出さない（DB・ジョブのペイロード・例外のメッセージにも書かない、ADR-0045 の D3・D4）。新聞の LLM のプロンプトと出力の全文もログに出さない
- 住民の年齢と誕生日（登録の要求・`/me`・プロフィールの応答の年齢と誕生日、誕生日の欄の中身。アクセスログ・エラー報告・メトリクス・ジョブのペイロードにも書かない、ADR-0093 の D8）

### §2.6 適用法令（仮定）

架空のサービスの設計として、日本の個人情報保護法（APPI）に準拠することを仮の前提にする [assumed]。
実際のサービスを運営する場合は法令の確認と専門家の助言が必要。
過去の新聞の検索から興味を推し量ること（ADR-0045）は、マスターの答え（OQ-059、2026-11-20）で、知らせるが個別の同意は取らず、推し量った興味を本人が見て消す仕組みは設けない。
住民は推し量ることを止められない（マスターの答え OQ-072、2026-11-21、ADR-0053）。
利用目的の知らせ方と、本人から開示・消去・利用の停止を求められたときの対応は OQ-032 で調べ、答えと食い違う求めがあれば新しい要回答としてマスターに出す。

## §3 認証

関連 ADR: ADR-0080（メール＋パスワード方式・認証の経路）、ADR-0090（サーバー側セッション・再認証・二要素認証）

### §3.1 方式

- **メールアドレス＋パスワード** を採用する（ADR-0080 の D1）。
- ソーシャルログイン・パスキーは将来の選択肢として ADR-0080 に記録するが、当面は採用しない。
- 登録時にメールを確認する（確認メールのリンクを開き、`POST /api/v1/email-verifications` で確認が済むまでアカウントを有効化しない。ADR-0080 の D2・D6）。確認のメールは `POST /api/v1/email-verification-requests` で送り直せる。
- **確認が済まない登録の期限**（ADR-0087、OQ-046 → 決定）: 確認が済まない登録が住所を押さえるのは `credentials.created_at` から 24 時間 `[assumed]`。確認のリンクも同じ時刻に切れ、送り直しても延びない。期限を過ぎた登録には送り直しても確認のメールを送らず、同じ 202 を返す。期限を過ぎたトークンは 400 `token_invalid`、ログインは 401 `unauthenticated`（期限の前と同じ）。期限を過ぎた登録は J14 が行ごと消し（`async.md` J14）、登録の要求も同じ住所か同じメールアドレスの期限切れの登録を先に消してから割り当てる。消した住所は使われたことのない住所として候補に戻る。
- アカウントがあるかどうかを応答から推測できないようにする（ADR-0080 の D4〜D7）。ログインの失敗は、メールアドレスがない・パスワードが違う・確認が済んでいない、のどれも同じ 401 `unauthenticated`。再設定の依頼と確認のメールの送り直しは、住民がいてもいなくても同じ 202 と同じ本文で、送るときだけメールを送る。
- 経路の名前と状態コードは `api.md` §7 F-02。

### §3.2 パスワードの要件と保存

- パスワードは 12 文字以上 [assumed]。
- **Argon2id** でハッシュにして保存する。
- 広く知られた漏えいパスワードのリスト（ローカルの辞書）と照合し、一致したら拒否する。
- パスワードの再設定は、`POST /api/v1/password-reset-requests` で依頼し、メールのトークンと新しいパスワードを `POST /api/v1/password-resets` に送って済ませる（ADR-0080 の D7）。トークンは 30 分で切れ [assumed]、1 回だけ使える。違う・切れた・使ったトークンは、どれも 400 `token_invalid`。再設定が済んだら、その住民のセッションの行をすべて消す。
- パスワードの変更（`PUT /api/v1/me/password`）には再認証が要り（§3.4）、変えたら今のセッションのほかのセッションの行をすべて消す（ADR-0090 の D7）。
- メールアドレスの変更（`PUT /api/v1/me/email`）には再認証が要る（§3.4）。新しいアドレスで確認が済むまで今のアドレスのままで、新しいアドレスをほかの住民が使っていても同じ 202 を返す。確認が済んだら、前のアドレスに変わったことを知らせる。流量の制限の対象で、超えたら 429 `rate_limited`（§3.5、ADR-0090 の D7）。

### §3.3 セッション

詳細は ADR-0090 を参照。

- セッションはサーバー側（DB）に持つ。JWT 等のステートレストークンは採用しない。
- Cookie は `__Host-` プレフィックス・`HttpOnly`・`SameSite=Lax`・`Secure` を設定する。
- **有効期限**: 操作なしで 30 日、発行から 90 日で切れる [assumed]。
- **複数デバイス**: 同時に複数の端末でセッションを持てる。住民は `GET /api/v1/sessions` で自分の有効なセッションを見て、`DELETE /api/v1/sessions/{id}` で 1 つずつ取り消せる（ADR-0090 の D2・D3）。一覧の `id` は Cookie の値とは別の識別子で、IP アドレスと端末の情報は持たない。
- **無効にする方法**（ADR-0090 の D4）: `invalidated_at` を付けるのは退去の受付だけ（§2.4、ADR-0091 の D7）。退去した住民のセッションの行は、J7 の最初の手順ですべて消す（ADR-0091 の D8）。
  ほかの無効化はどれもセッションの行を消す: ログアウト・セッションの取り消し・パスワードの再設定の完了（すべて）・パスワードの変更（今のセッションのほかすべて）・強制ログアウト・二要素認証の解除（そのモデレーターのすべて）。
- **強制ログアウト**: 運用者の CLI だけで行い、その住民のセッションの行をすべて消す。HTTP の経路（admin の経路を含む）は作らない（ADR-0090 の D4・ADR-0032）。
- セッションの行を消すとき・退去の受付で無効にするときは、その端末の通知の購読も同じトランザクションで消す（ADR-0090 の D4・ADR-0076）。
  ログアウトした端末には配達完了の通知が届かない。
- `sessions` の表（db.md §2、ADR-0089 の D1）: `id`（一覧で見せる識別子。Cookie の値とは別）・`token_hash`（Cookie のセッション ID の SHA-256。平文は持たない）・`resident_id`・`created_at`・`last_seen_at`・`expires_at`（`least(created_at + 90 日, last_seen_at + 30 日)`）・`reauthenticated_at`・`second_factor_at`（二要素認証を済ませた時刻）・`invalidated_at`。

### §3.4 再認証

- **条件**: そのセッションで直近 10 分以内にパスワードを入力していること [assumed]（ADR-0090 の D5）。確認は `sessions.reauthenticated_at` で行い、ログインと再認証（`POST /api/v1/sessions/current/reauthentication`）のときに書く。
- 再認証のパスワードが違えば 401 `reauthentication_failed` を返し、セッションは残す。試行は流量の制限の対象で、住民ごとに 10 回／15 分（§3.5、ADR-0090 の D5・ADR-0088 の D2）。
- **再認証が必要な操作**（MVP の 6 つ。段階 2 のエクスポートは作るときに足す、`roadmap.md` S2-6）: 退去（`DELETE /api/v1/me`）・パスワードの変更（`PUT /api/v1/me/password`）・メールアドレスの変更（`PUT /api/v1/me/email`）・二要素認証の登録（`POST /api/v1/me/second-factor`）・通報への操作（`POST /api/v1/admin/reports/{id}/actions`。投稿の取り下げを含む）・確認待ちの手紙への操作（`POST /api/v1/admin/held-letters/{id}/actions`）。
- 条件を満たさなければ 401 `reauthentication_required` を返し、何も変えない。確かめる順番は、認証 → 流量の制限（§3.5）→ ロールと二要素認証（admin の経路、§4.1）→ 再認証 → 入力の検証と対象の確かめ（ADR-0090 の D5）。認証なしの経路は、流量の制限を最初に確かめる。
- 住民への処置の経路を作るとき（OQ-048）は、その操作も再認証の対象に足す。

### §3.5 CSRF 対策と流量の制限

- CSRF 対策: `Origin` ヘッダの検査 ＋ 独自ヘッダ（`X-Requested-With` 相当）の確認。
- **流量の制限**（ADR-0088・ADR-0089 の D4）: PostgreSQL の `rate_limit_buckets`（`db.md` §2）で、固定の窓ごとに数える。1 つの要求に当たる規則をすべて数え、どれか 1 つでも上限を超えたら 429（code は `rate_limited`。手紙・投稿・住所録の追加の 1 日の上限の `daily_limit_reached` とは分ける）を返し、本来の処理をしない。残りの回数・窓の終わりの時刻・`Retry-After` は返さない（api.md §5）。
  規則の表（正本。値はどれも `[assumed]`。経路は api.md §7）:

  | 経路 | 数える主体 | 上限 | 守るもの |
  |---|---|---|---|
  | `POST /api/v1/registrations` | IP | 3 回／1 時間、10 回／1 日 | 開放式の登録の入り口（ADR-0030 の D2）・空き家を順に試す探りと先に押さえること（ADR-0084 の D18） |
  | `POST /api/v1/sessions` | 要求のメールアドレス | 10 回／15 分 | 1 人へのパスワードの総当たり |
  | `POST /api/v1/sessions` | IP | 50 回／15 分 | 多くのアドレスへの試し |
  | `POST /api/v1/sessions/current/reauthentication` | 住民 | 10 回／15 分 | 端末を取った人の総当たり（ADR-0090 の D5） |
  | `POST /api/v1/email-verifications` | IP | 20 回／1 時間 | トークンの総当たり |
  | `POST /api/v1/email-verification-requests` | 要求のメールアドレス | 3 回／1 時間 | ほかの人へのメールの踏み台 |
  | `POST /api/v1/email-verification-requests` | IP | 10 回／1 時間 | 同上・アカウントの有無の探り |
  | `POST /api/v1/password-reset-requests` | 要求のメールアドレス | 3 回／1 時間 | 同上 |
  | `POST /api/v1/password-reset-requests` | IP | 10 回／1 時間 | 同上 |
  | `POST /api/v1/password-resets` | IP | 20 回／1 時間 | トークンの総当たり |
  | `PUT /api/v1/me/email` | 住民 | 3 回／1 時間 | 任意のアドレスへのメールの踏み台（ADR-0090 の D7） |
  | `GET /api/v1/addresses/occupancy`・`GET /api/v1/addresses/candidates`（合わせて数える） | IP | 60 回／10 分 | 街のすべての家を返す認証なしの経路の負荷（ADR-0084 の D18） |
  | `POST /api/v1/reports` | 住民 | 10 回／1 時間 | 大量の通報 |
  | `POST /api/v1/blocks` | 住民 | 20 回／1 時間 | 住所を順に試す探り（T-05） |
  | `GET /api/v1/profiles/{address}` | 住民 | 60 回／1 時間 | 同上 |
  | `GET /api/v1/address-book`（検索語 `?q=` があるときだけ） | 住民 | 60 回／1 時間 | 同上 |
  | 上の表にない `/api/v1/*` の経路（既定。表にない経路をすべて合わせて数える） | 認証の要る経路は住民、認証なしの経路は IP | 300 回／5 分 | 人の操作でない連続の要求 |

  段階 2 の過去の新聞の検索（FR-119）は、作るときに住所録の検索と同じ 60 回／1 時間を当てる。1 日の上限（`daily_limit_reached`）と相互にならない追加の停止（`add_suspended`）は、この表と重ねて当てる。
- **数え方**（ADR-0088 の D3）: 主体（IP・メールアドレス・住民 ID）は平文で持たず、`HMAC-SHA-256(RATE_LIMIT_HMAC_KEY, <規則の名前> ":" <主体>)` を `key` にする（§6.1）。メールアドレスは小文字にそろえる。IPv6 は /64 にまとめる。成功も失敗も、上限を超えた要求も同じに数える。数えは本来の処理とは別の短いトランザクションで先に書き、本来の処理が 400・409 で戻っても残る。
  確かめる順番は、認証の要る経路は認証のすぐあと（§3.4 の順の認証とロールの間）、認証なしの経路は最初。上限に当たったことを住民・モデレーターに知らせない。
- メールアドレスの変更は住民が入れた任意のアドレスに確認のメールを送るので、ほかの人のアドレスへ大量にメールを送る踏み台にさせない（ADR-0090 の D7）。
  登録の住所は地図の空き家の印からも選べ、登録の要求は提示した候補かどうかを確かめない（ADR-0082 の D3・ADR-0084 の D7）。登録の制限が、空き家を順に試して 409 から前に使われた住所を探ることと、決まった住所を先に押さえることの数も抑える（ADR-0084 の D18）。1 つの IP から 1 日に押さえられる住所は 10 までで、確認が済まなければ 24 時間で手放す（ADR-0087）。
- 入居の一覧（`GET /api/v1/addresses/occupancy`、認証なし）は、街のすべての家を毎回返す認証なしの経路なので、負荷（DoS）を抑えるために IP ごとに数える（ADR-0084 の D18）。
  応答はキャッシュせず、要求を受けたときの状態を返す（ADR-0084 の D14・D18 `[assumed]`）。繰り返し取った差分から、どの住所でいつごろ登録や退去があったかが分かることは、答え 1「全員にいつでも公開してOK」の範囲で受け入れる（流量の制限はこれを止めるためのものではない。§7 の T-05）。
- 手紙の投函で 422（`letter_needs_review`・`letter_rejected`）になった回数と、手紙のほかの書き込みで 422（`content_rejected`）になった回数も、合わせて住民ごとに数え、超えたら 429（`rate_limited`）を返す。試し書きでルール表の項目を探られないようにするため（ADR-0069 の D7・D11・ADR-0070 の D4・§7 の T-22）。値は OQ-065（持ち越し、M4 の前に決める）で、上の規則の表には入れない（ADR-0088）。
- 住所録への追加は、住民ごとに JST の暦日で 1 日 20 件まで `[assumed]`。超えたら 429（`daily_limit_reached`）を返す。住所を変える `PATCH /api/v1/address-book/{id}` も同じ上限に数え、数えはエントリを消しても減らさない（`db.md` §2 `address_book_daily_counts`。消して足し直す・住所を書き換えるで上限を越えさせない）。住所を順に足して、相手が自分を足しているか（`acquainted`）を大量に探られないようにするため（ADR-0065 の D4・§7 の T-23）。
- 相互にならない住所録の追加は自動で止める（ADR-0066）。追加と住所を変える `PATCH` のたびに、同じロックの中で、今日を含む直近 7 日に数えた件数 N と、そのうち今互いに足しているエントリの数 M を求め、N ≥ 100 かつ M < N × 2% なら 429（`add_suspended`）を返して何も変えない `[assumed]`。
  割合・件数・残り・解除の時刻は返さない。止めるのは追加と住所を変える `PATCH` だけで、止めた状態は保存せず、7 日の窓から外れるか足し返されれば戻る。手で解除する経路はない。足された側にもモデレーターにも住民ごとには知らせない（アカウントへの処置ではない。処置は OQ-048）。

### §3.6 メールアドレスの扱い

- DB に保存するのは **暗号化した値** と **HMAC 値**（検索用）のみ（ADR-0080 の D3）。
- 平文のメールアドレスはログに残さない（§2.5）。

## §4 権限

関連 ADR: ADR-0020（ロールと権限表）

### §4.1 ロール

| ロール | 説明 | 付与方法 |
|--------|------|---------|
| `resident`（住民） | 一般の住民。登録後に自動付与 | 自動 |
| `moderator`（モデレーター） | 掲示板・通報の審査担当 | 運用者 CLI のみ（ADR-0020） |

- ロールは住民自身・API 経由で変更できない。運用者の CLI のみが付与・剥奪できる。
- モデレーターには二要素認証（TOTP）を必須とする [assumed]（ADR-0020・ADR-0090 の D6）。
  - 登録は `POST /api/v1/me/second-factor`（再認証が要る。秘密を 1 度だけ返す）、有効にするのは `POST /api/v1/me/second-factor/confirmation`（`totp_code`）。
  - 有効にしたモデレーターはログインで `totp_code` も送る。正しいパスワードで `totp_code` がなければ 401 `second_factor_required`、コードが違えば 401 `unauthenticated`。
  - admin の経路は、二要素認証を済ませたセッションだけが呼べ、済ませていなければ 403 `forbidden`。手紙を返す経路と確認待ちの手紙への操作は、§4.2 の条件のとおり 404。
  - 作り直しと解除は運用者の CLI だけで行い、解除したらそのモデレーターのセッションの行をすべて消す。HTTP の経路は作らない。
- モデレーターは自分が当事者（送信者・受取人・通報者・被通報者）の案件を処理できない。
- ロールの付与の記録は `staff_roles` の表（db.md §2、ADR-0089 の D2）: PK (`resident_id`, `role`)・`role` は `moderator` だけ・`granted_at`・`granted_by`。付与は CLI が行を入れ、剥奪は行を消す。退去では J7 の手順 5 が行を消す。
- TOTP の秘密は `credentials` の `totp_secret_encrypted`（メールアドレスと同じ鍵輪で暗号化、AAD に用途を入れる）・`totp_key_version`・`totp_enabled_at`・`totp_last_step` に持つ（db.md §2、ADR-0089 の D3）。平文は DB・ログに持たない。退去では `credentials` の行と一緒に J7 の手順 0 で消える。

### §4.2 権限表

規則は C3 の 1 か所に持ち、許可と拒否の両方をテストする（ADR-0020）。
どの規則にも住民の年齢の条件を持たせない。使える機能・権限は年齢に関係なく全員に同じ（OQ-063 → 決定、2026-11-20、ADR-0057 の D2）。

#### 郵便受け（`mailbox_items`）

| 操作 | 本人 | 他の住民 | モデレーター |
|------|------|---------|------------|
| 自分の郵便受けを読む | ✓ | ✗（404） | ✗（404） |

### §4.3 存在の秘匿

他人のデータは **404** で返す（ADR-0014）。403 で存在を明かさない。

例外は手紙の通報（`POST /api/v1/reports` の `mailbox_item_id`）。ほかの住民の行・見せる前の行・削除した行・新聞や掲示板の行・存在しない ID には、受け付けたときと同じ **202** と同じ本文を返し、何も保存しない（ADR-0078 の D10）。
通報は処理状態を返さないので、202 にそろえると郵便受けの行の存在と状態を探れない。

## §5 モデレーション

関連 ADR: ADR-0005（モデレーション方針）・ADR-0072（クローズドな手紙の審査）・ADR-0038（商店街の発信も配達の前に審査する）・ADR-0069（手紙は送るときに 2 段で照合し、送った人が頼んだ手紙をモデレーターが確かめる）・ADR-0070（絶対NGと絵文字の入力不可を全ての書き込みに当てる）・ADR-0071（街の外の連絡先は全ての書き込みで止める）

### §5.1 対象

| 対象 | 審査方法 |
|------|---------|
| 掲示板の投稿（`board_posts`） | 書いたときに絵文字の検査と、ルール表の `reject` の段の照合（当たれば 422 `content_rejected` で保存しない、ADR-0070）→ 締め切りのあとに自動審査（LLM ラベル）→ 規則表→ 必要に応じて人の審査 |
| クローズドな手紙（`letters`、個人宛・グループ宛） | 投函のときにルール表の手紙の項目だけで照合する。LLM には渡さない（ADR-0072）。`reject` の段に当たったら送れない。`review` の段に当たったら送った人が確認を頼むかを選び、頼んだ手紙だけをモデレーターが確かめる（ADR-0069、§5.2）。本文に絵文字は入れられない（入力の検査、ADR-0069 の D13）。通報があれば §5.4 |
| 商店街の発信（コミュニティ・商店、段階 3） | 掲示板の投稿と同じ（書いたときに絵文字の検査と `reject` の段の照合、配達の前に審査し、承認の前には出さない。ADR-0038 の D4・ADR-0070） |
| ニックネームと自己紹介（`residents`）・住所録のメモ（`address_book.memo`）・通報の理由（`reports.reason`）・マッチングの自由記述（段階 3、設けるなら。OQ-050） | 書いたときに絵文字の検査と、ルール表の `reject` の段の照合だけ。当たれば 422 `content_rejected` で保存しない（値も変えない）。`review` の段・LLM・人の審査は当てない（ADR-0070 の D3） |
| 検索語（住所録・段階 2 の過去の新聞） | 絵文字の検査だけ（400）。ルール表には当てない（ADR-0070 の D2・D3） |
| 新聞の記事の文字（J16 の LLM の出力、`newspaper_articles`） | 長さ・文字だけであること・絵文字がないこと（ADR-0070 の D6）の検査と、ルール表の掲示板向けの項目。外れたら記事を決まった形（外のニュースは素材の題と本文そのまま。投稿は決まった見出しで、まとめなし、ADR-0054 の D10）にする。投稿の素材の出力は見出しだけを使い、ほかは保存しない（ADR-0054 の D9）。素材は承認済みのものだけ（ADR-0055 の D8） |
| 取り込んだ外のニュース（J17、`external_news_items`） | 文字だけにし、ルール表の掲示板向けの項目に当てる。当たったら・絵文字を含んだら保存しない（ADR-0039 の D6・ADR-0070 の D6） |

ルール表の各項目は、規則の ID・版・当てる対象（掲示板の投稿 / 手紙）・種類を持ち、手紙の項目はさらに段（`tier`: `reject` / `review`）を持つ（ADR-0069 の D10）。
手紙の項目のうち `reject` の段の規則は、手紙のほかの全ての書き込み（上の表）にも書いたときに当てる（ADR-0070 の D3。持ち方は `[assumed]`）。
手紙に当てる項目は次の 4 種類（OQ-052 → 決定、2026-11-20・OQ-076 → 決定、2026-11-21・OQ-087 → 決定、2026-11-22、ADR-0069 の D1）。項目は送る人・受け取る人の年齢に関係なく全員に同じに当て、ルール表（段を含む）に年齢の条件を持たせない。年齢層ごとに別の言葉の一覧を持たない（OQ-063 → 決定、2026-11-20、ADR-0057 の D1）。掲示板の項目も同じ。

| 種類 | 中身 | 段 | 備考 |
|------|------|----|------|
| `spam` | 一般的なスパム（宣伝や勧誘の決まり文句・同じ文の繰り返しなど） | `review` だけ | 決める規則の細部は OQ-065 |
| `external_link` | 街の外へのリンク（URL の形の文字列） | URL の形は `reject`、崩した形など疑いは `review` | メールアドレスと電話番号は含めない（`real_info` で扱う）。形の細部は OQ-065 |
| `adult_words` | 成人向け（18 禁）の言葉 | 直接的な性的な言葉は `reject`、言い換えなど疑いは `review` | 一覧は公開レポジトリに置かない。置き場は OQ-065 |
| `real_info` | 本当の居住地（街の外の住まい）・本当の年齢・街の外の連絡先（メールアドレス・電話番号・他のサービスのアカウントなど）。聞く文・自分から書く文・ほかの人のものを書く文のどれも（ADR-0069 の D12・ADR-0071） | はっきりした形（メールアドレス・電話番号の形の文字列・はっきり聞く問い）は `reject`、疑いは `review` | 架空の街の住所・住民が設定した年齢・住まいと結び付かない地名・本名・学校・勤め先は対象にしない `[assumed]`。形の細部は OQ-065 |

- 照合はまず `reject` の段に当て、当たれば 422（`letter_rejected`）で送れない（確認に回さない）。当たらなければ `review` の段に当て、当たれば送った人が y / n を選ぶ。両方に当たる本文は `reject` を先にする（ADR-0069 の D10・D11）。
- どの規則をどちらの段に置くか・「疑い」の形（崩した URL・言い換えなど）の細部は OQ-065（持ち越し）。
- テストは偽の規則で確かめ、レポジトリに本物の言葉の一覧と規則を入れない: `review` の段は目印の文字列 `EXAMPLE_LETTER_RULE_DO_NOT_USE`、`reject` の段は `EXAMPLE_LETTER_REJECT_RULE_DO_NOT_USE` に当たる規則。
  URL・メールアドレス・電話番号の形の規則は言葉の一覧ではないので、本番の規則を偽の値（`https://example.invalid/`・`contact@example.invalid`・`000-0000-0000`）で確かめる（ADR-0069 の D1 `[assumed]`）。
- `review` の段に当たった手紙は、送った人が y を選べば `held` になり、モデレーターが承認すれば届く（ADR-0069 の D4・D5）。モデレーターが絶対NGと見れば `reject` する。
- 絵文字はルール表ではなく入力の検査で止める（全ての書き込みと検索語に入力できない。API は 400 `validation_failed`、ADR-0069 の D13・ADR-0070 の D2）。顔文字は止めない。
- 保存済みの書き込みは、ルール表の版が上がっても当て直さない（ADR-0069 の D3・ADR-0070 の D5）。

違法な物（大麻など）の取引の場にしないための項目は、まだ置かない。別のチケットで設計する（OQ-053、持ち越し、ADR-0078 の D6）。

FR-101（連絡先の共有の禁止）は全ての書き込みに及び、ルール表の `real_info` で止める（OQ-041・OQ-087 → 決定、ADR-0071 の D2・D3）。手紙は 422 `letter_rejected`（疑いは y / n）、ほかの書き込みは 422 `content_rejected`。手紙のほかの書き込みでは疑いの形（`review` の段）を止めず、J2 の掲示板向けの項目と LLM の基準に `real_info` は入れない（ADR-0070 の D3）`[assumed]`。

### §5.2 判定フロー

```
住民が投稿する（POST /api/v1/board/posts）
  ↓
0. 形式の確認（字数・絵文字があれば 400 validation_failed）→ ルール表の `reject` の段に当たれば
   何も保存せずに 422 content_rejected（当たった規則は返さない。ADR-0070 の D3）
   → 当たらない: `awaiting_review` で保存
  ↓
投稿が締め切りを過ぎる
  ↓
1. ポリシールール表に当たるか？
   → YES: 即却下（`rejected`）。理由とルール表の版を記録
   → NO: 次へ

2. LLM にラベルを依頼（本文のみを渡す。ID・送信者は含めない）
   → `ok`   : 承認（`approved`）
   → `review`: 人の審査へ
   → `block` : 却下（`rejected`）→ 住民は異議申し立てが 1 回できる [assumed]
   → 失敗・想定外の値: 人の審査へ（公開しない側に倒す。§1 原則 2）

3. 人の審査（モデレーター）
   → 承認（`approved`）/ 却下（`rejected`）
```

- 承認されていない投稿は配達しない（ADR-0005）。
- 判定には使用したルール表の版を記録する（再現性のため）。
- ニックネームと自己紹介・住所録のメモ・通報の理由は 0 だけで、当たらなければそのまま保存する（審査の流れに乗せない、ADR-0070 の D3）。確かめる順番は、形式（400）→ `reject` の段（422）→ 上限（429）。

**手紙の判定フロー**（ADR-0069・ADR-0072 の D3）:

```
住民が手紙を投函する（POST /api/v1/letters）
  ↓
0. 形式の確認（本文に絵文字があれば 400 validation_failed。何も保存しない）→ 知り合いの確認（ADR-0065 の D5）
  ↓
1. API が暗号化の前に、ルール表のうち手紙に当てる項目に当たるか？（LLM は呼ばない）
   → `reject` の段に当たる: 何も保存せずに 422 letter_rejected（request_review があっても同じ。当たった規則は返さない）
        web は決まった文面を出す。送った人は本文を直して送り直せる
   → `review` の段だけに当たり、request_review がない: 何も保存せずに 422 letter_needs_review（当たった規則は返さない）
        ↓ web のポップアップで送った人が選ぶ
        n: 何も送らない（何も保存しない）
        y: request_review: true で送り直す → 2 へ
   → どれにも当たらない: `pending` で保存（ルール表の版を記録）。配達の前に照合し直さない
2. もう一度照合して `review` の段だけに当たる → `held`（確認待ち）で保存（当たった規則の ID と版を記録）。送った人には「確認中」
   （どれにも当たらなければ 1 の「当たらない」と同じ。`reject` の段に当たれば 1 の 422 letter_rejected と同じ）
  ↓
3. モデレーターが 1 通ずつ確かめる（当事者でない・二要素認証済み・毎回 view_letter を記録）
   → approve: `pending` にして次の配達回に入れる
   → reject : `blocked`（配達しない）。送った人には「届けられませんでした」
```

- 手紙は `moderation_queue` に入れない（db.md §2 の CHECK 制約 `content_kind <> 'letter'`）。
- 送った人には `held` を「確認中」、`blocked` を「届けられませんでした」とだけ見せ、当たった規則は見せない（api.md §7 F-04）。
- 送った人が y を選ぶと、モデレーターが本文を読むことをポップアップで知らせる（文言は OQ-065）。
- 確認待ちの手紙は `review` の段からだけ出る。`reject` の段に当たった手紙は保存せず、モデレーターも見ない（ADR-0069 の D5・D11）。
- 422（`letter_needs_review`・`letter_rejected`）は、当たったという事実を返すので、ほかの書き込みの 422 `content_rejected` と合わせて §3.5 の流量の制限を掛ける（T-22）。`letter_rejected` の文面は決まった文で、どの規則に当たったかを出さない（文言は OQ-065）。

### §5.3 プロンプトインジェクション対策

- 審査の LLM（J2）には投稿の本文だけを渡す（送信者の住所・ID・名前を含めない）。新聞の LLM（J16）に渡すものは下の「新聞の LLM」のとおり。
- 本番では、投稿の本文は外部のサービス（Anthropic API。秘書の暫定の選定、ADR-0086）に渡る。手紙の本文は渡さない（§1 原則 4）。住民への説明の要否は OQ-032。
- LLM の出力はラベルの種類だけを検証し、それ以外の値を使わない（構造化出力で 3 つのラベルに限っても、検証は省かない。ADR-0086）。
- LLM の出力を直接 SQL やコマンドに組み込まない。

**新聞の LLM（J16、ADR-0055 の D8）**:
- 渡すもの: 承認済みの掲示板の投稿の本文（審査で外部の LLM にすでに渡している範囲）・取り込んだ外のニュース・版の興味の名前。
- 渡さないもの: 手紙（本文・一部・要約）・住所・ID・ニックネーム・住民ごとの興味。プロンプトは住民の表を読まずに組む。
- 出力の検査: 長さの上限・文字だけ（HTML を含めない。組版でエスケープする）・ルール表。外れたら決まった形にする。LLM のせいでは休刊にしない。
- 投稿の本文は書き換えずに `board_posts.body` をそのまま投稿の枠に載せ、その枠には LLM の文を入れない。LLM が書くのは外のニュースの見出しと記事・投稿の記事の見出し（生成部分）だけで、枠の外に新聞の文として置き、住民本人の文に見せない（ADR-0054 の D4〜D6）。
  住民の投稿を素材にした記事では、LLM は見出しだけを書き、まとめは書かない（OQ-074 → 決定、2026-11-21、ADR-0054）。投稿の行は `body` を持たず（NULL）、文章アダプタが見出しのほかに返したものは保存せず紙面に出さない。見出しを書くために投稿の本文は今までどおり渡す。
- LLM の文に「AI が書いた文」の印は付けない（ADR-0054 の D1）。外部のサービスの規約が示すことを求めるかは、本番の文章アダプタを作る前に秘書が確かめる（OQ-073、持ち越し）。
- 本番では素材が外部のサービスに渡る（モデルは OQ-062）。住民への説明の要否は OQ-032（興味の収集と合わせて調べる）。

### §5.4 通報の流れ

1. 住民が手紙または掲示板の投稿を通報する（`reports` に行を作る）。
   手紙を通報できるのは受け取った住民だけで、自分の郵便受けの行（`mailbox_item_id`）で指す。行が本人のもの・`kind = 'letter'`・`visible_at` を過ぎた・`deleted_at IS NULL`・手紙が `delivered` のときだけ、
   `content_id` に `letters.id` を書いた行を作る。条件に合わなければ同じ 202 を返し、何も保存しない（§4.3）。手紙の ID（`letter_id`）は受け取らない（400）ので、送った人は自分の手紙（`pending`・`held`・`blocked` を含む）を通報できない（ADR-0078 の D8〜D10）。
2. モデレーターが通報の内容を確認する。
3. 通報された**手紙**は、モデレーターが **1 通だけ** 復号して確認できる（`GET /api/v1/admin/reports/{id}/letter`、ADR-0072 の D4 (c)。OQ-043 → 決定、ADR-0078）。
   通報が `open`・当事者でない・二要素認証済みのときだけ。見るたびに `moderation_actions` に `view_letter` を記録する（書けなければ返さない）。
4. 通報された掲示板の投稿はモデレーターが取り下げ（`rejected`）・維持（`approved` のまま）・異議対応を行う。
5. `reports` を `closed`（対処済み）/ `dismissed`（棄却）にする。
6. 違反した住民への処置の内容は、マスターが後で決める（OQ-037 → 決定、2026-11-19、ADR-0032。内容は OQ-048、持ち越し）。
   決まるまで、住民を停止・警告する経路は作らない。通報への操作は approve / reject / dismiss だけ（ADR-0032 の D2）。

### §5.5 モデレーターの内部不正対策

- モデレーターは自分が当事者の案件を処理できない（§4.1）。
- 通報された手紙と確認待ちの手紙の復号は、見るたびに `moderation_actions` に `view_letter` として記録し、定期的に運用者が確認できるようにする（ADR-0072・ADR-0069）。
- モデレーターが手紙の本文に触れられるのは、通報された手紙と、送った人が確認を頼んだ確認待ちの手紙を 1 通ずつ見る経路だけ。本文の一覧・検索・却下した手紙（`blocked`）を見る経路はない。
- 確認待ちの手紙の承認・却下も `moderation_actions` に `letter_id` 付きで記録する（ADR-0069 の D5）。
- モデレーターによる処置はすべて `moderation_actions` に記録する（ADR-0091 の保持期間: 1 年）。

## §6 秘密情報

### §6.1 秘密の一覧

| 秘密の種類 | 保持するプロセス | 説明 |
|-----------|--------------|------|
| DB 接続文字列 | web・worker | PostgreSQL への接続情報 |
| セッション署名鍵 | web | Cookie の署名に使う対称鍵 |
| 手紙の暗号化鍵（版付き） | web・worker | 手紙の本文の暗号化・復号に使う（ADR-0021）。web は投函の暗号化と §2.3 の (a)(c)(d) に使う。(b) の照合は暗号化の前の平文で行い、鍵を使わない（ADR-0069）。worker は手紙を照合しないので、照合のためには使わない（鍵の入れ替え（§6.3）の再暗号化などで使う） |
| 手紙に当てる成人向けの言葉の一覧 | web | 公開レポジトリに置かない（ADR-0069 の D1）。置き場（秘密と同じ扱いにするか、運用者の CLI で入れるか）は OQ-065。テストは偽の規則だけを使う |
| メールアドレスの暗号化鍵 | web・worker | メールアドレスと、モデレーターの TOTP の秘密（`credentials.totp_secret_encrypted`。AAD に用途を入れて分ける、ADR-0089 の D3）の暗号化・復号に使う（ADR-0080） |
| メールアドレスの HMAC 鍵 | web | メールアドレスの検索用 HMAC に使う（ADR-0080） |
| LLM の API キー | worker のみ | J2（審査）と J16（新聞の記事の文字、ADR-0039）だけが使う。web プロセスには渡さない |
| 外のニュースの配信元の認証情報 | worker のみ | J17 だけが使う（ADR-0039）。本番は OQ-060 のあと。テストは偽の配信元で、本物の認証情報を使わない |
| メール送信サービスの認証情報 | worker | 確認メール・休眠通知の送信に使う。本番のサービスはマスターの事前承認を得て選ぶ（OQ-039 → 決定、ADR-0033。進め方は OQ-049）。テスト環境はモックかローカルの SMTP で、本物の認証情報を使わない |
| 再設定トークンの署名鍵 | web | 確認と再設定のトークンの鍵付きハッシュ（`auth_tokens.token_hash`、ADR-0089 の D6） |
| 流量の制限の HMAC 鍵 | web | `rate_limit_buckets.key` の HMAC（ADR-0088 の D3）。IP とメールアドレスを平文で持たないため。入れ替えると数えが窓の途中から始め直しになるだけで、作り直しは要らない |
| VAPID 秘密鍵 | worker のみ | 配達完了の通知（Web Push）の署名に使う（ADR-0076）。公開鍵は web が返す（api.md §7 F-05） |

**LLM の API キーは worker だけが持つ。** web プロセス（API）には渡さない（§1 原則 3）。

運用者の CLI は、ふだんは worker と同じ秘密で動く。メールアドレスの HMAC 鍵の入れ替えのときだけ、その作業の間だけ HMAC 鍵を読む（`environment.md` §8.1・§8.3）。
web と worker は、自分の行にない秘密が渡されたら起動に失敗する（`environment.md` §8.1、ADR-0052 の D7）。

### §6.2 保管方法

| 環境 | 方法 |
|------|------|
| 本番（設計だけ） | 秘密管理のサービスに置き、起動のときにそのプロセスが読める秘密だけを環境変数で渡す。手紙とメールアドレスの鍵は鍵管理で包んだデータ鍵。IaC は秘密の入れ物だけを作り、値は入れない（`environment.md` §7.3・§8.2、ADR-0052 の D7）。事業者は OQ-085（持ち越し） [assumed] |
| 開発 | 各自の `.env`（バージョン管理に含めない）。値は `environment.md` §8.1 の偽の値 |
| テスト・CI | テストの準備のコードが偽の値を渡す。`.env.test` は使わず、CI に秘密を登録しない（`environment.md` §4.2・§5） |

- 偽の鍵が必要なとき（テスト・文書）は、本物と見分けがつく値（例: `EXAMPLE_KEY_DO_NOT_USE`）を使う。
- テストの環境変数の例は `example.invalid` ドメインのアドレスを使う（例: `test@example.invalid`）。

### §6.3 鍵の入れ替え

詳細な手順は `environment.md` §8.3（ADR-0052 の D8）。方針:

- 手紙の暗号化鍵は版番号で管理し、古い版で暗号化されたデータは次の便の前に再暗号化する（ADR-0021）。
  新しい版はまず全プロセスに復号用として配り、そのあとで暗号化の版を切り替える。再暗号化は `keys.reencrypt` のジョブ（`async.md` §2）が 1,000 件ずつ行う。
- メールアドレスの暗号化鍵を入れ替える場合は、全レコードを再暗号化してから古い版を無効にする（同じジョブ）。
- 無効にした古い版は、バックアップの保持の 30 日のあいだ復元のためだけに残し、そのあとに消す。漏えいしたときは待たずに消す（§6.4）。
- セッション署名鍵を入れ替えると既存のセッションがすべて無効になる。告知ページを用意する。
- VAPID の鍵を入れ替えると既存の購読がすべて無効になり、住民は通知を許可し直す（ADR-0076）。

### §6.4 漏えいしたときの手順

1. 漏えいした鍵を即座に無効化する。
2. 影響するセッションをすべて無効化する（セッション鍵が漏えいした場合）。
3. 漏えいした暗号化鍵の版で暗号化されたデータを新しい鍵で再暗号化する（手紙の鍵が漏えいした場合）。
4. 影響を受けた住民への通知（メール送信サービスで対応。本番のサービスはマスターの事前承認を得て選ぶ。ADR-0033、OQ-049）。
5. インシデントを `retros.md` に記録する。

### §7.1 検知の指標

以下の指標を収集・監視する。

- ログイン失敗回数（同一 IP・同一メール HMAC）
- パスワード再設定の申請回数
- 1 日の送信上限に達した住民の数
- 通報数の急増
- LLM 審査で `review` / `block` の割合の急変
- モデレーターによる手紙の復号件数（`moderation_actions` の `view_letter`）
- 手紙の投函で 422（`letter_needs_review`・`letter_rejected`）になった件数・`held` になった件数・`blocked` になった件数の急変（規則の ID ごと。本文は見ない。`letter_rejected` は保存しないので、数だけを数える、ADR-0069 の D11）
- 手紙のほかの書き込みで 422 `content_rejected` になった件数の急変（入力の種類と規則の ID ごと。住民の ID と本文は付けない、ADR-0070 の D3）
- 確認待ち（`held`）の手紙の数と、いちばん古い手紙の待ち時間（OQ-065 の扱いを決める手がかり）
- 新聞の J16 で `written_by = 'template'` になった記事の割合（LLM の失敗・検査に外れた出力の急増、ADR-0039）
- 住所録の追加と住所を変える更新で 429 `add_suspended` を返した回数（住民の ID を付けず、回数だけ。ADR-0066 の D5）
- 流量の制限で 429 `rate_limited` を返した回数（§3.5 の規則ごと。主体・`rate_limit_buckets` の `key` は付けない、ADR-0088 の D4）

詐欺と事件の防止は、年齢での制限でなく、全員に同じに効くこの指標と §3.5 の流量の制限・§5 の審査で行う（FR-120、ADR-0057 の D3）。
住所録の追加による探り（相互にならない追加）は ADR-0066 で止める。ほかにどの挙動を不審と見て何をするか（不審な挙動への対処）は OQ-075（持ち越し、M4 を始める前に秘書が ADR で決める）で、指標と流量の制限に年齢の条件を持たせない。
