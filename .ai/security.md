- 状態: 草案
- 日付: 2026-11-19
- 根拠: brief・requirements・architecture・db・api・async・ADR-0001〜0017
- チケット: YGO-007
- 関連 ADR: 0001・0005・0006・0013・0014・0015・0018・0019・0020・0021

## §1 原則

1. **認可・公開の可否・処置は固定の規則表と人が決める**
   - 認可はロールと規則表（§4）で判断し、LLM に委ねない。
   - コンテンツの公開可否はポリシールール表との突合と、必要に応じてモデレーターの判断で決める。
   - 違反処置（取り下げ・利用停止）はモデレーターの判断で行う（OQ-037）。

2. **LLM は掲示板の審査で補助ラベルを付けるだけ**
   - LLM が返せるのは `ok` / `review` / `block` の 3 種のラベルだけ（ADR-0005）。
   - LLM の出力がどのような値であっても、公開されてはならない物が公開されることはない。
   - LLM の出力によって、権限が与えられることも、処置が確定することもない。
   - LLM が失敗したとき・決められた値以外を返したときは、公開しない側（人の審査）に倒す。

3. **API の経路では LLM を呼ばない**（ADR-0014、api.md §1）
   - 認証・認可のパスに LLM は関与しない。
   - LLM の呼び出しはすべて worker（非同期バッチ）で行う（async.md §2）。

4. **手紙の本文は LLM に渡さない**（ADR-0006）
   - クローズドな手紙は審査対象外（OQ-003 の暫定）。
   - 通報された手紙はモデレーターが直接確認する（§5）。LLM には渡さない。

## §2 個人情報

### §2.1 収集する項目

| 項目 | 目的 | 保存の形 | 保持期間 |
|------|------|---------|---------|
| メールアドレス | ログイン・連絡 | 暗号化（AES-256-GCM）+ 検索用 HMAC（ADR-0018） | アカウント削除まで。削除時に即消去 |
| パスワード（ハッシュ） | 認証 | Argon2id ハッシュ | アカウント削除まで。削除時に即消去 |
| 住所（架空） | ユーザー ID・識別 | 平文 | ADR-0013 の表を参照 |
| 自己紹介文 | プロフィール表示 | 平文 | アカウント削除時に消去 |
| セッション情報 | 認証状態の維持 | サーバー側（DB）に格納 | 有効期限切れ・ログアウト・退去で消去 |
| 手紙の本文 | 非同期メッセージ | 暗号化（ADR-0006） | ADR-0013 の表を参照 |
| 掲示板の投稿本文 | 情報共有 | 平文（審査後に公開） | ADR-0013 の表を参照 |
| 通報の内容（通報者情報含む） | モデレーション | 平文 | クローズ日から 1 年（ADR-0013） |
| 操作ログ（監査用） | 不正検知・監査 | 平文（個人を特定しない粒度） | 30 日（ADR-0013） |
| `erasure_log` | 削除の監査 | 操作種別・日時のみ | 60 日（ADR-0013） |

### §2.2 収集しないもの

以下の情報は収集しない。

- 実名・氏名
- 電話番号
- 生年月日・年齢（OQ-004 の回答待ち。恋愛のための年齢確認は要らない、OQ-001 → 決定、ADR-0024）
- 住民どうしの街の外の連絡先（マッチングの登録と提案に欄を設けない。FR-101、範囲は OQ-041）
- 顔写真・外見を識別できる画像（P-3 より）
- 位置情報（架空の住所のみ）
- 決済情報

### §2.3 手紙の暗号化

- 本文は AES-256-GCM で保存時に暗号化する（ADR-0006）。
- 鍵はサーバー側（KMS 相当）が管理し、鍵に版番号を付けて入れ替えられるようにする（ADR-0021）。
- 暗号化の付加データ（AAD）には手紙の ID を含め、別の手紙のデータを当てはめる攻撃を防ぐ（ADR-0021）。
- 復号してよい場面: (a) 本人が自分の手紙を読む、(b) 通報によりモデレーターが審査する（監査ログに記録）の 2 つに限る。
- 手紙の本文は LLM に渡さない。

### §2.4 保持期間と削除

ADR-0013 の表が正本。退去時の処理:

1. `residents.deleted_at` を現在時刻に設定（同期）。
2. 有効なセッションをすべて無効化（同期、ADR-0019）。
3. `account.erase` ジョブを積む（同期、ID のみ）。
4. worker が認証情報（メール暗号化値・HMAC・パスワードハッシュ）を消去（非同期、J7 の最初の手順）。

### §2.5 ログに残さないもの

以下はログに記録しない。

- 手紙の本文・掲示板の投稿本文（操作ログ・アクセスログには含めない）
- パスワード・セッションのトークン
- メールアドレスの平文（ハッシュ・暗号化値のみ）
- 通報の詳細内容（通報 ID の参照のみ記録する）

### §2.6 適用法令（仮定）

架空のサービスの設計として、日本の個人情報保護法（APPI）に準拠することを仮の前提にする [assumed]。
実際のサービスを運営する場合は法令の確認と専門家の助言が必要。

## §3 認証

関連 ADR: ADR-0018（メール＋パスワード方式）、ADR-0019（サーバー側セッション・再認証）

### §3.1 方式

- **メールアドレス＋パスワード** を採用する（ADR-0018）。
- ソーシャルログイン・パスキーは将来の選択肢として ADR-0018 に記録するが、当面は採用しない。
- 登録時にメールを確認する（確認メールのリンクをクリックするまでアカウントを有効化しない）。
- アカウントがあるかどうかを応答から推測できないようにする（ログイン失敗・パスワード再設定とも同じメッセージ）。

### §3.2 パスワードの要件と保存

- パスワードは 12 文字以上 [assumed]。
- **Argon2id** でハッシュにして保存する。
- 広く知られた漏えいパスワードのリスト（ローカルの辞書）と照合し、一致したら拒否する。
- パスワードリセットのトークンは 30 分で切れる [assumed]。

### §3.3 セッション

詳細は ADR-0019 を参照。

- セッションはサーバー側（DB）に持つ。JWT 等のステートレストークンは採用しない。
- Cookie は `__Host-` プレフィックス・`HttpOnly`・`SameSite=Lax`・`Secure` を設定する。
- **有効期限**: 操作なしで 30 日、発行から 90 日で切れる [assumed]。
- **複数デバイス**: 同時に複数の端末でセッションを持てる（ADR-0019）。
- 退去時・強制ログアウト時は有効なセッションをすべて即時無効化する（ADR-0015、§2.4）。

### §3.4 再認証

- **条件**: 直近 10 分以内にパスワードを入力していること [assumed]（ADR-0019）。
- **再認証が必要な操作**: パスワード変更・メールアドレス変更・退去申請・モデレーターによる重要な処置。
- 再認証の確認は `sessions` テーブルの `reauthenticated_at` カラムで管理する。

### §3.5 CSRF 対策と流量の制限

- CSRF 対策: `Origin` ヘッダの検査 ＋ 独自ヘッダ（`X-Requested-With` 相当）の確認。
- **流量の制限**: PostgreSQL のカウンタ（`rate_limit_buckets` または類似の表）で記録する。
- ログイン試行・パスワード再設定・確認メール送信に流量の制限を設ける。

### §3.6 メールアドレスの扱い

- DB に保存するのは **暗号化した値** と **HMAC 値**（検索用）のみ（ADR-0018）。
- 平文のメールアドレスはログに残さない（§2.5）。

## §4 権限

関連 ADR: ADR-0020（ロールと権限表）

### §4.1 ロール

| ロール | 説明 | 付与方法 |
|--------|------|---------|
| `resident`（住民） | 一般の住民。登録後に自動付与 | 自動 |
| `moderator`（モデレーター） | 掲示板・通報の審査担当 | 運用者 CLI のみ（ADR-0020） |

- ロールは住民自身・API 経由で変更できない。運用者の CLI のみが付与・剥奪できる。
- モデレーターには二要素認証（TOTP 等）を必須とする [assumed]（ADR-0020）。
- モデレーターは自分が当事者（送信者・受取人・通報者・被通報者）の案件を処理できない。

### §4.2 権限表

規則は C3 の 1 か所に持ち、許可と拒否の両方をテストする（ADR-0020）。

#### 郵便受け（`mailbox_items`）

| 操作 | 本人 | 他の住民 | モデレーター |
|------|------|---------|------------|
| 自分の郵便受けを読む | ✓ | ✗（404） | ✗（404） |
| 配達済み手紙を削除 | ✓（`deleted_at` 更新） | ✗ | ✗ |

#### 手紙（`letters`）

| 操作 | 送信者 | 受取人 | 他の住民 | モデレーター |
|------|--------|--------|---------|------------|
| 送信 | ✓（上限あり: 1 日 20 通） | — | ✗ | ✗ |
| 自分宛の手紙を読む | ✓ | ✓ | ✗（404） | ✗（404） |
| 通報された手紙を読む（監査） | ✗ | ✗ | ✗（404） | ✓（1 通のみ・監査ログあり） |

#### 掲示板（`board_posts`）

| 操作 | 投稿者 | 他の住民 | モデレーター |
|------|--------|---------|------------|
| 投稿（`awaiting_review`） | ✓（上限あり: 1 日 5 件） | ✗ | ✗ |
| 承認済み投稿を閲覧 | ✓ | ✓ | ✓ |
| 自分の投稿を削除 | ✓ | ✗ | ✗ |
| 任意の投稿を取り下げ | ✗ | ✗ | ✓ |
| ラベルを確認・人の審査を行う | ✗ | ✗ | ✓ |

#### 住所録（`address_book_entries`）

| 操作 | 本人 | 他の住民 | モデレーター |
|------|------|---------|------------|
| 自分の住所録を読む | ✓ | ✗（404） | ✗（404） |
| 住所録に追加・削除 | ✓ | ✗ | ✗ |

モデレーターも他人の住所録は読めない。

#### 朝刊・夕刊（`newspapers`）

| 操作 | すべての住民 | モデレーター |
|------|------------|------------|
| 配達済みの新聞を閲覧 | ✓ | ✓ |
| 新聞の内容を変更 | ✗ | ✗（worker のみ） |

#### プロフィール

| 操作 | 本人 | 他の住民 | モデレーター |
|------|------|---------|------------|
| プロフィールを見る（住所・自己紹介） | ✓ | ✓ | ✓ |
| プロフィールを更新 | ✓ | ✗ | ✗ |

#### ブロック（`blocks`）

| 操作 | 本人 | 他の住民 | モデレーター |
|------|------|---------|------------|
| 自分のブロックを管理 | ✓ | ✗ | ✗ |
| 相手がブロックしているかを確認 | ✗（存在を隠す） | ✗ | ✗ |

ブロックの存在は相手に気づかせない（ADR-0015 §3）。配達時に worker が `suppressed` にする。

#### 通報（`reports`）

| 操作 | 住民 | モデレーター |
|------|------|------------|
| 通報を送る | ✓ | ✓ |
| 通報を審査・クローズ | ✗ | ✓（当事者でない場合のみ） |

#### ロール・管理操作

| 操作 | 住民 | モデレーター | 運用者 CLI |
|------|------|------------|-----------|
| ロールを付与・剥奪 | ✗ | ✗ | ✓ |
| ロール一覧を確認 | ✗ | ✗ | ✓ |

### §4.3 存在の秘匿

他人のデータは **404** で返す（ADR-0014）。403 で存在を明かさない。

## §5 モデレーション

関連 ADR: ADR-0005（モデレーション方針）

### §5.1 対象

| 対象 | 審査方法 |
|------|---------|
| 掲示板の投稿（`board_posts`） | 自動審査（LLM ラベル）→ 規則表→ 必要に応じて人の審査 |
| クローズドな手紙（`letters`） | 審査対象外（OQ-003 の暫定）。通報があれば個別に対応 |

### §5.2 判定フロー

```
投稿が締め切りを過ぎる
  ↓
1. ポリシールール表に当たるか？
   → YES: 即却下（`rejected`）。理由とルール表の版を記録
   → NO: 次へ

2. LLM にラベルを依頼（本文のみを渡す。ID・送信者は含めない）
   → `ok`   : 承認（`approved`）
   → `review`: 人の審査へ
   → `block` : 却下（`rejected`）→ 住民は異議申し立てが 1 回できる [assumed]
   → 失敗・想定外の値: 人の審査へ（公開しない側に倒す。§1 原則 2）

3. 人の審査（モデレーター）
   → 承認（`approved`）/ 却下（`rejected`）
```

- 承認されていない投稿は配達しない（ADR-0005）。
- 判定には使用したルール表の版を記録する（再現性のため）。

### §5.3 プロンプトインジェクション対策

- LLM には投稿の本文だけを渡す（送信者の住所・ID・名前を含めない）。
- LLM の出力はラベルの種類だけを検証し、それ以外の値を使わない。
- LLM の出力を直接 SQL やコマンドに組み込まない。

### §5.4 通報の流れ

1. 住民が手紙または掲示板の投稿を通報する（`reports` に行を作る）。
2. モデレーターが通報の内容を確認する。
3. 通報された**手紙**は、モデレーターが **1 通だけ** 復号して確認できる（監査ログに記録）（OQ-003 の暫定対応）。
4. 通報された掲示板の投稿はモデレーターが取り下げ（`rejected`）・維持（`approved` のまま）・異議対応を行う。
5. `reports` を `closed`（対処済み）/ `dismissed`（棄却）にする。
6. 違反した住民への処置は OQ-037 で定める（現在未確定）。

### §5.5 モデレーターの内部不正対策

- モデレーターは自分が当事者の案件を処理できない（§4.1）。
- 通報された手紙の復号は監査ログに記録し、定期的に運用者が確認できるようにする。
- モデレーターによる処置はすべて `moderation_actions` に記録する（ADR-0013 の保持期間: 1 年）。

## §6 秘密情報

### §6.1 秘密の一覧

| 秘密の種類 | 保持するプロセス | 説明 |
|-----------|--------------|------|
| DB 接続文字列 | web・worker | PostgreSQL への接続情報 |
| セッション署名鍵 | web | Cookie の署名に使う対称鍵 |
| 手紙の暗号化鍵（版付き） | worker | 手紙の本文の暗号化・復号に使う（ADR-0021） |
| メールアドレスの暗号化鍵 | web・worker | メールアドレスの暗号化・復号に使う（ADR-0018） |
| メールアドレスの HMAC 鍵 | web | メールアドレスの検索用 HMAC に使う（ADR-0018） |
| LLM の API キー | worker のみ | 審査バッチだけが使う。web プロセスには渡さない |
| メール送信サービスの認証情報 | worker | 確認メール・休眠通知の送信に使う（OQ-039） |
| 再設定トークンの署名鍵 | web | パスワード再設定トークンの署名 |

**LLM の API キーは worker だけが持つ。** web プロセス（API）には渡さない（§1 原則 3）。

### §6.2 保管方法

| 環境 | 方法 |
|------|------|
| 本番 | 秘密管理のサービス（AWS Secrets Manager・GCP Secret Manager 等）または KMS [assumed] |
| 開発・CI | 環境変数（`.env`・`.env.test`）。バージョン管理に含めない |

- 偽の鍵が必要なとき（テスト・文書）は、本物と見分けがつく値（例: `EXAMPLE_KEY_DO_NOT_USE`）を使う。
- テストの環境変数の例は `example.invalid` ドメインのアドレスを使う（例: `test@example.invalid`）。

### §6.3 鍵の入れ替え

詳細な手順は J15（環境構成の設定チケット）で書く。方針:

- 手紙の暗号化鍵は版番号で管理し、古い版で暗号化されたデータは次の便の前に再暗号化する（ADR-0021）。
- メールアドレスの暗号化鍵を入れ替える場合は、全レコードを再暗号化してから古い版を無効にする。
- セッション署名鍵を入れ替えると既存のセッションがすべて無効になる。告知ページを用意する。

### §6.4 漏えいしたときの手順

1. 漏えいした鍵を即座に無効化する。
2. 影響するセッションをすべて無効化する（セッション鍵が漏えいした場合）。
3. 漏えいした暗号化鍵の版で暗号化されたデータを新しい鍵で再暗号化する（手紙の鍵が漏えいした場合）。
4. 影響を受けた住民への通知（OQ-039 のメール送信サービスで対応）。
5. インシデントを `retros.md` に記録する。

## §7 脅威と対策の一覧

| # | 脅威 | 対策 |
|---|------|------|
| T-01 | **なりすまし（不正ログイン）** | Argon2id ハッシュ、流量の制限、漏えいパスワード照合（§3.2）、再認証（§3.4） |
| T-02 | **IDOR（他人のデータを直接引く）** | 認可はすべて C3 の規則表で検査。他人のデータは 404 を返す（§4.3） |
| T-03 | **ログからの情報漏えい** | 本文・パスワード・平文メール・トークンをログに残さない（§2.5） |
| T-04 | **LLM 経由の情報漏えい** | 手紙の本文は LLM に渡さない。LLM には投稿本文だけを渡す（§1・§5.3） |
| T-05 | **住所の列挙** | 住所の候補は登録時の候補提示以外に API で列挙できないようにする（ADR-0001） |
| T-06 | **ブロックの露見** | ブロック済みの手紙は `suppressed` にするが、送信者には「配達済み」と見せる（ADR-0015） |
| T-07 | **XSS** | HTML をテンプレートエンジンでエスケープして出力。CSP ヘッダを設定する [assumed] |
| T-08 | **CSRF** | Origin ヘッダの検査 ＋ 独自ヘッダの確認（§3.5） |
| T-09 | **プロンプトインジェクション** | LLM には本文だけを渡す。出力はラベル 3 種のみ検証（§5.3） |
| T-10 | **大量送信（スパム）** | 1 日あたり手紙 20 通・掲示板 5 件の上限（ADR-0005）。流量の制限（§3.5） |
| T-11 | **セッションハイジャック** | `__Host-`・HttpOnly・SameSite=Lax・Secure の Cookie。サーバー側セッション（ADR-0019） |
| T-12 | **モデレーターの内部不正** | 当事者の案件を処理できない規則。すべての処置を監査ログに記録（§5.5） |
| T-13 | **リストアで削除したデータが戻る** | `erasure_log` を元に消し直す `erasure.replay` ジョブを実装する（async.md §2・ADR-0013） |
| T-14 | **手紙の暗号化鍵の漏えい** | 鍵を版で管理し、漏えい時に影響する版のデータを再暗号化する（ADR-0021・§6.4） |
| T-15 | **DB ダンプの漏えい** | 手紙の本文は暗号化済み。メールアドレスも暗号化済み。パスワードはハッシュのみ（§2・§3） |

### §7.1 検知の指標

以下の指標を収集・監視する。

- ログイン失敗回数（同一 IP・同一メール HMAC）
- パスワード再設定の申請回数
- 1 日の送信上限に達した住民の数
- 通報数の急増
- LLM 審査で `review` / `block` の割合の急変
- モデレーターによる手紙の復号件数

### db.md への提案

   - `email_hmac`（検索用 HMAC）
   - `password_hash`（Argon2id）
