## §1 原則

1. **認可・公開の可否・処置は固定の規則表と人が決める**
   - 認可はロールと規則表（§4）で判断し、LLM に委ねない。
   - コンテンツの公開可否はポリシールール表との突合と、必要に応じてモデレーターの判断で決める。
   - 掲示板の投稿の取り下げは、モデレーターの判断で行う。
   - 違反した住民への処置の内容はマスターが後で決める（OQ-037 → 決定、ADR-0032。内容は OQ-048、持ち越し）。決まるまで、処置を実行する手段は作らない。

2. **LLM は掲示板の審査で補助ラベルを付け、新聞では記事の文字を作るだけ**
   - 審査の LLM が返せるのは `ok` / `review` / `block` の 3 種のラベルだけ（ADR-0005）。
   - 新聞の LLM（J16）は、承認済みの素材から記事の文字を作るだけで、公開してよいかは決めない。出力は検査とルール表に当て、外れたら記事を決まった形で組む（OQ-051 → 決定、ADR-0039 の D8）。
   - LLM の出力がどのような値であっても、公開されてはならない物が公開されることはない。
   - LLM の出力によって、権限が与えられることも、処置が確定することもない。
   - LLM が失敗したとき・決められた値以外を返したときは、公開しない側（人の審査）に倒す。

3. **API の経路では LLM を呼ばない**（ADR-0014、api.md §1）
   - 認証・認可のパスに LLM は関与しない。
   - LLM の呼び出しはすべて worker（非同期バッチ）で行う（async.md §2。審査の J2 と新聞の記事の文字の J16 だけ、ADR-0039）。

4. **手紙の本文は LLM に渡さない**（ADR-0006・ADR-0026）
   - クローズドな手紙も配達の前に審査するが、ルール表だけで照合する（OQ-003 → 決定、ADR-0026、§5）。照合は投函のときに API が行う（OQ-052 → 決定、ADR-0040）。
   - 本文（一部や要約も）を LLM に渡さない。手紙の審査の経路には LLM のアダプタを渡さない。
   - 本文に触れてよい場面は §2.3 の 4 つに限る。通報された手紙（§5.4。OQ-043 → 決定、ADR-0036）と、送った人が確認を頼んだ確認待ちの手紙（§5.2。ADR-0040）は、モデレーターが 1 通ずつ確かめる。

5. **住民を守る制限は、住民が自分で外せる設定にしない**（OQ-043 → 決定、2026-11-19、ADR-0036 の D3）
   - 手紙と掲示板の審査（§5）・送信の上限・マッチングに街の外の連絡先の欄を設けないこと（FR-101）などを、住民の設定で外したり緩めたりできる形にしない。
   - ブロック（住民が自分で掛ける守り）を掛ける・外すのは住民のまま。
   - 方針は、老若男女・少年少女が使える、開かれていて安全な街（ADR-0036 の D1）。
   - 年齢で守り方を変える（OQ-052 → 決定、ADR-0041）。年齢は住民の設定をそのまま使い、確かめない。どの年齢にも危険な機能は設けない。
     何を変えるか（OQ-063）と年齢の扱い（OQ-064。あとから変えられると守りを自分で外せることになる）は要回答で、答えまで年齢による違いと年齢の項目は作らない（§2.2）。

## §2 個人情報

### §2.1 収集する項目

| 項目 | 目的 | 保存の形 | 保持期間 |
|------|------|---------|---------|
| メールアドレス | ログイン・連絡 | 暗号化（AES-256-GCM）+ 検索用 HMAC（ADR-0018） | アカウント削除まで。削除時に即消去 |
| パスワード（ハッシュ） | 認証 | Argon2id ハッシュ | アカウント削除まで。削除時に即消去 |
| 住所（架空） | ユーザー ID・識別 | 平文 | ADR-0013 の表を参照 |
| 自己紹介文 | プロフィール表示 | 平文 | アカウント削除時に消去 |
| セッション情報 | 認証状態の維持 | サーバー側（DB）に格納 | 有効期限切れ・ログアウト・退去で消去 |
| 通知の購読情報（`endpoint`・端末の鍵） | 配達完了の通知（ADR-0025） | 平文（`push_subscriptions`） | セッションの無効化・購読の削除・退去で即消去 |
| 手紙の本文 | 非同期メッセージ | 暗号化（ADR-0006） | ADR-0013 の表を参照 |
| 掲示板の投稿本文 | 情報共有 | 平文（審査後に公開） | ADR-0013 の表を参照 |
| 興味（`resident_interests`、一覧から選んだもの） | 新聞の版の組分け（ADR-0039 の D4・D5） | 平文。本人だけが見て変えられ、LLM・ほかの住民・モデレーターに渡さない | 本人が外すまで。退去で即時に消す |
| 推し量った興味（`inferred_interests`、段階 2。自分に届いた過去の新聞の検索で当たった興味の ID だけ） | 新聞の版の組分け（ADR-0045 の D1・D6） | 平文。検索語は持たない。本人にも返さず、本人が見て消す経路は作らない（OQ-059 の答え 4）。LLM・ほかの住民・モデレーターに渡さない。住民には検索の画面と利用の案内で知らせ、個別の同意は取らない（OQ-059 の答え 3、ADR-0045 の D7。止められるかは OQ-072） | 最後に当たってから 30 日 [assumed]（J14）。1 人 5 つまで [assumed]。退去で即時に消す |
| 新聞の記事の文字（`newspaper_articles`） | 紙面の組版（ADR-0039 の D7） | 平文（住民の ID・住所を持たない） | 紙面と同じ（ADR-0013）。素材の投稿の削除・投稿者の退去で即時に消す |
| 取り込んだ外のニュース（`external_news_items`） | 紙面の素材（ADR-0039 の D6） | 平文 | 30 日 [assumed]（OQ-060 で変わる） |
| 通報の内容（通報者情報含む） | モデレーション | 平文 | クローズ日から 1 年（ADR-0013） |
| 操作ログ（監査用） | 不正検知・監査 | 平文（個人を特定しない粒度） | 30 日（ADR-0013） |
| `erasure_log` | 削除の監査 | 操作種別・日時のみ | 60 日（ADR-0013） |

### §2.2 収集しないもの

以下の情報は収集しない。
例外は 1 つだけで、商店（段階 3）が公開するお店の実在の情報（お店の名前など）は「実名・氏名」の項目に当てない（ADR-0043 の D6）。
ほかの項目（電話番号・顔写真・位置情報・決済情報など）は、OQ-068・OQ-069 で決めるまで商店にも当てる。
担当者・経営者など個人の情報をどこまで出すかは公開の範囲にかかわるので、決めず、S3-2 の前にマスターに聞く（OQ-069 (3)）。
商店が出す実在の情報の項目と持ち方は OQ-069 で、契約と決済の情報（LP・問い合わせで受ける情報を含む）の扱いは OQ-068 で決める。
レポジトリ・テスト・シードに実在の名前を入れないこと（ADR-0038 の D5）は変えない。

- 実名・氏名
- 電話番号
- 生年月日（年齢は住民が設定した値をそのまま使うので要らない。ADR-0041 の D4）
- 年齢を確かめるための情報（本人確認の書類・外部の年齢確認の結果。年齢は確かめない、ADR-0041 の D2）。恋愛のための年齢確認も要らない（ADR-0024）
- 年齢そのものは、年齢で守り方を変える（ADR-0041 の D1）ので集める方針だが、何を変えるか（OQ-063）と年齢の扱い（OQ-064）が決まるまで項目を置かず、集めない（ADR-0041 の D5）
- 住民どうしの街の外の連絡先（マッチングの登録と提案に欄を設けない。FR-101。禁止はマッチングの中だけで、掲示板・手紙には及ばない、ADR-0034。守り方の細部は OQ-050）
- 顔写真・外見を識別できる画像（P-3 より）。段階 2 で住民がアップロードする画像は新聞用に加工し、元の画像は持たない。元の画像は加工が終わるか失敗した時点で消し、取りこぼしもアップロードから 24 時間 [assumed] を過ぎたあとの次の J14 で消す（最長で約 48 時間）。元の画像は住民にもモデレーターにも返さない（ADR-0044 の D5、FR-118）
- 位置情報（架空の住所のみ）
- 決済情報

### §2.3 手紙の暗号化

- 本文は AES-256-GCM で保存時に暗号化する（ADR-0006）。
- 鍵はサーバー側（KMS 相当）が管理し、鍵に版番号を付けて入れ替えられるようにする（ADR-0021）。
- 暗号化の付加データ（AAD）には手紙の ID を含め、別の手紙のデータを当てはめる攻撃を防ぐ（ADR-0021）。
- 本文に触れてよい場面は次の 4 つに限る（ADR-0026 の D4・ADR-0040、マスターの答え「厳格なアクセス制御」）。
  - (a) 送った人と受け取った人が、自分の手紙を読む（web）。
  - (b) 投函のときのルール表との照合（web の API の中、ADR-0040 の D2）。暗号化の前の平文を使い、復号はしない。平文はメモリの中だけに置き、DB・ログ・ジョブのペイロード・例外のメッセージに書かない。
    残すのはルール表の版と、当たったときの規則の ID だけ。当たって送った人が n を選んだ本文は保存しない。
    （もとは worker の J2 の照合で、OQ-052 → 決定、2026-11-20、ADR-0040 で置き換えた。worker は手紙を復号して照合しない）
  - (c) **決定**（OQ-043 の答え、2026-11-19、ADR-0036 の D2）: 通報された手紙を、モデレーターが確かめる（`GET /api/v1/admin/reports/{id}/letter`、api.md §7 F-08）。
    条件は、通報が `open`・当事者でない・二要素認証済み・1 回の操作で 1 通だけ。毎回 `moderation_actions` に `view_letter` を記録し（書けなければ本文を返さない）、
    応答は `Cache-Control: no-store`。条件に合わなければ 404。
  - (d) **決定**（OQ-052 の答え、2026-11-20、ADR-0040 の D5）: 送った人が確認を頼んだ確認待ちの手紙（`held`）を、モデレーターが確かめる（`GET /api/v1/admin/held-letters/{id}`、api.md §7 F-08）。
    条件は (c) と同じ（手紙が `held`・当事者（送った人・宛先の住民）でない・二要素認証済み・1 通だけ・毎回 `view_letter` を記録・`no-store`・合わなければ 404）。
- (a)・(b) は OQ-003 の答え（対象とする・LLM には渡さない）と OQ-052 の答え（送信時点でチェック）で決まった審査と配達に要る場面。人が手紙を読む (c) は OQ-043 の答え（「厳しい閲覧はプラスに働く」「ある程度の秘匿性は担保しないと」）で、(d) は OQ-052 の答え（「送った人の異議は有用」「モデレーター確認」）で決まった。
- 本文の一覧・検索の経路は作らない。通報されていない手紙は、送った人が確認を頼んだ `held` の手紙のほかは、モデレーターも読めない。`blocked`（却下した手紙）を見る経路もない（ADR-0040 の D5）。
- 手紙の本文は LLM に渡さない（§1 原則 4）。

### §2.4 保持期間と削除

ADR-0013 の表が正本。退去時の処理:

1. `residents.deleted_at` を現在時刻に設定（同期）。
2. 有効なセッションをすべて無効化し、その通知の購読を消す（同期、ADR-0019・ADR-0025）。
3. `account.erase` ジョブを積む（同期、ID のみ）。
4. worker が認証情報（メール暗号化値・HMAC・パスワードハッシュ）を消去（非同期、J7 の最初の手順）。
5. worker が興味（`resident_interests`）と推し量った興味（`inferred_interests`、段階 2、ADR-0045）を消し、その住民の投稿から作った記事（`newspaper_articles`）を消して版を組み直す（非同期、J7・J8、ADR-0039）。

### §2.5 ログに残さないもの

以下はログに記録しない。

- 手紙の本文・掲示板の投稿本文（操作ログ・アクセスログには含めない）。投函のときの照合で使った手紙の平文と、422 になった手紙の本文も、ログ・例外のメッセージに出さない（ADR-0026・ADR-0040）
- 手紙の照合で当たった規則の ID（`letters.matched_rule_id` と §7.1 の集計にだけ置き、アクセスログ・応答には出さない。ADR-0040 の D4）
- パスワード・セッションのトークン
- メールアドレスの平文（ハッシュ・暗号化値のみ）
- 通報の詳細内容（通報 ID の参照のみ記録する）
- 通知の購読の `endpoint`・端末の鍵（`p256dh`・`auth`）・通知の中身（件数を含む）（ADR-0025）
- 住民の興味（選んだものも推し量ったものも）・住所録の検索語と過去の新聞の検索語（`?q=`。アクセスログのクエリ文字列も伏せる）。住所録の検索から興味を集めない（ADR-0045 の D1）。過去の新聞の検索語は、照合のあとメモリの外に出さない（DB・ジョブのペイロード・例外のメッセージにも書かない、ADR-0045 の D3・D4）。新聞の LLM のプロンプトと出力の全文もログに出さない

### §2.6 適用法令（仮定）

架空のサービスの設計として、日本の個人情報保護法（APPI）に準拠することを仮の前提にする [assumed]。
実際のサービスを運営する場合は法令の確認と専門家の助言が必要。
過去の新聞の検索から興味を推し量ること（ADR-0045）は、マスターの答え（OQ-059、2026-11-20）で、知らせるが個別の同意は取らず、推し量った興味を本人が見て消す仕組みは設けない。
利用目的の知らせ方と、本人から開示・消去を求められたときの対応は OQ-032 で調べ、答えと食い違う求めがあれば新しい要回答としてマスターに出す。

## §3 認証

関連 ADR: ADR-0018（メール＋パスワード方式）、ADR-0019（サーバー側セッション・再認証）

### §3.1 方式

- **メールアドレス＋パスワード** を採用する（ADR-0018）。
- ソーシャルログイン・パスキーは将来の選択肢として ADR-0018 に記録するが、当面は採用しない。
- 登録時にメールを確認する（確認メールのリンクをクリックするまでアカウントを有効化しない）。
- アカウントがあるかどうかを応答から推測できないようにする（ログイン失敗・パスワード再設定とも同じメッセージ）。

### §3.2 パスワードの要件と保存

- パスワードは 12 文字以上 [assumed]。
- **Argon2id** でハッシュにして保存する。
- 広く知られた漏えいパスワードのリスト（ローカルの辞書）と照合し、一致したら拒否する。
- パスワードリセットのトークンは 30 分で切れる [assumed]。

### §3.3 セッション

詳細は ADR-0019 を参照。

- セッションはサーバー側（DB）に持つ。JWT 等のステートレストークンは採用しない。
- Cookie は `__Host-` プレフィックス・`HttpOnly`・`SameSite=Lax`・`Secure` を設定する。
- **有効期限**: 操作なしで 30 日、発行から 90 日で切れる [assumed]。
- **複数デバイス**: 同時に複数の端末でセッションを持てる（ADR-0019）。
- 退去時・強制ログアウト時は有効なセッションをすべて即時無効化する（ADR-0015、§2.4）。
- セッションを無効にすると（ログアウトを含む）、その端末の通知の購読も同じトランザクションで消す（ADR-0019・ADR-0025）。
  ログアウトした端末には配達完了の通知が届かない。

### §3.4 再認証

- **条件**: 直近 10 分以内にパスワードを入力していること [assumed]（ADR-0019）。
- **再認証が必要な操作**: パスワード変更・メールアドレス変更・退去申請・モデレーターによる重要な処置。
- 再認証の確認は `sessions` テーブルの `reauthenticated_at` カラムで管理する。

### §3.5 CSRF 対策と流量の制限

- CSRF 対策: `Origin` ヘッダの検査 ＋ 独自ヘッダ（`X-Requested-With` 相当）の確認。
- **流量の制限**: PostgreSQL のカウンタ（`rate_limit_buckets` または類似の表）で記録する。
- 登録の要求・ログイン試行・パスワード再設定・確認メール送信に流量の制限を設ける。超えた要求には 429（code は `rate_limited`。手紙・投稿の 1 日の上限の `daily_limit_reached` とは分ける。残りの数は返さない。api.md §5）を返す。
  登録は開放式で招待で入り口を絞らないため、登録の要求も対象にする（ADR-0030 の D2）。上限の数値は実装の段階で決める。
- 手紙の投函で 422（`letter_needs_review`）になった回数も住民ごとに数え、超えたら 429（`rate_limited`）を返す。試し送りでルール表の手紙の項目を探られないようにするため（ADR-0040 の D7・§7 の T-22）。値は OQ-065（持ち越し、M4 の前に決める）。

### §3.6 メールアドレスの扱い

- DB に保存するのは **暗号化した値** と **HMAC 値**（検索用）のみ（ADR-0018）。
- 平文のメールアドレスはログに残さない（§2.5）。

## §4 権限

関連 ADR: ADR-0020（ロールと権限表）

### §4.1 ロール

| ロール | 説明 | 付与方法 |
|--------|------|---------|
| `resident`（住民） | 一般の住民。登録後に自動付与 | 自動 |
| `moderator`（モデレーター） | 掲示板・通報の審査担当 | 運用者 CLI のみ（ADR-0020） |

- ロールは住民自身・API 経由で変更できない。運用者の CLI のみが付与・剥奪できる。
- モデレーターには二要素認証（TOTP 等）を必須とする [assumed]（ADR-0020）。
- モデレーターは自分が当事者（送信者・受取人・通報者・被通報者）の案件を処理できない。

### §4.2 権限表

規則は C3 の 1 か所に持ち、許可と拒否の両方をテストする（ADR-0020）。

#### 郵便受け（`mailbox_items`）

| 操作 | 本人 | 他の住民 | モデレーター |
|------|------|---------|------------|
| 自分の郵便受けを読む | ✓ | ✗（404） | ✗（404） |
| 配達済み手紙を削除 | ✓（`deleted_at` 更新） | ✗ | ✗ |

#### 手紙（`letters`）

| 操作 | 送信者 | 受取人 | 他の住民 | モデレーター |
|------|--------|--------|---------|------------|
| 送信 | ✓（上限あり: 1 日 20 通。投函のときにルール表に当て、当たったら確認を頼むか選ぶ、ADR-0040） | — | ✗ | ✗ |
| 自分宛の手紙を読む | ✓ | ✓ | ✗（404） | ✗（404） |

## §5 モデレーション

関連 ADR: ADR-0005（モデレーション方針）・ADR-0026（クローズドな手紙の審査）・ADR-0034（連絡先の共有の禁止はマッチングの中だけ）・ADR-0038（商店街の発信も配達の前に審査する）・ADR-0040（手紙は送るときに照合し、送った人が頼んだ手紙をモデレーターが確かめる）

### §5.1 対象

| 対象 | 審査方法 |
|------|---------|
| 掲示板の投稿（`board_posts`） | 自動審査（LLM ラベル）→ 規則表→ 必要に応じて人の審査 |
| クローズドな手紙（`letters`、個人宛・グループ宛） | 投函のときにルール表の手紙の項目だけで照合する。LLM には渡さない（ADR-0026）。当たったら送った人が確認を頼むかを選び、頼んだ手紙だけをモデレーターが確かめる（ADR-0040、§5.2）。通報があれば §5.4 |
| 商店街の発信（コミュニティ・商店、段階 3） | 掲示板の投稿と同じ（配達の前に審査し、承認の前には出さない。ADR-0038 の D4） |
| 新聞の記事の文字（J16 の LLM の出力、`newspaper_articles`） | 長さ・文字だけであることの検査と、ルール表の掲示板向けの項目。外れたら記事を決まった形（素材の題と本文そのまま）にする。素材は承認済みのものだけ（ADR-0039 の D8） |
| 取り込んだ外のニュース（J17、`external_news_items`） | 文字だけにし、ルール表の掲示板向けの項目に当てる。当たったら保存しない（ADR-0039 の D6） |

ルール表の各項目は、規則の ID・版・当てる対象（掲示板の投稿 / 手紙）・種類を持つ。
手紙に当てる項目は次の 3 種類（OQ-052 → 決定、2026-11-20、ADR-0040 の D1）。年齢で変えるかは OQ-063（要回答）で、答えまですべての住民に同じ項目を当てる。

| 種類 | 中身 | 備考 |
|------|------|------|
| `spam` | 一般的なスパム（宣伝や勧誘の決まり文句・同じ文の繰り返しなど） | 決める規則の細部は OQ-065 |
| `external_link` | 街の外へのリンク（URL の形の文字列） | メールアドレスと電話番号は含めない（ADR-0034 とそろえる）。形の細部は OQ-065 |
| `adult_words` | 成人向け（18 禁）の言葉 | 一覧は公開レポジトリに置かない。置き場は OQ-065 |

- テストは偽の規則（例: 目印の文字列 `EXAMPLE_LETTER_RULE_DO_NOT_USE` に当たる規則）で確かめ、レポジトリに本物の言葉の一覧を入れない。
- 答えの「等」にあたる項目は足していない。足すときは ADR-0040 の D1 を改める。

違法な物（大麻など）の取引の場にしないための項目は、まだ置かない。別のチケットで設計する（OQ-053、持ち越し、ADR-0036 の D6）。

ルール表に FR-101（連絡先の共有の禁止）を理由にした項目は置かない（ほかの理由で個人情報を止める項目を置くかは、この決定の範囲の外）。禁止はマッチングの中だけで、掲示板・手紙には及ばない（OQ-041 → 決定、2026-11-19、ADR-0034 の D3）。

### §5.2 判定フロー

```
投稿が締め切りを過ぎる
  ↓
1. ポリシールール表に当たるか？
   → YES: 即却下（`rejected`）。理由とルール表の版を記録
   → NO: 次へ

2. LLM にラベルを依頼（本文のみを渡す。ID・送信者は含めない）
   → `ok`   : 承認（`approved`）
   → `review`: 人の審査へ
   → `block` : 却下（`rejected`）→ 住民は異議申し立てが 1 回できる [assumed]
   → 失敗・想定外の値: 人の審査へ（公開しない側に倒す。§1 原則 2）

3. 人の審査（モデレーター）
   → 承認（`approved`）/ 却下（`rejected`）
```

- 承認されていない投稿は配達しない（ADR-0005）。
- 判定には使用したルール表の版を記録する（再現性のため）。

**手紙の判定フロー**（ADR-0040。ADR-0026 の締め切りのあとの J2 の照合を置き換えた）:

```
住民が手紙を投函する（POST /api/v1/letters）
  ↓
1. API が暗号化の前に、ルール表のうち手紙に当てる項目に当たるか？（LLM は呼ばない）
   → NO : `pending` で保存（ルール表の版を記録）。配達の前に照合し直さない
   → YES かつ request_review がない: 何も保存せずに 422（当たった規則は返さない）
        ↓ web のポップアップで送った人が選ぶ
        n: 何も送らない（何も保存しない）
        y: request_review: true で送り直す → 2 へ
2. もう一度照合して当たる → `held`（確認待ち）で保存（当たった規則の ID と版を記録）。送った人には「確認中」
   （当たらなければ 1 の NO と同じ）
  ↓
3. モデレーターが 1 通ずつ確かめる（当事者でない・二要素認証済み・毎回 view_letter を記録）
   → approve: `pending` にして次の配達回に入れる
   → reject : `blocked`（配達しない）。送った人には「届けられませんでした」
```

- 手紙は `moderation_queue` に入れない（db.md §2 の CHECK 制約 `content_kind <> 'letter'`）。
- 送った人には `held` を「確認中」、`blocked` を「届けられませんでした」とだけ見せ、当たった規則は見せない（api.md §7 F-04）。
- 送った人が y を選ぶと、モデレーターが本文を読むことをポップアップで知らせる（文言は OQ-065）。
- 確認を求める 422 は、当たったという事実を返すので、§3.5 の流量の制限を掛ける（T-22）。

### §5.3 プロンプトインジェクション対策

- 審査の LLM（J2）には投稿の本文だけを渡す（送信者の住所・ID・名前を含めない）。新聞の LLM（J16）に渡すものは下の「新聞の LLM」のとおり。
- 本番では、投稿の本文は外部のサービス（Anthropic API。秘書の暫定の選定、ADR-0031）に渡る。手紙の本文は渡さない（§1 原則 4）。住民への説明の要否は OQ-032。
- LLM の出力はラベルの種類だけを検証し、それ以外の値を使わない（構造化出力で 3 つのラベルに限っても、検証は省かない。ADR-0031）。
- LLM の出力を直接 SQL やコマンドに組み込まない。

**新聞の LLM（J16、ADR-0039 の D8）**:
- 渡すもの: 承認済みの掲示板の投稿の本文（審査で外部の LLM にすでに渡している範囲）・取り込んだ外のニュース・版の興味の名前。
- 渡さないもの: 手紙（本文・一部・要約）・住所・ID・ニックネーム・住民ごとの興味。プロンプトは住民の表を読まずに組む。
- 出力の検査: 長さの上限・文字だけ（HTML を含めない。組版でエスケープする）・ルール表。外れたら決まった形にする。LLM のせいでは休刊にしない。
- 投稿の本文は書き換えずに載せ、LLM の文には「AI が書いた文」の印を付ける（OQ-061 の暫定）。
- 本番では素材が外部のサービスに渡る（モデルは OQ-062）。住民への説明の要否は OQ-032（興味の収集と合わせて調べる）。

### §5.4 通報の流れ

1. 住民が手紙または掲示板の投稿を通報する（`reports` に行を作る）。
2. モデレーターが通報の内容を確認する。
3. 通報された**手紙**は、モデレーターが **1 通だけ** 復号して確認できる（`GET /api/v1/admin/reports/{id}/letter`、ADR-0026 の D4 (c)。OQ-043 → 決定、ADR-0036）。
   通報が `open`・当事者でない・二要素認証済みのときだけ。見るたびに `moderation_actions` に `view_letter` を記録する（書けなければ返さない）。
4. 通報された掲示板の投稿はモデレーターが取り下げ（`rejected`）・維持（`approved` のまま）・異議対応を行う。
5. `reports` を `closed`（対処済み）/ `dismissed`（棄却）にする。
6. 違反した住民への処置の内容は、マスターが後で決める（OQ-037 → 決定、2026-11-19、ADR-0032。内容は OQ-048、持ち越し）。
   決まるまで、住民を停止・警告する経路は作らない。通報への操作は approve / reject / dismiss だけ（ADR-0032 の D2）。

### §5.5 モデレーターの内部不正対策

- モデレーターは自分が当事者の案件を処理できない（§4.1）。
- 通報された手紙と確認待ちの手紙の復号は、見るたびに `moderation_actions` に `view_letter` として記録し、定期的に運用者が確認できるようにする（ADR-0026・ADR-0040）。
- モデレーターが手紙の本文に触れられるのは、通報された手紙と、送った人が確認を頼んだ確認待ちの手紙を 1 通ずつ見る経路だけ。本文の一覧・検索・却下した手紙（`blocked`）を見る経路はない。
- 確認待ちの手紙の承認・却下も `moderation_actions` に `letter_id` 付きで記録する（ADR-0040 の D5）。
- モデレーターによる処置はすべて `moderation_actions` に記録する（ADR-0013 の保持期間: 1 年）。

## §6 秘密情報

### §6.1 秘密の一覧

| 秘密の種類 | 保持するプロセス | 説明 |
|-----------|--------------|------|
| DB 接続文字列 | web・worker | PostgreSQL への接続情報 |
| セッション署名鍵 | web | Cookie の署名に使う対称鍵 |
| 手紙の暗号化鍵（版付き） | web・worker | 手紙の本文の暗号化・復号に使う（ADR-0021）。web は投函の暗号化と §2.3 の (a)(c)(d) に使う。(b) の照合は暗号化の前の平文で行い、鍵を使わない（ADR-0040）。worker は手紙を照合しないので、照合のためには使わない（鍵の入れ替え（§6.3）の再暗号化などで使う） |
| 手紙に当てる成人向けの言葉の一覧 | web | 公開レポジトリに置かない（ADR-0040 の D1）。置き場（秘密と同じ扱いにするか、運用者の CLI で入れるか）は OQ-065。テストは偽の規則だけを使う |
| メールアドレスの暗号化鍵 | web・worker | メールアドレスの暗号化・復号に使う（ADR-0018） |
| メールアドレスの HMAC 鍵 | web | メールアドレスの検索用 HMAC に使う（ADR-0018） |
| LLM の API キー | worker のみ | J2（審査）と J16（新聞の記事の文字、ADR-0039）だけが使う。web プロセスには渡さない |
| 外のニュースの配信元の認証情報 | worker のみ | J17 だけが使う（ADR-0039）。本番は OQ-060 のあと。テストは偽の配信元で、本物の認証情報を使わない |
| メール送信サービスの認証情報 | worker | 確認メール・休眠通知の送信に使う。本番のサービスはマスターの事前承認を得て選ぶ（OQ-039 → 決定、ADR-0033。進め方は OQ-049）。テスト環境はモックかローカルの SMTP で、本物の認証情報を使わない |
| 再設定トークンの署名鍵 | web | パスワード再設定トークンの署名 |
| VAPID 秘密鍵 | worker のみ | 配達完了の通知（Web Push）の署名に使う（ADR-0025）。公開鍵は web が返す（api.md §7 F-05） |

**LLM の API キーは worker だけが持つ。** web プロセス（API）には渡さない（§1 原則 3）。

### §6.2 保管方法

| 環境 | 方法 |
|------|------|
| 本番 | 秘密管理のサービス（AWS Secrets Manager・GCP Secret Manager 等）または KMS [assumed] |
| 開発・CI | 環境変数（`.env`・`.env.test`）。バージョン管理に含めない |

- 偽の鍵が必要なとき（テスト・文書）は、本物と見分けがつく値（例: `EXAMPLE_KEY_DO_NOT_USE`）を使う。
- テストの環境変数の例は `example.invalid` ドメインのアドレスを使う（例: `test@example.invalid`）。

### §6.3 鍵の入れ替え

詳細な手順は環境構成の設定チケット（`environment.md`）で書く。方針:

- 手紙の暗号化鍵は版番号で管理し、古い版で暗号化されたデータは次の便の前に再暗号化する（ADR-0021）。
- メールアドレスの暗号化鍵を入れ替える場合は、全レコードを再暗号化してから古い版を無効にする。
- セッション署名鍵を入れ替えると既存のセッションがすべて無効になる。告知ページを用意する。
- VAPID の鍵を入れ替えると既存の購読がすべて無効になり、住民は通知を許可し直す（ADR-0025）。

### §6.4 漏えいしたときの手順

1. 漏えいした鍵を即座に無効化する。
2. 影響するセッションをすべて無効化する（セッション鍵が漏えいした場合）。
3. 漏えいした暗号化鍵の版で暗号化されたデータを新しい鍵で再暗号化する（手紙の鍵が漏えいした場合）。
4. 影響を受けた住民への通知（メール送信サービスで対応。本番のサービスはマスターの事前承認を得て選ぶ。ADR-0033、OQ-049）。
5. インシデントを `retros.md` に記録する。

### §7.1 検知の指標

以下の指標を収集・監視する。

- ログイン失敗回数（同一 IP・同一メール HMAC）
- パスワード再設定の申請回数
- 1 日の送信上限に達した住民の数
- 通報数の急増
- LLM 審査で `review` / `block` の割合の急変
- モデレーターによる手紙の復号件数（`moderation_actions` の `view_letter`）
- 手紙の投函で 422（`letter_needs_review`）になった件数・`held` になった件数・`blocked` になった件数の急変（規則の ID ごと。本文は見ない、ADR-0040）
- 確認待ち（`held`）の手紙の数と、いちばん古い手紙の待ち時間（OQ-065 の扱いを決める手がかり）
- 新聞の J16 で `written_by = 'template'` になった記事の割合（LLM の失敗・検査に外れた出力の急増、ADR-0039）

## §9 他の文書への変更提案（別チケット）

以下は本文書の内容を反映して他の文書に追加・修正が必要な箇所。変更は別チケットで行う。

### db.md への提案

1. `credentials` テーブル（またはカラム）を `residents` テーブルに追加または別テーブルとして設ける:
   - `email_encrypted`（暗号化済みメール）
   - `email_hmac`（検索用 HMAC）
   - `password_hash`（Argon2id）
   - `email_verified_at`
2. `sessions` テーブル: `session_id`・`resident_id`・`created_at`・`last_seen_at`・`expires_at`・`reauthenticated_at`・`invalidated_at`
3. `staff_roles` テーブル（またはカラム）: `resident_id`・`role`・`granted_at`・`granted_by`
4. `letters` テーブルに `body_key_version` カラムを追加（ADR-0021）。
5. `rate_limit_buckets` テーブル: `key`・`count`・`window_start`・`updated_at`
6. `moderation_queue` に `rule_version`（使用したルール表の版）カラムを追加。→ 済み（db.md §2。`matched_rule_id` と手紙の行の CHECK 制約も一緒に足した、ADR-0026）

### api.md への提案

1. 認証エンドポイントの追加: `POST /auth/register`・`POST /auth/login`・`POST /auth/logout`・`POST /auth/forgot-password`・`POST /auth/reset-password`・`POST /auth/verify-email`・`POST /auth/reauth`
2. セッション管理エンドポイントの追加: `GET /auth/sessions`・`DELETE /auth/sessions/:id`

### async.md への提案

1. J7（`account.erase`）の「最初の手順」として認証情報の削除（メール暗号化値・HMAC・パスワードハッシュ）を明記する。
