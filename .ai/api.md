## §1 原則

1. **即時性を持ち込まない**（P-1、FR-014、FR-030）[explicit]
   - WebSocket、SSE、ロングポーリングは作らない。
   - 「新着があるか」を問い合わせるエンドポイントも作らない。
   - 住民がアプリを開いたときに郵便受けを取りに行く形にする。
   - 配達の通知（OQ-002・OQ-042 → 決定、ADR-0076・ADR-0035）は、worker（J15）が新聞の通知を配達回の公開のあとに、手紙の通知を受取人の手紙の時刻のあとに送る。API からは通知を送らない。
   - 郵便受けは、配達回が `done` で、かつ `visible_at` を過ぎた項目だけを返す（手紙は午前・午後の受取人ごとの時刻から、新聞は 07:00 / 17:00 から。ADR-0035）。受取人ごとの時刻は返さない。
     API が受けるのは、通知の購読の登録と削除だけ（§7 F-05）。

2. **数値の評価を返さない**（P-2、FR-017、FR-038、FR-044、FR-055）[explicit]
   - 返さないもの: 既読フラグ、未読件数、総件数、閲覧数、反応数、住所録への登録数、1 日の上限の残り回数。
   - 配達完了の通知に載せる郵便の件数は、通知の中身にだけ載せる。API の応答には載せない（ADR-0076 の D5）。

3. **同期で返すのは「受け付けた」まで**（ADR-0004、ADR-0008）[explicit]
   - 配達・審査・組版は worker が定時に行う。API は受付の状態（pending / awaiting_review）まで。
   - 例外として、手紙は投函のときに API がルール表の手紙の項目に 2 段で当てる（LLM は使わない）。`reject` の段に当たったら保存せずに 422 `letter_rejected` を返す。`review` の段だけに当たったら保存せずに 422 を返し、送った人が確認を頼んだときだけ `held` で保存する（OQ-052・OQ-076 → 決定、ADR-0069）。
   - 手紙のほかの書き込みも、書いたときに API がルール表の `reject` の段に当て、当たれば保存せずに 422 `content_rejected` を返す（LLM は使わない。OQ-087 → 決定、ADR-0070）。

4. **外から見える識別子は住所文字列のみ**（ADR-0001、db.md §3）[inferred]
   - 内部の UUID や `registered_tenancy_id` はレスポンスに含めない。

5. **API の経路で LLM を呼ばない**（NFR-011）[explicit]
   - 認可やポリシーの判断に LLM を使わない。

## §2 API・DB・バッチの責務の分け方

### §2.1 3 者の責務の表

| | 行うこと | 行わないこと |
|---|---|---|
| **API（web、C2 → C3）** | 認証、認可（本人のものか・ロール）、入力の検証（JSON Schema）、上限の確認（2,000 字・1,000 字・1 日 20 通・1 日 5 件・住所録の追加の 1 日 20 件）、手紙の投函のときの知り合いの確認（ADR-0065）とルール表の照合（暗号化の前、LLM なし。ADR-0069）、全ての書き込みの絵文字の検査と手紙のほかの書き込みの `reject` の段の照合（ADR-0070）、受付の状態での保存、配達済みの物の読み出し、手紙の復号（本人に返すときと、通報された手紙・確認待ちの手紙をモデレーターに 1 通だけ返すときだけ。ADR-0072・ADR-0069）、確認待ちの手紙へのモデレーターの操作（`approve` で `pending` に・`reject` で `blocked` に）、すぐに実行するジョブの投入（ID だけを同じトランザクションで積む） | 配達、審査（手紙の投函のときの照合を除く）、LLM の呼び出し、組版、画像の加工、時刻で決まる状態の変更、配達先の決定（転送・差し戻し・ブロックによる抑止）、物理削除の実行 |
| **DB（C7）** | 正本、一意の制約（配達・組版の冪等性）、外部キー、状態の値の制約、ジョブのキュー | 業務ロジックをトリガーやストアドプロシージャに置くこと [assumed]。理由: C3 に集めてテストしやすくするため（NFR-061） |
| **バッチ（worker、C4 → C3）** | JST の cron で動く処理（締め切り、審査、組版、配達、休眠の判定、保持期間による削除）と、すぐに実行するジョブ（退去時の消去、組み直し） | HTTP の受け付け、住民の権限での操作（システムの権限で動く） |

### §2.3 締め切りの境目

- API は共有の関数 `nextDeliveryRun(now)` で配達回 ID を決める。
- `delivery_runs` の行がなければ `INSERT … ON CONFLICT DO NOTHING`（`status=pending`）で作る。
- 同じトランザクションの中でその行を `FOR SHARE` で読み、`pending` でなければ次の便の配達回にする。
- 締め切り処理は `status=running` に更新するので、共有ロックの解放を待つ。こうして、締め切った配達回に書き込みが紛れ込まないようにする [inferred]。詳しくは async.md に引き継ぐ。

### §2.4 同期でやること・非同期でやることの流れ

**F-04 手紙の投函**
1. API: 宛先住所と本文の形式を確かめ（本文に絵文字があれば何も保存せずに `400`（`validation_failed`）、ADR-0069 の D13）、宛先が送る人の知り合いかを確かめる（ADR-0065 の D5。ブロックは見ない）
   - 知り合いでない（住所がない・空き家・どちらも足していない・片方だけ足している・投稿から足したエントリの投稿がオープンの掲載中でなくなった）→ 何も保存せずに `422`（`not_acquainted`）を返す。1 日の上限に数えず、本文はルール表に当てない
2. API: 暗号化の前に、本文をルール表の手紙の項目（スパム・外部リンク・成人向けの言葉・本当の情報（本当の居住地・本当の年齢・街の外の連絡先））に、`reject` の段 → `review` の段の順に当てる（ADR-0069 の D10。平文はメモリの中だけ。LLM は使わない）
   - `reject` の段に当たる → `request_review` があってもなくても、何も保存せずに `422`（`letter_rejected`）を返す。web は送れないことの決まった文面を出す
   - `review` の段だけに当たり、`request_review` がない → 何も保存せずに `422`（`letter_needs_review`）を返す。web はポップアップで y / n を聞く（n なら何もしない）
   - `review` の段だけに当たり、`request_review: true` → 本文を暗号化し、`held` 状態で保存する（`delivery_run_id` は NULL、`matched_rule_id`・`rule_version` を書く）。`202` と `{id}` を返す
   - 当たらない → 3 へ
3. API: 本文を暗号化し、`pending` 状態で `letters` に保存する（`rule_version` を書く）。同じトランザクションで `nextDeliveryRun` を呼び `delivery_runs` 行を冪等に作る（§2.3）
4. API: `202` と `{id, delivery_run_id}` を返す
5. worker: 締め切り時刻に `scheduled` → 公開の時刻（07:00 / 17:00）に `delivered` / `suppressed` / `returned` に遷移させる。受取人の郵便受けに見えるのは、その受取人の手紙の時刻（午前 08:00〜11:50・午後 18:00〜20:50 の枠、ADR-0035）を過ぎてから。worker は手紙を照合し直さない（ADR-0069 の D3）
6. `held` の手紙: モデレーターが `approve` すると、API が `pending` にして `nextDeliveryRun` の配達回に入れ（§2.3 の手順）、5 に進む。`reject` すると `blocked` になる（§7 F-08）

**F-07 掲示板の投稿**
1. API: 本文（1,000 字以内・絵文字があれば何も保存せずに `400`（`validation_failed`））を検証する（ADR-0070 の D2）
2. API: 本文をルール表の `reject` の段の規則（`external_link`・`adult_words`・`real_info`）に当てる（LLM は使わない）。当たれば何も保存せずに `422`（`content_rejected`）を返す。1 日の上限に数えない（ADR-0070 の D3）
3. API: 当たらなければ `awaiting_review` 状態で `board_posts` に保存し、`202` と `{id}` を返す
4. worker: 締め切り処理でモデレーション（J2。ルール表 → LLM → 人）→ `approved` / `rejected` → 配達時に `published`

**手紙のほかの書き込み**（ADR-0070。OQ-087 → 決定、2026-11-22）: ニックネームと自己紹介（`PATCH /api/v1/me`）・住所録のメモ（`POST` / `PATCH /api/v1/address-book`）・通報の理由（`POST /api/v1/reports`）も、掲示板の投稿の 1・2 と同じ順に確かめる（形式と絵文字の 400 → `reject` の段の 422 `content_rejected` → 上限の 429）。
当たらなければそのまま保存する（`review` の段は当てない `[assumed]`）。422 では何も変えない（新しい行を作らず、保存済みの値も変えない）。保存済みの値はルール表の版が上がっても当て直さない（ADR-0070 の D5）。
検索語（`GET /api/v1/address-book?q=`・段階 2 の `GET /api/v1/newspapers?q=`）は絵文字だけを確かめ（400）、`reject` の段には当てない。

**退去（DELETE /me）**
1. API: `residents.deleted_at` を設定、セッションを無効化、`account.erase` ジョブを同一トランザクションで積む
2. API: `202` を返す
3. worker: `account.erase` ジョブを受け取り、ADR-0077 の表に従い消去・組み直しを行う

### §2.5 コードの置き場所

- ルートのハンドラは薄くする: 解析 → 認証 → C3 のサービスを呼ぶ → エラーの対応付け。
- 本人のものかの確認と、クエリを本人の分に絞ること（`WHERE owner_id = $me` など）は、C3 のサービスの関数で必ず行う。
- worker も同じ C3 を使う（ADR-0008）。

## §3 API の形

- HTTPS と JSON、資源ごとの区切り、接頭辞は `/api/v1` [assumed]。
- スキーマは Fastify の JSON Schema で、型はクライアントと共有する（ADR-0009）。

**時刻**
- ISO 8601 の `+09:00` で返し、JST だけに対応する（OQ-034、NFR-048）。
- メッセージは日本語のみ（NFR-047）。
- 受取人に見せるのは「書いた時刻」ではなく配達回（例: `2026-11-19-morning`）[inferred]。

**キャッシュ**
- 住民の情報には `Cache-Control: no-store` を付ける。

## §4 認証と権限の確認の位置

- 認証は Fastify の preHandler で行う。方式はメールアドレス＋パスワード（ADR-0018、OQ-028 は決定）。
  セッションはサーバー側に持ち、複数の端末で同時に持てる（ADR-0019、OQ-036 は決定）。詳細は security.md §3。
- 認証なしで呼べるのは次の 5 つだけ（NFR-014）: 住所の候補、入居の一覧（`GET /api/v1/addresses/occupancy`。登録の前にもいつでも見せるため。住所と `occupied` だけを返し、セッションの有無で応答を変えない、ADR-0064 の D10・D15）、登録、ログイン、興味の一覧（登録の画面で選ぶため。一覧だけを返し、住民の情報と件数は返さない、ADR-0039）。
- 本人のものかの確認は C3 で行う。本人のものでないときや存在しないときは `404` を返し、存在するかどうかを明かさない [inferred]。
  例外は手紙の通報（`POST /api/v1/reports` の `mailbox_item_id`）で、本人の行でないときや存在しないときも、受け付けたときと同じ `202` を返して何も保存しない（§7 F-08、ADR-0078 の D10）。
- `/api/v1/admin/*` はロールで確認する。ロールは住民とモデレーターの 2 つで、admin 経路はモデレーターだけが呼べる（ADR-0020、security.md §4、OQ-031 は決定）。`403` を返すのは admin 経路のときだけ。
- ブロックの判断は API ではしない。送った人にブロックを気づかれないよう、送信は受け付け、配達のときに `suppressed` にする（db.md §3）。
  投函のときの知り合いの判定（ADR-0065 の D2・D5・D7）と、住所録の `acquainted` でもブロックを見ない（ブロックで 422 や `acquainted` が変わると、ブロックが分かるため。security.md T-06）。
  - architecture.md C2 の「ブロック」は「ブロックの登録を受け付けること」と読む。§10 で文言の整理を提案する。

## §5 エラーの形

```json
{ "error": { "code": "...", "message": "日本語のメッセージ", "details": {} } }
```

| 状態コード | code |
|---|---|
| 400 | `validation_failed`、`body_too_long` |
| 401 | `unauthenticated` |
| 403 | `forbidden`（admin 経路のみ） |
| 404 | `not_found` |
| 409 | `conflict`（住所を選ぶときの競合など） |
| 422 | `letter_needs_review`（手紙がルール表の手紙の項目の `review` の段だけに当たった。何も保存していない。当たった規則・理由は返さない、ADR-0069 の D4）、`letter_rejected`（手紙が `reject` の段に当たった。`request_review` があっても確認に回さない。何も保存していない。規則の ID・種類・段・本文の位置は返さない、ADR-0069 の D11）、`content_rejected`（手紙のほかの書き込み（掲示板の投稿・ニックネームと自己紹介・住所録のメモ・通報の理由。段階 3 の商店街の発信・マッチングの自由記述）が `reject` の段に当たった。何も保存せず、何も変えていない。規則の ID・種類・段・入力の位置は返さない、ADR-0070 の D3）、`not_acquainted`（手紙の宛先が送る人の知り合いでない。何も保存していない。住所がない・空き家・どちらも足していない・片方だけ足している・投稿から足したエントリの投稿がオープンの掲載中でなくなった、のどれも同じ決まった文面、ADR-0065 の D5・D7） |
| 429 | `daily_limit_reached`（手紙・投稿・住所録の追加の JST の暦日ごとの上限）、`add_suspended`（相互にならない住所録の追加の停止。追加と住所を変える `PATCH` だけ。割合・件数・残り・解除の時刻は返さない、ADR-0066 の D2）、`rate_limited`（登録の要求・ログイン試行・パスワード再設定・確認メール送信・入居の一覧（IP ごと、ADR-0064 の D18）・手紙の `letter_needs_review` と `letter_rejected` とほかの書き込みの `content_rejected` を合わせた流量の制限、security.md §3.5、ADR-0030・ADR-0069 の D7・ADR-0070 の D4）。どれも残りの数・解除までの時間は返さない |
| 500 | `internal` |
| 503 | `unavailable` |

スタックトレース、内部 UUID、`registered_tenancy_id` は返さない。

## §6 ページング

- カーソル方式。`?cursor=&limit=`、limit は既定 20・最大 50 [assumed]。
- 応答は `{ items, next_cursor }` で、総件数は返さない。
- 並びは決定的にし、人気の順は使わない。
  - 郵便受け: 配達回の新しい順 → 新聞 → 手紙 → id
  - 掲示板: 掲載された配達回の新しい順 → `created_at` → id
- 1 日の上限の数え方: JST の暦日ごとに数え、住民ごとに `pg_advisory_xact_lock` で直列にする [assumed]。
  住所録の追加は、消しても減らない `address_book_daily_counts`（`db.md` §2）で数え、住所を変える `PATCH /api/v1/address-book/{id}` も数える（ADR-0065 の D4）。
  同じロックの中で、今日を含む直近 7 日（JST の暦日）の数えの合計 N と、`counted_at` がその 7 日に入り今互いに足しているエントリの数 M を求め、N ≥ 100 かつ M < N × 2% なら 429 `add_suspended` を返す [assumed]（ADR-0066 の D1）。
  確かめる順番は、400 の検査 → `add_suspended` → `daily_limit_reached`（ADR-0066 の D2）。

## §7 MVP の機能ごとのエンドポイントの概略（F-01〜F-09・F-19）

### F-01 架空の住所・プロフィール

| メソッド | パス | 要約 | 状態コード | FR / ADR |
|---|---|---|---|---|
| `GET` | `/api/v1/addresses/candidates` | 住所の候補（OQ-022）。MVP では使われたことのない住所だけを返す。空き家の再割り当ては段階 3（ADR-0062） | 200 | FR-002, FR-003 |
| `GET` | `/api/v1/profiles/{address}` | 住所・ニックネーム・自己紹介だけを返す。空き家も存在しない住所も 404。今の年齢（`age`）は、下の見せる条件を満たすときだけ返し、満たさないときは項目そのものを返さない（`null` も返さない）（ADR-0073 の D4）。誕生日（`birthday`）は、見る住民が誰でも返さない（本人の誕生日は `GET /me` だけが返す。ADR-0073 の D4） | 200, 404 | FR-008, FR-113, FR-127, ADR-0073 |

年齢の見せる条件（ADR-0073 の D4。OQ-064 → 決定、2026-11-20）: 見る住民がプロフィールの住民本人でないとき、次をすべて満たすときだけ `age` を返す。

(c) 見る住民が、プロフィールの住民をブロックしていない。
プロフィールの住民が見る住民をブロックしても、`age` の有無は変えない（ブロックを気づかせない、security.md T-06・ADR-0015）。

**宛先の確認**（ADR-0065 の D5。OQ-066 → 決定、2026-11-20）: 確かめる順番は、形式の確認 → 知り合いの確認 → ルール表の照合（下の投函のときの照合）。
宛先は住所か、自分の住所録のエントリの ID（`address_book_entry_id`。掲示板の投稿から足したエントリは住所を見せないので、こちらで指す。ADR-0065 の D12）のどちらか 1 つ。両方・どちらもなし・自分のものでないエントリの ID は 400 `validation_failed`。
宛先が送る人の知り合い（互いの住所録のエントリが相手の今の居住記録を指す（ADR-0065 の D2）か、宛先のエントリが投稿から足したもので、その投稿がオープンの掲載中で、エントリが投稿者の今の居住記録を指す（D7）。どちらもブロックは見ない）でなければ 422 `not_acquainted` を返す。
住所がない・空き家・どちらも足していない・片方だけ足している・投稿から足したエントリの投稿がオープンの掲載中でなくなった、のどれも同じ決まった文面で、何も保存せず、1 日の上限にも数えない（security.md T-05）。
住所を見せないエントリ（投稿から足したもの・届いた手紙から足したもの、ADR-0065 の D12・D15）宛ての手紙は、`GET /api/v1/letters/sent`・`/sent/{id}` でも宛先の住所を返さず（エントリの ID を返す）、受け取った側の郵便受けでも差出人の住所を返さない（§7 F-03）。
知り合いを確かめるのは投函のときだけ。投函したあとで知り合いでなくなった手紙（`pending`・`held`・承認されたもの。宛先がオープンを外した・投稿を消したものを含む、ADR-0065 の D6）は、そのまま配達のときの振り分け（届く・転送・差し戻し・`suppressed`、db.md §3）に進む。  
「配達済み」（`delivered`・`suppressed`）は、その配達回の手紙の時間帯の終わり（朝便 12:00・夕便 21:00）を過ぎてから見せる。
それまでは「投函済み」と見せ、宛先ごとの時刻（`letter_recipients.delivered_at`）は返さない（ADR-0035 の D10）。  
`suppressed` は「配達済み」として見せる。`held`（送った人が確認を頼んだ手紙）は「確認中」、`blocked`（モデレーターが却下した手紙）は「届けられませんでした」と見せ、
どちらも当たった規則・理由は返さない（ADR-0072 の D5・ADR-0069 の D4・D5）。  
**送信済みに出す期間**（ADR-0077 の D5）[assumed]: 確定した手紙（`delivered`・`suppressed`・`returned`・`blocked`）は、状態にかかわらず確定の時刻（`settled_at`、`blocked` は `decided_at`）から 30 日まで `GET /api/v1/letters/sent` と `/sent/{id}` に返す。30 日を過ぎた手紙は、行が残っていても（受取人が持っている `delivered`・通報された手紙）一覧に出さず、`/sent/{id}` は 404 `not_found`。確定していない手紙（`pending`・`scheduled`・`held`）は返し続ける。
J14 が手紙を消す（db.md §4）のは、どれもこの 30 日のあとなので、送った人からは消したかどうかも消した時期も見えず、`suppressed` の手紙も `delivered` の手紙と同じ時期に送信済みから消える（security.md T-06）。

**本文の絵文字**（ADR-0069 の D13・ADR-0070 の D2。OQ-076・OQ-087 → 決定）:
- 本文に絵文字（Unicode の `Emoji_Presentation` の性質を持つ文字と、U+FE0F・U+20E3・`Emoji_Modifier`・`Regional_Indicator` の文字。`[assumed]`）があれば、形式の確認で 400 `validation_failed` を返し、何も保存しない。1 日の上限に数えない。
- 顔文字（例 `(^_^)`）・`〒`・`「」` と、ふだん文字の形で出る記号（★・♪・♥・☀・☎・✉・©・®・™ など）は通す。後ろに U+FE0F を付けて絵の形にしたもの（例 ☀ U+FE0F）は 400 になる。
- web の手紙の入力欄は絵文字を受け付けない（入力・貼り付けで入らない）。API の 400 は、web を通らない要求への守り。
- 同じ定義を、手紙のほかの全ての書き込みと検索語にも当てる（§2.4）。

**投函のときの照合**（ADR-0069。OQ-076・OQ-087 → 決定）:
- 照合は暗号化の前に、ルール表の手紙の項目だけで行う。LLM は呼ばない。平文はメモリの中だけに置き、ログ・例外のメッセージに書かない。
- 項目は段（`reject` / `review`）を持つ。まず `reject` の段に当て、当たれば `letter_rejected`。当たらなければ `review` の段に当て、当たれば `letter_needs_review`（`request_review: true` なら `held`）。両方に当たる本文は `reject` を先にする（ADR-0069 の D10）。
- 本当の情報（`real_info`）は、本当の居住地・本当の年齢・街の外の連絡先（メールアドレス・電話番号・他のサービスのアカウントなど）を、聞く文・自分から書く文・ほかの人のものを書く文のどれでも対象にする。架空の街の住所と住民が設定した年齢は対象にしない（ADR-0069 の D12・ADR-0071）。
- 422 `letter_rejected` と `letter_needs_review` の応答は、決まった文面だけで、当たった規則・項目の種類・段・本文の位置を含めない。手紙は保存せず、1 日の上限にも数えない。
  2 つの 422 とほかの書き込みの 422 `content_rejected` を合わせた住民ごとの流量の制限を超えると 429 `rate_limited`（security.md §3.5。値は OQ-065）。
- web は `letter_rejected` を受けたら、送れないことの決まった文面（文言は OQ-065）を出し、確認を頼む選択は出さない。送った人は本文を直して送り直せる。
- web は `letter_needs_review` を受けたら、モデレーターに確かめてもらって送るか（y）・送らないか（n）をポップアップで聞く。y を選ぶとモデレーターが本文を読むことを書く（文言は OQ-065）。
  n なら何も送らない。y なら同じ本文と宛先に `request_review: true` を付けて送り直す。
- `request_review: true` でも、本文がどの規則にも当たらなければ、ふつうの手紙として `pending` で保存する。`reject` の段に当たれば `letter_rejected`。`held` の手紙は 1 日の上限に数える。
- 送ったときに当たらなかった手紙は、あとでルール表の版が上がっても当て直さない（ADR-0069 の D3）。

- `inferred_interests` に書けなくても検索の結果は返す。応答には、当たった興味も、推し量ったかどうかも含めない（ADR-0045 の D8）。
- web は検索の入力欄のそばに、推し量って新聞を届けることを明るく開いた文で示す（文言は仮置き、ADR-0045 の D7）。同意の画面・チェックは置かない。
- 住民は推し量ることを止められない（OQ-072 → 決定、2026-11-21、ADR-0053）。照合と書き込みは、この検索の要求の処理の一部として、どの住民の検索でもいつも行う。推し量りを切る（照合を止める）引数は受け付けない。並び替えや期間で絞るなど、照合を止めない引数を置くかは、S2-3 で検索のしかたと合わせて決める。止める設定の経路・`/me` と `/me/interests` の止める項目・住民ごとの例外の分岐は作らない（§8）。
- 照合の位置・書き込みに失敗したときの扱い・知らせの文と画面・B-09 の確かめ方は、S2-3 の設計で整理してここに書く（ADR-0053 の D4）。
- 流量の制限は、ほかの住民の API と同じ（security.md §3.5）。

**掲示板の経路**（ADR-0065 の D7・D10〜D12。OQ-081 → 決定、2026-11-21）:
- オープンは投稿ごと。`accepts_letters: true` の投稿が `published` の間だけ効き、期限はない。`awaiting_review`・`approved`・`rejected`・`deleted` の投稿では効かない `[assumed]`。
- 投稿者の住所は、どの投稿の応答にも含めない（投稿と住所を結び付けて見せない、ADR-0065 の D12）。宛先は投稿の ID で指す。
- 投稿を見た住民 X が、オープンの掲載中の投稿 P から投稿者 Y を住所録に足すと（`POST /api/v1/address-book` に `board_post_id = P`、§7 F-09）、そのエントリは `acquainted: true` になり、X はそのエントリ宛てに（`address_book_entry_id`、§7 F-04）Y へ手紙を出せる。
  効くのは P から足したエントリだけで、住所を入れたエントリやほかの投稿から足したエントリでは効かない（P を見ていない住民は、この経路では出せない、D7）。
  向きは X から Y だけ。Y が X に出すには、Y が X からの手紙で X を足し返す（`POST /api/v1/address-book` に `mailbox_item_id`。互いの追加になる、ADR-0065 の D15）か、X のオープンの投稿から Y が X を足すことが要る。
- オープンにした時点で、その投稿を見た住民からの手紙を許したことになる。一人ずつ許す経路・申請・承認の経路は作らない（§8）。
- オープンを外す・投稿を消す・退去する・引っ越すと、その時点からその投稿の経路は効かない。それより前に投函した手紙は届く（§7 F-04）。相手には何も知らせない。
- web はオープンの投稿に、住所録に足す導線を出す。

### F-08 通報・ブロック・モデレーション

**手紙の通報**（`POST /api/v1/reports`、ADR-0078 の D8〜D10）
- 手紙を通報できるのは、その手紙を受け取った住民だけ。要求は `mailbox_item_id`（`GET /api/v1/mailbox` が返す郵便受けの行の ID）で手紙を指す。手紙の ID（`letter_id`）は受け取らない（400 `validation_failed`）。送った人が投函の応答で受け取る `{id}` では通報できない。
- `reports` に行を作るのは、郵便受けの行が次のすべてを満たすときだけ: 呼んだ住民の行である・`kind = 'letter'` で `visible_at` を過ぎ、`deleted_at IS NULL` である・行が指す手紙が `delivered` である。
- 行には `content_kind = 'letter'` と、郵便受けの行から引いた `letters.id` を `content_id` に書く。郵便受けの行の ID は保存しない。
- 条件に合わないとき（ほかの住民の行・見せる前の行・削除した行・新聞や掲示板の行・存在しない ID）は、条件に合うときと同じ 202 と同じ本文を返し、何も保存しない（存在と状態を明かさない。§4 の 404 の例外、`security.md` §4.3）。
- 理由の絵文字（400）と `reject` の段（422 `content_rejected`）は、郵便受けの行の確かめより前に確かめる。
- 掲示板の投稿の通報は `board_post_id` で指す。

**通報された手紙の取得**（`GET /api/v1/admin/reports/{id}/letter`、ADR-0072 の D4 (c)）
- この経路は決定（OQ-043 の答え、2026-11-19、ADR-0078 の D2）。住民が通報した手紙は、モデレーターが下の条件で確かめてよい。通報の行があるのは、受取人が通報した `delivered` の手紙だけ（上の「手紙の通報」）。
- 返すのは、通報が `open`・対象が手紙・呼んだモデレーターがその手紙の当事者（送った人・受け取った人・通報した人）でない・
  セッションが二要素認証を済ませている、のすべてを満たすときだけ。満たさなければ 404（存在を明かさない）。
- 1 回の呼び出しで返すのは、その通報の手紙 1 通だけ。複数の手紙をまとめて返す経路・本文の一覧・本文の検索は作らない。
- 呼ぶたびに `moderation_actions` に `view_letter` の行を書く。書けなければ本文を返さない（同じトランザクション）。
- 応答には `Cache-Control: no-store` を付ける。
- 通報されていない手紙を見る経路は、次の確認待ちの手紙の経路だけ。`blocked`・`pending` などほかの状態の手紙を見る経路はない（OQ-052 → 決定、2026-11-20、ADR-0069 の D5）。

**確認待ちの手紙の確認**（`/api/v1/admin/held-letters`、ADR-0069 の D5）
- 送った人が投函のときに確認を頼んだ（`request_review: true`）手紙だけが対象。確認待ちの手紙は `review` の段に当たった手紙からだけ出る。`reject` の段に当たった手紙は保存しないので、ここに出ない（ADR-0069 の D5・D11）。
- 取得と操作は、手紙が `held`・呼んだモデレーターがその手紙の当事者（送った人・宛先の住民）でない・セッションが二要素認証を済ませている、のすべてを満たすときだけ。満たさなければ 404。
- 取得のたびに `moderation_actions` に `letter_id` 付きの `view_letter` の行を書く。書けなければ本文を返さない（同じトランザクション）。応答には `Cache-Control: no-store` を付ける。
- 1 回の呼び出しで返す本文は 1 通だけ。一覧は本文を返さない。本文の検索は作らない。
- `approve`: `held` → `pending` にし、`nextDeliveryRun(now)` の配達回に入れる（§2.3 の `FOR SHARE` の手順）。`moderation_actions` に `approve` を書く。次の配達回で届く。
- `reject`: `held` → `blocked` にし、`decided_at` を書く。`moderation_actions` に `reject` を書く。送った人には「届けられませんでした」と見せる。
- 状態の更新は `WHERE id=$1 AND state='held'` で行う。すでに操作された手紙への操作は 404（2 人のモデレーターが同時に操作しても 1 回だけ効く）。

### F-09 住所録

**知り合いの登録**（ADR-0065。OQ-066・OQ-040 → 決定、2026-11-20）: ふつうの経路（既定）は、住所を入れて住所録に足すこと。相手も自分を足したとき（互いのエントリが相手の今の居住記録を指すとき）に知り合いになる。
「申請」の資源・申請の一覧・承認の経路は作らない。足し返すことが承認にあたる。足された側には、通知・一覧・件数のどれでも知らせない（§8）。
掲示板の経路（ADR-0065 の D7）は、オープンの掲載中の投稿から `board_post_id` で足すこと。投稿者の住所は見せない（§7 F-07）。
投稿者は、その経路で届いた手紙から `mailbox_item_id` で差出人を足し返す（ADR-0065 の D15。差出人の住所は見せない）。足し返すと互いの追加（D2）になり、オープンを外しても続く。
`acquainted` は、ブロックを見ずに `registered_tenancy_id`・`tenancies.is_current`・`address_book.source`・`board_post_id` とその投稿（`status = 'published'`・`accepts_letters`）からそのつど求める（db.md §2）。
互いの追加（D2）にする組は、住所を入れたエントリどうしか、投稿から足したエントリと手紙から足したエントリだけ。住所を入れたエントリと住所を見せないエントリは組にしない。
足した側が、相手もすでに自分を足していたと知れる程度は許す（ADR-0065 の D13、OQ-081 → 決定）。守りは 1 日 20 件の上限と、相互にならない追加の停止（ADR-0066）。
掲示板の経路で新しく分かるのは、投稿から足したエントリの `acquainted` が、投稿がオープンの掲載中の間は true で外すと false に戻ること（オープンは掲示板で誰にでも見える）と、投稿者が届いた手紙から足し返したことだけ。投稿者が前から住所を入れて足していても、投稿から足したエントリとは組にしないので、匿名の投稿と住所は結び付かない。住所を入れたエントリの `acquainted` は掲示板の経路で変わらない。
投稿が消され、物理削除されても、投稿から足したエントリは残る（`board_post_id: null`。web は決まった文面「消えた掲示板の投稿から足した相手」と足した日付・メモで示す、ADR-0065 の D6・D12）。

**相互にならない追加の停止**（ADR-0066。OQ-081 → 決定、2026-11-21）:
- 判定は §6 の数え方のとおり（7 日・100 件・2% は `[assumed]`）。M に入れるのは互いに足したエントリ（ADR-0065 の D2）だけで、掲示板の経路だけの相手は入れない。
- 止めるのは追加と住所を変える `PATCH` だけ。削除・メモだけの `PATCH`・住所録の読み出し・手紙・掲示板は止めない。
- 429 `add_suspended` は決まった文面だけで、割合・件数・残り・解除の時刻を返さない。何も変えず、数えにも入れない。
- 止めた状態は保存せず、要求のたびに求める。7 日の窓から外れるか足し返されれば自然に戻る。解除・延長の経路は作らない（§8）。

```json
{ "houses": [ { "address": "夕暮ヶ丘三丁目 2-5", "occupied": true } ] }
```

- `occupied` は、`addresses.status` が `active`・`dormant` なら `true`（休眠は空き家にしない）、使われたことのない住所（`addresses` に行がない）と `vacant_deleted`・`vacant_expired`・`vacant_forwarded` なら `false`。状態の種類は返さない（ADR-0064 の D13）。
  MVP で起きるのは `active`・使われたことのない住所・`vacant_deleted` だけ。休眠を空き家にする判定と転送中の旧住所の示し方は OQ-088（持ち越し）。
- 示すのは要求を受けたときの状態（ADR-0064 の D14、`[assumed]`）。退去のすぐあとの要求では `false` になる。
- 並びは番・号の数の順で、登録の順・状態に依らない。ページング・`total`・件数（住んでいる家の数・空き家の数）は返さない（§1 原則 2・§8）。
- ニックネーム・自己紹介・年齢・住み始めた日・`status` の値は返さない。

印（OQ-054 → 決定、2026-11-20、ADR-0064）は C1 が土台の上に重ね、住所から位置を求めるのは C1 の静的な配置の定義と計算で行う。
印に使う住所は、すでにある経路が本人に返すものだけで、位置・座標は足さない（住所録に足したのは `acquainted` だけ、ADR-0065 の D4）。

| 印 | 使う経路 | マイルストーン |
|---|---|---|
| 自分の家（窓の中心に置く） | `GET /api/v1/me` の住所 | M1 |
| 登録のときの候補（候補の一覧と同じ見出し。候補の印を押すか、一覧から選ぶ。OQ-080 → 決定、2026-11-21、ADR-0064 の D7） | `GET /api/v1/addresses/candidates` | M1 |
| 知り合いの家 | `GET /api/v1/address-book` のすべてのエントリの住所（`acquainted` によらず、C1 の地図の画面は `acquainted` を読まない。登録した時点の住所、ADR-0003。OQ-071 → 決定、ADR-0051）。掲示板の投稿から足したエントリは住所を返さない（`address: null`）ので、印は付かない（ADR-0065 の D12） | M2 |

入居の層（FR-115）は、C1 が入居の一覧の応答から家ごとに白黒の 2 つの形のどちらかの印を描き、上の印をその上に重ねる（ADR-0064 の D8）。登録の画面（M1）とログインした住民の地図の画面（M1）の両方に出す。

登録のときの選び方（OQ-080 → 決定、2026-11-21、ADR-0064 の D7）: 住民は登録の画面の地図の候補の印を押すか（キーボードでも選べる）、候補の一覧から住所を選ぶ。選ぶのは C1 の中で、選んだ候補は今までどおり登録の要求で候補の住所として送る。
候補の印を押して選ぶための経路・応答の項目は足さず、`GET /api/v1/addresses/candidates` と登録の要求の形は変えない（ADR-0064 の D16）。
押して選べるのは候補の印だけで、入居の層の印（空き家の印を含む）は押しても何も起きない。空き家の印から住所を選ぶ経路は作らない（空き家の印も選べるかは OQ-089、要回答）。

OQ-066 の答え（2026-11-20、ADR-0065）で、知り合いには相手の同意（互いの追加か掲示板でのオープン）が要ると決まり、`GET /api/v1/address-book` の各エントリに `acquainted` が入った（§7 F-09）。
地図の印は、住所録のすべてのエントリに付ける（OQ-071 → 決定、2026-11-20、ADR-0051 の D1。OQ-054 の答え「2:1」、ADR-0064 の D1 (c) のまま）。地図の「知り合い」は自分の住所録に入れた住民で、手紙・新聞の知り合いと定義を分ける（ADR-0051 の D2）。
印の有無・形・見出し・代替テキストを `acquainted` で変えないので、地図の印から相手が自分を住所録に入れたかは分からない（ADR-0051 の D3）。片方だけ足したエントリにも印が付くので、印があっても手紙を出せるとは限らない（出せるかは住所録の画面と手紙の画面の `acquainted`）。応答の形は変えない。

**画面の確かめ方の約束**: 地図の画面が呼ぶ API は、`me`・`candidates`・`address-book`・`occupancy` の 4 つだけ（登録の画面は `candidates` と `occupancy` の 2 つ。ADR-0064 の D5）。ほかの住民の情報を地図のために取りに行かない。

- **手紙の宛先**: OQ-066 → 決定（2026-11-20、ADR-0065）。手紙は知り合いにだけ出せ、知り合いでなければ 422 `not_acquainted`（§2.4・§7 F-04）。住所録の `acquainted` と 1 日 20 件の追加の上限を足した（§7 F-09）。
