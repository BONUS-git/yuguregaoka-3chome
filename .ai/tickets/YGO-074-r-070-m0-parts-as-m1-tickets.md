# YGO-074 R-070 M0 の土台を M1 のチケットに混ぜ範囲が曖昧
状態: done
M: M1

## 目的
`reviews/0004-phase-evaluation-2026-11-27.md` の R-070（区別: 中、評価の ID: E-024）を直す。
YGO-062・YGO-065 は M0 の残り（時計・メールのアダプタ・キュー・2 プロセスの骨組み・環境変数の読み込み など）を「M0 の別のチケット」とするが、そのチケットはない。M1 の登録の TC はそれに依存する。M1 の TC に要る M0 の部品を、`M: M1` のチケットとして切る。

## 依存
- このチケット（チケットを切ること）は、YGO-062・YGO-078 の done を待たない。切ったチケットの実装は、YGO-062 と YGO-078（`.ai/tickets/YGO-078-m1-package-json-lockfile-vitest.md`。`package.json` とロックファイルを入れ、`check.sh` から Vitest を動かす）の両方の done を待ち、YGO-065 のあとに並べる（切ったチケットの TC は Vitest で動くため）。

## M1 の TC が使う M0 の部品
`tests/test-plan.md` の種類「ジョブ」は、worker のジョブ J14・J18 を差し替えた時計で動かす。J18 はメールのアダプタを worker の環境変数 `MAIL_ADAPTER` で選ぶ（`async.md` §4 J18、`environment.md` §8.1）。そのため、M1 の TC が使う部品は次のとおり。

| 部品 | 使う M1 の TC |
|---|---|
| 差し替えられる時計 | TC-016・TC-017 |
| `jobs` のキュー（pg-boss の依存と、積む口） | TC-017・TC-019 |
| worker のジョブの実行（2 プロセスの骨組みのうち worker が J14・J18 のハンドラを動かす部分） | TC-017（J14）・TC-020（J18） |
| 環境変数の読み込み（`MAIL_ADAPTER` の選択） | TC-020 |
| モックのメールのアダプタ | TC-020 |
| テストの準備で外への接続を失敗させる（`roadmap.md` A-07 の (4)・`tests/test-plan.md` の冒頭）。`test/setup.ts` を作る YGO-076 の範囲に入れる | すべての TC |
| KeyProvider の偽の鍵（メールアドレスの暗号化と検索の HMAC。J18 も `EMAIL_KEYRING` で復号する、`async.md` §4 J18・`environment.md` §8.1） | TC-018・TC-019・TC-020・TC-023・TC-001 |

## 範囲
- 次の 5 枚の新しいチケット（`状態: open`・`M: M1`）を切る。
  1. 時計（差し替えられる時計。TC-016・TC-017 が使う）
  2. `jobs` のキュー（TC-017・TC-019 が使う）
  3. 環境変数の読み込みと `MAIL_ADAPTER` の選択（TC-020 が使う）
  4. モックのメールのアダプタ（TC-020 が使う）。3 に依存する
  5. worker のジョブの実行（worker のプロセスが `jobs` から J14・J18 を取ってハンドラを動かす。TC-017・TC-020 が使う）。1・2・4・6 に依存する
- 6 枚目として KeyProvider の偽の鍵（TC-018・TC-019・TC-020・TC-023・TC-001 が使う）を切る。3 に依存する `[assumed]`。理由: 上の表の TC はメールアドレスの暗号化と HMAC に偽の鍵を使い、今の M の TC が依存する前の M の部品は今の M のチケットとして切る決まりがあるため。J18 が `EMAIL_KEYRING` で復号する（`async.md` §4 J18）ので、5 は 6 に依存し、worker はハンドラに KeyProvider を渡す。
- 7 枚目として、2 の `jobs` のキューのうち pg-boss を固定の版で依存に足しロックファイルを直すこと（道具の追加）を切る。2 は積む口（機能の実装）だけにし、7 に依存する。理由: 道具の追加と機能の実装が 1 枚に入るときは別々のチケットに分ける決まりがあるため。
- 1〜5 の番号の並びを変えないよう、6 枚目・7 枚目を最後の番号にする。番号: 1 は YGO-080、2 は YGO-081、3 は YGO-082、4 は YGO-083、5 は YGO-084、6 は YGO-085、7 は YGO-086。
- 7 枚の「依存」の節に、YGO-062 と YGO-078 の両方の done を待つことを先頭に書き、続けて YGO-065 のあとに並べること（YGO-062 → YGO-075 と YGO-078（並んで進む）→ YGO-076 → YGO-065。YGO-075 の依存の節のとおり、YGO-075 は YGO-078 を待たない）と、互いの依存の順（YGO-080・YGO-082・YGO-086 → YGO-081・YGO-083・YGO-085 → YGO-084）を書く。同じ列を書いている YGO-065・YGO-077 の依存の節もそろえる。
- 部品のチケットは自分のテストを持たない `[assumed]`。`check.sh` は名前に TC-NNN のない `testcase` で失敗し、`tests/test-plan.md` に部品だけを確かめる TC がない。部品は、使う FR のチケット（YGO-071 で切る）の TC で確かめる。
- 切ったチケットと土台のチケット（YGO-062・YGO-078・YGO-075・YGO-076・YGO-065・YGO-077）の作るものと依存の順を、`roadmap.md` §4「M1 の土台のチケット」に書く。
- `.ai/tickets/YGO-062-m1-test-harness.md` と `.ai/tickets/YGO-065-m1-resident-address-schema.md` にある「M0 の別のチケット」「別のチケット」のうち、時計・メールのアダプタ・キュー・2 プロセスの骨組み・環境変数の読み込みを指す記述を、切ったチケットの番号に直す。
- YGO-062 の直さないところの「`scripts/dev-db.sh`・時計・アダプタ・2 プロセスの骨組み・キュー・`APP_ENV` と環境変数の読み込み」の 1 行を分ける。時計・アダプタ・キュー・worker のジョブの実行・環境変数の読み込みには切ったチケットの番号を書く。残る `scripts/dev-db.sh`（開発の DB の台本。`check.sh` は使い捨ての PostgreSQL を使い、TC はこの台本を使わない）と、`APP_ENV` の起動の検査（`staging`・`production` で偽の鍵か `CLOCK_OFFSET` があれば起動に失敗する。M1 の TC はどれも確かめない）は、M1 の TC が使わないため M1 のチケットにせず、使う TC のチケットを切るときに扱うと書く `[assumed]`。YGO-062 の範囲の M0 の残りの列挙・§3.2 の 2 以降（`dev-db.sh`・`.local/`）の行・受け入れ確認 12、YGO-065 の直さないところの同じ列挙も、同じように分ける。
- 切ったチケットを `.ai/INDEX.md` に載せる。
- テストの準備で外への接続を失敗させること（A-07 の (4)）は新しいチケットにせず、`test/setup.ts` を作る YGO-076 の範囲と受け入れ確認 12 に足す `[assumed]`（同じファイルの準備で、道具の追加を増やさないため）。
- YGO-080（時計）は時計とその差し替え方だけを範囲にし、DB の側の時刻の比べ方（`db.md` §2・`async.md` §4 J14 の `now()`）は、TC-016・TC-017 を作る FR のチケット（YGO-071 の範囲の 3）に任せる。
