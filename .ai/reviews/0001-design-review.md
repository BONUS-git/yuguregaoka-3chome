## 重大

### R-001 — 要求仕様の「空き家」が ADR-0002・ADR-0023 と食い違う
- 区別: 重大
- 根拠: `requirements.md` §2 用語「空き家」(:60)、FR-006 (:79)、FR-007 (:80)、FR-071 (:199)、FR-074 (:202)、FR-093 (:238)。`adr/0002` の決定 (:14-18)、`adr/0023` の D2・D3。`open-questions.md` OQ-027 (:413-418)、§7 の 1 (:1494-1496)
- 内容: 正本の要求が、まだ「一定期間ログインのない住所は空き家」と書いている。ADR-0002 で決めた流れは次の 3 つだが、要求にはそれが書かれていない。
  - 削除すれば即時に空き家
  - 12 か月ログインがなければ通知し、そこから 30 日で休眠空き家
  - 引っ越しから 6 か月で転送後空き家

  FR-007・FR-074・FR-093 は、空いた住所がすぐ新しい住民の候補になるように読める。だが ADR-0023 は、再割り当てを段階 3 まで行わない。FR-006・FR-071 は [explicit] のままだが、構想にあるのは「空き家」という語だけ。OQ-027 で [inferred] に直すと決めたのに、それが「別チケット」に回されたまま残っている（R-007）。
- 直し方の案: §2 の「空き家」を ADR-0002 の 3 種類に書き分ける。FR-006・FR-071 を通知と休眠を経る流れに書き換え、区分を [inferred] にする。FR-007・FR-074・FR-093 に「再割り当ては段階 3（ADR-0023）」と書く。ADR-0002 の題（vacancy-requires-explicit-deletion）と本文がずれているので、注記を足す。
- マスターの判断: 不要

### R-002 — 配達回（`delivery_runs`）を 30 日で消すと、届いた手紙と過去の新聞が消えるか、削除が失敗する
- 区別: 重大
- 根拠: `db.md` §4 (:539)、`async.md` §4 J14 (:605)、`adr/0013` (:56) は、配達回を 30 日で消すとしている。一方、`db.md` §2 では郵便受けの行 (:155)・`letters` (:126)・`newspapers` (:221) などが、外部キーでこの表を指している。郵便受けは受取人が消すまで残り (:538)、新聞は無期限に残る (:542)。`api.md` (:18・:210・:272) と `roadmap.md` S2-3 (:160) は、「配達回が `done`」を返す条件にしている。`async.md` §8 (:824) と §9 (:841) は、この点を未確定と認めている
- 内容: 30 日を過ぎた配達回の DELETE は、外部キー違反で失敗する。CASCADE や SET NULL にすれば、今度は「`done` の回だけ返す」の条件が成り立たなくなり、30 日より前の手紙とバックナンバーが郵便受けから消える。それなのに、未確定のまま J14 の削除が書かれている。
- 直し方の案: 配達回は消さない（1 日 2 行）と決め、ADR で ADR-0013 のその行を置き換える。`db.md` §4 と J14 から削除を外す。または、API の条件を「郵便受けの行があり `visible_at` を過ぎた」に変えたうえで外部キーを外す。どちらを採るかを ADR に書く。受け入れ条件（A-03 か A-13）に「31 日後も郵便受けに手紙が残る」を足す。
- マスターの判断: 不要

### R-003 — 差し戻しと抑止の手紙は、暗号化した本文が消えない
- 区別: 重大
- 根拠: `db.md` §4 (:536)（受取人全員が郵便受けから消したとき、または通報のクローズから 1 年で消す）。`async.md` J4 (:353-354)（差し戻しと抑止では郵便受けの行を作らない）、J7 の手順 1 (:457)（退去した人の未配達の手紙を `returned` にする）、J14 の対象の表 (:600-617)（手紙は `blocked` だけ）。`db.md` (:159)（郵便受けは `deleted_at` を付けるだけ）
- 内容: `returned`・`suppressed` の手紙は郵便受けに入らないので、本文と宛先が無期限に残る。届いた手紙も、「受取人全員が消した」ことを見て物理削除するジョブがない。データのライフサイクル（構想 §4）の抜けで、個人情報を必要以上に持ち続けることにもなる。
- 直し方の案: J14 に 2 行足す。`returned`・`suppressed` は確定から N 日 [assumed] で宛先ごと消す。`delivered` は、`deleted_at IS NULL` の郵便受けの行が 1 つもない手紙を消す（通報中のものは除く）。同じ期間を `db.md` §4 と ADR-0013 に書く。
- マスターの判断: 不要

### R-004 — 手紙を通報する人が受取人かを確かめていない
- 区別: 重大
- 根拠: `api.md` §7 F-08 `POST /reports` (:294、:306-313)、`security.md` §4.2 (:304-309)、§5.4 (:423-426)、§2.3(c) (:97-99)、`db.md` `reports` (:412-423)（`content_id` だけで制約がない）。`adr/0026` D4(c) (:66)、`adr/0036` D2 (:37)（条件はモデレーターの側だけ）。送った人には手紙の `{id}` を返す（`api.md` :80・:218）
- 内容: 通報できる人の条件がない。手紙の ID を知っている住民が通報すれば、モデレーターが本文を復号して見る経路が開く。送った人は、自分の `blocked`・`pending` の手紙を通報できる。これで、ADR-0040 (:78)・`api.md` (:313)・`security.md` (:103・:228) が「ない」としている閲覧の経路ができてしまう。クローズドな手紙の秘匿（NFR-004・NFR-005）が崩れる。
- 直し方の案: `POST /reports` の手紙の通報に、3 つの条件を足す。通報する人が受取人であること、手紙が `delivered` であること、その人の郵便受けの行があること。条件に合わなければ同じ 202 を返し、何も保存しない。手紙の ID ではなく郵便受けの行の ID を受け取る形にする。`security.md` §4.2・§5.4 と ADR-0036 にも同じことを書く。
- マスターの判断: 不要

### R-024 — 公開の文書が、実在の外の LLM 事業者の名前と価格表を載せている
- 区別: 重大（公開レポジトリの規則にかかわるため。初稿では中としたが、見直しで上げた）
- 根拠:
  - 事業者の名前: `architecture.md` (:282)、`async.md` (:812)、`roadmap.md` (:22・:361・:386・:391)、`security.md` §5.3 (:408)・§8 (:554)、`open-questions.md` (:240・:243・:1024)、`adr/0031`（題 :1、:23・:30・:52・:60・:67）。範囲の外では `adr/0005`・`adr/README.md` にもある
  - 価格表: `roadmap.md` §9.1 (:391) が日付つきで引き、(:397-398・:402・:410-411) でそれをもとに計算している
  - 規則: CLAUDE.md の「公開レポジトリ」（実在の人や団体を書かない）。NFR-020・NFR-090 も同じ
- 内容: 公開の文書が、実在の事業者の名前と価格を載せている。技術の名前（言語・DB・ライブラリ）と違い、契約先になりうる事業者の名前と価格は、この規則に当たるおそれがある。ただ、技術の選定（ADR-0031）を書くには名前が要るともいえる。どこで線を引くかは公開の範囲の判断で、マスターにしか決められない。このレビューは事業者の名前を書かない。
- 直し方の案: 名前を「外部の LLM サービス（暫定）」「軽量のモデル」などの一般の呼び名に置き換える。価格は変数の式と「見積もりのときに確かめる」に置き換える。線の引き方（ライブラリやツールの名前はよいか）をマスターの答えに合わせて ADR に書き、ほかの文書もそろえる。答えが出るまでの暫定は「一般の呼び名に置き換える」とし、答えで変わる箇所は上の根拠の各文書と ADR-0031 の題・本文とする。
- マスターの判断: 要る（公開の範囲。事業者の名前と価格を公開の文書に載せてよいか）。問いは、直しの変更で `open-questions.md` に新しい要回答の OQ（次の空き番号、§2 の表の行に `OQ-NNN` と `要回答` を書き、本文は `### OQ-NNN — 事業者の名前と価格を公開の文書に載せてよいか` の見出しの下に質問と暫定）として立てる。この変更はレビューを書くだけなので、ここでは立てない

### R-008 — J7 の手順が足りず、住民の行の削除が外部キーで止まる
- 区別: 中
- 根拠: `async.md` J7 (:456-465)。`db.md` (:123・:627)・`adr/0013` (:32)（差出人を NULL にする）、`db.md` (:350)（投稿者を NULL にする）、(:538)（本人の郵便受けの行）、(:465)（`images.uploader_id`）、(:449)（`moderation_actions.moderator_id`）。`async.md` J14 (:610)・J4 (:332)（`is_current = true` の全員に新聞）

- 直し方の案: J7 に上の処理を足す。居住記録は、住所を `vacant_deleted` にするのと同じトランザクションで終わらせる。外部キーごとの ON DELETE を `db.md` §2 に書く。

### R-013 — 審査キューに一意制約がなく、LLM を二重に呼ぶ

### R-022 — FR-122・FR-053 の `acquainted` に、OQ-081 (3) の暫定の印と参照がない
- 区別: 軽微（初稿では中としたが、見直しで範囲を狭めて下げた）
- 根拠: `open-questions.md` OQ-081 の暫定 (:1389-1390)（「(3) は `acquainted` を返し、1 日 20 件の上限を置く（ADR-0049 の D4）」と、答えで変わる箇所 `api.md` F-07・F-09・`security.md` T-23・FR-122 など）。`adr/0049` D4 (:52)（「OQ-081 (3) で確かめる」）。`requirements.md` FR-122 (:170)（OQ-081 を掲示板の経路 (2) についてだけ書き、`acquainted` を返すことには書いていない）・FR-053 (:169)（OQ-081 への参照がない）
- 内容: 暫定と、答えで変わる箇所は OQ-081 にすでに書かれていて、ADR-0049 D4 も OQ-081 (3) を指している。CLAUDE.md の「暫定を置くなら、答えで変わる箇所を書く」は満たされている。抜けているのは正本の要求の側だけで、FR-122・FR-053 を読んでも、`acquainted` を返すことが OQ-081 (3) の答えで変わりうる暫定だと分からない。
- 直し方の案: FR-122 の「足した側には住所録の各エントリの `acquainted`（真偽値）だけを返す」と FR-053 に、「（暫定。OQ-081 (3)、要回答）」を足す。
- マスターの判断: 不要（直しは秘書ができる。探りを許すかの問いは、すでに要回答の OQ-081 (3)。新しい問いは立てない）
