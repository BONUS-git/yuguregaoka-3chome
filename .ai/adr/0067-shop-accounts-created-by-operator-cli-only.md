# 0067 — 商店のアカウントは運用者の CLI だけで作る

- 状態: 採用
- 日付: 2026-11-21

ADR-0029 を丸ごと置き換える。ADR-0029 の D1 のうち「住民は団体を開けない」は ADR-0038 の D2（コミュニティ（団体）は住民が作る）で変わったので、
残る商店の部分（D1〜D3）を今の状態に書き直して同じ番号でこの ADR に移した。新しい決定はない。

## 背景

構想（brief §2-C）に「商店街・地域コミュニティ」とあり、`requirements.md` の FR-046（商店・団体が情報を発信できる場）・
FR-047（商店・団体も住所を持ち、掲示板・住所録から見つけられる）と、`features.md` の F-17（商店街、段階 3）がある。
`open-questions.md` の OQ-006 でマスターに、商店・団体のアカウントを誰が作成・管理するかを聞き、2026-11-19 に次のとおり答えが出た（原文。ADR-0029）。

> 管理者作成で良いと思う。これって、企業とかが商店、団体になるんだっけ？

前半（管理者作成）を決定として扱った。後半はマスターからの問い返しで、OQ-045 にした。
OQ-045 の答え（2026-11-20、ADR-0038）で、商店には実在の企業・個人のお店を迎えることを目指し、コミュニティ（F-17 の団体と読む）は住民が作ると決まった。
OQ-056 の答え（2026-11-20、ADR-0043）で、商店として発信するのはお店の担当者と決まった。
そのため、管理者が作るのは商店のアカウントだけになる。

## 決定

1. **D1 商店のアカウントは管理者が作る**（OQ-006 の答え）: 住民の登録（M1 の登録の経路）とどの API からも、商店のアカウントは作れない。
   作ったアカウントはお店の担当者に渡す（ADR-0043 の D4。担当者のログイン・主体・権限は OQ-069、持ち越し）。
   コミュニティ（団体）は住民が作る（ADR-0038 の D2）。
2. **D2 作る手段は運用者の CLI だけ**（秘書の判断）: ロールの付与（ADR-0020）と同じ考えで、API が侵害されても作れないようにする。
   管理者画面（C10、モデレーター専用）に開設の機能は足さず、モデレーターに作る権限を与えない（`security.md` §4.2）。
3. **D3 区分**: ADR-0024 の決定 5 に従い、FR-104 は `[inferred]`（マスターの答え OQ-006（2026-11-19）・OQ-045（2026-11-20）より）とし、根拠にこの ADR と ADR-0038 を書く。

## 理由

- 管理者が作り、住民は開けないこと（D1）は、OQ-006 の答え（上の原文）による。団体の部分は OQ-045 の答え（ADR-0038 の D2）による。
- 運用者の CLI にする（D2）のは、ADR-0020 にアプリの中の管理者のロールがなく、C10 はモデレーター専用で、特権の操作は API から行えないから。
  ロールを増やさず（ADR-0020）、権限の規則表を C3 の 1 か所に保てる。

## 代わりの案（選ばなかった理由）

- **住民や担当者が自分で商店を開く**: OQ-006 の答え（管理者作成）と食い違う。OQ-056 の答えはアカウントを作る経路に触れていない。
- **C10（管理者画面）から作る**: モデレーターの権限が広がり、API に特権の経路が増える。
- **アプリに管理者のロールを新しく作る**: ADR-0020 で選ばなかった案。

## 決めていないこと

- 商店の担当者のログイン・主体・権限など（OQ-069、持ち越し）。答えで変わる箇所: 発信する主体の認証（C2）と、ロール・主体の種類（ADR-0020、`security.md` §4）。
- 契約と利用料の中身（OQ-068、持ち越し）。
- 架空の店の持ち方と張り紙の出し方（OQ-084、持ち越し。大枠は ADR-0050）。
- コミュニティの制約の中身（OQ-057、持ち越し）。

## 影響

- ADR-0029: 状態を `置き換え（→ 0067）` にする。ADR の README の一覧。
- ADR-0038・ADR-0043、`requirements.md`（FR-104）・`features.md`・`architecture.md` §8・`security.md` §4.2・`roadmap.md`（§2 の F-17・S3-2 と依存）: 商店のアカウントを作る経路の参照先をこの ADR にする。
