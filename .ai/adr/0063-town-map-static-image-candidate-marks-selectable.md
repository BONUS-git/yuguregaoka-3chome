# 0063 — 地図は静的な画像で候補の印は押せる、API は入居だけ

- 状態: 置き換え（→ 0083）
- 日付: 2026-11-21

ADR-0058 を丸ごと置き換える。ADR-0058 の決定（D1〜D7）は、OQ-080 の答えに合わせて今の状態に書き直し、同じ番号でこの ADR に移した。
変わったのは D1 (a)（対話的な操作）・D3（候補の印を押すために経路を足さない）・D5（押す処理を印の層に付ける）・D7（根拠に OQ-080 を足す）。D1 (b)・D1 の最後の項・D2・D4・D6 は ADR-0058 と同じ（参照する ADR の番号だけを付け替えた）。

## 背景

構想（brief §2 の共通機能）に「架空の街・地図・住所」とあるが、`requirements.md` に地図の要件 ID がなく、
`features.md` の F-19（架空の街の地図）は段階が未確定だった。`open-questions.md` の OQ-005 でマスターに、
地図の具体的な形（静的な画像か、インタラクティブか、住民が自分の住所の場所を見られるものか）と、どの段階で実装するかを聞いた。
2026-11-19、マスターが OQ-005 に次のとおり答えた（原文）。

> 静的な画像として実装し、開発の初期段階で行う

OQ-044 の答え（2026-11-19、ADR-0061）で、地図は全住民で共有する 1 枚の白黒の画像になった。
OQ-054 の答え（2026-11-20）で、自分の家・登録のときの候補・知り合いの家に印を付け、空き家か人がいるかを名前なしの 2 値で示すことになった（ADR-0064）。
印は C1 が土台の上に重ねる層として描き、住所と位置の対応は C1 の静的な配置の定義と計算で求める。

空き家・入居の表示の範囲は OQ-079 で聞き、2026-11-21 の答え（「1:これは全員にいつでも公開してOK。登録前、後いつでも確認が可能にする。」「2：休眠は空き家にしない。…」）で、
街のすべての家の入居の有無を、入居の一覧の経路で全員に見せることになった（D3、ADR-0064 の D10・D13〜D15）。

OQ-054 の答えの「登録時に選択可能」が、(a) 候補の一覧から選び地図で場所を確かめる形か、(b) 地図の上の候補の印を押して選ぶ形かを、OQ-080 で聞いた。
地図を押さないことは、OQ-005 の答えの「静的な画像」を秘書がそう読んだもので、(b) ならこの読み方を変えると添えた。2026-11-21、マスターが次のとおり答えた（原文）。

> b

答えは (b) で、登録の画面の地図の候補の印を押して住所を選ぶ。問いにあわせて聞いた「空き家の印も選べるか」には答えがない（OQ-089）。

## 決定

1. **D1 静的な画像**:
   - (a) マスターの答え OQ-005・OQ-080: 地図は 1 枚の静的な画像とする。拡大・移動・検索はしない。
     登録の画面の候補の印は、押して住所を選べる（OQ-080 の答え「b」。選び方は ADR-0064 の D7）。
     押せるのは候補の印だけで、土台の画像・入居の層の印（空き家の印を含む）・自分の家の印・知り合いの家の印は押しても何も起きない（空き家の印も選べるかは OQ-089。暫定は押せない）。
     「静的な画像」は、土台の画像が動かず、拡大・移動・検索がなく、地図の中身が要求のたびに変わらない（印と入居の層が API の応答から決まる）ことと読む。
   - (b) マスターの答え OQ-044（2026-11-19、ADR-0061 の D1 (a)）: 画像は全住民で共有する 1 枚の画像（土台）とする。
     土台の画像は住民ごとに中身を変えない（バイト単位で同じ。ADR-0064 の D3）。
     印（自分の家・登録のときの候補・知り合いの家）と入居の層は、土台に描き込まず、C1 が土台の上に重ねる（ADR-0064 の D1・D10）。
   - 登録の画面（ログインの前の画面）には、地図（土台の画像）・候補の印・入居の層を出す（OQ-054 の答えの「登録時に選択可能」、OQ-079 の答え 1「登録前、後いつでも確認が可能」）。
     登録の画面のほかのログインの前の画面（ログインの画面など）には、MVP では地図を出さない `[assumed]`。
     答え 1 で入居の一覧は誰に見せてもよくなったので、出すかどうかは公開の範囲ではなく画面の作りの話になる。M1 の画面の範囲に地図を置く画面はほかにないため、出さない。
2. **D2 段階は MVP、マイルストーンは M1**: 段階は MVP（段階 1）とする（答えの「開発の初期段階」）。
   マイルストーンは M1（住所・アカウント）に置く（秘書の判断）。M0 は基盤だけで画面がなく、地図は住所と同じ「街と住所」の話だから。
3. **D3 地図のための API は入居の一覧だけ**: 地図のための API の経路は、入居の一覧 `GET /api/v1/addresses/occupancy` の 1 つだけにする（OQ-079 の答え 1。中身と応答の形は ADR-0064 の D13〜D15）。
   この経路は住所と入居の 2 値だけを返し、画像・位置・座標・区画の形を返さない。候補の印を押して選ぶために経路を足さない（選ぶのは C1 の中で、登録で送るのは今までどおり候補の住所。ADR-0064 の D16）。
   DB の地図の表・住所のジオデータ（座標）・外部の地図サービスは持たない。入居の一覧も、新しい表を作らず、すでにある `addresses` から読む（`db.md` §2）。
   画像は C1（Web クライアント）の静的なファイルとして、同じオリジンから配る（`architecture.md` §2）。
   技術上の結果として、画像のファイルは SPA の他の静的なファイルと同じく、セッションなしでも取れる（API の認証の範囲（`api.md` §4）の外）。
   そのため D4 のとおり、画像に住民や住所の割り当てにかかわる情報を入れない。
4. **D4 載せないもの**: 画像に住民・入居の有無・空き家・数（住民数など）を描かない。区画は「番」まで描き、号までの住所（例: `2-5`）は描かない
   （`security.md` §7 の T-05 住所の列挙、P-2 数値の評価）。入居の有無は、画像ではなく C1 が重ねる入居の層で示す（ADR-0064 の D10）。
5. **D5 出し方**: 画像は SVG とし、`<img>` で出す（インラインに埋め込まない）。SVG に `<script>`・イベント属性・外部への参照（外部の URL・フォント・画像）を入れない
   （`security.md` §7 の T-07）。候補の印を押す処理は、土台の画像ではなく C1 が重ねる印の層に付ける（ADR-0064 の D8）。
6. **D6 中身**: レポジトリの中で描いた架空の図とし、実在の地名・地図データ・他の地図の写しは使わない（CLAUDE.md の公開レポジトリの決まり）。
   画像は白黒（色相を持たない白・黒・灰色だけ）で描く（ADR-0061 の D2、マスターの答え OQ-044）。
   代替テキストを付ける（NFR-041。アクセシビリティの水準は OQ-033）。
7. **D7 区分**: ADR-0024 の決定 5 に従い、FR-103 は `[inferred]`（マスターの答え OQ-005（2026-11-19）・OQ-080（2026-11-21）より）とし、根拠にこの ADR を書く。

## 理由

- 静的な画像であること・初期段階で作ることは、マスターの答え OQ-005 による。全住民で共有する 1 枚の画像は OQ-044 の答えによる（ADR-0061 の D1 (a)）。
- D1 (a) で候補の印を押せるのは、OQ-080 の答え「b」による。OQ-080 の問いは、(b) なら「地図を押さない」という OQ-005 の読み方を変えると示して聞いたので、答えはその読み方を変えることを含む。
  拡大・移動・検索は、問いが触れておらず答えも求めていないので、今までどおり作らない。押せる印を候補だけにするのは、答えが (b)「候補の印を押して選ぶ形」で、空き家の印は答えに書かれていないから（OQ-089）。
- D3 で経路を 1 つ足すのは、入居の有無が時とともに変わり、静的なファイルに置けないから。経路は入居の一覧だけにし、画像・位置は今までどおり C1 の静的なファイルと計算で持つ。
  こうすると、経路が返すのは答え 1 で全員に見せてよいと決まった住所と 2 値だけで、座標やジオデータを持つ理由が生まれない（NFR-055 必要以上に複雑にしない）。
  候補の印を押しても、選ぶ住所は候補の提示（`GET /api/v1/addresses/candidates`）の中の住所なので、経路を足さずに済む。
- D1 で登録の画面のほかのログインの前の画面に地図を出さないのは、MVP の画面の範囲（`roadmap.md` §4 の M1）に、それを求める画面がないから。答え 1 で公開の範囲は決まったので、出すときに聞き直す必要はない。
- M1 に置くのは、住所（F-01）と同じマイルストーンで、住所の形（番・号）と地図の区画を一緒に確かめられるから。
- 外部の地図サービスは費用と外部への通信が要り、架空の街には使えない。
- `<img>` で出すと、SVG の中のスクリプトが動かない。インラインの SVG や `<object>` より XSS の面が小さい。押す処理を土台に入れず印の層に付けるので、`<img>` のままにできる。

## 代わりの案（選ばなかった理由）

- **対話的な地図（拡大・移動・検索）**: 答え（静的な画像）と食い違う。候補の印を押せること（OQ-080）は、拡大・移動・検索を足す理由にならない。
- **候補の印を押せないままにし、一覧だけで選ぶ**: OQ-080 の答え「b」と食い違う。
- **土台の画像をインラインの SVG にし、区画を押せるようにする**: 押す対象は候補の印で、区画ではない。インラインにすると土台の中身が DOM に入り、D5 の XSS の面が大きくなる。
- **入居を静的なファイルに焼き込む（入居の一覧を JSON や SVG の層としてビルドのときに作る）**: 入居は登録と退去で変わり、ビルドのときの中身では「いつでも確認が可能」（OQ-079 の答え 1）を満たせない。
  配るたびに作り直すと、デプロイと住民の動きが結び付き、土台の画像がバイト単位で同じであること（ADR-0064 の D3）も崩れうる。
- **入居を土台の画像に描き込み、API で画像を配る（`/api/v1/map`）**: 土台が時とともに変わり、全住民で共有する同じ画像（ADR-0061 の D1 (a)）と食い違う。画像を返す経路は認証と権限の面が大きい。
- **座標を持つ地図の API（住所ごとの位置を返す）**: 位置は C1 の配置の定義と計算で求められ（ADR-0064 の D4）、座標を返す理由がない。
- **M0 に置く**: M0 は基盤だけで画面がない。
- **段階 2 以降に置く**: 答え（開発の初期段階）と食い違う。
- **PNG などのラスター画像**: 拡大で粗くなり、画像の中の文字（地名）を確かめるテストが書きにくい。SVG なら中身をテキストとして走査できる（A-16）。

## 決めていないこと

- 空き家の印も押して選べるようにするか: OQ-089（要回答）。暫定は押せない（D1 (a)、ADR-0064 の D7）。
- 休眠を空き家にする判定と閾値・転送中の旧住所の表示: OQ-088（持ち越し、ADR-0064 の D13）。
- ゲーム風の地図: OQ-055（持ち越し、ADR-0061 の D4）。
- 代替テキストとアクセシビリティの水準: OQ-033（持ち越し、仮の目標は WCAG 2.2 AA）。
