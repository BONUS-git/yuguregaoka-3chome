# 0018 — ログインはメールとパスワード。メールは暗号化して持ち検索用に HMAC を持つ

- 状態: 置き換え（→ 0080）
- 日付: 2026-11-19

## 背景

OQ-028「認証方式」は `security.md` で決定する持ち越し項目だった（FR-092、NFR-013）。
選択肢として次の 3 つが考えられた。

1. メールアドレス＋パスワード（古典的な方式）
2. ソーシャルログイン（OAuth 2.0 / OIDC）
3. パスキー（WebAuthn）

また、メールアドレスをどのように保存するかは別の問いとして存在した。
平文で保存すると DB 漏洩時にメールアドレスが露出する。暗号化する場合、等値検索ができなくなる問題がある。

## 決定

### 認証方式

**メールアドレス＋パスワード** を採用する [assumed] 。

- パスワードは Argon2id でハッシュして保存する。
- パスワードは 12 文字以上を必須とする [assumed]。
- 広く知られた漏えいパスワードのリスト（ローカルの辞書ファイル）と照合し、一致したら拒否する。
- 登録時にメールアドレスへの確認メールを送る。確認が完了するまでアカウントを有効化しない。
- パスワードリセットトークンの有効期間は 30 分 [assumed]。

ソーシャルログイン・パスキーは将来の追加の選択肢として記録しておくが、当面は採用しない。

### メールアドレスの保存方法

**暗号化した値**（AES-256-GCM）と**HMAC 値**（検索用）の 2 列で保存する。

- `email_encrypted`: AES-256-GCM で暗号化した値。復号するときだけ使う。
- `email_hmac`: 決定的 HMAC（HMAC-SHA-256）で計算した値。等値検索（ログイン・重複確認）に使う。
- 暗号化鍵と HMAC 鍵は別々に管理する（§6.1）。
- 平文のメールアドレスはログに残さない（security.md §2.5）。

## 理由

- **メール＋パスワードを選ぶ理由**: ソーシャルログインは外部サービスへの依存が生まれる。
  パスキーはブラウザ対応・端末紛失時の復旧が複雑で、MVP での採用コストが高い。
  メール＋パスワードは実績があり、依存が少ない。
- **Argon2id を選ぶ理由**: bcrypt・scrypt より GPU 攻撃耐性が高く、現時点の推奨（RFC 9106）。
- **メールを暗号化する理由**: DB 漏洩時に平文でメールアドレスが露出しない（NFR-017 の精神の拡張）。
- **HMAC で検索する理由**: 暗号化すると等値検索ができなくなる。HMAC は決定的で等値比較が可能。
  ただし HMAC では部分一致検索（前方一致）はできない。ログイン・重複確認は等値検索で十分。

## 代わりの案（選ばなかった理由）

**ソーシャルログイン（OAuth 2.0）**: 外部サービス（プロバイダ）への依存が生まれる。
サービスの停止・仕様変更の影響を受ける。現時点では不採用。将来的には追加できる。
**パスキー（WebAuthn）**: 端末紛失時の復旧手段を別途設計する必要がある。
ブラウザ・端末の対応状況を確認する必要がある。MVP では採用コストが高い。
**メールを平文で保存**: DB 漏洩時にメールアドレスが露出する。不採用。
**メールをハッシュのみで保存（HMAC のみ）**: 本人に確認メールを送れなくなる。不採用。

## 影響

- DB 設計: `residents`（または `credentials`）テーブルに `email_encrypted`・`email_hmac`・
  `password_hash`・`email_verified_at` カラムを追加する（db.md §2 の `credentials`）。
- API 設計: `POST /auth/register`・`POST /auth/login`・`POST /auth/forgot-password`・
  `POST /auth/reset-password`・`POST /auth/verify-email` を設ける（今の経路は api.md §7 F-02）。
- 秘密管理: 暗号化鍵と HMAC 鍵を security.md §6 の一覧に追加する。
- OQ-028: 本 ADR の決定により持ち越し → 決定に変更する。
