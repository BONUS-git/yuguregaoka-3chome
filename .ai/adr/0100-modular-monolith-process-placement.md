# 0100 — モジュラーモノリスと 2 プロセス、ルール表は共有

- 状態: 採用
- 日付: 2026-11-26

ADR-0008 を丸ごと置き換える。`reviews/0001-design-review.md` の R-037、`gaps.md` の G-013（YGO-049）。
すべて秘書の判断で、新しい要回答はない。

## 背景

brief §4「API・DB・バッチの責務を明確にする」（NFR-051）と「必要以上に複雑なアーキテクチャを
採用しない」（NFR-055）という 2 つの要求が同時に存在する。
コードをどう分割し、いくつのプロセスで動かすかを決める必要がある。
ADR-0008 は C5 モデレーションを worker だけに置いていたが、手紙の照合は投函のときに web で行い（ADR-0069）、
手紙のほかの書き込みの `reject` の段も書いたときに web で当てる（ADR-0070 の D3）。
また、あとから足した C11〜C13 の置き場が ADR に書かれていなかった（R-037）。

## 決定

1. 1 つのリポジトリのモジュール構造（モジュラーモノリス）でコードを管理し、動かすプロセスは
   `web`（API・クライアント配信）と `worker`（cron ジョブ実行）の 2 つに分ける。
2. **web プロセス**: HTTP リクエストを受けて返す。C2 API（Fastify）、C3 ドメインモジュールの API 側、C10 管理者画面が動く。
   C5 モデレーションのうち、web で使うのはルール表だけで、用途は次の 2 つに限る:
   投函のときの手紙の 2 段の照合（ADR-0069）と、手紙のほかの書き込みへの `reject` の段の照合（ADR-0070 の D3）。
   web に LLM の分類器は渡さない（ADR-0072）。
3. **worker プロセス**: 外部リクエストなしに定期実行する。C4 worker（cron）、C3 ドメインモジュールの worker 側、
   C5 モデレーションの審査（ルール表と LLM の分類器、ADR-0005）、C6 組版エンジン、C11 通知の送信（ADR-0076）、
   C12 記事の文字の作成（ADR-0054・ADR-0055）、C13 外のニュースの取り込み（ADR-0055）が動く。
   ジョブを実行するのは worker だけで、web はジョブを積むだけ。
4. 両プロセスは C3 ドメインモジュールのコードを共有する（依存は import、コードは同一リポジトリ）。
   ルール表と照合の関数は C3 のモデレーションのサブモジュールの 1 か所に置き、web と worker が同じものを使う `[assumed]`。
5. `web` と `worker` は別のエントリポイント（`src/server.ts` と `src/worker.ts`）を持ち、本番はコンテナ 2 本
   （web / worker）で動かす想定にする。手元では 2 つのふつうのプロセスとして起こす（`environment.md`・ADR-0052）。

## 理由

- 責務の分離（NFR-051）: HTTP と非同期バッチを別プロセスに置くことで、API の応答性能がバッチの処理時間に影響されない。
- 複雑化しない（NFR-055）: マイクロサービスに比べてデプロイ・監視・型共有が格段に単純。今の想定規模（ADR-0012）では分散システムの複雑さは不要。
- コードの再利用: ドメインロジックを 1 か所に集めることで、API と worker で同じ検証・ビジネスルールを使える。
  ルール表を 1 か所に置けば、投函のときの照合と worker の審査で規則が食い違わない。
- 外への接続を worker に寄せる: LLM（C5 の分類器・C12）・Web Push（C11）・外のニュース（C13）は時刻の決まったジョブから呼び、
  web の応答が外のサービスの遅れに左右されない。
- テスト容易性（NFR-061）: モジュール境界が明確なため、ユニットテストが書きやすい。

## 代わりの案

**マイクロサービス**: サービスごとにデプロイ・スケールできる利点があるが、想定規模（住民 1 万人程度、ADR-0012）では過剰設計。サービス間通信の複雑さを増す。不採用。

**1 プロセスで全部（cron も API も同一プロセス）**: シンプルだが、API の応答待ちとバッチ処理が同一プロセスを占有しあうリスクがある。コンテナ 1 つで running/stopped の判断が難しくなる。不採用。

**サーバーレス（関数単位のデプロイ）**: デプロイしない方針（NFR-071）では利点が生きない。コールドスタートが組版・配達の時刻制約（ADR-0004）に影響する可能性がある。不採用。

**照合を worker だけに置く**: C5 を worker だけにすれば web が軽くなるが、投函のときに 422 を返して送った人に確認を頼むかを聞く流れ（ADR-0069）と、
書いたときに `content_rejected` を返す流れ（ADR-0070 の D3）が作れない。不採用。

## 影響

- コードベースは `src/modules/` 等のディレクトリ構造で 8 サブモジュールを分ける（`architecture.md` §2 の C3）。
- 各要素の動くプロセスは `architecture.md` §2 の表の「動くプロセス」の列に書く。この ADR と食い違わせない。
- ホスティングの細部は `environment.md` で定義する（ADR-0052）。
