# 0074 — 新聞の知り合いの版に、知り合いの投稿と誕生日を載せる

- 状態: 採用
- 日付: 2026-11-22

ADR-0044 を丸ごと置き換える。ADR-0044 の決定（D1〜D8）は今の状態に書き直して同じ番号でこの ADR に移した。OQ-077 の答え（2026-11-21）で D7 を変え、D9 を足した。

## 背景

OQ-051 の答え（ADR-0055）で、新聞は一人 1 枚にせず、「知り合いで埋まる組」（組 1）「一部埋まらない組」（組 2）「知り合い 0 の組」（組 0）に分け、組 0 は興味で分けると決まった。
組 1・2 については、`open-questions.md` の OQ-058 でマスターに聞き、2026-11-20 に次のとおり答えが出た（原文）。

> 暫定通りで。全住民を「知り合い0の組」として扱う。
>
> (1) 知り合いの定義は b。新聞でも同じ定義
> (2) 一般的なSNSのツイートに当たる部分。手紙はDMなので新聞には載せない。
> (3) サーバー負荷は要検討だが、現時点では知り合いに合わせて構成したい。一般的なSNSと異なり、動画、画像を自由に無制限に上げることはできないので、割と軽量だと思ってる。アップロードした画像は新聞用に加工し、元データは保持しない方針
> (4) 共通の記事と興味の記事。
> (5) 秘書（システム）の設計で決めていい。手間をかけずに、シンプルに動く仕組みにすること。

（b は「互いに住所録に入れた住民」。地図の知り合いの印は、自分の住所録のすべてのエントリに付け、新聞・手紙と定義を分ける（OQ-071 → 決定、ADR-0051）。）

2026-11-21、マスターが OQ-077（誕生日を集めて新聞に載せるか）に次のとおり答えた（原文）。

> 1:後からの変更は不可で必須。架空でOK。あくまでこの町（夕暮ヶ丘三丁目）内での設定
> 2:互いに登録済みならニックネームと年齢、住所載せる
> 3:知り合い同士以外は載せない

答えから読み取れることと、読み取れないことを分ける。

| 答え | 読み取れること（決定、`[inferred]`） | 読み取れないこと → 扱い |
|---|---|---|
| OQ-058 冒頭 | 全住民を組 0 として扱う。MVP（M5）では組 1・2 を作らない | 組 1・2 をいつ作るか → OQ-070 (1)（持ち越し） |
| OQ-058 (1) | 新聞の「知り合い」は互いに住所録に入れた住民 | — |
| OQ-058 (2) | 載せるのは、一般的な SNS のツイートに当たる部分。この街では掲示板の投稿と読む。手紙は載せない | 知り合いの側が載ることを断れるか → OQ-070 (3)（持ち越し） |
| OQ-058 (3) | 知り合いに合わせて組む（組 1・2 は住民ごとに組む）。アップロードした画像は新聞用に加工し、元の画像は持たない | 負荷 → OQ-070 (2) で見積もる |
| OQ-058 (4) | 組 2 の足りない分は、共通の記事と興味の記事で埋める | — |
| OQ-058 (5) | 組の境は秘書の設計で決めてよい。簡単に動く仕組みにする | — |
| OQ-077 2 | 誕生日の住民のニックネーム・年齢・住所を、互いに住所録に入れた住民の紙面に載せる | どの版・どの欄・何件まで・組み方 → 秘書の判断 `[assumed]`（D7・D9） |
| OQ-077 3 | 知り合いでない住民の紙面（共通の版・興味の版）には載せない | 本人が載らないことを選べるか → OQ-070 (3) に含める（持ち越し） |

知り合いだけに載せられるのは住民ごとの版（D4）だけで、共通の版と興味の版はほかの住民と共有する。MVP では組 1・2 を作らない（D1）ので、誕生日の欄は組 1・2 と一緒に作る。
誕生日の集め方と年齢の進め方は ADR-0073 で決めた。

## 決定

区分は ADR-0024 の決定 5 に従う。

1. **D1 MVP は全住民が組 0**（OQ-058 の答えの冒頭、`[inferred]`）: MVP（M5）では、全住民を知り合い 0 の組として扱う。版は共通の版（`common`）と興味の版（`interest:<key>`）だけで、休刊の回は `holiday`。
   組 1・2（と誕生日の欄、D9）は MVP では作らない。作る時期は OQ-070 (1)（持ち越し）。
2. **D2 新聞の「知り合い」は互いに住所録に入れた住民**（OQ-058 の答え (1)、`[inferred]`）:
   住民 A と B が知り合いなのは、A の住所録のエントリの `address_book.registered_tenancy_id` が B の今の居住記録（`tenancies.is_current = true`）を指し、
   かつ B の住所録のエントリが A の今の居住記録を指すときだけとする。
   - 相手が引っ越すと、登録した時点の居住記録は今のものでなくなるので、知り合いから外れる。住所録は自動で直さない（ADR-0003 と同じ考え）。住民が手で住所を直せば、そのときの居住記録に取り直す（`api.md` §7 F-09）。
   - 組にする 2 つのエントリは、どちらも住所を入れたエントリ（`address_book.source = 'address'`）のときだけ（ADR-0065 の D14）。投稿から足したエントリと、その経路で届いた手紙から足したエントリの組（ADR-0065 の D2・D15）は、手紙の知り合いにはなるが新聞の知り合いにはしない。住所を見せない相手を、紙面で住民（住所）と結び付けて見せないため。
   - どちらかがもう一方をブロックしている（`blocks` に行がある）ときは、知り合いにしない（秘書の判断）。
   - 手紙の知り合い（ADR-0065 の D2）は、ブロックの条件を入れず（ブロックを 422 で気づかせないため、T-06）、投稿と手紙から足したエントリの組も含む。掲示板の経路（ADR-0065 の D7）だけの相手は、新聞の知り合いに含めない（ADR-0065 の D14）。
   - 地図の知り合いの家の印は、自分の住所録のすべてのエントリに付け、`acquainted` で変えない（ADR-0051・ADR-0064）。地図と新聞・手紙で定義を分ける。
3. **D3 載せるのは知り合いの掲示板の投稿**（OQ-058 の答え (2)、`[inferred]`）: 組 1・2 の紙面の知り合いの記事は、その配達回の素材（`board_posts.status = 'approved'` かつ `board_posts.delivery_run_id = run_id`）のうち、
   知り合いが書いた投稿だけとする。「ツイートに当たる部分」を掲示板の投稿と読むのは秘書の読み方。
   手紙は、個人宛・グループ宛のどちらも載せない。審査（J2）とルール表で公開してよいと決まった投稿だけが載る。
4. **D4 組 1・2 の版は住民ごとに組む**（OQ-058 の答え (3)、`[inferred]`）:
   - 組 1・2 の住民には、住民ごとの版を組み、`edition_key = 'acquaintance:<resident_id>'` とする（`<resident_id>` は `residents.id`）。
   - 住民ごとの版を見られるのは本人だけで、ほかの住民とモデレーターには 404 を返す。API は `edition_key` を返さない（ADR-0055 の D11）。web が C8 の HTML を中継するので、保存のキーも返さない。
   - 記事の文字は、素材ごとに 1 回だけ J16 が作り（ADR-0055 の D7、UNIQUE(delivery_run_id, source_kind, source_id)）、住民ごとの版でも使い回す。住民ごとの版で LLM を呼ばないので、LLM の費用は増えない。
   - ADR-0055 の D1 の「版の数は住民の数によらない」は、組 0 の版だけに当たる。組 1・2 の版の数は、組 1・2 の住民の数だけ増える。負荷の見積もりは OQ-070 (2)。
   - 住民ごとの版に載る投稿から「その投稿者が自分を住所録に入れている」ことが分かるが、互いに足したことは住所録の応答の `acquainted` で本人に見える（ADR-0065 の D4）ので、新しく漏れることはない。
5. **D5 アップロードした画像は加工し、元の画像は持たない**（OQ-058 の答え (3)、`[inferred]`。段階 2・F-11）:
   - 住民がアップロードした画像（手紙・掲示板）は、J13 `image.process` が新聞用（新聞写真風）に加工する（FR-016）。
   - 元の画像は、J13 の加工が終わった時点（`state = 'processed'`）か、最後の再試行に失敗した時点（`state = 'failed'`）で C8 から消し、`images.original_url` を NULL にする。
   - 取りこぼしに備え、アップロードから 24 時間 `[assumed]` を過ぎて残った元の画像は、その次の J14 `retention.purge`（毎日 1 回、`async.md` §2）が消し、`original_url` を NULL にする。取りこぼしが残るのは最長でアップロードから約 48 時間。そのとき加工が済んでいなければ `state = 'failed'` にする。
   - 加工が済んでいない画像はどこにも出さず、元の画像は住民にもモデレーターにも返さない（`roadmap.md` の B-03）。画像の審査を足すときも、加工した画像を使う。
6. **D6 組 2 の足りない分**（OQ-058 の答え (4)、`[inferred]`）: 組 2 の住民の紙面の、知り合いの記事で埋まらない枠は、その住民が組 0 なら受け取る版の記事で埋める。
   その版は ADR-0055 の D3 のとおり、興味が 1 つならその興味の版、複数ならハッシュで選んだ興味の版、興味がなければ共通の版とする。
   埋めるのは、その版に載る記事の順（共通の記事と、その興味の記事）で先頭からとする。知り合いの記事にすでに載った素材は、二重に載せない。
7. **D7 組の境**（OQ-058 の答え (5)、秘書の判断。誕生日の数え方は `[assumed]`）: 状態を保存せず、J3 が配達回ごとに次の規則で計算する。
   - S は、組 1・2 の紙面のテンプレート（ADR-0011 の組版エンジン）が持つ記事の枠の数（テンプレートの定数。値は組 1・2 のテンプレートを作るときに決める）。
   - k は、その配達回の素材のうち、その住民の知り合い（D2）の投稿（D3）の件数。
   - b は、その配達回が朝刊のとき、その日（JST）が誕生日（D9）の知り合いの人数。夕刊では 0。
   - k = 0 かつ b = 0 なら組 0（住民ごとの版を組まない）。
   - それ以外で k < S なら組 2（k 件の知り合いの記事と、D6 で埋めた S − k 件）。k = 0 で b ≥ 1 の住民も組 2 で、S 件すべてを D6 で埋める。
   - k ≥ S なら組 1（知り合いの記事を `(created_at, id)` の順で先頭の S 件）。
   - 誕生日の欄（D9）は S の枠の外に置き、k と S に数えない。
   - J3 は住民ごとの版を、ほかの版と同じトランザクションで入れる（版がそろうか休刊かのどちらか、ADR-0055）。J4 は組を計算し直さず、その配達回に `acquaintance:<resident_id>` の版があればそれを、なければ組 0 の版を選ぶ。
     これで J3 と J4 のあいだに住所録が変わっても、住民の版は J3 の時点の計算で決まり、J4 のやり直しでも同じ版になる。休刊の回は全住民に `holiday`。
8. **D8 要求の区分**: FR-108 を直し、FR-118（アップロードした画像は加工し、元の画像は持たない）と FR-127（誕生日と誕生日の欄）を足す。どれも `[inferred]`（マスターの答え OQ-058（2026-11-20）・OQ-077（2026-11-21）より）。
9. **D9 誕生日の欄**（OQ-077 の答え 2・3、`[inferred]`。細部は `[assumed]`）:
   - 載せるのは住民ごとの版（`acquaintance:<resident_id>`）だけ。共通の版・興味の版・休刊（`holiday`）には載せない。
   - 載る人は、読む住民の新聞の知り合い（D2）のうち、その日（JST）が誕生日（ADR-0073 の D3）の住民。誕生日が 2/29 の住民は、うるう年でない年は 3/1 に載る。読む住民自身は載せない。
   - 載せる項目は、ニックネーム・その日に上がったあとの年齢（ADR-0073 の D3）・今の住所。自己紹介と誕生日の月日の数字は載せない。
   - 載せるのは朝刊だけ。その朝刊が休刊なら、次の配達回に持ち越さない。人数の上限は置かず、住所の順に並べる。
   - 欄は C6 のテンプレートの決まった文で組む。J16（LLM）には誕生日・年齢・ニックネーム・住所を渡さない（ADR-0055 の D8）。
   - 本人が載らないことを選べるかは OQ-070 (3)。それまで断る設定は置かない。
   - J3 が組を計算するときに `residents` と住所録から読む。組は保存しない（D7）。
   - 欄の中身は保存する `[assumed]`: J3 は欄に載せた住民ごとに `newspaper_birthday_entries` の行（版・載った住民の `resident_id`・ニックネーム・年齢・住所・並び順）を、その版と同じトランザクションで入れる。
     J3 の再試行と J8 の組み直しは、この行から欄を組み、`residents` と住所録を読み直さない（保存した行から同じ HTML を組む決まり、`db.md` §2 の `newspaper_articles`）。組んだあとにニックネームや知り合いの関係が変わっても、その版の欄は変わらない。
   - 欄に載った住民が退去したら、J7 がその住民の `newspaper_birthday_entries` の行を消し、同じトランザクションで、行のあった版の紙面の J8 を積む。J8 は残った行から欄を組み直す（投稿者の退去で記事を消して組み直すのと同じ形） `[assumed]`。
   - この表は組 1・2 と一緒に作る（MVP では作らない）。
   - 組 1・2 と一緒に作る（D1。時期は OQ-070 (1)）。MVP では誕生日は集めて年齢の計算に使うが、新聞には載らない。

## 理由

- D1 は、OQ-058 の答えの冒頭による。組 1・2 をいつ作るかは書かれておらず、負荷も「要検討」なので、MVP には入れない。
- D2 は、OQ-058 の答え (1) による。居住記録で決めるのは、住所録の住所の文字列は登録した時点のままで（ADR-0003）、今その住所に住んでいる人が知り合いとは限らないため（`db.md` §3）。
  ブロックした相手を知り合いにしないのは、ブロック（FR-068）した相手の投稿や誕生日を、その住民だけに組む紙面に「知り合い」として出さないため。
- D3 は、OQ-058 の答え (2) による。掲示板の投稿は誰でも読める公開の内容（ADR-0005 で審査済み）で、SNS のツイートに当たる。手紙はクローズドなやり取り（FR-019）なので載せない。
- D4 は、OQ-058 の答え (3) の「知り合いに合わせて構成したい」による。知り合いは住民ごとに違うので、組の中で紙面を共有すると、ほかの住民の知り合いの投稿が載る。
  本人だけが見られるようにするのは、住民ごとの版から、その住民の住所録と知り合いの関係が分かるため（ADR-0055 の D11 と同じ考え）。記事の文字を使い回すのは、費用を版の数で掛け算しないため。
- D5 は、OQ-058 の答え (3) の「元データは保持しない方針」による。24 時間は、J13 の再試行（`async.md` §5）が終わる時間より十分に長い仮の値。
- D6 は、OQ-058 の答え (4) による。組 0 の版と同じ選び方にすれば、新しい規則を足さずに済む。
- D7 は、OQ-058 の答え (5) の「手間をかけずに、シンプルに動く仕組み」による。組を保存しないので、住所録・ブロック・引っ越しが変わったときに組を直す処理が要らない。
  b を足すのは、知り合いの投稿がない日でも、誕生日の知り合いがいれば住民ごとの版でしか載せられない（D9）ため。誕生日の欄を k に数えないのは、S が記事の枠の数で、「埋まる」の意味を変えないため。
- D9 は、OQ-077 の答え 2「互いに登録済みならニックネームと年齢、住所載せる」と 3「知り合い同士以外は載せない」による。知り合いだけが読む版は住民ごとの版だけなので、そこにだけ載せる。
  月日の数字を載せないのは、その日の紙面に載ることで誕生日だと分かり、答えに数字を載せることは書かれていないため。朝刊だけにするのは、同じ日に二度載せないため（`[assumed]`）。
  決まった文で組み LLM に渡さないのは、住民と結び付いた情報を LLM に渡さない（ADR-0055 の D8）ため。
  欄には今の住所を載せるので、新聞の知り合いを住所を入れたエントリどうしの組に限る（D2・ADR-0065 の D14）ことが要る。投稿と手紙から足したエントリの組まで入れると、住所を見せていない相手の住所が欄に出て、投稿と住所を結び付けて見せない決まり（ADR-0065 の D12）が守れない。
  欄の中身を保存するのは、J8 の組み直しが保存した行から同じ HTML を組む決まりと両立させ、退去した住民の載った版を J7 が引けるようにするため。

## 代わりの案（選ばなかった理由）

- **組 1・2 を MVP（M5）で作る**: OQ-058 の答えの冒頭「全住民を「知り合い0の組」として扱う」と食い違う。負荷も見積もっていない（OQ-070）。
- **MVP で誕生日のためだけに住民ごとの版を組む**: OQ-058 の答え（全住民を知り合い 0 の組）と食い違う。
- **誕生日を共通の版・興味の版に載せる**: OQ-077 の答え 3「知り合い同士以外は載せない」と食い違う。
- **誕生日の欄を k に数える**: 誕生日の人数で組 1 になり、知り合いの記事が S に足りないのに枠が埋まった扱いになる。枠の数の意味が崩れる。
- **誕生日の欄を朝刊と夕刊の両方に載せる**: 同じ日に同じ欄が二度載る。
- **欄の中身を保存せず、組み直しのたびに `residents` と住所録から作る**: 組み直しでニックネームや知り合いの関係の変化まで紙面に入り、保存した行から同じ HTML を組む決まりと食い違う。退去した住民がどの版に載ったかも引けない。
- **知り合いの手紙も載せる**: OQ-058 の答え (2)「手紙はDMなので新聞には載せない」と食い違う。
- **組 1・2 の紙面を組で共有する**: ほかの住民の知り合いの投稿や誕生日が載る。OQ-058 の答え (3) と食い違う。
- **住民ごとの版で LLM を呼ぶ**: 費用が住民の数で増え、LLM に住民と結び付いた情報を渡すことになる（ADR-0055 の D8）。
- **組を表に保存し、住所録・ブロック・引っ越しのたびに直す**: 直す処理が増え、OQ-058 の答え (5) の「シンプルに」と食い違う。
- **元の画像を保持期間を決めて残す**: OQ-058 の答え (3)「元データは保持しない方針」と食い違う。

## 決めていないこと
