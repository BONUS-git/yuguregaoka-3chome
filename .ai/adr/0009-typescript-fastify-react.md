# 0009 — TypeScript・Fastify・React と Vite

- 状態: 採用
- 日付: 2026-11-19

## 背景

brief §4「技術選定は秘書に任せる（理由は ADR に残す）」とされており、
言語・API フレームワーク・クライアントの選択が未確定だった。
フルスタックの TypeScript で統一するか、フロントとバックで言語を分けるかが主な論点。

## 決定

- **言語・ランタイム**: TypeScript（Node.js の最新 LTS）
- **API フレームワーク**: Fastify + JSON Schema バリデーション
- **クライアント**: React + Vite（SPA として配信）

## 理由

### TypeScript（Node.js LTS）を選ぶ理由

- フロントとバックで型定義を共有できる（API レスポンス型・バリデーション スキーマ等）。
- npm エコシステムにより、画像加工・HTML 組版・暗号化など必要なライブラリが揃う。
- Node.js LTS は安定しており、コンテナ化が容易（NFR-058）。
- Fastify・React・Vitest（テスト）がすべて TypeScript ファーストで動く。

### Fastify を選ぶ理由

- JSON Schema による入力バリデーションが組み込みで、API 仕様（文字数上限・型検査）を 1 か所に集められる（ADR-0004 の上限値と整合）。
- Express より高速で、パフォーマンスへの余裕が生まれる（NFR-032）。
- プラグインモデルが明確で、認証・CORS・ロギングのプラグインを差し込みやすい。

### React + Vite を選ぶ理由

- SPA として配信することで、web プロセス（Fastify）が HTML を組み立てる必要がなく責務が明確（ADR-0008）。
- Vite は開発サーバーの起動が速く、HMR が安定している。
- React は TypeScript との親和性が高く、テスト（Vitest + Testing Library）も整っている。

## 代わりの案

**Go（バックエンド）**: 型安全で高性能だが、フロントとの型共有ができない。npm エコシステムの豊富なライブラリを活用しにくい。不採用。

**Python + Django（バックエンド）**: ORM や管理画面は充実しているが、フロントと型を共有できない。非同期ジョブ（Celery 等）を別途入れる必要があり構成要素が増える。不採用。

**Next.js 等の SSR フレームワーク**: SSR は即時性を前提とした最適化が多く、夕暮ヶ丘三丁目の「配達済みの項目のみを返す」モデルとは相性が悪い。サーバー側レンダリングの複雑さが増す。不採用。

**ネイティブアプリ（iOS / Android）**: 配達完了の通知は Web Push で送れる（ADR-0025）ので、ネイティブアプリの利点が生きない。Web だけで MVP の体験は成立する。不採用。

## 影響

- C1 Web クライアントは React + Vite で実装し、`web` プロセスから静的ファイルとして配信する
- C2 API は Fastify で実装し、JSON Schema を使って C3 ドメインモジュールへの入口で入力を検証する
- C3〜C6 のサーバーサイドはすべて TypeScript（Node.js）で実装する
- テストは Vitest を使い、`check.sh` からつなぐ（コードができてから）
