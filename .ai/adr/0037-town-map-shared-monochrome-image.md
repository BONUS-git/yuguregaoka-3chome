# 0037 — 架空の街の地図は、全住民で共有する 1 枚の白黒の画像とする。印（知り合いの家・自分の住所・候補）とゲーム風の地図は今は作らない

- 状態: 置き換え（→ 0061）
- 日付: 2026-11-19

（追記 2026-11-20）OQ-054 の答え「1:MVP」「2:1」「3:どちらもyes, 登録時に選択可能かつ、地図を表示する際は中心に置き印もつける。また、空き家か人がいるかも表示する。ここにはユーザー名は載せず、boolean的に表示するものと考えている」で、
自分の家・登録のときの候補・知り合い（自分の住所録に入れた住民）の家に印を付けることになった（ADR-0042 の D1）。土台の画像は全住民でバイト単位で同じのままとし（ADR-0042 の D3。D1 (b) を決定にした）、印は C1 が土台の上に重ねる。
空き家・入居の表示の範囲は OQ-079（要回答。もとは OQ-066。OQ-066 は 2026-11-20 に決定し、ADR-0049）。D1 (a)・D2・D4・D5 は変わらない。

## 背景

OQ-005 の答え（ADR-0028）で、架空の街の地図は 1 枚の静的な画像として MVP（M1）で作ると決まった。
答えに書かれていない「住民が自分の住所の場所を見られるものか」を、`open-questions.md` の OQ-044 でマスターに聞いていた。
(1) 地図の上で住民に自分の住所の場所を示すか、(2) 登録のときに住所の候補（F-01・FR-010）の場所を地図で示すか。
暫定は「示さない。全住民に同じ 1 枚の画像で、住所の場所の印は付けない」（ADR-0028 の D1 (b)）だった。

2026-11-19、マスターが OQ-044 に次のとおり答えた（原文）。

> 全ユーザーで共有して、知り合いの家には印ができるようなものが理想。ほんとはゲーム風にしたいが、現時点では１枚の画像。白黒の地図が今のイメージ

答えから読み取れることと、読み取れないことを分ける。

- 「全ユーザーで共有して」: 地図は全住民で共有する（同じ土台の地図）。ADR-0028 の D1 (b) のうち「全住民で共有する 1 枚の画像」は、暫定から決定になる。
  ただし同じ文で、共有する地図の上に知り合いの家の印が付くことを理想としているので、住民ごとに見え方を一切変えないことまでは読み取れない（OQ-054）。
- 「現時点では１枚の画像」: 今は 1 枚の画像のまま。ADR-0028 の D1 (a)・D3・D5 は変わらない。
- 「白黒の地図が今のイメージ」: 今の地図は白黒にする。
- 「知り合いの家には印ができるようなものが理想」: 理想として書かれていて、いつ作るか・誰を「知り合い」とするか・印で何を示すかは書かれていない。
- 「ほんとはゲーム風にしたいが」: 今は作らないことは読み取れるが、ゲーム風が何を指すか・どの段階で作るかは書かれていない。
- もとの質問の (1) 自分の住所の場所と (2) 登録のときの候補の場所には、答えが直接は答えていない。

## 決定

1. **D1 全住民で共有する 1 枚の画像**（マスターの答えの「全ユーザーで共有して」「現時点では１枚の画像」より）:
   - (a) 決定（答え）: 地図は全住民で共有する 1 枚の画像（土台）とする。ADR-0028 の D1 (b) のうち「全住民で共有する 1 枚の画像」を、暫定から決定にする。
   - (b) 決定（ADR-0042 の D3、2026-11-20。もとは OQ-054 の暫定）: 土台の画像は住民ごとに中身を変えない（どの住民にもバイト単位で同じ画像を出す）。
     OQ-054 の答えで印を付けることになったが、印は土台の画像に描き込まず、C1 が土台の上に重ねる層として描く。住民ごとに変わるのは印の層だけ。
   ADR-0028 の D1 (a)（静的・対話的な操作なし）・D3（API・DB・ジオデータ・外部サービスなし）・D4（載せないもの）・D5（SVG を `<img>` で出す）は変えない。
2. **D2 白黒**（マスターの答えの「白黒の地図が今のイメージ」より）: 地図の画像は白黒で描く。
   秘書の読み方として、「白黒」は色相を持たないこと（白・黒と、その間の灰色だけ。sRGB で R=G=B の色）とする。
   区画と道を見分けるのに灰色が要り、受け入れ確認（`roadmap.md` の A-16 (6)）で確かめられる形にするため。
   画像の中のすべての色（`fill`・`stroke`・`stop-color` など）を、この範囲に限る。
3. **D3 印**（ADR-0042 で置き換え。もとは「今は付けない」で、OQ-054 の暫定だった）: OQ-054 の答え（2026-11-20）で、知り合いの家の印・自分の住所の印・登録のときの候補の印を付けることになった。
   いつ・誰を・どう示すか、住所と画像の上の位置の対応（C1 の静的な配置の定義と計算。DB・API は持たない）は ADR-0042 の D1〜D9 に書く。
4. **D4 ゲーム風の地図は今は作らない**（マスターの答えの「ほんとはゲーム風にしたいが、現時点では１枚の画像」より）:
   ゲーム風の地図は作らない。何を指すか・どの段階で作るかは決めず、OQ-055（持ち越し）にする。段階 2 の計画を立てる前にマスターに聞く。
5. **D5 要求の区分**: ADR-0024 の決定 5 に従い、FR-103 は `[inferred]`（マスターの答え OQ-005・OQ-044（2026-11-19）より）のままとし、根拠にこの ADR を足す。

## 理由

- D1 (a) は、答えの「全ユーザーで共有して」「現時点では１枚の画像」による。D1 (b) は、もとは印を付けない（D3）間は住民ごとに変える中身がないからで、OQ-054 の暫定だった。印を付けることになったあとも、印を別の層にして土台を同じにした（ADR-0042 の D3）。同じ画像なら、住所と位置の対応を持たずに済み、地図から住所や住民の有無が漏れない（ADR-0028 の理由のまま）。
- D2 は、答えの「白黒の地図が今のイメージ」による。灰色を含めるのは秘書の読み方で、白と黒の 2 色だけでは区画・道・地名の見分けが付きにくいから。
  R=G=B に限れば、画像のファイルを読む単体テストで機械的に確かめられる。
- D3 は、答えが印を「理想」と書き、時期・対象・中身を書いていないことによる。
  知り合いの家に印を付けると、住民ごとに見え方が変わり（共有する土台の画像（D1 (a)）の上に住民ごとの印を重ねる仕組みが要り、D1 (b) が変わる）、住所と位置の対応を持つことになり、
  ある住民の家の場所が別の住民に見える（公開の範囲・`security.md` §7 の T-05）。マスターにしか決められないので、CLAUDE.md の「要回答の答えを前提にした決定をしない」に従い、今は付けない（のちに OQ-054 → 決定、2026-11-20、ADR-0042）。
- D4 は、答えの「ほんとはゲーム風にしたいが、現時点では１枚の画像」による。今の段階（MVP）に要らないので持ち越しにする。

## 代わりの案（選ばなかった理由）

- **知り合いの家の印を、この変更で設計する（住所録に入れた相手の区画に印を付ける）**: 答えは「理想」で、誰を知り合いとするか・いつ作るかが書かれていない（OQ-054）。
- **白と黒の 2 色だけに限る**: 区画と道・地名の見分けが付きにくい。答えの「白黒」は、灰色を除くとまでは書いていない。
- **色を限らない（白黒は目安とする）**: 答えの「白黒の地図」と食い違い、受け入れ確認で確かめられない。
- **ゲーム風の地図の段階をこの変更で決める**: 答えに書かれていない（OQ-055）。

## 決めていないこと

- 地図に印を付けるか（知り合いの家・自分の住所・登録のときの候補）: OQ-054 → 決定（2026-11-20、ADR-0042）。
  空き家・入居の表示の範囲は OQ-079（要回答、ADR-0042 の D10）。手紙を出せる知り合いに相手の同意が要ることは OQ-066 → 決定（2026-11-20、ADR-0049）。地図の印を付けるエントリは OQ-071 → 決定（2026-11-20、ADR-0051。住所録のすべてのエントリ。ADR-0049 の D8 で ADR-0042 の D11 を書き直した）。
- ゲーム風の地図が何を指すか・どの段階で作るか: OQ-055（持ち越し）。
- 登録の画面のほかのログインの前の画面（ログインの画面など）に地図を出すか: 決めない（ADR-0028 の D1）。
  登録の画面に地図（この土台の画像）と候補の印を出すことは決定（OQ-054 → 決定、2026-11-20、ADR-0042 の D1 (b)）。
- 代替テキストとアクセシビリティの水準: OQ-033（持ち越し）。白黒の濃淡の差（コントラスト）は、その水準に合わせる。
