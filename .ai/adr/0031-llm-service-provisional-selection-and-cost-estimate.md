# 0031 — 外部 LLM の費用の見積もりはロードマップに置き、サービスは秘書が暫定で選ぶ（Anthropic API の Haiku）。本番のアダプタは承認のあとに作る

- 状態: 採用（呼ぶジョブと渡すものに、新聞の J16 を ADR-0039 で追記）
- 日付: 2026-11-19

## 背景

`requirements.md` の NFR-077 は「AI モデレーションに使う LLM の費用は、スタックの計画に見積もりを含める」（`[inferred]`）とだけ書き、
どの外部 LLM サービスを使うか、見積もりをどの文書に置くかは決めていなかった。
`open-questions.md` の OQ-008 で、費用の見積もりをロードマップに含めてよいか、サービスの選定を秘書に任せるかをマスターに聞いていた。
暫定は「テストではモックの LLM を使い（NFR-065）、本番向けの選定は roadmap / environment に書く。契約と費用の発生はマスターの事前承認を得る（NFR-080）」で、
`architecture.md` §8・`roadmap.md` §8・§9 は、見積もりを `environment.md`（まだない）に置くとしていた。

2026-11-19、マスターが OQ-008 に次のとおり答えた（原文）。

> 費用見積もりをロードマップに含め、サービス選定は秘書に任せる（暫定）

## 決定

1. **D1 費用の見積もりはロードマップに置く**（マスターの答え）: 外部 LLM の費用の見積もりは `roadmap.md` §9.1 に書く。
   NFR-077 の置き場所を `roadmap.md` §9.1 にする。メール送信（OQ-039）・画像加工（NFR-078）・ホスティングの費用は、今までどおり `environment.md` に置く。
2. **D2 サービスは秘書が暫定で選ぶ**（答えは「秘書に任せる（暫定）」。選んだものは秘書の判断）:
   - サービスは Anthropic API、モデルは `claude-haiku-5-5`。
   - 出力は構造化出力（JSON のスキーマ）で `ok` / `review` / `block` の 3 つのラベルのどれか 1 つに限る。effort は `low`。
     それでも受け取った値はラベルの種類だけを検証し、失敗・想定外の値は人の審査に倒す（`security.md` §1 原則 2・§5.2。今までどおり）。
   - Batch API は使わない。1 件ずつ同期で呼ぶ（呼ぶのは worker の J2 だけ）。
     （ADR-0039 で追記）新聞の記事の文字を作る J16 `newspaper.write` も外部の LLM を呼ぶようになった（worker だけ）。
     J16 のモデル・プロンプトはこの選定とは別に OQ-062（持ち越し）で決める。
   - 「暫定」は、確定をマスターの確認に残すという意味で扱う。確定の時期と手続きは OQ-047（持ち越し）。
3. **D3 本番のアダプタは承認のあとに作る**（秘書の判断）: C5 の LLM の分類器のうち、Anthropic API を呼ぶ本番のアダプタは、
   デプロイと契約の承認（NFR-080）のあとに作る。それまでは分類器のインターフェースとモックだけを作り、M4 はモックの LLM で受け入れる（受け入れ条件 A-06・A-07 は変わらない）。
4. **D4 変わらないこと**:
   - 契約と支出はマスターの事前承認を得る（NFR-080）。この ADR は契約も支出もしない。
   - テストはモックの LLM を使い、`sh scripts/check.sh` はネットワークなしで通る（NFR-063・NFR-065）。
   - LLM はラベルを返すだけ（ADR-0005）。LLM に渡すのは掲示板の投稿の本文だけで、手紙は渡さない（ADR-0026）。
     （ADR-0039 で追記）J16 に渡すものは ADR-0039 の D8 のとおり（承認済みの投稿の本文・取り込んだ外のニュース・版の興味の名前。手紙・住所・ID・ニックネーム・住民ごとの興味は渡さない）。
   - LLM の API キーは worker だけが持つ（`security.md` §6.1）。
5. **区分**: ADR-0024 の決定 5 に従い、NFR-077 は `[inferred]`（マスターの答え OQ-008（2026-11-19）より）とし、根拠にこの ADR を書く。

## 理由

- 見積もりをロードマップに置くことと、選定を秘書に任せること（暫定）は、マスターの答え（上の原文）による。
- Haiku にしたのは、LLM の仕事が掲示板の投稿を 3 つのラベルに分けることだけで（ADR-0005）、手紙は渡さない（ADR-0026）ので、
  いちばん安い今のモデルで足りると見たため。公開してよいかはルール表との突合で決まり、LLM の誤りは人の審査に倒れる（NFR-011・NFR-012）。
- 構造化出力で 3 つのラベルに限るのは、想定外の値を減らし、出力のトークンを少なくするため。検証は今までどおり残す。
- Batch API を使わないのは、審査の時間（J2 の開始から審査の打ち切りまで、朝便は 02:00〜04:00 の 2 時間、夕便は 15:00〜16:00 の 1 時間。ADR-0016・`async.md` §3）の中で
  終わる保証がないため。終わらなかった投稿はすべて人の審査か次の便に回り、体験を損なう。
- 本番のアダプタを先に作らないのは、デプロイしない方針（NFR-071）で使う場面がなく、選定が暫定で変わりうるため。

## 代わりの案（選ばなかった理由）

- **Sonnet 5.5 など上位のモデル**: 3 つのラベルへの分類には過ぎ、費用が数倍になる。誤りは人の審査で受け止める設計なので、上位のモデルの利点が小さい。
- **Batch API で安くする**: 上のとおり、審査の時間の中で終わる保証がない。
- **ほかの事業者の LLM**: 比べて選ぶ理由が今はない。暫定なので、OQ-047 で確定するときに見直せる。
- **LLM を自分で動かす（セルフホスト）**: GPU のホスティングの費用と運用が要り、デプロイしない方針と費用の面で合わない。

## 決めていないこと

- 暫定の選定をいつ・どの手続きで確定するかと、LLM の費用の上限を置くか: OQ-047（持ち越し）。契約の前にマスターに聞く。
- 掲示板の投稿が外部のサービス（Anthropic API）で審査されることを住民に知らせる必要があるか（規約・プライバシーの説明）: OQ-032（持ち越し、適用法令）で合わせて調べる。
