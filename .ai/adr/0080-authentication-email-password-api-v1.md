# 0080 — ログインはメールとパスワード、認証の経路は /api/v1

- 状態: 採用
- 日付: 2026-11-22

ADR-0018 を丸ごと置き換える。ADR-0018 の決定（メールアドレス＋パスワードの方式・パスワードの要件・メールの確認・再設定のトークン・メールアドレスの保存方法）は、今の状態に書き直してこの ADR の D1〜D3 に移した。
新しく決めたのは、メールの確認・パスワードの再設定・ログインの経路を `/api/v1` の名前で置くこと（D4〜D7）。`reviews/0001-design-review.md` の R-006 による。

## 背景

OQ-028「認証方式」は `security.md` で決める持ち越し項目だった（FR-092、NFR-013）。選択肢は次の 3 つだった。

1. メールアドレス＋パスワード
2. ソーシャルログイン（OAuth 2.0 / OIDC）
3. パスキー（WebAuthn）

メールアドレスを平文で保存すると、DB が漏れたときにメールアドレスが出る。暗号化すると等値検索ができない。

`api.md` §7 F-02 には登録（`POST /api/v1/registrations`）とログイン・ログアウト（`/api/v1/sessions`）しかなく、メールの確認とパスワードの再設定の経路がなかった。`api.md` §4 の認証なしの一覧にもなかった。

## 決定

### D1 認証方式

**メールアドレス＋パスワード** を採用する [assumed]。ソーシャルログイン・パスキーは将来の選択肢として記録し、当面は採用しない。

- パスワードは Argon2id でハッシュして保存する。
- パスワードは 12 文字以上を必須とする [assumed]。
- 広く知られた漏えいパスワードのリスト（ローカルの辞書ファイル）と照合し、一致したら拒否する。

### D2 メールの確認と再設定のトークン

- 登録のときにメールアドレスへ確認のメールを送る。確認が済むまでアカウントを有効にしない。確認が済まない登録が住所を押さえる期限と、確認のリンクの期限は OQ-046（持ち越し）で決める。
- パスワードの再設定のトークンは 30 分で切れる [assumed]。1 回使うと使えなくなる。
- 確認と再設定のトークンは推測できない値にし、平文をログに残さない。トークンの保存先の表の定義は R-025 で決める。

### D3 メールアドレスの保存方法

**暗号化した値**（AES-256-GCM）と**HMAC 値**（検索用）の 2 列で保存する。

- `email_encrypted`: AES-256-GCM で暗号化した値。復号するときだけ使う。
- `email_hmac`: 決定的 HMAC（HMAC-SHA-256）で計算した値。等値検索（ログイン・重複確認）に使う。
- 暗号化鍵と HMAC 鍵は別々に管理する（`security.md` §6.1）。
- 平文のメールアドレスはログに残さない（`security.md` §2.5）。

### D4 認証なしで呼べる認証の経路

認証なしで呼べる認証の経路は次の 6 つ。どれも、アカウントがあるか・確認が済んでいるかを、状態コードと応答の本文で明かさない [assumed]。

| メソッド | パス | 決めたこと |
|---|---|---|
| `POST` | `/api/v1/registrations` | 登録。確認のメールを送る（`api.md` §7 F-02） |
| `POST` | `/api/v1/sessions` | ログイン（D5） |
| `POST` | `/api/v1/email-verifications` | 確認の完了（D6）。メールアドレスの変更の確認にも使う（ADR-0081 の D7） |
| `POST` | `/api/v1/email-verification-requests` | 確認のメールの送り直し（D6） |
| `POST` | `/api/v1/password-reset-requests` | 再設定の依頼（D7） |
| `POST` | `/api/v1/password-resets` | 再設定の完了（D7） |

どれも流量の制限の対象で、超えたら 429 `rate_limited`（`security.md` §3.5）。

### D5 ログイン

- `POST /api/v1/sessions` は `email`・`password` と、任意の `totp_code` を受け取る。
- メールアドレスがない・パスワードが違う・確認が済んでいない、のどれも同じ 401 `unauthenticated` と同じ本文を返す [assumed]。web は失敗の文面のそばに、確認のメールを送り直す導線を出す。
- 二要素認証を登録したモデレーターの扱いは ADR-0081 の D6。

### D6 メールの確認

- `POST /api/v1/email-verifications` は確認のメールのトークンを受け取る。正しければ `email_verified_at` を書いて 204 を返す。トークンが違う・切れた・使った、のどれも 400 `token_invalid`（区別しない）。
- `POST /api/v1/email-verification-requests` はメールアドレスを受け取り、確認が済んでいない登録があるときだけ確認のメールを送り直す。あってもなくても同じ 202 と同じ本文を返す。

### D7 パスワードの再設定

- `POST /api/v1/password-reset-requests` はメールアドレスを受け取り、確認が済んだ住民がいるときだけ再設定のメールを送る。あってもなくても同じ 202 と同じ本文を返す。
- `POST /api/v1/password-resets` はトークンと新しいパスワードを受け取る。D1 の要件に合わなければ 400 `validation_failed`、トークンが違う・切れた・使った、のどれも 400 `token_invalid`。完了したら 204 を返し、同じトランザクションでその住民のセッションの行をすべて消す（購読も消す、ADR-0081 の D4）。

## 理由

- **メール＋パスワード**: ソーシャルログインは外部サービスへの依存が生まれる。パスキーはブラウザ対応・端末紛失時の復旧が複雑で、MVP での採用コストが高い。メール＋パスワードは実績があり、依存が少ない。
- **Argon2id**: bcrypt・scrypt より GPU 攻撃耐性が高く、現時点の推奨（RFC 9106）。
- **メールを暗号化する**: DB 漏洩時に平文でメールアドレスが露出しない（NFR-017 の考えを広げる）。
- **HMAC で検索する**: 暗号化すると等値検索ができない。HMAC は決定的で等値比較ができる。部分一致はできないが、ログイン・重複確認は等値検索で足りる。
- **`/api/v1` の資源の名前にする**: ほかの経路（`api.md` §3）と同じ接頭辞と資源ごとの区切りにそろえる。確認と再設定は「依頼」と「完了」を別の資源にし、どちらも作成（`POST`）で表す。
- **アカウントの有無を明かさない**: 依頼の経路が応答を変えると、メールアドレスから住民がいるかを探れる（`security.md` §3.1、T-05）。
- **再設定でセッションをすべて消す**: パスワードを盗まれて再設定したとき、盗んだ側のセッションを残さない。

## 代わりの案（選ばなかった理由）

- **ソーシャルログイン（OAuth 2.0）**: プロバイダの停止・仕様変更の影響を受ける。当面は不採用。将来は足せる。
- **パスキー（WebAuthn）**: 端末紛失時の復旧手段を別に設計する必要がある。MVP では採用コストが高い。
- **メールを平文で保存**: DB 漏洩時にメールアドレスが露出する。不採用。
- **メールを HMAC だけで保存**: 本人に確認のメールを送れない。不採用。
- **`/auth/*` の接頭辞を別に置く**: ほかの経路と名前の付け方が分かれ、認証なしの経路の一覧が 2 か所に分かれる。不採用。
- **確認が済んでいないログインに別のエラーの符号を返す**: メールアドレスとパスワードが合っていることが分かり、アカウントの有無も分かる。不採用。

## 影響

- `api.md`: §4 の認証なしの一覧、§5 の `token_invalid`、§7 F-02 の経路。
- `security.md`: §3.1・§3.2・§3.5。
- `db.md`: `credentials` の `email_verified_at`。トークンの保存先の表は R-025 で定義する。
- 秘密管理: 暗号化鍵・HMAC 鍵・再設定トークンの署名鍵（`security.md` §6.1）。
- OQ-028: 決定。OQ-046（持ち越し）の答えで、確認のリンクの期限と、確認が済まない登録の扱いが決まる。
