# 0044 — MVP は全住民を知り合い 0 の組とする。新聞の知り合いは互いに住所録に入れた住民で、載せるのは知り合いの掲示板の投稿（手紙は載せない）。組 1・2 は住民ごとに組み、足りない分は興味の版か共通の版の記事で埋める。アップロードした画像は加工し、元の画像は持たない

- 状態: 採用
- 日付: 2026-11-20

## 背景

OQ-051 の答え（ADR-0039）で、新聞は一人 1 枚にせず、「知り合いで埋まる組」（組 1）「一部埋まらない組」（組 2）「知り合い 0 の組」（組 0）に分け、組 0 は興味で分けると決まった。
組 1・2 については答えに書かれていないことがあったので、`open-questions.md` の OQ-058 でマスターに次の 5 点を聞いていた。
(1) 「知り合い」は誰か（(a) 自分の住所録に入れた住民、(b) 互いに住所録に入れた住民、(c) 手紙をやり取りしたことのある住民）。地図の印（ADR-0042 の D1 (c)）と同じ定義にするか。
(2) 知り合いの何を紙面に載せるか。手紙は載せない前提でよいか。知り合いの側の同意は要るか。
(3) 組 1・2 の紙面を組の中で共有するか、住民ごとに組むか（版の数が住民の数で増え、サーバーの負荷にかかわる）。
(4) 組 2 の足りない分を何で埋めるか。(5) 「埋まる」の境を秘書が決めてよいか。
暫定は、全住民を組 0 として扱う（ADR-0039 の D2）だった。

2026-11-20、マスターが OQ-058 に次のとおり答えた（原文）。

> 暫定通りで。全住民を「知り合い0の組」として扱う。
>
> (1) 知り合いの定義は b。新聞でも同じ定義
> (2) 一般的なSNSのツイートに当たる部分。手紙はDMなので新聞には載せない。
> (3) サーバー負荷は要検討だが、現時点では知り合いに合わせて構成したい。一般的なSNSと異なり、動画、画像を自由に無制限に上げることはできないので、割と軽量だと思ってる。アップロードした画像は新聞用に加工し、元データは保持しない方針
> (4) 共通の記事と興味の記事。
> (5) 秘書（システム）の設計で決めていい。手間をかけずに、シンプルに動く仕組みにすること。

答えから読み取れることと、読み取れないことを分ける。

| 答え | 読み取れること（決定） | 読み取れないこと（新しい OQ） |
|---|---|---|
| 冒頭 | 暫定のとおり、全住民を組 0 として扱う。MVP（M5）では組 1・2 を作らない | 組 1・2 をいつ作るか → OQ-070（持ち越し） |
| (1) | 新聞の「知り合い」は (b) 互いに住所録に入れた住民 | 「新聞でも同じ定義」は、地図の決定（ADR-0042 の D1 (c)。(a) 自分の住所録に入れた住民）と食い違う。地図も (b) にするか → OQ-071（要回答） |

| (3) | 今の時点では知り合いに合わせて組む（組 1・2 は住民ごとに組む）。アップロードした画像は新聞用に加工し、元の画像は持たない | 負荷は「要検討」のまま → OQ-070 で見積もる |

答えは、ADR-0039 の D1（版の数は住民の数によらない）を組 1・2 について置き換え、D2 の暫定を決定にする。

## 決定

区分は ADR-0024 の決定 5 に従う。

1. **D1 MVP は全住民が組 0**（答えの冒頭、`[inferred]`）: MVP（M5）では、全住民を知り合い 0 の組として扱う。版は共通の版（`common`）と興味の版（`interest:<key>`）だけで、休刊の回は `holiday`。
   ADR-0039 の D2 の暫定を、この範囲で決定にする。組 1・2 は MVP では作らない。作る時期は OQ-070 (1)（持ち越し）。
2. **D2 新聞の「知り合い」は互いに住所録に入れた住民**（答え (1)、`[inferred]`）:
   住民 A と B が知り合いなのは、A の住所録のエントリの `address_book.registered_tenancy_id` が B の今の居住記録（`tenancies.is_current = true`）を指し、
   かつ B の住所録のエントリが A の今の居住記録を指すときだけとする。
   - 相手が引っ越すと、登録した時点の居住記録は今のものでなくなるので、知り合いから外れる。住所録は自動で直さない（ADR-0003 と同じ考え）。住民が手で住所を直せば、そのときの居住記録に取り直す（`api.md` §7 F-09）。
   - どちらかがもう一方をブロックしている（`blocks` に行がある）ときは、知り合いにしない（秘書の判断）。
   - 地図の知り合いの家の印（ADR-0042 の D1 (c)、(a) 自分の住所録に入れた住民）は、この ADR では変えない。地図も (b) にするかは OQ-071（要回答）。
3. **D3 載せるのは知り合いの掲示板の投稿**（答え (2)、`[inferred]`）: 組 1・2 の紙面の知り合いの記事は、その配達回の素材（`board_posts.status = 'approved'` かつ `board_posts.delivery_run_id = run_id`）のうち、
   知り合いが書いた投稿だけとする。「ツイートに当たる部分」を掲示板の投稿と読むのは秘書の読み方。
   手紙は、個人宛・グループ宛のどちらも載せない（答えの「手紙はDMなので新聞には載せない」）。審査（J2）とルール表で公開してよいと決まった投稿だけが載る。
4. **D4 組 1・2 の版は住民ごとに組む**（答え (3)、`[inferred]`）:
   - 組 1・2 の住民には、住民ごとの版を組み、`edition_key = 'acquaintance:<resident_id>'` とする（`<resident_id>` は `residents.id`）。
   - 住民ごとの版を見られるのは本人だけで、ほかの住民とモデレーターには 404 を返す。API は `edition_key` を返さない（ADR-0039 の D11 のまま）。web が C8 の HTML を中継するので、保存のキーも返さない。
   - 記事の文字は今までどおり、素材ごとに 1 回だけ J16 が作り（ADR-0039 の D7、UNIQUE(delivery_run_id, source_kind, source_id)）、住民ごとの版でも使い回す。住民ごとの版で LLM を呼ばないので、LLM の費用は増えない。
   - ADR-0039 の D1 の「版の数は住民の数によらない」は、組 0 の版だけに当たる。組 1・2 の版の数は、組 1・2 の住民の数だけ増える。負荷の見積もりは OQ-070 (2)。
5. **D5 アップロードした画像は加工し、元の画像は持たない**（答え (3)、`[inferred]`。段階 2・F-11）:
   - 住民がアップロードした画像（手紙・掲示板）は、J13 `image.process` が新聞用（新聞写真風）に加工する（FR-016）。
   - 元の画像は、J13 の加工が終わった時点（`state = 'processed'`）か、最後の再試行に失敗した時点（`state = 'failed'`）で C8 から消し、`images.original_url` を NULL にする。
   - 取りこぼし（worker が止まった・消すのに失敗した）に備え、アップロードから 24 時間 `[assumed]` を過ぎて残った元の画像は、その次の J14 `retention.purge`（毎日 1 回、`async.md` §2）が消し、`original_url` を NULL にする。J14 は毎日 1 回なので、取りこぼしが残るのは最長でアップロードから約 48 時間。そのとき加工が済んでいなければ `state = 'failed'` にする。
   - 加工が済んでいない画像はどこにも出さず、元の画像は住民にもモデレーターにも返さない（`roadmap.md` の B-03 のまま）。画像の審査を足すときも、加工した画像を使う（段階 2 の画像加工の ADR で決める）。
6. **D6 組 2 の足りない分**（答え (4)、`[inferred]`）: 組 2 の住民の紙面の、知り合いの記事で埋まらない枠は、その住民が組 0 なら受け取る版の記事で埋める。
   その版は ADR-0039 の D3 のとおり、興味が 1 つならその興味の版、複数ならハッシュで選んだ興味の版、興味がなければ共通の版とする。
   埋めるのは、その版に載る記事の順（共通の記事と、その興味の記事）で先頭からとする。知り合いの記事にすでに載った素材は、二重に載せない。
7. **D7 組の境**（答え (5)、秘書の判断）: 状態を保存せず、J3 が配達回ごとに次の規則で計算する。
   S は、組 1・2 の紙面のテンプレート（ADR-0011 の組版エンジン）が持つ記事の枠の数（テンプレートの定数。値は組 1・2 のテンプレートを作るときに決める）。k は、その配達回の素材のうち、その住民の知り合い（D2）の投稿（D3）の件数。
   - k = 0 なら組 0（住民ごとの版を組まない）。
   - 1 ≤ k < S なら組 2（k 件の知り合いの記事と、D6 で埋めた S − k 件）。
   - k ≥ S なら組 1（知り合いの記事を `(created_at, id)` の順で先頭の S 件）。
   - J3 は住民ごとの版を、ほかの版と同じトランザクションで入れる（版がそろうか休刊かのどちらか、ADR-0039 のまま）。J4 は組を計算し直さず、その配達回に `acquaintance:<resident_id>` の版があればそれを、なければ組 0 の版を選ぶ。
     これで J3 と J4 のあいだに住所録が変わっても、住民の版は J3 の時点の計算で決まり、J4 のやり直しでも同じ版になる。休刊の回は今までどおり全住民に `holiday`。
8. **D8 要求の区分**: FR-108 を直し、FR-118（アップロードした画像は加工し、元の画像は持たない）を足す。どちらも `[inferred]`（マスターの答え OQ-058（2026-11-20）より）。

## 理由

- D1 は、答えの冒頭「暫定通りで。全住民を「知り合い0の組」として扱う」による。組 1・2 をいつ作るかは書かれておらず、負荷も「要検討」なので、MVP には入れない。
- D2 は、答え (1) による。居住記録で決めるのは、住所録の住所の文字列は登録した時点のままで（ADR-0003）、今その住所に住んでいる人が知り合いとは限らないため（`db.md` §3）。
  ブロックした相手を知り合いにしないのは、ブロック（FR-068）した相手の投稿を、その住民だけに組む紙面に「知り合い」として出さないため。
  地図を変えないのは、地図は OQ-054 の答え「2:1」で決まっており（ADR-0042）、(b) にすると「相手が自分を住所録に入れたか」が地図の印から分かってしまうため（OQ-040 の暫定「MVP では知らせない」と食い違う）。これは公開の範囲にかかわり、マスターにしか決められない（OQ-071）。
- D3 は、答え (2) による。掲示板の投稿は誰でも読める公開の内容（ADR-0005 で審査済み）で、SNS のツイートに当たる。手紙はクローズドなやり取り（FR-019）なので載せない。
- D4 は、答え (3) の「知り合いに合わせて構成したい」による。知り合いは住民ごとに違うので、組の中で紙面を共有すると、ほかの住民の知り合いの投稿が載る。
  本人だけが見られるようにするのは、住民ごとの版から、その住民の住所録と知り合いの関係が分かるため（ADR-0039 の D11 と同じ考え）。記事の文字を使い回すのは、費用を版の数で掛け算しないため（ADR-0039 の D7）。
- D5 は、答え (3) の「元データは保持しない方針」による。元の画像を持たなければ、外見を識別できる画像（`security.md` §2.2、P-3）が漏れる面がなくなる。
  失敗でも消すのは、加工できない画像のために元の画像を残し続けないため。24 時間は、J13 の再試行（`async.md` §5）が終わる時間より十分に長い仮の値。取りこぼしの掃除のためだけに J14 より短い間隔のジョブは足さず、最長約 48 時間を許す（答え (5) の「シンプルに動く仕組み」）。
- D6 は、答え (4) による。組 0 の版と同じ選び方にすれば、新しい規則を足さずに済む（答え (5) の「シンプルに」）。
- D7 は、答え (5) の「手間をかけずに、シンプルに動く仕組み」による。組を保存しないので、住所録・ブロック・引っ越しが変わったときに組を直す処理が要らない。境を枠の数にすれば、「埋まる」をテンプレートの枠と同じ意味で決められる。

## 代わりの案（選ばなかった理由）

- **組 1・2 を MVP（M5）で作る**: 答えの冒頭「全住民を「知り合い0の組」として扱う」と食い違う。負荷も見積もっていない（OQ-070）。
- **知り合いを (a) 自分の住所録に入れた住民にする（地図と同じ）**: 答え (1)「知り合いの定義は b」と食い違う。
- **地図も (b) に直す**: 答えの「新聞でも同じ定義」は地図を (b) にする意図とも読めるが、地図の決定（ADR-0042）を変え、相手が自分を住所録に入れたかが地図から分かるようになる。公開の範囲にかかわるので、聞いてから決める（OQ-071）。
- **知り合いの手紙も載せる**: 答え (2)「手紙はDMなので新聞には載せない」と食い違う。
- **組 1・2 の紙面を組で共有する**: ほかの住民の知り合いの投稿が載る。答え (3)「知り合いに合わせて構成したい」と食い違う。
- **住民ごとの版で LLM を呼ぶ（住民に合わせた見出し・まとめを書く）**: 費用が住民の数で増え、LLM に住民と結び付いた情報を渡すことになる（ADR-0039 の D8）。
- **組を表に保存し、住所録・ブロック・引っ越しのたびに直す**: 直す処理が増え、答え (5) の「シンプルに」と食い違う。
- **境を割合（例: 枠の半分）や別の件数にする**: 枠の数のほかに値が増える。枠の数なら「埋まる」の意味がそのまま決まる。
- **元の画像を保持期間を決めて残す**: 答え (3)「元データは保持しない方針」と食い違う。
- **加工に失敗した画像の元の画像を、やり直しのために残す**: 同じ理由で取らない。住民はもう一度アップロードすればよい。

## 決めていないこと

- 組 1・2 をいつ作るか・負荷の見積もり・知り合いの側の同意（OQ-070、持ち越し）。暫定は置かず、組 1・2 は作らない（D1）。
  組 1・2 を作る段階の計画の前に、秘書が負荷を見積もり、同意とあわせてマスターに聞く。住民ごとの版に載る投稿から「その投稿者が自分を住所録に入れている」ことが推し量れる点（OQ-040）も、そのときに聞く。
- 地図の知り合いの印も (b) にするか（OQ-071、要回答）。暫定は (a) のまま（ADR-0042 の D1 (c)）。
- S の値と、組 1・2 のテンプレートの形: 組 1・2 を作るときに決める（OQ-070 のあと）。
- 元の画像を消すまでの 24 時間（J14 が毎日 1 回なので最長約 48 時間）は仮置き `[assumed]`。画像の加工の方式と基準は段階 2 の画像加工の ADR（`roadmap.md` の S2-2）で決める。
