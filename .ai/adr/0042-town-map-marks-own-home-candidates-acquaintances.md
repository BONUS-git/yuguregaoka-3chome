# 0042 — 地図に印を付ける。自分の家と登録のときの候補は M1、知り合い（自分の住所録に入れた住民）の家は M2（知り合いの定義は ADR-0049。印を付けるエントリは OQ-071）。土台の画像は全住民で同じまま、印は C1 が重ねる。空き家・入居の表示は OQ-079 の答えまで作らない

- 状態: 採用（D11 は ADR-0049 の D8 で書き直した。2026-11-20。印に使うのは今までどおり自分の住所録のすべてのエントリ（OQ-071 の暫定 (i)）。OQ-066 の参照は OQ-079・OQ-080 に直した）
- 日付: 2026-11-20

## 背景

ADR-0037 で、地図は全住民で共有する 1 枚の白黒の画像と決まった。印（知り合いの家・自分の住所・登録のときの候補）は今は付けないこと（ADR-0037 の D3）と、
住民ごとに中身を変えないこと（ADR-0037 の D1 (b)）は OQ-054 の暫定で、`open-questions.md` の OQ-054 でマスターに次の 3 点を聞いていた。
(1) 知り合いの家の印をいつ作るか。(2) 「知り合い」は誰か（(a) 自分の住所録に入れた住民、(b) 互いに住所録に入れた住民、(c) 手紙をやり取りしたことのある住民）と、相手の同意が要るか。
(3) 自分の住所の場所に印を付けるか・登録のときに住所の候補の場所を地図で示すか。

2026-11-20、マスターが OQ-054 に次のとおり答えた（原文）。

> 1:MVP
> 2:1
> 3:どちらもyes, 登録時に選択可能かつ、地図を表示する際は中心に置き印もつける。また、空き家か人がいるかも表示する。ここにはユーザー名は載せず、boolean的に表示するものと考えている

答えから読み取れることと、読み取れないことを分ける。

- 「1:MVP」: 知り合いの家の印は MVP で作る。
- 「2:1」: 質問の (2) の 1 つ目の例、(a) 自分の住所録に入れた住民と読む（秘書の読み方。質問の (2) の例は (a)(b)(c) の 3 つで、その 1 つ目）。
  相手の同意が要るか（相手が断れるか）には答えがない。新聞の知り合いの組（OQ-058 (1)）と同じ定義にするかにも答えがない（のちに OQ-058 → 決定、2026-11-20、ADR-0044 の D2。新聞は (b) 互いに住所録に入れた住民。地図も (b) にするかは OQ-071、要回答）。
- 「3:どちらもyes」: 自分の住所の場所に印を付ける。登録のときに住所の候補の場所を地図で示す。
- 「登録時に選択可能」: 登録のとき、地図で示した候補から住所を選べる。候補の一覧から選び、地図で場所を確かめる形と読む（秘書の読み方）。
  地図の印そのものから選ぶ（地図をクリックする）ことを指しているとも読め、どちらかは答えに書かれていない（OQ-080。もとは OQ-066 (4)）。
- 「地図を表示する際は中心に置き印もつける」: 地図を出すときは、自分の家を中心に置き、自分の家に印を付ける。
- 「空き家か人がいるかも表示する。ここにはユーザー名は載せず、boolean的に表示する」: 家ごとに、空き家か人が住んでいるかの 2 値だけを示し、住民の名前（住所・ニックネーム）は載せない。
  どの家について示すか（街のすべての家か・知り合いの家だけか）、誰に見せるか（登録の前の人にも見せるか）、いつの状態を示すか、
  ここでの「空き家」が `addresses.status`（ADR-0002 の 5 つの値）のどれに当たるかは書かれていない。

## 決定

1. **D1 印を付ける（答え）**: 地図に次の 3 種類の印を付ける。
   - (a) 自分の家の印（答え 3）。ログインしている住民の地図に、自分の住所の場所を示す。
   - (b) 登録のときの候補の印（答え 3）。登録の画面の地図に、提示した住所の候補の場所を示す。
     登録の画面はログインの前の画面（まだセッションのない人の画面）なので、答えの「登録時に選択可能」により、ログインの前の画面のうち登録の画面には地図（土台の画像）と候補の印を出すことが決まった。
     ADR-0028 の D1 で「決めない」としていたログインの前の画面に地図を出すかのうち、決めないまま残るのは、登録の画面のほかのログインの前の画面（ログインの画面など）だけになる。
   - (c) 知り合いの家の印（答え 1・2）。「知り合い」は自分の住所録に入れた住民（答え 2 の秘書の読み方）とし、住所録の各エントリの住所の場所に印を付ける。
     （追記 2026-11-20）OQ-066 の答えで、手紙を出せる「知り合い」には相手の同意（互いの追加か、掲示板でのオープン）が要ると決まった（ADR-0049 の D2・D8）。
     この答えは地図に触れていないので、地図の印は今までどおり住所録のすべてのエントリの住所に付ける（OQ-071 の暫定 (i)。答え「2:1」のまま。知り合い（`acquainted: true`）だけに付けるかは OQ-071、要回答）。
     このため、地図の「知り合いの家」の印は、手紙を出せる知り合い（ADR-0049 の D2）と一致しないことがある（片方だけ足した相手の家にも印が付く）。
2. **D2 段階（答え 1・秘書の判断）**: どれも MVP。自分の家の印と候補の印は M1（住所・アカウント）に置く。知り合いの家の印は、住所録を作る M2（住所録・手紙）に置く（秘書の判断。住所録がないと作れないため）。
3. **D3 土台の画像は全住民で同じ（秘書の判断。ADR-0037 の D1 (b) を暫定から決定にする）**: 土台の SVG は、どの住民にも、ログインの前にもバイト単位で同じにする。
   印は土台の画像に描き込まず、C1 が土台の画像の上に重ねる層（印の層）として描く。土台の画像には今までどおり号までの住所・住民・入居・空き家・数を描かない（ADR-0028 の D4）。
4. **D4 住所と位置の対応（秘書の判断）**: 住所から画像の上の位置を求めるのは、C1 の静的な配置の定義（番ごとの区画の位置と大きさ）と、C1 の中の関数（番と号から区画の中の位置を計算する）とする。
   住所ごとの位置の一覧（使われている住所・使われていない住所の一覧）は持たない。DB の表・地図の API・ジオデータ・外部の地図サービスは今までどおり持たない（ADR-0028 の D3）。
   配置の定義にない番・解釈できない住所には印を付けず、画面に誤りの知らせも出さない（その住所があるかどうかを地図から推し量らせない）。
5. **D5 印に使う住所（秘書の判断）**: 印に使うのは、すでにある API が本人に返す住所だけにする。自分の家は `GET /api/v1/me`、候補は `GET /api/v1/addresses/candidates`、知り合いの家は `GET /api/v1/address-book` の応答の住所。
   応答の形は変えない（位置・座標を応答に足さない）。知り合いの家の印は住所録のエントリの住所（登録した時点の住所、ADR-0003）の場所に付け、相手が引っ越しても自動で動かさない。
   （追記 2026-11-20）住所録の応答に足したのは `acquainted`（真偽値、ADR-0049 の D4）だけで、位置・座標は足さない。印は `acquainted` によらず、住所録のすべてのエントリに付ける（OQ-071 の暫定 (i)）。印の付け方は変わらない（相手が引っ越しても、印は登録した時点の住所に残る）。
6. **D6 表示の窓（答え 3・秘書の判断）**: 地図を出すときは、自分の家の位置を表示の窓の中心に置く（答え）。窓の幅と高さは土台の画像の 2 倍とし、どこに住んでいても街の全体が窓に入るようにする。窓のうち土台の画像の外は白い余白にする（秘書の判断）。
   拡大・移動はしない（ADR-0028 の D1 (a)）。登録の画面（まだ自分の家がない）では、土台の画像をそのまま窓にし、候補の印を付ける。
7. **D7 登録のときの選び方（答え 3・秘書の判断）**: 候補の印には、候補の一覧と同じ見出し（候補の住所）を添える。住民は候補の一覧から住所を選ぶ（答えの「登録時に選択可能」）。
   一覧で選んだ候補の印は、ほかの候補の印と見分けられる形に変える。地図の上では選ばない（秘書の読み方）。地図そのものはクリックできない（ADR-0028 の D1 (a) の「クリックしない」を変えない）。
   ADR-0028 の D1 (a) の「クリックしない」は、マスターの答え OQ-005 の「静的な画像」を秘書がそう読んだもので、今回の答えの「登録時に選択可能」が地図の印から選ぶことを指すなら、この読み方と衝突する。
   地図の印から選べるようにするかは OQ-080（要回答。構想の意図にかかわる。もとは OQ-066 (4)）。暫定は一覧から選ぶ（この D7）。
8. **D8 印の層の中身（秘書の判断）**: 印の層は白黒（ADR-0037 の D2、R=G=B）で描き、印の種類は形で見分ける（色に頼らない）。
   印の層に、住民が書いた文字（ニックネーム・自己紹介・住所録のメモ）を入れない。添える文字は、候補の住所と、決まった語（「自分の家」など）だけにする。
   印の層は C1 のコードが描き、外部への参照・`<script>`・イベント属性を入れない（ADR-0028 の D5 の考え方を印の層にも当てる）。
9. **D9 代替テキスト（秘書の判断）**: 代替テキストには、人の名前（ニックネーム・住所録のメモ）と数（知り合いの家の数など）を入れない。
   自分の家の住所・候補の住所と、「知り合いの家に印があります」のような決まった文だけにする（P-2 数値の評価、NFR-041）。
10. **D10 空き家・入居の表示（答え 3。範囲は OQ-079 の答えまで作らない）**: 家ごとに空き家か人が住んでいるかを、住民の名前を載せない 2 値で示すことは決める（答え）。
    どの家について示すか・誰に見せるか・いつの状態か・何を「空き家」とするかは答えに書かれておらず、住所の列挙（`security.md` §7 の T-05）と公開の範囲にかかわるので OQ-079（要回答。もとは OQ-066 の (1)(2)。OQ-066 の答えはこの点に触れていない）にする。
    答えまで、空き家・入居の表示は作らず、それを返す経路も作らない。
11. **D11 相手の同意（ADR-0049 の D8 で書き直し、2026-11-20）**: OQ-066 の答えで、手紙を出せる知り合いには相手の同意（互いに住所録に入れること、または掲示板でのオープン）が要ると決まった。
    地図の印に相手の同意を求めるか（印を知り合い（`acquainted: true`）だけに付けるか）は、答えが地図に触れていないので OQ-071（要回答）。暫定は (i) 住所録のすべてのエントリに付け、印には相手の同意を求めない（答え「2:1」のまま）。
12. **D12 要求の区分**: ADR-0024 の決定 5 に従い、FR-103 を直し、FR-114（印）と FR-115（空き家・入居の表示）を `[inferred]`（マスターの答え OQ-054（2026-11-20）より）として足す。

## 理由

- D1・D2 は答え 1〜3 による。知り合いの家の印を M2 に置くのは、住所録（F-09）が M2 で、M1 には印にする住所がないから。
- D3 は、答え（OQ-044）の「全ユーザーで共有して」と、答え（OQ-054）の印を、両方とも満たすため。土台を同じにし、印を本人の画面の上だけで重ねれば、共有する地図を崩さずに住民ごとの印を出せる。
  土台が同じなら、土台の画像から住民や住所の割り当てが漏れない（ADR-0028 の D3 の「セッションなしでも取れる」の結果を守れる）。
- D4・D5 は、印のために新しい API・表を足さないため（NFR-055）。住所ごとの位置の一覧を持つと、使われている住所の一覧に近いものが C1 に載り、住所の列挙（T-05）の面が増える。
  番の区画と計算だけなら、分かるのは住所の形（番・号）だけで、どの住所が使われているかは分からない。
  すでにある API の応答は本人の住所・本人に出した候補・本人の住所録だけなので、印を付けても、本人が知らない住所は増えない。
- D6 は答えの「中心に置き」による。窓を 2 倍にするのは、街の端に住む住民でも街の全体が見えるようにし、拡大・移動（ADR-0028 の D1 (a)）を足さずに済ませるため。
- D7 は、答えの「登録時に選択可能」を、地図のクリック（ADR-0028 の D1 (a) で作らない）を足さずに満たすため。一覧から選び、地図で場所を確かめられる。
  答えをこう読むのは秘書の読み方で、地図の印から選ぶことを指すかは OQ-080 に残す。
- D8・D9 は、地図を住民の名前・数の出る場所にしないため（答えの「ユーザー名は載せず」・P-2）。住民が書いた文字を入れなければ、印の層からの XSS（T-07）の面も増えない。
- D10 は、答えの「ユーザー名は載せず、boolean的に表示する」を決めたうえで、範囲が答えにないため。街のすべての家の入居の有無を見せると、住んでいる住所の一覧になり、
  知らない住民に手紙を出す相手の一覧として使える（T-05）。誰にどこまで見せるかは公開の範囲で、マスターにしか決められない（CLAUDE.md）。
- D11 は、もとは OQ-054 (2) の同意の問いに答えがないため、新しく知らせることのない形を暫定にしていた。OQ-066 の答え（2026-11-20）で手紙の知り合いに同意が要ると決まったが、地図には触れていないので、地図の印は答え「2:1」のままを OQ-071 の暫定 (i) とした（ADR-0049 の D8）。

## 代わりの案（選ばなかった理由）

- **住民ごとに印を描き込んだ SVG を出す**: 土台が住民ごとに変わり、全住民で共有する画像（ADR-0037 の D1 (a)）と食い違う。画像を API で配ることになり、ADR-0028 の D3 と食い違う。
- **住所ごとの位置を DB の表に持ち、地図の API で返す**: 新しい経路と表が要り、使われている住所の一覧に近いものを返すことになる（T-05）。
- **地図の印をクリックして住所を選ぶ**: ADR-0028 の D1 (a)（クリックしない。秘書の「静的な画像」の読み方）と食い違う。一覧から選べば、秘書の読み方での答えを満たせる。
  答えが地図の印から選ぶことを指すなら、この案を取ることになる（OQ-080）。
- **表示の窓を自分の家を中心に切り取る（街の一部だけを見せる）**: 拡大・移動がないので、窓の外の家が見えなくなる。
- **知り合いを「互いに住所録に入れた住民」とする**: 答え 2 は 1 つ目の例を選んでいる。互いにすると、相手が自分を住所録に入れたかが分かり、OQ-040 の暫定（MVP では知らせない）と食い違う。
  （追記 2026-11-20）この理由は変わった。OQ-066 の答えで、手紙の知り合いは互いに住所録に入れた住民になり、`GET /api/v1/address-book` が `acquainted` を返すので、互いに足したことは足した側にも分かる（ADR-0049 の D2・D4）。
  OQ-040 は決定（足されたことは知らせない、ADR-0049 の D3）。それでも地図は答え「2:1」で決まっているので、暫定は (i) 住所録のすべてのエントリのまま。知り合いだけに付けるかは OQ-071（要回答）。
- **空き家・入居の表示を、街のすべての家について今作る**: 範囲が答えに書かれておらず、住所の列挙（T-05）と公開の範囲にかかわる（OQ-079）。
