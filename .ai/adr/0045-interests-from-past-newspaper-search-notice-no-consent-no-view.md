# 0045 — 興味は、自分に届いた過去の新聞の検索から推し量って集める。検索語は残さず、当たった興味だけを持つ。住民には明るく開いた文で知らせ、個別の同意は取らない。推し量った興味を本人が見て消す仕組みは設けない

- 状態: 採用（住民が止められるかは ADR-0053 で決定、2026-11-21。止められない）
- 日付: 2026-11-20

## 背景

OQ-051 の答え「２：登録の時と後から設定、検索などから収集しようかな」（ADR-0039）で、興味は登録のとき（任意）とあとからの設定で集めると決まった（ADR-0039 の D4）。
検索などから集めることは、住民の行いから興味を推し量ることになるので、`open-questions.md` の OQ-059 でマスターに次の 4 点を聞いていた。
(1) どの検索から集めるか（今ある検索は住所録の検索 `?q=` だけで、自分のメモも検索する私的なもの）。(2) 「など」に入るものは何か。
(3) 集めることを住民に知らせるか・同意を取るか・住民が止められるか。(4) 推し量った興味を、本人が見て消せるようにするか。
暫定は、検索からは集めず、住所録の検索語を DB・ログに残さない（ADR-0039 の D4）だった。

2026-11-20、マスターが OQ-059 に次のとおり答えた（原文）。

> 1:過去の新聞
> 2: などについては具体的に考えていない。設計詰めながら、利用できそうなところを秘書が検討、追加してOK
> 3: 知らせるが、個別に同意は取らない。興味から新聞を届けます！と、ポジティブにオープンにする
> 4: 設けない。

答えから読み取れることと、読み取れないことを分ける。

| 答え | 読み取れること（決定） | 読み取れないこと（新しい OQ） |
|---|---|---|
| 1 | 興味を集める検索は、過去の新聞の検索。住民が読めるのは自分に届いた版だけ（ADR-0039 の D11）なので、自分に届いた過去の新聞（バックナンバー、F-12、段階 2）の検索と読む（秘書の読み方）。住所録の検索からは集めない | — |
| 2 | 「など」は秘書が設計を詰めながら検討し、足してよい | — |
| 3 | 集めることを住民に知らせる。個別の同意は取らない。知らせ方は「興味から新聞を届けます！」と、明るく開いた形にする | 住民が止められるか（問い (3) の 3 つ目）には答えがない → OQ-072（のちに決定、2026-11-21、ADR-0053。止められない） |
| 4 | 推し量った興味を本人が見て消す仕組みは設けない | — |

答えは、ADR-0039 の D4 の暫定（検索からは集めない）を置き換える。ADR-0039 の D5（興味は本人だけが見て変えられる）は、選んだ興味についてのものとし、推し量った興味には当てない。

## 決定

区分は ADR-0024 の決定 5 に従う。

1. **D1 興味を集める検索は、自分に届いた過去の新聞の検索だけ**（答え 1、`[inferred]`）:
   - 段階 2 の S2-3（F-12 バックナンバー）に、自分に届いた過去の新聞の検索（`GET /api/v1/newspapers?q=`）を足し（FR-119）、その検索語から興味を推し量る（FR-109）。
   - 検索の対象は、`delivery_runs.status = 'done'` の配達回で自分の郵便受けに届いた版の、記事の見出しと文だけ（ADR-0039 の D11・`roadmap.md` の B-04 と同じ範囲）。ほかの版・休刊の回は検索にも出さない。
   - 住所録の検索（`GET /api/v1/address-book?q=`、自分のメモも含む私的な検索）からは、今までどおり興味を集めない。検索語を DB・ログに残さない。
   - MVP（M5）には検索がないので、MVP で推し量った興味はない。M5 の興味は今までどおり登録と設定だけ。
2. **D2 「など」はこの変更では足さない**（答え 2、秘書の判断）:
   - 答えは「具体的に考えていない」なので、この ADR では過去の新聞の検索のほかに足さない。
   - 足すときは、足すものごとに ADR を書き、D7 の知らせの文を同じ変更で直す（知らせていないところから集めないため）。
   - 次からは集めない（秘書の判断）: 手紙（クローズドなやり取り、FR-019）・住所録とそのメモ（私的なもの）・ブロック・通報・ログインや通知の記録。
3. **D3 照合のしかた**（秘書の判断）:
   - API（C2）が検索を受けたとき、検索語を NFKC で正規化して小文字にそろえ、`active` な `interest_categories` の `label` と `keywords`（同じく正規化したもの）のどれかを、検索語が含むかをメモリの中だけで調べる。
   - `keywords` は運用者が CLI で保つ語の配列で、2 文字以上の語だけを受け付ける（短すぎる語で何にでも当たらないため）。中身は興味の一覧と同じく OQ-062 で決め、シードには架空の一般的な語だけを入れる。
   - LLM は使わない。照合のために検索語を worker・ジョブのペイロード・外部のサービスに渡さない。
4. **D4 持ち方**（秘書の判断）:
   - 当たった興味の ID だけを、新しい表 `inferred_interests`（`resident_id`・`interest_category_id`・`last_matched_at`）に書く。同じ興味にまた当たったら `last_matched_at` だけを更新する。
   - 検索語そのものは、DB・ログ・ジョブのペイロード・例外のメッセージ・C8 のどこにも残さない。検索の結果もサーバーに残さない。
   - 選んだ興味（`resident_interests`）とは別の表に持ち、`resident_interests.source` は今までどおり `registration` / `settings` だけ。
   - 書くのは検索の応答と同じ要求の中で、書けなくても検索の結果は返す（ログには検索語を書かない）。
5. **D5 保持**（秘書の判断）:
   - 1 人 5 つまで `[assumed]`。5 つあるときに新しい興味に当たったら、`last_matched_at` がいちばん古い行を置き換える。
   - 最後に当たってから 30 日 `[assumed]` を過ぎた行は、J14 `retention.purge` が消す。
   - 退去すると、J7 `account.erase` が即時に消す（ADR-0013）。
6. **D6 新聞での使い方**（秘書の判断）: J4 で版を選ぶときの候補は、選んだ興味（`resident_interests`）と推し量った興味（`inferred_interests`）を合わせた集合（どちらも `active` な興味だけ、重なりは 1 つにする）にする。
   選び方は ADR-0039 の D3 のまま（候補がなければ共通の版、1 つならその版、複数なら `SHA-256(run_id:resident_id)` で選ぶ。並びは `interest_categories.sort_order, id`）。
   LLM には今までどおり版の興味の名前だけを渡し、住民ごとの興味（選んだものも推し量ったものも）は渡さない（ADR-0039 の D8）。
7. **D7 知らせる。個別の同意は取らない**（答え 3、`[inferred]`）:
   - 同意の画面・チェックの欄・同意の記録は置かない。
   - 過去の新聞の検索の画面（入力欄のそば）と利用の案内に、明るく開いた文で、検索した言葉から興味を推し量って新聞を届けることを書く。
   - 文言の案（仮置き `[assumed]`、S2-3 で決める）: 「過去の新聞を検索した言葉から、あなたの興味を見つけます。興味から新聞を届けます！（検索した言葉そのものは残しません）」。原文の「興味から新聞を届けます！」はそのまま入れる。
   - 住民は推し量ることを止められない（OQ-072 → 決定、2026-11-21、ADR-0053）。止める設定も、検索ごとに推し量らない選択も置かない。
8. **D8 推し量った興味を本人が見る・消す経路は作らない**（答え 4、`[inferred]`）:
   - `GET /api/v1/me/interests` は選んだ興味だけを返し、`PUT /api/v1/me/interests` は推し量った興味に触れない。データのエクスポート（F-15）にも入れない。
   - ほかの住民・モデレーターに返す経路も作らず、LLM にも渡さない。件数（興味ごとの住民の数など）も返さない。
   - 消えるのは D5 の 30 日と退去のときだけ。推し量った興味についての NFR-010（自分のデータの削除）は、この 2 つで満たす。
9. **D9 段階**: MVP（M5）は変えない。S2-3 に、過去の新聞の検索・`inferred_interests`・J4 の候補を合わせること・J14 と J7 の削除・知らせの文と、受け入れ条件 B-09 を足す。
10. **D10 要求の区分**: FR-109 を直し、FR-119（自分に届いた過去の新聞の検索）を足す。どちらも `[inferred]`（マスターの答え OQ-059（2026-11-20）より）。

## 理由

- D1 は、答え 1 による。過去の新聞は住民に届いた公開の紙面で、住所録のような私的な情報ではない。対象を自分に届いた版に限るのは、ほかの版の中身からほかの住民の興味が分からないようにするため（ADR-0039 の D11）。
- D2 は、答え 2「秘書が検討、追加してOK」による。今は使い道の具体的な案がないので足さず、足すときは ADR と知らせの文を一緒に直す。手紙・住所録・ブロック・通報は、私的なやり取りや住民を守る仕組みで、そこから興味を推し量ると住民がそれらを使いにくくなる。
- D3 は、決定的で説明しやすく、検索語をどこにも渡さずに済むため。LLM を使うと検索語を外部のサービスに渡すことになる（NFR-002）。
- D4 は、データを最小にするため。興味の ID だけなら、検索語から分かる私的な事情（言葉そのもの）を持たずに済み、漏れても分かるのは興味の一覧の名前だけ。
- D5 は、推し量った興味を本人が見て消せない（答え 4）ので、古い推し量りがいつまでも残らないようにするため。5 つは選んだ興味の上限（ADR-0039 の D4）とそろえた仮の値。
- D6 は、ADR-0039 の D3 の選び方をそのまま使えば、新しい規則を足さずに済むため。版の数は興味の一覧の数のままで、住民の数によらない（ADR-0039 の D1）。
- D7 は、答え 3 による。止められるかは、住民が自分の情報の使われ方を選べるかという倫理と公開の範囲にかかわり、マスターにしか決められないので聞いた（OQ-072）。答えは止められない（ADR-0053）。
- D8 は、答え 4 による。本人にも返さないので、ほかの経路でも返さない。法令（APPI）の開示の求めとの関係は OQ-032 で調べ、答えと食い違う求めがあれば新しい要回答にする。

## 代わりの案（選ばなかった理由）

- **住所録の検索からも集める**: 答え 1 は過去の新聞だけで、住所録の検索は自分のメモも含む私的なもの。
- **ほかの住民に届いた版も検索できるようにする**: ほかの住民の興味が分かる（ADR-0039 の D11）。
- **検索語を残して、あとでまとめて推し量る**: 私的な言葉そのものを持つことになり、漏れたときの害が大きい。
- **照合をジョブ（worker）でする**: 検索語がジョブのペイロード（DB）に残る。
- **LLM で検索語から興味を推し量る**: 検索語を外部のサービスに渡すことになる。
- **同意の画面を置く**: 答え 3「個別に同意は取らない」と食い違う。
- **推し量った興味を設定の画面に出して、本人が消せるようにする**: 答え 4「設けない」と食い違う。
- **推し量った興味を選んだ興味（`resident_interests`）に混ぜて持つ**: `GET /me/interests` で本人に返ることになり、答え 4 と食い違う。また本人が外せてしまい、扱いが分かれない。
- **推し量った興味を消さずに持ち続ける**: 本人が見て消せないので、古い推し量りが残り続ける。

## 決めていないこと

- 「など」に足すもの（D2）: 秘書が設計を詰めながら検討し、足すときに ADR を書く。
- 知らせの文言（D7）・検索のしかた（全文検索の方式・結果の並び・`q` とカーソルのほかに置く引数。どの引数も照合を止めるものにはしない、ADR-0053 の D2）・`keywords` の中身（OQ-062）は S2-3 で決める。
- 1 人 5 つ・最後に当たってから 30 日は仮置き `[assumed]`。
- 推し量った興味を本人に返さないことと、法令の開示の求めとの関係（OQ-032、持ち越し）。食い違う求めがあれば、新しい要回答としてマスターに出す。
