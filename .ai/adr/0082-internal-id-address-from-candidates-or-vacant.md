# 0082 — 内部 ID と住所を分け、住所は候補か空き家から選ぶ

- 状態: 採用
- 日付: 2026-11-22

ADR-0001 を丸ごと置き換える。ADR-0001 の決定は、OQ-089 の答えに合わせて今の状態に書き直し、D1〜D4 としてこの ADR に移した。
D1（内部 ID）・D2（住所は属性）は ADR-0001 と同じ。D3（割り当て）は書き直した。D4（表と経路の名前）は今の文書の書き方にそろえた。

## 背景

構想では「架空の街の住所をユーザー ID とする」と定められている（FR-001）。
しかし住所は引っ越し（FR-004）で変わる可能性があり、住所をシステム内部の一次 ID として
直接使うと、引っ越しのたびに手紙・住所録など全参照を書き換える必要が生じる。
住所割り当て方法（FR-010）が変わった場合も影響が広がる。

登録の画面では、提示した住所の候補の印と、街のすべての家の空き家・入居の印を地図に出す（ADR-0084 の D1・D10）。
OQ-089 でマスターに、(a) 選べるのは提示した候補の印だけか、(b) 候補に出ていない空き家の印も押して、その住所を選べるようにするかを聞いた。
2026-11-22、マスターが次のとおり答えた（原文）。

> b

答えは (b) で、住民は候補の住所のほかに、地図の空き家の印からも住所を選べる。

## 決定

1. **D1 内部 ID**: システムは各住民に対して不変の内部 ID（UUID v4）を持つ。
2. **D2 住所は属性**: 住所は内部 ID に紐づく属性として管理し、住民 ID として画面には表示するが、内部参照（外部キー）には使用しない。
3. **D3 割り当て（OQ-089 の答え「b」）**: 新規登録のときに複数の住所の候補を提示し（`GET /api/v1/addresses/candidates`）、住民は候補か、登録の画面の地図の空き家の印（ADR-0084 の D7）から住所を 1 つ選ぶ。
   - 登録の要求（`POST /api/v1/registrations`）は、送られた住所が提示した候補かどうかを確かめない（候補の提示をサーバーに覚えさせない）`[assumed]`。
   - 住所が C3 の住所のプールの静的な定義にない・解釈できないときは 400（`validation_failed`）`[assumed]`。
   - 割り当てられるのは、その段階で候補になる住所だけとする。MVP では使われたことのない住所（`addresses` に行がない住所）だけ（ADR-0062 の D3・D4）`[assumed]`。
     `addresses` に行がある住所（住んでいる・退去のあと）と、同じ住所を同時に選んだ登録の負けた側（`addresses.address_text` の一意制約）は、どちらも同じ 409（`conflict`）を返し、何も作らない `[assumed]`。
   - 登録の要求の状態コードは 201・400・409・429（`rate_limited`、登録の要求の流量の制限。`security.md` §3.5）。
4. **D4 表と経路**: DB は `residents` の表に UUID の主キーを持ち、`addresses` の表を別に持って住民を参照する（`db.md` §2）。
   API の経路のパスには内部 ID を出さず、外から見える識別子は住所の文字列だけとする（`api.md` §1 原則 4）。

## 理由

- D1・D2: 引っ越し（FR-004）で住所が変わっても内部参照が壊れない。住所転送（FR-005）の実装がシンプルになる（旧住所 → 新住所のマッピングのみ）。住所割り当て方式の変更が内部参照に影響しない。
- D3 で空き家からも選べるのは、OQ-089 の答え「b」による。候補を提示することは残す。地図を見られない人・押しにくい人と、配置の定義にない住所（ADR-0084 の D4）にも選ぶ手段が要るから（NFR-041）。
- D3 で提示した候補かどうかを確かめないのは、答えで空き家の印からも選べるようになり、候補の外の住所を受け付けることが決まったから。候補の提示を覚えると、表かセッションの状態が要る（NFR-055）。
- D3 で割り当てを候補になる住所に限るのは、退去のあとの住所の再割り当てが段階 3（ADR-0062）で、MVP で退去のあとの住所を割り当てると、その住所宛ての住所録と手紙の扱い（`db.md` §3）を前倒しで決めることになるから。
  地図の空き家の印は退去のあとの住所にも付く（ADR-0084 の D13）が、MVP ではその住所を選んでも 409 になる。答え「b」の「空き家の印も押して選べる」は、割り当てられる空き家について満たす `[assumed]`。
- D3 で行のある住所と同時の登録の負けた側を同じ 409 にするのは、409 から「その住所が前に使われたか」と「いま誰かが同時に登録したか」を分けて読ませないため。前に使われたことは入居の一覧の差分から分かる範囲で（ADR-0084 の D18）、試せる数は登録の要求の流量の制限が抑える。
- 住所を選べることは、住民の「街に住む」体験を強める。

## 代わりの案（選ばなかった理由）

- **住所そのものを主 ID にする**: 引っ越しのたびに全参照を書き換えるか、住所変更を不可能にするかのどちらかが必要。体験と矛盾する。
- **選べるのは提示した候補だけにする**: OQ-089 の答え「b」と食い違う。
- **候補の提示をなくし、地図の空き家だけで選ぶ**: 地図を見られない人・押しにくい人と、配置の定義にない住所が選べなくなる（NFR-041）。答えは候補をなくすことを求めていない。
- **提示した候補をサーバーに覚え、候補でない住所は空き家の印から来たと確かめる**: どちらから来ても割り当ての規則は同じで、確かめても守れるものがない。表かセッションの状態が増える。
- **MVP でも退去のあとの住所を割り当てる**: 再割り当ては段階 3（ADR-0062）で、住所録の旧住所と手紙の扱い（`db.md` §3）を段階 3 の F-16 と一緒に決める。
- **行のある住所と同時の登録で違う状態コードを返す**: 前に使われたことを 1 回の要求で確かめられる道になる。登録の画面に出す文も変わらない。

## 決めていないこと

- 確認が済まない登録が住所を押さえる期限: OQ-046（持ち越し、M1 の前に決める）。空き家の印から選べるので、街のどの空き家でも先に押さえられる。押さえる期限はこの OQ で決める。
- 段階 3 で退去のあとの住所を候補に戻す規則と、そのときの空き家の印からの割り当て: ADR-0062（段階 3 の F-16）。
