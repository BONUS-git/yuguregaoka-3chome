# 0076 — 配達の通知は Web Push で送り、記録は配達回から 30 日

- 状態: 採用
- 日付: 2026-11-22

ADR-0025 を丸ごと置き換える。ADR-0025 の決定（ADR-0035 が直した箇所を含む）は、今の状態に書き直してこの ADR に移した。
変えたのは D7 の保持だけである。配達回（`delivery_runs`）は消さないことになった（ADR-0075）ので、通知の記録を配達回より先に消すという順番の決まりをなくした。

## 背景

`requirements.md` の FR-028 は、配達のあとに住民へプッシュ通知を送るかどうかを決めていなかった（OQ-002）。
2026-11-19、マスターが OQ-002 に次のとおり答えた（原文）。

> 通知あり（内容：郵便の件数を含む）

通知の数え方と文面は、OQ-042 の答え（2026-11-19、ADR-0035）で決まった。新聞と手紙で通知を分ける。

答えを実装するには、送る時刻・手段・購読の単位・送り先の検査・冪等性・保持を決める必要がある。
これらは技術と設計の事柄なので秘書が決め、ここに残す。

ADR-0075 で、配達回（`delivery_runs`）の行は消さないことになった。通知の記録（`delivery_notifications`）は配達回を外部キーで指す。
配達回が残るので、記録を消すときに配達回より先に消す決まりは要らなくなった。

## 決定

1. **D1 通知と中身**（マスターの答え。ADR-0035 の D4・D5）: 配達が済んだら住民に通知を送る。通知は新聞と手紙で分ける。
   - 新聞は「新聞が配達されました！」（件数なし）。
   - 手紙は「手紙が配達されました！（N通）」。N は、その回にその住民に届いた手紙の数。
   - 手紙が 0 通の住民には手紙の通知を送らない。
   - どちらにも差出人・本文・住所は載せない。
2. **D2 送る時刻**: J15 `notify.delivery`（`async.md` §4）が送る。配達回ごと・購読ごとに、新聞と手紙を 1 回ずつ送る（ADR-0035 の D11）。
   - 新聞の通知は、J5 が公開と同じトランザクションで積む。休刊の回にも送る（郵便受けには休刊の印が届く）。
   - 手紙の通知は、J0 がその住民の手紙の枠の時刻を過ぎてから積む。
   - 期限: 新聞は公開（`delivery_runs.finished_at`）から、手紙は枠の時刻から、30 分 [assumed] を過ぎたら送らない。Web Push の TTL も 30 分。
   - 手紙が届くたびには送らない。`skipped` の便では送らない。持ち越した手紙は、次の便の件数に入る。
   - 通知は定時の配達を知らせるだけで、定時の外に物を届けない。これで P-1（即時性を持ち込まない、FR-030）は保たれる、と解釈する。
3. **D3 手段**: Web Push（VAPID。中身は暗号化）を使う（FR-102）。ネイティブアプリは作らない（ADR-0009 のまま）。
   送信は worker の C11（`architecture.md` §2）が、アダプタを通して行う。テストではモックのプッシュ送信を使う。
4. **D4 購読の単位**: 端末（セッション）ごとに 1 つ。住民がその端末のブラウザで通知を許可したときだけ購読を作る。
   セッションが無効になったら（ログアウト・強制ログアウト・期限切れ・退去）、その購読も消す（ADR-0019）。
5. **D5 件数を載せる場所**: 件数は通知の中身にだけ載せる。API の応答には件数を足さない（ADR-0014 の決定 3）。
   API が持つプッシュ通知は、この通知だけである（ADR-0014 の決定 2）。WebSocket・SSE・ロングポーリング・
   「新着があるか」を問い合わせるエンドポイントは作らない。
   件数は本人だけに届き、他の住民と比べ合うものではないので、P-2（数値の評価を持ち込まない）には当たらない、と解釈する。
6. **D6 送り先の検査（SSRF 対策）**: 購読の `endpoint` は住民が渡す値なので、登録のときと送るときに検査する。
   - `https` だけを受け付ける。
   - 許可するプッシュサービスのホストの一覧を持つ（値は `environment.md` で決める）。
   - 名前解決のあとに、プライベート・ループバック・リンクローカルのアドレスを宛先にしない。
   - リダイレクトに従わない。時間切れは短くする（5 秒 [assumed]）。
   - 検査で外れた `endpoint` は、登録の API が 400 で拒む（`api.md` §7）。
7. **D7 冪等性と保持**:
   - 送った記録を `delivery_notifications`（`db.md` §2）に持つ。`kind`（`newspaper` / `letter`）を持ち、`UNIQUE(delivery_run_id, push_subscription_id, kind)` で重ねない（ADR-0035 の D12）。
   - 記録は、指している配達回の `finished_at` から 30 日 [assumed] で J14 が消す（`async.md` §4 J14・ADR-0075）。配達回の行は消さない（ADR-0075）ので、消す順番の決まりは置かない。
   - 購読 `push_subscriptions` と送った記録は、購読を消すときと退去のときに即時に消す。
8. **D8 段階**: MVP の M3（`roadmap.md` §4）で作る。受け入れ条件は A-15。
9. **D9 要求の区分**: ADR-0024 の決定 5 に従い、FR-028・FR-102 は `[inferred]`（マスターの答え OQ-002・OQ-042 より）とし、根拠にこの ADR と ADR-0035 を書く。

## 理由

- 通知を送ることと件数を含めることは、マスターの答え（上の原文）による。構想の意図はマスターにしか決められない。
- 配達回ごとに新聞と手紙を 1 回ずつ送れば、住民が受け取るのは「朝便・夕便が来た」という定時の知らせだけになる。
  手紙ごとに送るより P-1 に近い。
- Web Push はブラウザで受けられ、今の構成（Web だけ、ADR-0009）のまま足せる。中身は暗号化されるので、
  プッシュサービスに件数が平文で渡らない。
- 端末ごとの購読にすれば、ログアウトした端末に通知が届かない。セッション（ADR-0019）と同じ単位で消せる。
- 件数を API に載せないことで、ADR-0014 の「数値を返さない」の範囲を広げずに済む。
- 送り先を住民が決められる値は、検査しなければ worker から内部のネットワークへ届く経路になる。
- 記録の保持の起点を配達回の `finished_at` にすると、同じ配達回を指す記録はすべて同じ回の J14 で消える。
  配達回の行は残る（ADR-0075）ので、外部キーが削除を止めることはなく、順番を決めておく必要がない。

## 代わりの案（選ばなかった理由）

- **手紙が届くたびに即時に通知する**: 定時の外に知らせが届き、P-1 に反する。
- **メールで知らせる**: 本番のメール送信サービスはマスターの事前承認を得て選ぶもので、まだ選んでいない（ADR-0033。進め方は OQ-049）。朝夕に毎日メールを送ると量が多く、費用にもかかわる。
- **ネイティブアプリを作ってプッシュ通知を送る**: ADR-0009 のとおり Web だけで MVP の体験は成り立つ。作る物が増える。
- **新着の件数を問い合わせる API を作り、クライアントが数える**: ADR-0014 の決定 2・3 に反し、即時性と数値を API に持ち込む。
- **通知の記録を配達回と同じ期間だけ持つ（配達回と一緒に残す）**: 記録は購読（端末）を指し、住民にひもづく。配達回のように残し続けると、個人情報を最小限にすること（NFR-002）に反する。

## 決めていないこと

- 一部のモバイルのブラウザでは、ホーム画面に加えた Web アプリでないと通知を受けられない。この制約は住民向けの案内に書く（実装で決める）。
- 許可するプッシュサービスのホストの一覧と、VAPID の鍵の置き場所: `environment.md` §6.4 で決める。
- 新聞の中身は ADR-0039 以降で決める（OQ-051 → 決定。残りは OQ-058〜OQ-062）。
