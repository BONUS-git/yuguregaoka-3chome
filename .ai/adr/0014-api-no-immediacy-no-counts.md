# 0014 — API は即時性と数値を返さない

- 状態: 採用
- 日付: 2026-11-19

## 背景

構想の 2 つの基本方針（P-1: 即時性を持ち込まない、P-2: 数値の評価を持ち込まない）を
API の形として具体化する必要があった。

関係する要件: FR-017（既読なし）・FR-030（配達は定時のみ）・FR-038（反応数なし）・
FR-044（閲覧数なし）・FR-055（住所録の登録数なし）、OQ-002 の暫定（プッシュ通知なし）。

## 決定

1. **API の形は HTTPS + JSON**（プレフィックス `/api/v1`）。REST 的な資源の区切り。
   スキーマは Fastify の JSON Schema で定義し、TypeScript の型をクライアントと共有する（ADR-0009）。

2. **リアルタイムの経路を作らない**。
   WebSocket・SSE・ロングポーリング・プッシュ通知は提供しない。
   「新着があるか」を問い合わせるエンドポイントも作らない。

3. **数値を返さない**。
   既読フラグ・未読件数・総件数・閲覧数・反応数・住所録への登録数・
   1 日の上限の残り回数はいずれも返さない。

4. **ページングは総件数なしのカーソル方式**。
   `{ items, next_cursor }` を返す。`total` フィールドは持たない。
   limit は既定 20・最大 50 [assumed]。

5. **受取人に見せるのは配達回**。
   手紙・新聞の「いつ届いたか」は、書いた時刻ではなく配達回 ID（例: `2026-11-19-morning`）で示す。

6. **エラーの形を 1 つにそろえる**。
   `{ "error": { "code": "...", "message": "...", "details": {} } }`
   スタックトレース・内部 UUID は返さない。

## 理由

- 構想（P-1・P-2）に合わせるため。
- 数を返さなければ、クライアントの側で数の評価が育たない。
- リアルタイム経路がない分、キャッシュと監視が単純になる（NFR-055）。
- カーソルページングは大きなテーブルでも性能が劣化しない（オフセット方式と比較）。

## 代わりの案（選ばなかった理由）

- **SSE・WebSocket**: P-1 に反する。
- **総件数付きのオフセット方式**: P-2 に反し、大きなテーブルでの `COUNT(*)` は性能も劣る。
- **GraphQL**: クライアントが必要なフィールドだけ取得できる利点があるが、
  スキーマ管理・認可・ページング設計が複雑化する。今の想定規模（ADR-0012）では不要（NFR-055）。
- **未読の印**: FR-017 に反する。

## 影響

- `api.md` §3・§6・§8 がこの ADR の具体化。
- async.md・security.md の設計がこの方針の前提を受け継ぐ。
- OQ-002 の回答によってはプッシュ通知経路を追加する可能性がある（P-1 との整合性を別途確認）。
