# 0028 — 架空の街の地図は、1 枚の静的な画像として MVP（M1）で作る。API・DB・ジオデータは持たない

- 状態: 採用（D1 (b) のうち「全住民で共有する 1 枚の画像」は ADR-0037 で暫定から決定にした。住民ごとに中身を変えないことは OQ-054 の暫定。白黒は ADR-0037 の D2）
- 日付: 2026-11-19

## 背景

構想（brief §2 の共通機能）に「架空の街・地図・住所」とあるが、`requirements.md` に地図の要件 ID がなく、
`features.md` の F-19（架空の街の地図）は段階が未確定だった。`open-questions.md` の OQ-005 でマスターに、
地図の具体的な形（静的な画像か、インタラクティブか、住民が自分の住所の場所を見られるものか）と、
どの段階で実装するかを聞いていた。暫定は「段階未確定のまま（作らない）」で、`roadmap.md` §8 と ADR-0022 の決定 6 では「止まる」に入れていた。

2026-11-19、マスターが OQ-005 に次のとおり答えた（原文）。

> 静的な画像として実装し、開発の初期段階で行う

答えに書かれていないこと（住民が自分の住所の場所を見られるものか）は決めず、OQ-044 にした。

（追記 2026-11-19）OQ-044 の答え「全ユーザーで共有して、知り合いの家には印ができるようなものが理想。ほんとはゲーム風にしたいが、現時点では１枚の画像。白黒の地図が今のイメージ」で、
D1 (b) のうち「全住民で共有する 1 枚の画像」は決定になり、画像は白黒になった（ADR-0037 の D1 (a)・D2）。住民ごとに中身を変えないことは OQ-054 の暫定（ADR-0037 の D1 (b)）。
印（知り合いの家・自分の住所・登録のときの候補）は OQ-054（要回答）に、ゲーム風の地図は OQ-055（持ち越し）に移った（ADR-0037 の D3・D4）。

## 決定

1. **D1 静的な画像（全住民で共有は ADR-0037 の D1 (a) で決定。住民ごとに変えないは OQ-054 の暫定）**:
   - (a) マスターの答え: 地図は 1 枚の静的な画像とする。対話的な操作（拡大・移動・クリック・検索）はしない。
   - (b) マスターの答え OQ-044（2026-11-19、ADR-0037 の D1 (a)）: 画像は全住民で共有する 1 枚の画像（土台）とする。
     住民ごとに中身を変えない（バイト単位で同じ）のは OQ-054 の暫定（ADR-0037 の D1 (b)）で、答えで変わる。
     住所の場所の印（知り合いの家・自分の住所・登録のときの候補）は今は付けない（ADR-0037 の D3。OQ-054 の暫定で、答えで変わる）。
   - ログインしていない人に地図の画面を出すか（ログインの前の画面に置くか）は、この ADR では決めない（公開の範囲に当たる。D3 の技術上の結果だけを書く）。
2. **D2 段階は MVP、マイルストーンは M1**: 段階は MVP（段階 1）とする（答えの「開発の初期段階」）。
   マイルストーンは M1（住所・アカウント）に置く（秘書の判断）。M0 は基盤だけで画面がなく、地図は住所と同じ「街と住所」の話だから。
3. **D3 API・DB・ジオデータ・外部サービスを持たない**: 地図のための API の経路・DB の表・住所のジオデータ（座標）・外部の地図サービスは持たない。
   画像は C1（Web クライアント）の静的なファイルとして、同じオリジンから配る（`architecture.md` §2）。
   技術上の結果として、画像のファイルは SPA の他の静的なファイルと同じく、セッションなしでも取れる（API の認証の範囲（`api.md` §4）の外）。
   そのため D4 のとおり、画像に住民や住所の割り当てにかかわる情報を入れない。地図の画面をログインの前に出すかは決めない（D1）。
4. **D4 載せないもの**: 画像に住民・入居の有無・空き家・数（住民数など）を描かない。区画は「番」まで描き、号までの住所（例: `2-5`）は描かない
   （`security.md` §7 の T-05 住所の列挙、P-2 数値の評価）。
5. **D5 出し方**: 画像は SVG とし、`<img>` で出す（インラインに埋め込まない）。SVG に `<script>`・イベント属性・外部への参照（外部の URL・フォント・画像）を入れない
   （`security.md` §7 の T-07）。
6. **D6 中身**: レポジトリの中で描いた架空の図とし、実在の地名・地図データ・他の地図の写しは使わない（CLAUDE.md の公開レポジトリの決まり）。
   画像は白黒（色相を持たない白・黒・灰色だけ）で描く（ADR-0037 の D2、マスターの答え OQ-044）。
   代替テキストを付ける（NFR-041。アクセシビリティの水準は OQ-033）。
7. **D7 区分**: ADR-0024 の決定 5 に従い、FR-103 は `[inferred]`（マスターの答え OQ-005（2026-11-19）より）とし、根拠にこの ADR を書く。

## 理由

- 静的な画像であること・初期段階で作ることは、マスターの答え（上の原文）による。
- 全住民で共有する 1 枚の画像にする（D1 (b)）のは、OQ-044 の答えの「全ユーザーで共有して」「現時点では１枚の画像」による（ADR-0037 の D1 (a)）。住民ごとに中身を変えないのは OQ-054 の暫定（ADR-0037 の D1 (b)）。
  同じ画像なら、住所と位置の対応を持たずに済み、地図から住所や住民の有無が漏れない。
- M1 に置くのは、住所（F-01）と同じマイルストーンで、住所の形（番・号）と地図の区画を一緒に確かめられるから。
  地図は API・DB を持たず、ほかのマイルストーンに依存しない。
- API・DB・ジオデータを持たないのは、静的な画像に要らないから（NFR-055 必要以上に複雑にしない）。外部の地図サービスは費用と外部への通信が要り、架空の街には使えない。
- `<img>` で出すと、SVG の中のスクリプトが動かない。インラインの SVG や `<object>` より XSS の面が小さい。

## 代わりの案（選ばなかった理由）

- **対話的な地図（拡大・移動・クリック）**: 答え（静的な画像）と食い違う。
- **住民ごとに自分の住所に印を付けた画像を出す**: OQ-005・OQ-044 の答えに書かれていない（OQ-054、ADR-0037 の D3）。住所と位置の対応が要り、住民ごとに画像が変わる。
- **地図を API で配る（`/api/v1/map`）**: 中身が全員に同じで、静的なファイルで足りる。経路を増やすと認証と権限の面が増える。
- **M0 に置く**: M0 は基盤だけで画面がない。
- **段階 2 以降に置く**: 答え（開発の初期段階）と食い違う。
- **PNG などのラスター画像**: 拡大で粗くなり、画像の中の文字（地名）を確かめるテストが書きにくい。SVG なら中身をテキストとして走査できる（A-16）。

## 決めていないこと

- 地図の上で住所の場所を示すか（全住民で共有する 1 枚の画像かは OQ-044 → 決定、2026-11-19、ADR-0037）: 印（知り合いの家・自分の住所・登録のときの候補）は OQ-054（要回答）。暫定は付けない（D1 (b)・ADR-0037 の D3）。
  答えで、住所と画像の上の位置の対応（持つか・どこに持つか）・FR-103・D1・D3・`roadmap.md` の M1 と A-16・`security.md` の T-05 が変わる。
- ゲーム風の地図: OQ-055（持ち越し、ADR-0037 の D4）。
- ログインしていない人に地図の画面を出すか: 決めない（D1）。画面の置き場所は M1 の画面の範囲に従い、ログインの前の画面に地図を足す場合は公開の範囲としてマスターに聞く。
- 代替テキストとアクセシビリティの水準: OQ-033（持ち越し、仮の目標は WCAG 2.2 AA）。
