# 0048 — 年齢は登録で必須にし、あとから変えられない。年は登録の日から 1 年ごとに進む。ほかの住民には、本人から手紙を受け取った住民にだけ見せる

- 状態: 採用
- 日付: 2026-11-20

## 背景

OQ-052 の答え（2026-11-20）で、年齢は住民が設定した値をそのまま使い、確かめないと決めた（ADR-0041 の D2）。
OQ-063 の答え（2026-11-20）で、年齢による違いは作らないと決めた（ADR-0047）。答えは「データ構造として年齢を持っておくこと」「年齢によって（属性として）表示が変わる可能性」を意図に含むとしていた。
年齢の項目の扱いは答えに書かれていなかったので、`open-questions.md` の OQ-064 で次の 4 点を聞いていた。
(1) 登録のときに年齢の入力を必須にするか。(2) あとから変えられるか。(3) ほかの住民に見せるか（見せるなら、年齢の属性で何の表示が変わるか）。(4) 年とともに進むか。
暫定は、年齢の項目と `residents` の列を置かない（ADR-0041 の D5・ADR-0047 の D5）だった。

2026-11-20、マスターが OQ-064 に次のとおり答えた（原文）。

> (1) 必須
> (2) 変更は不可
> (3) 一定条件で見せる。一定条件は安全性に基づき秘書が決定する
> (4) 進む。誕生日の情報も新聞に載せたら面白そう

答えから読み取れることと、読み取れないことを分ける。

| 答え | 読み取れること（決定） | 読み取れないこと（新しい OQ） |
|---|---|---|
| 1 | 登録で年齢の入力を必須にする。入れなかった住民の扱いは要らない | 値の範囲 → 秘書の判断（D1） |
| 2 | 年齢はあとから変えられない | 間違えたときの直し方 → 秘書の判断（D2、退去して登録し直す） |
| 3 | ほかの住民に、一定の条件のときだけ見せる。条件は安全性に基づいて秘書が決める | 条件の中身 → 秘書の判断（D4）。年齢の属性で何の表示が変わるか（OQ-064 の (3) の後半）は答えにない → OQ-078（持ち越し） |
| 4 | 年齢は年とともに進む | 何を基準に進めるか → 秘書の判断（D3、登録の日） |
| 4 | 誕生日の情報を新聞に載せる案がある（「面白そう」） | 誕生日を集めるか・新聞に何を載せるか・誰の新聞に載せるか・本人が断れるか → OQ-077（要回答） |

答えは、ADR-0041 の D5（年齢の項目と列は置かない）と ADR-0047 の D5 のうち D5 を待つ部分、ADR-0027 の D3 のうち「年齢を集めない」を置き換える。
ADR-0041 の D2〜D4・D6（年齢は住民の設定をそのまま使い確かめない・危険な機能は設けない・生年月日は集めない・登録に年齢制限を置かない）と、
ADR-0047 の D1〜D4（年齢による違いは作らない）は変わらない。

## 決定

区分は ADR-0024 の決定 5 に従う。

1. **D1 登録で必須**（答え 1、`[inferred]`）: `POST /api/v1/registrations` は `age`（整数）を必須で受け取る。
   - `age` がない・整数でない・範囲の外なら 400（`validation_failed`）。範囲は 0〜999（`[assumed]`、秘書の判断。架空の年齢（ADR-0041 の D2）を許すために広く取る）。
   - 既定値と「未設定」の状態は置かない。
   - 登録の画面（C1）は、送る前に「年齢はあとから変えられません」と示して確かめる。
   - 年齢は確かめない（ADR-0041 の D2 のまま。本人確認の書類・外部の年齢確認・保護者の同意は設けない）。
2. **D2 あとから変えられない**（答え 2、`[inferred]`）: `PATCH /api/v1/me` は `age` を受け取らない。要求に `age` があれば 400（`validation_failed`）で、値は変わらない。
   - モデレーターと運用者の CLI を含め、年齢を書き換える経路をどこにも作らない。
   - 直したい住民は、退去して登録し直すしかない（秘書の判断）。
   - 年齢で守りは変わらない（ADR-0047）ので、変えられないことは ADR-0036 の D3（住民を守る制限は住民が自分で外せる設定にしない）とはぶつからない。
3. **D3 年とともに進む**（答え 4、`[inferred]`。進め方は秘書の判断）: `residents` に 2 列を足す。
   - `age_at_registration smallint NOT NULL`（CHECK 0〜999）: 登録のときに入れた年齢。
   - `age_base_date date NOT NULL`: 登録した日の JST の日付。
   - 今の年齢 = `age_at_registration` + `age_base_date` から JST の日付で満了した年数。基準の日が 2/29 なら、うるう年でない年は 3/1 に 1 つ上がる。
   - 年齢は C2 が読むときに時計のアダプタで計算する。worker のジョブも、列の書き換えも持たない。上限の 999 を超えても今の年齢はそのまま返す（CHECK は登録のときの値だけに掛かる）。
   - 誕生日は集めない（D5）ので、基準は登録の日にする。
4. **D4 見せる条件**（答え 3、秘書に任された判断。`[inferred]`）:
   - 本人には、`GET /api/v1/me` が今の年齢を返す。
   - ほかの住民には、`GET /api/v1/profiles/{address}` が、次をすべて満たすときだけ `age` を返す。満たさないときは `age` の項目そのものを返さない（`null` も返さない）。
     - (a) 見る住民の `mailbox_items`（`kind = 'letter'`、`visible_at` を過ぎたもの、`deleted_at IS NULL` の行だけ）に、プロフィールの住民が送った手紙（`letters.sender_id`）が 1 通以上ある。見る住民が郵便受けから削除した手紙は数えない（削除で `mailbox_items`・`letters` は消える、ADR-0013・FR-099）。
     - (b) その手紙の `created_at` が、プロフィールの住民の今の居住記録（`tenancies.is_current`）の `started_at` 以後である。
     - (c) 見る住民が、プロフィールの住民をブロック（`blocks`）していない。
   - プロフィールの住民が見る住民をブロックしても、年齢の見え方は変えない（(a)〜(c) だけで決める）。ブロックした側の年齢がブロックされた側から消えると、ブロックされたと分かる（`security.md` T-06・ADR-0015）。
     ブロックの後も、ブロックされた側の郵便受けに残っている手紙で (a) を満たすあいだは見え続け、その手紙をすべて削除すると見えなくなる。
     ブロックした側から手紙が新しく届くのは、ブロックした側が自分で出したときだけ。
   - 年齢を見せる事実だけを持つ表（見る住民・見られる住民・居住記録）は足さない。
   - 次には出さない: 住所録・地図・掲示板・新聞・マッチング・通知・検索、モデレーターと運用者の画面、LLM・ログ・ジョブのペイロード。
   - 見せるかどうかの住民の設定は置かない。条件は全員に同じ。
   - 年齢で並べる・探す経路は作らない（`api.md` §8）。
5. **D5 誕生日と新聞は決めない**: 答え 4 の「誕生日の情報も新聞に載せたら面白そう」は案で、集めるか・何を・誰に載せるかは答えにない。OQ-077（要回答）で聞く。
   - **暫定（OQ-077 の答えまで）**: 誕生日を集めない。新聞に誕生日の欄を置かない。M5 の前に答えを確かめる。
6. **D6 年齢の属性で変わる表示は決めない**: OQ-064 の (3) の後半（年齢の属性で何の表示が変わるか）は答えにない。OQ-078（持ち越し）にし、暫定は作らない（D4 の `age` の数値を出すほかに、年齢で変わる表示は置かない）。
   表示が変わっても、権限と照合には年齢の条件を持たせない（ADR-0047）。
7. **D7 置き換える決定**: 次をこの ADR で置き換える。
   - ADR-0041 の D5（年齢の項目と列は置かない）。
   - ADR-0047 の D5 のうち、ADR-0041 の D5 の待つ条件を OQ-064 にした部分。
   - ADR-0027 の D3 のうち「年齢を集めない」（ADR-0041 で置き換え、D5 で待っていた部分）。生年月日を集めないことは変わらない。
   - ADR-0041 の D2〜D4・D6 と、ADR-0047 の D1〜D4 は変えない。
8. **D8 保存と消去**: 年齢は平文で持つ（暗号化するのは手紙の本文、ADR-0006）。退去で `residents` の行ごと即時に消す（ADR-0013）。ログ・メトリクス・エラー報告には残さない（`security.md` §2.5）。
   要求の区分: FR-008 と FR-113 を直す（`[inferred]`、マスターの答え OQ-064（2026-11-20）より。範囲の 0〜999 は `[assumed]`）。

## 理由

- D1・D2・D4 の「一定条件で見せる」・D3 の「進む」は答えのとおり。
- D1 の範囲を広く取るのは、架空の年齢を許す（ADR-0041 の D2）ため。上限は、型と入力の誤りを弾くためだけに置く。
- D2 の直し方を退去と登録のし直しにするのは、答えが「変更は不可」で、例外の経路（モデレーターの書き換えなど）を作ると、その経路が書き換えの手段になるため。
- D3 の基準を登録の日にするのは、誕生日を集めない（D5 の暫定・ADR-0041 の D4）まま、答えの「進む」を満たせるため。読むときに計算するので、ジョブの失敗で年齢がずれることがなく、テストは偽の時計で済む。
- D4 の条件は、次の安全性による。
  - 住所を順に引いて年齢で住民を探すこと（`security.md` T-05）ができない。見るには、相手から手紙を受け取っている必要がある。
  - 見せる相手は、年齢の持ち主が自分で手紙を出したかどうかで決まる。手紙を出していない住民には知られない。
  - (b) によって、引っ越した住民の新しい住所が、前の住所から届いた手紙と結び付かない（ADR-0003）。
  - (c) によって、見る住民が自分でブロックした相手の年齢は出さない。見る住民が自分で決めたことなので、相手には何も漏れない。
  - プロフィールの住民がしたブロックを条件に入れないのは、ブロックを相手に気づかせない（T-06・ADR-0015）ことを、ブロックされた側から年齢を隠すことより優先するため。
    ブロックされた側は、ブロックの前に手紙を受け取って年齢をすでに知っている。年齢は登録の日から決まった進み方をする（D3）ので、後から隠しても守りにはほとんどならない。一方、消えればブロックが露見する。
    新しく知られることは、ブロックした側が手紙を出さないことで防げる。引っ越せば (b) で前の手紙は数えられなくなる。
  - 削除した手紙を数えないのは、削除で `mailbox_items` の行と（受取人全員が削除すれば）`letters` の行が消え（ADR-0013・FR-099）、判断に使える行が残らないため。
    年齢のために削除した行や「見せてよい」という事実を残すと、削除した手紙の痕跡を残すことになり、データの最小化（NFR-002）とぶつかる。
    郵便受けを片付けると相手の年齢が見えなくなるが、見る住民が自分でしたことなので、相手には何も漏れない。条件は届いて残っている手紙の事実だけで決まり、読んだかどうか（FR-017）には寄らない。
- D5・D6 は、答えに書かれていないことを決めないため（CLAUDE.md）。誕生日は個人情報の収集と公開の範囲にかかわるので要回答、表示の変化は技術と設計で決められるので持ち越しにする。
- D8 は、年齢が個人情報で、使い道がプロフィールの表示だけだから（データ最小化、NFR-002・NFR-010）。

## 代わりの案（選ばなかった理由）

- **全住民に見せる**: 住所を順に引くと年齢で住民を探せる（T-05）。答えの「一定条件で」と食い違う。
- **互いに住所録に入れた住民に見せる**: 年齢が見えたことで、相手が自分を住所録に入れたと分かってしまう。誰が自分を住所録に入れたかは知らせない（FR-058、OQ-040 の暫定、`api.md` §8）に反する。
  （追記 2026-11-20）ADR-0049 で、互いに住所録に入れた住民（知り合い）は `acquainted` で互いに見えるようになり、この理由はなくなった。決定（本人から受け取った手紙が郵便受けに残っている住民に見せる、D4）は変えない。
  手紙は知り合いにだけ出せるので、D4 の条件を満たすのは、手紙を出した時点で知り合いだった住民だけになる。
- **見せるかを住民の設定にする**: 条件は安全性に基づいて秘書が決めることになっており、住民が守りを外せる設定は置かない（ADR-0036 の D3）。
- **年代だけ見せる**: 答えの「見せる」は年齢を見せることと読める。年代で丸めるかは表示の変化（OQ-078）で決める。
- **誕生日を集めて基準にする**: 誕生日を集めるかは OQ-077（要回答）で、答えを前提にしない。月日と年齢がそろうと生年月日に近くなる（ADR-0041 の D4）。
- **どちらの向きのブロックでも年齢を隠す**: ブロックされた側から年齢が消え、ブロックされたと分かる（T-06・ADR-0015 に反する）。年齢はすでに知られているので、隠しても守りにはほとんどならない。
- **ブロックの前から見えていた住民にだけ見せ続け、ブロックの後に初めて条件を満たした住民には隠す**: ブロックの時刻と見え方の組み合わせから、ブロックが推し量れる。条件が増え、確かめることも増える。
- **削除した `mailbox_items` の行を年齢のために残す／年齢を見せてよいという事実だけを持つ表を足す**: 削除した手紙の痕跡が残り、FR-099・データの最小化（NFR-002）とぶつかる。保持と退去での消去の決まりも増える。
- **毎年ジョブで列を書き換える**: ジョブの失敗・やり直しで年齢がずれうる。読むときの計算で足りる。
- **モデレーターが年齢を直せる経路を作る**: 答え 2「変更は不可」と食い違い、モデレーターの内部不正（T-12）の手段が増える。

## 決めていないこと

- 誕生日を集めて新聞に載せるか（集めるか・必須か・架空でよいか・変えられるか・何を・誰の新聞に・本人が断れるか）: OQ-077（要回答。暫定は集めず載せない。M5 の前に答えを確かめる）。
- 年齢の属性で何の表示が変わるか: OQ-078（持ち越し。マスターが決める。年齢で変わる表示を足す前に聞く。暫定は作らない）。
- 商店・団体のアカウント（段階 3、ADR-0029。登録を通らない）に年齢を持たせるか: 担当者のログインと主体（OQ-069、持ち越し）とあわせて決める。
- 適用法令が年齢の収集と表示について何を求めるか: OQ-032（持ち越し）。
