# 0021 — 手紙の暗号鍵に版を付けて入れ替える。AAD に手紙の ID を含める

- 状態: 採用
- 日付: 2026-11-19

## 背景

ADR-0006 では「手紙はサーバー鍵（KMS 管理の対称鍵）で保存時に暗号化する」と決定している。
しかし ADR-0006 は次の点を未定のままにしていた。

1. **鍵の入れ替え（ローテーション）**: 鍵が漏えいした場合や定期的な入れ替えをどうするか。
2. **付加データ（AAD）**: AES-256-GCM の AAD に何を含めるか。
3. **手紙ごとの鍵**: 1 通の手紙に 1 つの鍵を持つ方式（per-letter key）の採否。

また ADR-0013 の「代わりの案」で「手紙を住民ごとに暗号化して退去時に鍵を破棄する」が
不採用になっており、鍵の扱いの方針を明確にする必要があった。

## 決定

### 鍵の版管理

手紙の暗号化鍵に **版番号**（`key_version`）を付けて管理する。

- 現在有効な版の鍵で暗号化する。
- `letters` テーブルに `body_key_version` カラムを追加し、どの版の鍵で暗号化されたかを記録する。
- 鍵を新しい版に更新したあと、古い版で暗号化されたレコードを順次再暗号化する
  （次の配達便の前までに完了させることを目標とする [assumed]）。
- 古い版の鍵は、その版で暗号化されたレコードがすべてなくなったら無効化する。

### 付加データ（AAD）

AES-256-GCM の AAD に **手紙の ID**（`letter_id`）を含める。

- こうすることで、暗号文と letter_id の対が一致しない場合に復号が失敗する。
- 別の手紙の暗号文を別の手紙の行に移し替える攻撃（コピー＆ペースト攻撃）を防ぐ。

### 手紙ごとの鍵（per-letter key）

採用しない。ADR-0013 と同じ理由（鍵破棄だけでは DB のレコードが残り、管理が複雑になる）により
不採用とする。

## 理由

- **版管理を導入する理由**: 鍵が漏えいした場合に影響を最小化できる。
  版で管理することで、漏えいした版のデータだけを再暗号化できる。
  定期的なローテーションも版単位で行える。
- **AAD に letter_id を入れる理由**: AES-256-GCM 自体は認証付き暗号だが、
  暗号文の行を入れ替える攻撃（同じ鍵で暗号化された別レコードのデータを当てはめる攻撃）を
  スキーマレベルで防げる。付加データとして ID を入れるコストは低い。
- **per-letter key を採用しない理由**: ADR-0013 で既に記録したとおり。
  鍵が住民ごと・手紙ごとに増えると、鍵の管理コストが急増する。
  退去時に鍵を破棄しても DB のレコード自体は残るため、完全な削除にならない。
  ADR-0013 の退去処理（物理削除・NULL 化）で十分な対応が取れる。

## 代わりの案（選ばなかった理由）

**版管理なしの単一鍵**: 鍵が漏えいしたとき全手紙の暗号文が危険にさらされる。ローテーションができない。
**per-letter key**: 管理コストが高く、ADR-0013 の退去処理との整合性が難しい（ADR-0013 参照）。
**AAD を使わない**: 暗号文の移し替え攻撃を防げなくなる。コストが低いため採用する。

## 影響

- DB 設計: `letters` テーブルに `body_key_version` カラムを追加する（db.md §2 の `letters`）。
- 非同期処理: 鍵の入れ替え後に旧版で暗号化されたレコードを再暗号化するジョブを設ける
  （環境構成の設定チケット（`environment.md`）で詳細を書く）。
- 秘密管理: security.md §6.3 の鍵の入れ替え手順が本 ADR の版管理方針を引き継ぐ。
- ADR-0006: 本 ADR は ADR-0006 の「影響」節に書かれた「鍵管理（KMS）の方針と鍵ローテーション手順」を
  具体化するもの。ADR-0006 自体は置き換えない（at-rest 暗号化の決定はそのまま有効）。
