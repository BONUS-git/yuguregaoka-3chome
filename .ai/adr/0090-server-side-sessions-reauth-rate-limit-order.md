# 0090 — セッションと再認証の API、確かめる順と流量

- 状態: 採用
- 日付: 2026-11-25

ADR-0081 を丸ごと置き換える。ADR-0081 の決定（サーバー側のセッション・複数の端末・セッションの一覧と取り消し・無効にする方法・再認証・モデレーターの二要素認証・パスワードとメールアドレスの変更）は、今の状態に書き直してこの ADR の D1〜D7 に同じ番号で移した。
新しく決めたのは、確かめる順番に流量の制限を入れること（D5）と、再認証の流量の制限を住民ごとの 10 回／15 分にすること（D5。値の正本は ADR-0088 の D2・`security.md` §3.5）。表の定義は ADR-0102 を指す（D1・D6）。K-010（`triage.md` 仕分け 3、YGO-027）と、その見直しの指摘による。

## 背景

OQ-036「複数デバイス同時アクセスへの対応」は、`security.md` で OQ-028（認証方式、ADR-0080）とあわせて決める持ち越し項目だった（FR-100、FR-098）。
セッション管理の方式として、サーバー側のセッション（Cookie にセッション ID、中身は DB）と JWT（署名付きトークン、サーバーに状態を持たない）が考えられた。

流量の制限の値と数え方（ADR-0088）を決めると、要求のどの段で数えるかを、再認証・ロール・二要素認証の確かめと 1 つの順番に並べる必要が出た。
再認証の流量の制限は「ログインと同じ」と書かれていたが、ログインはメールアドレスごとと IP ごとに数え（ADR-0088 の D2）、再認証はログインしている住民の操作なので、同じ主体では数えられない。

## 決定

### D1 セッションの方式

**サーバー側のセッション**を採用する。

- セッション ID を乱数で作り、`__Host-session` Cookie に入れる。Cookie は `HttpOnly`・`SameSite=Lax`・`Secure`。
- セッションの中身（住民 ID・作成日時・最終操作日時・再認証日時・二要素認証の日時・一覧で見せる識別子）は DB の `sessions` に置く。表の定義は ADR-0102 の D1（`db.md` §2）。
- 有効期限: **操作なしで 30 日、発行から 90 日** [assumed]。
- 認証の確かめは、行があり・`invalidated_at IS NULL`・有効期限の中のセッションだけを通す。

### D2 複数の端末

同時に複数の端末でセッションを持つことを**許す**。住民は自分のセッションを一覧で見て、1 つずつ取り消せる（D3）。

### D3 セッションの一覧と取り消し

| メソッド | パス | 決めたこと |
|---|---|---|
| `GET` | `/api/v1/sessions` | 自分の有効なセッションを返す。各項目は `id`・`created_at`・`last_seen_at`・`current`（今のセッションか）だけ。`id` は Cookie の値とは別の識別子 [assumed]。IP アドレスと端末の情報は持たず返さない [assumed]。ページングせず、件数は返さない |
| `DELETE` | `/api/v1/sessions/{id}` | 自分のセッションを 1 つ取り消す（行を消す）。204。ほかの住民の `id`・存在しない `id` は 404。今のセッションを指せばログアウトと同じ |
| `DELETE` | `/api/v1/sessions/current` | ログアウト。今のセッションの行を消す。204 |

セッションの取り消しには再認証を求めない [assumed]（取り消しは守る側の操作なので）。

### D4 セッションを無効にする方法

- `invalidated_at` を付けるのは、退去の受付（`DELETE /api/v1/me`）だけ（ADR-0091 の D7）。行は J7 の手順 0 で消す（ADR-0091 の D8）。
- ほかの無効化はどれもセッションの行を消す: ログアウト、セッションの取り消し（D3）、パスワードの再設定の完了（その住民のすべて、ADR-0080 の D7）、パスワードの変更（今のセッションのほかのすべて、D7）、強制ログアウト、二要素認証の解除（そのモデレーターのすべて、D6）。
- **強制ログアウト**は運用者の CLI だけで行い、その住民のセッションの行をすべて消す。HTTP の経路（admin の経路を含む）は作らない。住民への処置の内容は ADR-0032 でマスターが後で決めるので、モデレーターの経路にしない。
- セッションの行を消すとき・`invalidated_at` を付けるときは、そのセッションの通知の購読（`push_subscriptions`）と送った記録（`delivery_notifications`）を同じトランザクションで消す（ADR-0076）。有効期限の切れた行は J14 が購読と一緒に消す（ADR-0091 の保持期間）。

### D5 再認証と確かめる順番

- **条件**: 直近 10 分以内に、そのセッションでパスワードを入れていること [assumed]。`sessions.reauthenticated_at` が `now() - interval '10 minutes'` より新しいかで確かめる。ログインした時刻も `reauthenticated_at` に書く。
- **経路**: `POST /api/v1/sessions/current/reauthentication` が `password` を受け取る。正しければ `reauthenticated_at` を書いて 204。違えば 401 `reauthentication_failed` で、セッションは残す（ログアウトさせない）。
- **再認証の流量の制限**: 住民ごとに 10 回／15 分 [assumed]（ADR-0088 の D2。ログインのメールアドレスごとの上限と同じ値だが、数える主体は住民）。成功も失敗も数え、超えたら 429 `rate_limited`。
- **再認証が要る操作**（MVP の 6 つ。段階 2 のエクスポート（F-15、`roadmap.md` S2-6）は作るときに足す）:
  1. `DELETE /api/v1/me`（退去）
  2. `PUT /api/v1/me/password`（D7）
  3. `PUT /api/v1/me/email`（D7）
  4. `POST /api/v1/me/second-factor`（D6）
  5. `POST /api/v1/admin/reports/{id}/actions`（通報への操作。投稿の取り下げを含む）
  6. `POST /api/v1/admin/held-letters/{id}/actions`（確認待ちの手紙への操作）
- 条件を満たさなければ 401 `reauthentication_required` を返し、何も変えない。
- **確かめる順番**（認証の要る経路）: 認証 → 流量の制限（ADR-0088）→ ロールと二要素認証（admin の経路、D6）→ 再認証 → 入力の検証と対象の確かめ [assumed]。認証なしの経路は、流量の制限を最初に確かめる。

### D6 モデレーターの二要素認証

- モデレーターは TOTP（RFC 6238）の二要素認証を登録する [assumed]（ADR-0020）。
- **登録**: `POST /api/v1/me/second-factor` が TOTP の秘密（`otpauth://` の URI）を 1 度だけ返す（201）。再認証が要る（D5）。まだ有効にしていなければ、呼び直すと秘密を作り直す。有効にしたあとは 409 `conflict`。モデレーターでない住民には 404。
- **有効にする**: `POST /api/v1/me/second-factor/confirmation` が `totp_code` を受け取る。正しければ有効にし、今のセッションを二要素認証を済ませたものにして 204。違えば 400 `validation_failed`。
- **ログイン**: 二要素認証を有効にしたモデレーターは、ログイン（`POST /api/v1/sessions`、ADR-0080 の D5）で `totp_code` も送る。正しいパスワードを送って `totp_code` がなければ 401 `second_factor_required` を返し、セッションを作らない。コードが違えば、パスワードの誤りと同じ 401 `unauthenticated`。両方正しければ、二要素認証を済ませたセッションを作る。
- **admin の経路**: `/api/v1/admin/*` は、モデレーターのロールがあり、二要素認証を済ませたセッションだけが呼べる。済ませていなければ 403 `forbidden`。ただし、手紙を返す経路と確認待ちの手紙への操作（`GET /api/v1/admin/reports/{id}/letter`・`GET /api/v1/admin/held-letters/{id}`・`POST /api/v1/admin/held-letters/{id}/actions`）は、今の条件のとおり 404 を返す（存在を明かさない、ADR-0072・ADR-0069 の D5）。
- **作り直しと解除**: 端末をなくしたときの作り直しと解除は運用者の CLI だけで行う。HTTP の経路は作らない。解除したら、そのモデレーターのセッションの行をすべて消す。
- TOTP の秘密は暗号化して持つ。置き場は `credentials` の列（ADR-0102 の D3）。

### D7 パスワードとメールアドレスの変更

- `PUT /api/v1/me/password` は新しいパスワードを受け取る。再認証が要る（D5）。ADR-0080 の D1 の要件に合わなければ 400 `validation_failed`。変えたら 204 を返し、同じトランザクションで今のセッションのほかのセッションの行をすべて消す。
- `PUT /api/v1/me/email` は新しいメールアドレスを受け取る。再認証が要る（D5）。新しいアドレスに確認のメールを送り、202 を返す。確認（`POST /api/v1/email-verifications`、ADR-0080 の D6）が済むまで、今のアドレスのまま。新しいアドレスをほかの住民が使っていても同じ 202 で、確認のメールは送らない [assumed]（アカウントの有無を明かさない）。確認が済んだら、前のアドレスに変わったことを知らせるメールを送る [assumed]。
- メールアドレスの変更は流量の制限の対象（住民ごとに 3 回／1 時間、ADR-0088 の D2）で、超えたら 429 `rate_limited` を返し、確認のメールは送らない [assumed]。住民が入れた任意のアドレスにメールを送る経路で、再認証のあとの 10 分は何度でも呼べるため、ほかの人のアドレスへ大量にメールを送る踏み台にさせない。

## 理由

- **サーバー側のセッション**: JWT は発行したトークンを途中で無効にできない。退去・セッションの乗っ取り・パスワードの再設定ではすぐに無効にしたい。
- **複数の端末**: スマートフォンと PC など複数の端末で使うのは自然で、1 つに絞っても安全性は大きく上がらない。一覧と取り消しで代わりにする。
- **再認証を 10 分**: 短いと操作のたびにパスワードを求めることになり、長いと放置した端末での不正操作を招く。
- **再認証を住民ごとに数える**: 再認証はログインしたセッションの操作で、送るのはパスワードだけ。総当たりをするのは端末を取った人なので、その住民ごとに数えれば足りる。値をログインのメールアドレスごとの上限にそろえ、ログインより試しやすい入り口にしない。
- **流量の制限を認証のすぐあとに置く**: 住民ごとの規則は住民が分からないと数えられないので認証のあと。ロール・二要素認証・再認証の確かめより先に数えるので、403・401 を返す試しも数えから漏れない（ADR-0088 の理由「数えを先に別のトランザクションで書く」と同じ考え）。
- **`invalidated_at` は退去の受付だけ**: 退去の受付では、J7 が `erasure_log` に記録してから行を消すので行を残す（ADR-0091 の D8）。ほかの無効化では行を残す理由がなく、消せば認証の確かめも J14 も単純になる。
- **強制ログアウトを CLI だけにする**: 住民への処置は ADR-0032 で決まるまで手段を作らない。乗っ取りが分かったときの守りは運用者が行えれば足りる。
- **admin の経路を二要素認証の済んだセッションに限る**: モデレーターのパスワードが漏れても、手紙の本文と通報への操作に届かないようにする（`security.md` §4.1）。手紙を返す経路が 404 のままなのは、存在を明かさない今の決定を変えないため。
- **再認証の失敗でセッションを残す**: 打ち間違いで端末からログアウトさせない。試行は流量の制限で抑える。
- **メールアドレスの変更を確認まで効かせない**: 打ち間違えたアドレスや他人のアドレスに切り替わり、再設定のメールを取られることを防ぐ。

## 代わりの案（選ばなかった理由）

- **JWT（ステートレストークン）**: サーバー側ですぐに無効にできない。不採用。
- **1 デバイス制限**: 複数の端末を使う住民の利便性を損なう。不採用。
- **再認証なし**: パスワードの変更・退去など高リスクの操作に守りがない。不採用。
- **再認証の有効期間を 60 分**: 離席中に不正操作される時間が長くなる。不採用。
- **再認証をログインと同じ主体（メールアドレスと IP）で数える**: 再認証の要求にはメールアドレスがなく、セッションの住民から引き直すことになる。IP ごとの 50 回は 1 人の総当たりには緩い。不採用。
- **流量の制限を入力の検証のあとに置く**: 検証で 400 を返す試しと 401・403 を返す試しが数えに入らない。不採用。
- **無効化をすべて `invalidated_at` にする**: 残った行を消す仕組みが別に要り、無効にした行が保持期間の表に増える。不採用。
- **強制ログアウトを admin の経路に置く**: モデレーターが住民へ処置をする手段になる（ADR-0032）。不採用。
- **二要素認証の解除を住民（モデレーター）の経路に置く**: パスワードを盗んだ側が二要素認証を外せる。不採用。
- **セッションの一覧の `id` に Cookie の値を使う**: 一覧の応答やログからセッションを乗っ取れる。不採用。
