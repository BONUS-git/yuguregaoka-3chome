# 0010 — PostgreSQL を DB とジョブキューの両方に使う

- 状態: 採用
- 日付: 2026-11-19

## 背景

非同期ジョブ（配達バッチ・組版バッチ・モデレーション）の実行管理に何を使うかが未確定だった。
選択肢として Redis + キューライブラリ・クラウドキュー・OS の cron だけ・SQLite が考えられる。
また ADR-0004 では「配達回 ID（`delivery_runs`）」でジョブを管理する方針が決まっており、
DB とジョブ管理の一体化が検討できる状況にあった。

## 決定

PostgreSQL を DB（正本データの保存）とジョブキュー（非同期ジョブの管理）の両方に使う。
ジョブキューの実装は pg-boss 相当（PostgreSQL の上で動く Node.js ライブラリ）を採用する。
cron は JST 基準のスケジュールで worker プロセス内から起動する（OS の cron ではなく、
Node.js プロセス内のスケジューラ、例: `node-cron`）。

## 理由

採用の主な理由は 3 つ。

1. **ジョブをトランザクションの中で積める**: 手紙の「保留（pending）」保存とジョブの enqueue が同一トランザクションになるため、保存だけ成功してジョブが積まれない・またはその逆、という不整合が起きない。

2. **一意制約で重複配達を防げる**: `delivery_runs` テーブルの（配達回 ID × 宛先 × 項目）に UNIQUE 制約を置くことで、ジョブの重複実行があっても配達が 2 度起きない（NFR-021 の冪等性）。

3. **構成要素が 1 つ減る**: Redis 等を別途立てる必要がなく、開発・テスト環境の再現が単純になる（NFR-058）。

## 代わりの案

**Redis + キューライブラリ（BullMQ 等）**: 高速でキューの機能が充実しているが、構成要素が増える。DB とキューがトランザクションを共有できないため、不整合のリスクが残る。不採用。

**クラウドキュー（SQS 相当）**: デプロイしない方針（NFR-071）では、ローカルの再現にエミュレーターが必要になり開発環境が複雑化する。不採用。

**OS の cron だけ**: 再試行・状態追跡・冪等性の保証が難しく、`delivery_runs` テーブルとの統合に追加実装が要る。不採用。

**SQLite**: 単一ファイルで手軽だが、複数プロセス（web / worker）が同時書き込みをするケースで排他制御が難しい。想定規模（住民 1 万人程度、ADR-0012）でも同時書き込みは発生するため不採用。

## 影響

- DB 設計: `delivery_runs` テーブルは配達回 ID・状態・対象レコードの参照を持つ（詳細は `db.md` で定義）
- 非同期処理: pg-boss 相当ライブラリの選定と設定は `async.md` で詳細化する
- 環境構成: PostgreSQL のスペック（想定規模は ADR-0012 参照）は `environment.md` で定義する
