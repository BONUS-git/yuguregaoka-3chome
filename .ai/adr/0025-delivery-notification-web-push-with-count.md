# 0025 — 配達完了の通知は、配達回の公開のあとに Web Push で 1 回送り、郵便の件数を含める

- 状態: 採用
- 日付: 2026-11-19

## 背景

`requirements.md` の FR-028 は「配達完了後に住民へプッシュ通知を送るかどうかは要回答」とし、
`open-questions.md` の OQ-002 でマスターに聞いていた。暫定は「通知なし」で、
ADR-0014 の決定 2 は「プッシュ通知は提供しない」としていた。

2026-11-19、マスターが OQ-002 に次のとおり答えた（原文）。

> 通知あり（内容：郵便の件数を含む）

答えを実装するには、送る時刻・手段・購読の単位・送り先の検査・冪等性・保持を決める必要がある。
これらは技術と設計の事柄なので秘書が決め、ここに残す。答えに書かれていないこと（何を「郵便」として数えるか、など）は決めず、OQ-042 にした。

## 決定

1. **D1 通知と中身**（マスターの答え）: 配達が済んだら住民に通知を送る。通知には、その住民に届いた郵便の件数を含める。
2. **D2 送る時刻**: J15 `notify.delivery`（`async.md` §4）が、J5 の公開のあとに、配達回ごと・購読ごとに 1 回だけ送る。
   - 手紙が届くたびには送らない。公開から 30 分 [assumed] を過ぎたら送らない（Web Push の TTL も 30 分）。
   - `skipped` の便では送らない。持ち越した手紙は、次の便の件数に入る。
   - 通知は定時の配達を知らせるだけで、定時の外に物を届けない。これで P-1（即時性を持ち込まない、FR-030）は保たれる、と解釈する。
3. **D3 手段**: Web Push（VAPID。中身は暗号化）を使う（FR-102）。ネイティブアプリは作らない（ADR-0009 のまま）。
   送信は worker の C11（`architecture.md` §2）が、アダプタを通して行う。テストではモックのプッシュ送信を使う。
4. **D4 購読の単位**: 端末（セッション）ごとに 1 つ。住民がその端末のブラウザで通知を許可したときだけ購読を作る。
   セッションが無効になったら（ログアウト・強制ログアウト・期限切れ・退去）、その購読も消す（ADR-0019）。
5. **D5 件数を載せる場所**: 件数は通知の中身にだけ載せる。API の応答には件数を足さない（ADR-0014 の決定 3 は変えない）。
   ADR-0014 の決定 2 のうち「プッシュ通知は提供しない」は、この通知に限って置き換える。WebSocket・SSE・ロングポーリング・
   「新着があるか」を問い合わせるエンドポイントは作らないまま。
   件数は本人だけに届き、他の住民と比べ合うものではないので、P-2（数値の評価を持ち込まない）には当たらない、と解釈する。
6. **D6 送り先の検査（SSRF 対策）**: 購読の `endpoint` は住民が渡す値なので、登録のときと送るときに検査する。
   - `https` だけを受け付ける。
   - 許可するプッシュサービスのホストの一覧を持つ（値は `environment.md` で決める）。
   - 名前解決のあとに、プライベート・ループバック・リンクローカルのアドレスを宛先にしない。
   - リダイレクトに従わない。時間切れは短くする（5 秒 [assumed]）。
   - 検査で外れた `endpoint` は、登録の API が 400 で拒む（`api.md` §7）。
7. **D7 冪等性と保持**: 送った記録を `delivery_notifications`（`db.md` §2）に持ち、`UNIQUE(delivery_run_id, push_subscription_id)` で重ねない。
   保持は 30 日 [assumed]（ADR-0013）。起点は指している配達回の `finished_at` で、J14 が `delivery_runs` より先に消す（`async.md` §4 J14）。購読 `push_subscriptions` と送った記録は、退去のときに即時に消す。
8. **D8 段階**: MVP の M3（`roadmap.md` §4）で作る。受け入れ条件は A-15。
9. **D9 要求の区分**: ADR-0024 の決定 5 に従い、FR-028・FR-102 は `[inferred]`（マスターの答え OQ-002 より）とし、根拠にこの ADR を書く。

## 理由

- 通知を送ることと件数を含めることは、マスターの答え（上の原文）による。構想の意図はマスターにしか決められない。
- 配達回の公開のあとに 1 回だけ送れば、住民が受け取るのは「朝便・夕便が来た」という定時の知らせだけになる。
  手紙ごとに送るより P-1 に近い。
- Web Push はブラウザで受けられ、今の構成（Web だけ、ADR-0009）のまま足せる。中身は暗号化されるので、
  プッシュサービスに件数が平文で渡らない。
- 端末ごとの購読にすれば、ログアウトした端末に通知が届かない。セッション（ADR-0019）と同じ単位で消せる。
- 件数を API に載せないことで、ADR-0014 の「数値を返さない」の範囲を広げずに済む。
- 送り先を住民が決められる値は、検査しなければ worker から内部のネットワークへ届く経路になる。

## 代わりの案（選ばなかった理由）

- **手紙が届くたびに即時に通知する**: 定時の外に知らせが届き、P-1 に反する。
- **メールで知らせる**: 本番のメール送信サービスはマスターの事前承認を得て選ぶもので、まだ選んでいない（OQ-039 → 決定、ADR-0033。進め方は OQ-049）。朝夕に毎日メールを送ると量が多く、費用にもかかわる。
- **ネイティブアプリを作ってプッシュ通知を送る**: ADR-0009 のとおり Web だけで MVP の体験は成り立つ。作る物が増える。
- **新着の件数を問い合わせる API を作り、クライアントが数える**: ADR-0014 の決定 2・3 に反し、即時性と数値を API に持ち込む。

## 決めていないこと

- 何を「郵便」として数えるか（手紙だけか、新聞も数えるか）・手紙が 0 通の便でも送るか・件数のほかに何を載せるか: OQ-042（要回答）。
  暫定は (1) 手紙だけを数える (2) 0 通の住民には送らない (3) 中身は便（朝便・夕便）と件数だけ。差出人・本文・住所は載せない。
  答えで変わる箇所: J15 の数え方と送る相手（`async.md` §4）、この ADR の D1 の中身、`security.md` §7 の T-17、`roadmap.md` の A-15。
- 一部のモバイルのブラウザでは、ホーム画面に加えた Web アプリでないと通知を受けられない。この制約は住民向けの案内に書く（実装で決める）。
- 許可するプッシュサービスのホストの一覧と、VAPID の鍵の置き場所: `environment.md` で決める。
