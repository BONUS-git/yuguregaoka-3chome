# 0096 — 消去の再生は控えから J7 をやり直す

- 状態: 採用
- 日付: 2026-11-26

`reviews/0001-design-review.md` の R-014、`triage.md` 仕分け 3 の K-008（YGO-034）。
R-014 のマスターの判断は「不要」で、すべて秘書の判断 `[assumed]`。新しい要回答はない。
この ADR が決めるのは、リストアのあとに消去をやり直す仕組み（`erasure.replay` の手順と、それに使う消去の控え・`erasure_log` の制約）だけ。
何を消すか・何を `erasure_log` に記録するか・何日持つかは ADR-0091（退去の表・保持期間の表・D1〜D14）のままで、この ADR はどれも変えない。
ADR-0091 の D11・D13 が R-014 に回した「記録の範囲」は、記録を足さずに、再生が J7 と J14 をやり直すことで答える（D1）。
ADR-0091 の D6（バックアップから戻したときは、次の J14 が同じ条件でまた消す）もそのまま使い、再生はその次の J14 を web を戻す前に動かす（D4）。

## 背景

`erasure_log`（`db.md` §2）は、削除した表の名前と行の ID と時刻だけを持つ。記録するのは J7 の手順 0 と手順 10 の削除だけで、次の 3 つは記録が残らない。

1. 本文を消す UPDATE（J7 の手順 2・3 の掲示板の投稿の `body`）
2. 差出人などの住民を指す列を NULL にする UPDATE（J7 の手順 9、ADR-0091 の D11）
3. J14 の削除（却下・差し戻し・抑止・届いた手紙、興味、居住記録など。ADR-0091 の D6・D14）

J7 の手順 1（届いていない手紙）・4（住所録）・5（ブロックとロール）・6（興味など）・8（郵便受けの行）の削除も記録しない。
このため、バックアップから戻すと、消したはずの本文・却下した手紙・興味が戻り、`erasure_log` を「順番に再生」しても消し直せない。

もう 1 つの穴がある。`erasure_log` は復元する DB の中にある。DB を時点 T に戻すと、`erasure_log` も T に戻り、T より後の消去の記録が一緒になくなる。
戻したい消去（T より後に行った退去）の記録が、再生に使う表から消えている。

## 決定

### D1 再生は記録に頼らず、J7 と J14 をやり直す

`erasure.replay` は、`erasure_log` の記録を順に当てるのではなく、退去した住民ごとに J7 をやり直し、そのあと J14 を 1 回動かす `[assumed]`。
そのため `erasure_log` に記録する表は ADR-0091 のまま（D8 の `sessions`・`auth_tokens`・`credentials` と手順 10 の `residents`）で足りる。J7 のすべての削除と UPDATE、J14 の削除を行ごとに記録する案（R-014 の直し方の案）は採らない。

- J7 の手順はどれも 2 回動かして安全（`async.md` J7 の冪等性）。戻った行は条件に合うので消え、もうない行には何もしない。本文の消去（手順 2・3）・住民を指す列の NULL（手順 9）・記録しない削除（手順 1・4〜8）も、J7 をやり直せば当たり直す。
- J14 の条件は行の列（`settled_at`・`decided_at`・`resident_erased_at`・`last_matched_at` など）で決まる。戻った行も同じ値を持つので、ADR-0091 の D6 のとおり、次の J14 がまた消す。再生が積む J14（D4 の 3）が、その次の J14 になる。

### D2 `erasure_log` の形

- `table_name` に `CHECK (table_name IN ('sessions', 'auth_tokens', 'credentials', 'residents'))` を付ける `[assumed]`。
- `UNIQUE (table_name, record_id)` を付け、J7 の記録は `INSERT … ON CONFLICT (table_name, record_id) DO NOTHING` で書く `[assumed]`。J7 をやり直しても同じ行の記録は 1 つだけになる。
- 列は今のまま（`id`・`table_name`・`record_id`・`erased_at`）。住民の ID を別の列に持たない（`credentials` と `residents` の `record_id` が住民の ID）。

### D3 消去の控え

- J7 は手順 0 の前に、オブジェクトストレージ（C8）の `erasure/<resident_id>.json` に消去の控えを置く `[assumed]`。中身は `resident_id` と受付の時刻（`residents.deleted_at`）の 2 つだけ。ニックネーム・住所・メールアドレスなど、ほかの値は入れない。
- 控えがすでにあれば書き換えない（条件付きの書き込み。J7 のやり直しでも受付の時刻は最初の値のまま）。控えを置けなければ J7 は手順 0 に進まず、失敗で終えて pg-boss の再試行に任せる。
- 控えは DB の外にあるので、DB を戻しても巻き戻らない（オブジェクトストレージは版を持たず、バックアップから戻さない。`environment.md` §6.5）。
- 受付（`DELETE /me`）から J7 が控えを置くまでの間（ふつうは数秒）は控えがない。その間に受付より前の時点に DB を戻すと、その退去は再生から抜ける。これは受け入れる（受付で控えを書くと、受付の API が DB の外への書き込みを待ち、DB のトランザクションと控えがずれる）。

### D4 `erasure.replay` の手順

運用者の CLI が、DB を戻したあと、web を止めたまま積む（worker は動かす）。1 回のジョブで次の順に行う `[assumed]`。

1. オブジェクトストレージの `erasure/` の控えをすべて読み、住民ごとに次を行う。
   - `residents` の行があれば、`deleted_at` が NULL のとき控えの受付の時刻を書く（受付より前の時点に戻したとき。API が退去した住民を 404 にするため）。
   - J7 `account.erase` をその `resident_id` で積む。
2. 戻した DB の `erasure_log` の、`table_name` が `sessions`・`auth_tokens`・`credentials` の行について、`record_id` の行がそれぞれの表に残っていれば消す（`credentials` は `resident_id`。消すのは外部キーの向きのとおり `sessions`（指す `push_subscriptions`・`delivery_notifications` を先に）→ `auth_tokens` → `credentials`）。控えが欠けたときの守りで、記録はし直さない。
3. J14 `retention.purge` を 1 回積む（`singletonKey` は `'retention.purge:replay:<日時>'`。その日の J14 とは別に動く）。
4. 1 で積んだ J7 と 3 で積んだ J14 がすべて終わってから（`jobs` の状態で確かめる）、運用者が web を戻す。

- J7 のやり直しが積む J8（投稿の消去による組み直し）は、web を戻す前に終わらなくてよい（紙面の差し替えは住民の操作を待たない。終わるまで古い紙面が見えうるのは、ふだんの退去と同じ）。
- 2 回動かしても安全（1 の J7 と 3 の J14 は冪等。2 は残っている行だけを消す）。

### D5 控えの保持

控えは置いてから **60 日** 持ち（`erasure_log` と同じ。バックアップの 30 日より長い）、J14 が消す `[assumed]`（中身の受付の時刻が 60 日より前の控え）。

### D6 再生で戻らないもの

再生が戻すのは、退去（J7）と保持期間（J14）による消去だけ。復元の時点より後に住民やモデレーターが行った操作（郵便受けの削除・ログアウト・パスワードの変更・住所録やブロックの変更・処置など）は戻らない `[assumed]`。ログアウトした・取り消したセッションは有効なまま戻り、変える前のパスワードでログインできうる。
J7 の手順 9 の `tenancies.resident_erased_at` は、やり直した J7 の時刻（`now()`、ADR-0091 の D10）になり、居住記録の保持は最長でバックアップの保持（30 日）だけ延びる。
これらの扱いは M6 で決める（`gaps.md` G-055）。

## 理由

- **記録の範囲を広げない（D1）**: J7 と J14 は、どちらも行の列の条件で消すので、やり直せば同じ行に当たる。行ごとに記録すると、J14 が毎日消す手紙・居住記録・数えのすべての ID が `erasure_log` に残り、表が大きくなる。記録した ID だけでは本文の消去や列の NULL を表せず、表ごとの再生の処理が別に要る。やり直しなら再生の処理は J7 と J14 のままで、手順を足しても再生が追いつく。
- **控えを DB の外に置く（D3）**: `erasure_log` は DB と一緒に戻るので、戻した時点より後の退去を知る手がかりにならない。DB の外に住民の ID と時刻だけを置けば、戻したあとも、やり直す住民が分かる。中身を 2 つの値にすれば、控えそのものが個人情報を増やさない（`residents` の行の ID は退去のあとは誰も指さない）。
- **CHECK と UNIQUE（D2）**: 記録する表を決めておけば、記録の範囲が知らないうちに広がらない。J7 のやり直しで同じ記録が重ならない。
- **web を止めて再生する（D4）**: 戻した DB には、退去した住民のセッションが有効なまま戻りうる。再生が終わるまで要求を受けなければ、退去した住民が戻った行で操作できない。
- **60 日（D5）**: バックアップ（30 日）のどの時点に戻しても、その後の退去の控えが残る。

## 代わりの案

- **J7・J14 のすべての削除と本文の消去を `erasure_log` に行ごとに記録する（R-014 の案）**: 上の理由のとおり表が大きくなり、記録だけでは列の NULL と本文の消去を再生できない。`erasure_log` が DB と一緒に戻る穴も残る。採らない。
- **`erasure_log` を DB の外（ログのサービス）に書く**: ログは 30 日で廃棄し（ADR-0091）、個人を特定しない粒度で持つ（`security.md` §2.1、`db.md` §2）。退去した住民の ID と行の ID をログに出すと、その方針に反し、60 日の保持にも届かない。採らない。
- **受付（`DELETE /me`）のトランザクションで控えを書く**: DB のコミットと控えの書き込みを 1 つにできず、どちらかだけが残りうる。受付の API が DB の外を待つ。D3 の数秒の穴は、J7 がすぐに動けば小さいので採らない。
- **web を戻してから、毎日の J14 の時刻を待つ**: ADR-0091 の D6 のとおり次の J14 が消すことは同じだが、待つ間（最長 1 日）、消したはずの手紙が戻ったまま web が動く。採らない（再生が次の J14 を積み、終わってから web を戻す）。
- **web を止めずに再生する**: 再生が終わるまで、退去した住民のセッションと戻った手紙が見える。採らない。
