# 0020 — ロールは住民とモデレーターの 2 つ。権限の規則表は 1 か所に持ち LLM は判定に関わらない

- 状態: 採用
- 日付: 2026-11-19

## 背景

OQ-031「管理者・モデレーター役割の定義」は `security.md` で定義する持ち越し項目だった
（FR-081、NFR-019）。

通報の受け付け先・異議申し立ての処理者として管理者ロールが必要であることは以前から認識されていた。
一方で、次の点が未決定だった。

1. ロールは何種類か（管理者・モデレーター・一般住民などの区別）。
2. ロールを付与・剥奪できるのは誰か。
3. 権限の規則表はどこに置くか。
4. LLM が認可判断に関与しないことをどのように保証するか。

## 決定

### ロールの種類

住民（`resident`）と**モデレーター**（`moderator`）の **2 種** のみとする [assumed]。

- `resident`（住民）: 一般の住民。登録後に自動付与される。
- `moderator`（モデレーター）: 掲示板の投稿と通報を審査する担当者。

「システム管理者」（インフラ・DB への直接アクセス権を持つ運用者）は、
アプリケーション層のロールとしては定義しない。運用者は CLI を通じてロールの付与・剥奪を行う。

### ロールの付与・剥奪

**運用者の CLI のみ**がロールを付与・剥奪できる。API 経由ではロールを変更できない。

- `staff_roles` テーブル（または `residents` のカラム）で管理する。
- `granted_by`（付与した運用者の識別子）・`granted_at` を記録する。

### 権限の規則表の置き場所

すべての認可ロジックは **C3 ドメインモジュールの 1 か所**にまとめる（ADR-0015 §5）。

- 規則表は「主体（ロール）× 資源 × 操作」の形で記述する。
- 許可と拒否の両パスをテストする。
- 分散させない（API レイヤー・DB トリガーに認可ロジックを置かない）。

### LLM と認可の分離

LLM は認可判断に一切関与しない。LLM の出力が権限の変更・ロールの付与・アクセス拒否の覆しに
使われることはない（security.md §1）。

### モデレーターへの追加の要件

- 二要素認証（TOTP 等）を必須とする [assumed]。
- 自分が当事者（送信者・受取人・通報者・被通報者）の案件を処理できない。
- すべての処置を `moderation_actions` に記録する。

## 理由

- **ロールを 2 つにする理由**: MVP の段階では「住民」と「コンテンツ審査担当」の区別で十分。
  「スーパー管理者」「コンテンツ編集者」などの細かいロールは将来の拡張で対応できる。
  ロールが増えると規則表の管理コストが上がる。
- **ロールの付与を CLI のみに限る理由**: API 経由で誰でもモデレーターになれると重大なセキュリティ問題になる。
  運用者 CLI は本番環境への直接アクセスを持つ人が使うものとし、フォーマルな承認プロセスを経ることを想定する。
- **規則表を 1 か所に集める理由**: 分散すると認可ロジックの全体像が見えなくなり、
  抜け穴が生まれやすくなる（NFR-061）。テストも 1 か所で網羅できる。
- **LLM を認可から除外する理由**: NFR-011 に従い、セキュリティ上の判断を LLM の自由裁量に
  依存させない（security.md §1）。LLM の判定は入力と出力の制御が難しく、プロンプトインジェクションの
  リスクがある（security.md §5.3）。

## 代わりの案（選ばなかった理由）

**3 種以上のロール（管理者・モデレーター・一般住民）**: 細分化すること自体は合理的だが、
MVP の段階では複雑さのコストが高い。将来的に追加できる。
**API 経由でモデレーターを付与できる「管理者ロール」を作る**: API が侵害された場合に
モデレーターを大量に作れてしまうリスクがある。CLI に限定するほうが安全。
**規則表を API レイヤーに分散させる**: 認可ロジックのテストが難しくなる。抜け穴が生まれやすい。

## 影響

- DB 設計: `staff_roles` テーブル（または `residents` の `role` カラム）を追加する（security.md §9）。
- API 設計: 認可ミドルウェアが C3 の規則表を参照する形にする。
- security.md §4 に権限表を記述し、このADRを参照する。
- OQ-031: 本 ADR の決定により持ち越し → 暫定決定に変更する（将来のロール追加の余地あり）。
