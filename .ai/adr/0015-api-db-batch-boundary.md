# 0015 — API・DB・バッチの責務の境界

- 状態: 採用
- 日付: 2026-11-19

## 背景

NFR-051「API・DB・バッチの責務を明確にする」と ADR-0008（2 プロセス構成）・
ADR-0010（PostgreSQL をジョブキューに使う）・ADR-0013（退去処理）を組み合わせると、
次の 3 つの問いに答える必要があった。

1. `delivery_runs` の行を誰がいつ作るか。  
   db.md §4 は「締め切り処理時」と書いているが、API が手紙を保存するときにも
   `delivery_run_id` が必要で、外部キー制約を満たすには先に行が要る。

2. ブロックの判断を送信時に API がするか、配達時に worker がするか。

3. 退去（DELETE /me）をどこまで同期で処理するか。

## 決定

### 1. API が行うこと・行わないこと

**行うこと**
- 認証・認可（本人のものか・ロール）
- 入力の検証（JSON Schema・文字数上限）
- 1 日の上限の確認（手紙 20 通・掲示板 5 件）
- 受付の状態（`pending` / `awaiting_review`）での保存
- 配達済みの物の読み出し
- 手紙の復号（本人に返すときだけ）
- すぐに実行するジョブの投入（消去・組み直し）: ID だけを同じトランザクションで積む（ADR-0010）
- （ADR-0040 で追記、2026-11-20）手紙の投函のとき、暗号化の前に本文をルール表の手紙の項目に当てる（LLM は使わない）。
  当たったら保存せずに 422 を返し、送った人が確認を頼んだときだけ `held` で保存する。
  モデレーターの操作（`approve`）で `held` を `pending` にし、2 の手順で配達回に入れる。通報された手紙と `held` の手紙を、モデレーターに 1 通ずつ復号して返す

**行わないこと**
- 配達・審査（手紙の送るときの照合を除く、ADR-0040）・LLM の呼び出し・組版・画像の加工
- 時刻で決まる状態の変更
- 配達先の決定（転送・差し戻し・ブロックによる抑止）
- 物理削除の実行

### 2. delivery_runs の冪等な作成

API が手紙や掲示板の投稿を受け付けるとき、次の手順で配達回を決める。

1. `nextDeliveryRun(now)` で次の配達回 ID を計算する（JST 基準、ADR-0004）。
2. `INSERT INTO delivery_runs (run_id, status) VALUES ($id, 'pending') ON CONFLICT DO NOTHING` で行を作る。
3. 同じトランザクション内で `SELECT … FOR SHARE` を使い、`status = 'pending'` を確認する。
4. `pending` でなければ（締め切り処理が既に走っている）、次の便の配達回 ID を使って 2〜3 を繰り返す。

締め切り処理（worker）は `status = 'running'` に更新してから処理を始めるため、
共有ロックが解放されるまで API の確認が待たされる。これにより、締め切った配達回に
書き込みが紛れ込まないことが保証される [inferred]。

手紙と掲示板は締め切り処理が拾うので、API は配達用のジョブを積まない。

### 3. ブロックの判断は配達時

API はブロックの登録を受け付けるだけで、送信時にブロックを確認しない。
配達時に worker がブロックを参照し、`state = suppressed` にする（db.md §3）。
送った人には「配達済み」と見せ、ブロックしたことを相手に気づかせない。

### 4. 退去は同期と非同期に分ける

**API が同一トランザクションで行うこと（同期）**
- `residents.deleted_at` を現在時刻に設定する
- 有効なセッションをすべて無効化する
- `account.erase` ジョブを `jobs` テーブルに積む（ID のみ）

API は `202` を返す。

**worker が行うこと（非同期）**
- ADR-0013 の表に従い消去・組み直しを実行する（物理削除・NULL 化・状態変更）

`deleted_at` が付いた住民は、API では存在しないものとして扱う（`404` を返す）。

### 5. 業務ロジックは DB のトリガーに置かない

業務ロジック（バリデーション・状態遷移の判断）は C3 ドメインモジュールに集める。
DB は一意制約・外部キー・状態の値の制約によって整合性を保証するが、
トリガーやストアドプロシージャでロジックを実行しない [assumed]（NFR-061）。

## 理由

- **API の応答がバッチに左右されない**: API は受付の状態まで同期的に処理し、`202` を返すことで
  応答時間が短く一定になる。
- **時刻で決まる処理が 1 か所にまとまる**: 配達・審査・組版はすべて worker の cron 経由となり、
  API が勝手に状態を進めることがない。
- **ブロックを明かさない**: 送信時にブロックで拒否すると、ブロックしたことが相手に知られる。
  配達時の `suppressed` ならば送信は「受け付け済み」として見せられる。
- **締め切ったあとの書き込み混入を防ぐ**: `FOR SHARE` により、API が誤って締め切り済み配達回に
  書き込む競合状態を排除できる。
- **冪等性を UNIQUE 制約で保てる**: `ON CONFLICT DO NOTHING` と UNIQUE 制約の組み合わせで、
  worker の再試行があっても配達が重複しない（ADR-0010）。
- **テスト容易性**: ドメインロジックが C3 に集まることで、ユニットテストが書きやすい（NFR-061）。

## 代わりの案（選ばなかった理由）

- **API で配達する（同期配達）**: P-1 と ADR-0004（定時配達）に反する。
- **API が送信時にブロックを確認して拒否する**: ブロックしたことが相手に知られる。
- **退去を API が同期で物理削除する**: 組み直しが長時間かかるため、HTTP リクエストがブロックされる。
- **worker が前もって delivery_runs を作っておく**: worker が止まっているとき API も書き込めなくなる。
  API が冪等に作ることで worker の可用性に依存しない。
- **DB のトリガーに業務ロジックを置く**: アプリケーション層のコードと乖離し、テストが難しくなる。
