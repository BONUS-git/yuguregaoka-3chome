# 0064 — 地図の候補の印を押して選べ、空き家・入居を全員に見せる

- 状態: 採用
- 日付: 2026-11-21

ADR-0059 を丸ごと置き換える。ADR-0059 の決定（D1〜D18）は、OQ-080 の答えに合わせて今の状態に書き直し、同じ番号でこの ADR に移した。
書き直したのは D6（拡大・移動の参照）・D7・D8・D12（FR-114 の根拠に OQ-080 を足す）・D16。ほかの決定（D1〜D5・D9〜D11・D13〜D15・D17・D18）は ADR-0059 と同じ。

## 背景

ADR-0061 で、地図は全住民で共有する 1 枚の白黒の画像と決まった。`open-questions.md` の OQ-054 でマスターに、
(1) 知り合いの家の印をいつ作るか、(2) 「知り合い」は誰か（(a) 自分の住所録に入れた住民、(b) 互いに住所録に入れた住民、(c) 手紙をやり取りしたことのある住民）と相手の同意が要るか、
(3) 自分の住所の場所に印を付けるか・登録のときに住所の候補の場所を地図で示すか、を聞いた。2026-11-20、マスターが次のとおり答えた（原文）。

> 1:MVP
> 2:1
> 3:どちらもyes, 登録時に選択可能かつ、地図を表示する際は中心に置き印もつける。また、空き家か人がいるかも表示する。ここにはユーザー名は載せず、boolean的に表示するものと考えている

「2:1」は (2) の 1 つ目の例、(a) 自分の住所録に入れた住民と読む（秘書の読み方）。地図の印を住所録のすべてのエントリに付けることは OQ-071 の答え（2026-11-20、ADR-0051）で決まった。
手紙を出せる知り合いには相手の同意が要ることは OQ-066 の答え（2026-11-20、ADR-0049）で決まった。

空き家・入居の表示の範囲（どの家・誰に・いつの状態・何を空き家とするか）は答えになく、OQ-079 で聞いていた。2026-11-21、マスターが次のとおり答えた（原文）。

> 1:これは全員にいつでも公開してOK。登録前、後いつでも確認が可能にする。
> 2：休眠は空き家にしない。長くログインしていない判定に対する閾値などはMVP後に検討。いずれ空き家判定にする可能性はある。

「登録時に選択可能」が、(a) 候補の一覧から選び地図で場所を確かめる形か、(b) 地図の上の候補の印を押して選ぶ形か、(b) なら空き家の印も選べるかを、OQ-080 で聞いた。2026-11-21、マスターが次のとおり答えた（原文）。

> b

答えから読み取れることと、読み取れないことを分ける。

| 答え | 読み取れること（決定） | 読み取れないこと |
|---|---|---|
| OQ-079 の 1「全員にいつでも公開してOK」 | 空き家・入居の 2 値を、登録の前の人にもログインした住民にも見せる（D10）。どの家についてかは、問いの例 (a)(b) のとおり街のすべての家と読む `[inferred]` | — |
| OQ-079 の 1「登録前、後いつでも確認が可能」 | 登録の画面と、ログインした住民の地図の画面の両方に出す（D10）。要求を受けたときの状態を示す（D14、`[assumed]`） | 登録の画面のほかのログインの前の画面に出すか → MVP では出さない `[assumed]`（ADR-0063 の D1） |
| OQ-079 の 2「休眠は空き家にしない」 | `dormant` は入居と示す（D13） | — |
| OQ-079 の 2「閾値などはMVP後に検討。いずれ空き家判定にする可能性はある」 | MVP では休眠の判定を作らない（今までどおり段階 3、ADR-0062）。休眠から空き家（`vacant_expired`）にする移行は答えまで作らない（ADR-0060 の D3。ADR-0002 を置き換え） | 休眠を空き家にするか・その閾値・転送中の旧住所の表示 → OQ-088（持ち越し） |
| OQ-080「b」 | 登録の画面の地図の候補の印を押して住所を選ぶ（D7） | 空き家の印も選べるか → OQ-089（要回答。暫定は候補の印だけ）。一覧を残すか・キーボードでの操作 → `[assumed]`（D7） |

## 決定

1. **D1 印を付ける（OQ-054 の答え）**: 地図に次の 3 種類の印を付ける。
   - (a) 自分の家の印（答え 3）。ログインしている住民の地図に、自分の住所の場所を示す。
   - (b) 登録のときの候補の印（答え 3）。登録の画面の地図に、提示した住所の候補の場所を示す。
     登録の画面はログインの前の画面（まだセッションのない人の画面）で、答えの「登録時に選択可能」により、地図（土台の画像）と候補の印を出す。登録の画面のほかのログインの前の画面は ADR-0063 の D1。
   - (c) 知り合いの家の印（答え 1・2）。地図の「知り合い」は自分の住所録に入れた住民とし、住所録のすべてのエントリの住所の場所に印を付ける（ADR-0051 の D1・D2）。
     手紙を出せる知り合い（ADR-0049 の D2）・新聞の知り合い（ADR-0044 の D2）とは定義を分ける。地図の印は、手紙を出せる知り合いと一致しないことがある（片方だけ足した相手の家にも印が付く）。印は `acquainted` で変えない（ADR-0051 の D3）。
2. **D2 段階（答え 1・秘書の判断）**: どれも MVP。自分の家の印・候補の印・入居の層は M1（住所・アカウント）に置く。知り合いの家の印は、住所録を作る M2（住所録・手紙）に置く（秘書の判断。住所録がないと作れないため）。
3. **D3 土台の画像は全住民で同じ（秘書の判断）**: 土台の SVG は、どの住民にも、ログインの前にもバイト単位で同じにする。
   印と入居の層は土台の画像に描き込まず、C1 が土台の画像の上に重ねる層として描く。土台の画像には号までの住所・住民・入居・空き家・数を描かない（ADR-0063 の D4）。
4. **D4 住所と位置の対応（秘書の判断）**: 住所から画像の上の位置を求めるのは、C1 の静的な配置の定義（番ごとの区画の位置と大きさ）と、C1 の中の関数（番と号から区画の中の位置を計算する）とする。
   C1 の静的なファイルに、号までの住所の一覧（住所ごとの位置の一覧を含む）を持たない。地図に出す家の一覧は、入居の一覧の応答（D15）から得る。
   DB の地図の表・ジオデータ・外部の地図サービスは持たない（ADR-0063 の D3）。
   配置の定義にない番・解釈できない住所には印を付けず、画面に誤りの知らせも出さない。
5. **D5 地図の画面が呼ぶ API（秘書の判断）**: 地図の画面が呼ぶ API は、`GET /api/v1/me`（自分の家）・`GET /api/v1/addresses/candidates`（候補）・`GET /api/v1/address-book`（知り合いの家）・`GET /api/v1/addresses/occupancy`（入居の層、D15）の 4 つだけにする。
   登録の画面が呼ぶのは、候補と入居の 2 つ。`me`・`candidates`・`address-book` の応答の形は変えない（位置・座標を応答に足さない）。
   知り合いの家の印は住所録のエントリの住所（登録した時点の住所、ADR-0003）の場所に付け、相手が引っ越しても自動で動かさない。地図の画面は `acquainted` を読まない（ADR-0051 の D3）。
6. **D6 表示の窓（答え 3・秘書の判断）**: 地図を出すときは、自分の家の位置を表示の窓の中心に置く（答え）。窓の幅と高さは土台の画像の 2 倍とし、どこに住んでいても街の全体が窓に入るようにする。窓のうち土台の画像の外は白い余白にする（秘書の判断）。
   拡大・移動はしない（ADR-0063 の D1 (a)）。登録の画面（まだ自分の家がない）では、土台の画像をそのまま窓にし、候補の印と入居の層を付ける。
7. **D7 登録のときの選び方（OQ-080 の答え「b」・`[assumed]`）**:
   - 住民は、登録の画面の地図の候補の印を押して住所を選ぶ（答え「b」）。候補の印には、候補の一覧と同じ見出し（候補の住所）を添える。
   - 候補の一覧も残し、一覧からも選べるようにする `[assumed]`。地図を見られない人・押しにくい人も選べるようにするため（NFR-041）と、配置の定義にない住所（D4）の候補にも選ぶ手段を残すため。
     地図と一覧の選択は 1 つの状態で、どちらで選んでも、選んだ候補の印はほかの候補の印と見分けられる形に変わり、一覧でも同じ候補が選ばれている。もう一度選ぶと、選ぶ候補が替わる。
   - 候補の印は、キーボードでも選べる（Tab で印に移れ、Enter か Space で選ぶ）`[assumed]`（NFR-041）。印の代替テキストは、候補の住所と、選んでいるかどうかの決まった語だけ（D9）。
   - 押して選べるのは候補の印だけ。土台の画像・入居の層の印（空き家の印を含む）・自分の家の印・知り合いの家の印は、押しても何も起きない（ADR-0063 の D1 (a)）。空き家の印も選べるかは OQ-089（要回答）。暫定は押せない。
   - 選んだ候補は、今までどおり登録の要求で候補の住所として送る。地図で選ぶための API の経路・応答の項目は足さない（D5・D16）。拡大・移動・検索はしない（ADR-0063 の D1 (a)）。
8. **D8 印の層の中身（秘書の判断）**: 印と入居の層は白黒（ADR-0061 の D2、R=G=B）で描き、印の種類は形で見分ける（色に頼らない）。
   入居の印は、入居と空き家を見分ける白黒の 2 つの形とする（例: 塗った四角と輪郭だけの四角）`[assumed]`。自分の家・候補・知り合いの家の印は、入居の印の上に重ねる。選んだ候補の印は、選んでいない候補の印と形で見分ける（D7）。
   印の層に、住民が書いた文字（ニックネーム・自己紹介・住所録のメモ）を入れない。添える文字は、候補の住所と、決まった語（「自分の家」など）だけにする。入居の印には文字を添えない。
   印の層は C1 のコードが描き、外部への参照・`<script>`・文字列のイベント属性（`onclick="…"` のように属性の文字列にコードを書くもの）を入れない（ADR-0063 の D5 の考え方を印の層にも当てる）。
   候補の印を押す処理は、C1 の React のイベントハンドラで印の要素に付ける `[assumed]`。ハンドラを付けるのは候補の印だけにする（D7）。
9. **D9 代替テキスト（秘書の判断）**: 代替テキストには、人の名前（ニックネーム・住所録のメモ）と数（知り合いの家の数・住んでいる家の数・空き家の数・家の総数）を入れない。
   自分の家の住所・候補の住所と、「知り合いの家に印があります」「家ごとに、人が住んでいるか空き家かを形で示しています」のような決まった文だけにする（P-2 数値の評価、NFR-041）。
10. **D10 空き家・入居の表示（OQ-054 の答え 3、OQ-079 の答え 1）**: 街のすべての家について、空き家か人が住んでいるかを、住民の名前を載せない 2 値で示す。
    登録の前の人（登録の画面）にもログインした住民（地図の画面）にも、いつでも見せる。経路は認証なしで呼べる（`api.md` §4）。
    表示は C1 が土台の上に重ねる入居の層で行い、土台の画像は変えない（D3）。どの家についてかは、OQ-079 の問いの例 (a)(b) が街のすべての家で、答えの「全員にいつでも」がそれを狭めていないことからの読み方 `[inferred]`。
11. **D11 相手の同意（OQ-066・OQ-071 の答え）**: 手紙を出せる知り合いには相手の同意（互いに住所録に入れること、または掲示板でのオープン）が要る（ADR-0049 の D2）。
    地図の印には相手の同意を求めない。印は住所録のすべてのエントリに付ける（ADR-0051）。
12. **D12 要求の区分**: ADR-0024 の決定 5 に従い、FR-114（印）と FR-115（空き家・入居の表示）を `[inferred]` とする（FR-114 はマスターの答え OQ-054・OQ-080、FR-115 は OQ-054 と OQ-079 の答えより）。
    FR-114 のうち、一覧を残すこと・キーボードで選べること・React のハンドラで付けることは `[assumed]`（D7・D8）。区分の細部は D17。
13. **D13 何を空き家とするか（OQ-079 の答え 2・`[inferred]`）**: 家ごとに、次のとおり読む。
    - 入居（`occupied: true`）: `addresses.status` が `active` または `dormant` の住所。休眠は空き家にしない（答え 2）。
    - 空き家（`occupied: false`）: 使われたことのない住所（`addresses` に行がない）と、`addresses.status` が `vacant_deleted`・`vacant_expired`・`vacant_forwarded` の住所。
      `vacant_expired` は、休眠から空き家にする移行を OQ-088 の答えまで作らない（ADR-0060 の D3）ので今は起きない。値は残し、なったときは空き家と読む。
    - 応答では状態の種類を分けない（使われたことのない住所と退去のあとの住所を同じ `false` にし、休眠を `true` にする）。`[inferred]`（答えの「boolean的に表示」）。
    MVP で起きる状態は、`active`・使われたことのない住所・`vacant_deleted` だけ（ADR-0062。`dormant`・`vacant_forwarded` は段階 3 の F-16）。
    `vacant_forwarded` になるのは転送期間が終わったあとで、転送中の旧住所は `active` のままなので入居と示す。休眠を空き家にする判定と、転送中の旧住所の示し方は OQ-088（持ち越し）。
14. **D14 いつの状態か（`[assumed]`）**: 要求を受けたときの状態を示す。状態のスナップショットの表・配達の時刻ごとの区切りは持たない。
    退去（`vacant_deleted`）のすぐあとの要求では、その家は空き家と示される。答え 1 の「いつでも確認が可能」を、そのときの状態がいつでも見られることと読む。
15. **D15 入居の一覧の応答（`[assumed]`）**: `GET /api/v1/addresses/occupancy` は次の形を返す。
    ```json
    { "houses": [ { "address": "夕暮ヶ丘三丁目 2-5", "occupied": true } ] }
    ```
    - 家の集合は、C3 の住所のプールの静的な定義（候補の提示が候補を選ぶのと同じ住所の集合）とする `[assumed]`。DB にまだ行のない、使われたことのない住所も含む。
    - 並びは番・号の数の順（番が小さい順、同じ番では号が小さい順）にし、登録の順・状態に依らない。ページングと総件数は置かない。
    - 呼んだ人やセッションの有無で応答を変えない（自分の家・知り合いの家を応答で区別しない。印は C1 が D5 のほかの API から付ける）。
    - 名前（ニックネーム）・自己紹介・年齢・住み始めた日・`addresses.status` の値・件数（住んでいる家の数・空き家の数・総数）は返さない。
16. **D16 既存の応答は変えない（秘書の判断）**:
    - `GET /api/v1/profiles/{address}` は、空き家と存在しない住所を同じ 404 にし、ログインが要ることも変えない。入居の一覧で入居の有無は分かるので、この 404 は入居を隠すためのものではなく、空き家と存在しない住所に見せるプロフィールがないことを同じ形で返すもの。
    - 手紙の 422 `not_acquainted` と、住所録の追加の同じ 201（ADR-0049 の D4・D5）は変えない。相手が自分を足したかを探らせないため。
    - 候補の印を押して選ぶために、経路・応答の項目を足さない。`GET /api/v1/addresses/candidates` と登録の要求の形は変えない（D7）。
    - 空き家の印から住所を選ぶ経路は作らない（登録の候補は今までどおり `GET /api/v1/addresses/candidates` の候補から、地図の候補の印か一覧で選ぶ。D7。空き家の印も選べるかは OQ-089）。
17. **D17 要求の区分（ADR-0024 の決定 5）**: FR-115 は `[inferred]`（OQ-054 の答え 3 と OQ-079 の答え 1・2 より）とし、経路と応答の形（D15）・状態の時点（D14）は `[assumed]`。
    FR-006 は、ログインしないだけでは空き家にしないこと・休眠を入居と示すことを OQ-079 の答え 2 による `[inferred]` とし、休眠を空き家にする判定と閾値を OQ-088 にする。
18. **D18 流量の制限と差分（秘書の判断）**:
    - 入居の一覧には、IP ごとの流量の制限を掛け、超えた要求には 429 `rate_limited` を返す（`security.md` §3.5。上限の数値は実装の段階で決める `[assumed]`）。負荷（DoS）を抑えるため。
    - 応答のキャッシュ（サーバー側・`Cache-Control` での共有キャッシュ）は置かない `[assumed]`。D14 の「要求を受けたときの状態」をそのまま保つため。1 回の応答は住所のプール（ADR-0012 の想定で 1 万程度）の住所と 2 値だけで、1 つの問い合わせで返せる（`db.md` §2）。
    - 繰り返し取って差分を見れば、どの住所でいつごろ登録や退去があったかが分かる。これは答え 1「全員にいつでも公開してOK」「登録前、後いつでも確認が可能」の範囲として受け入れる。流量の制限は差分を見ることを止めるものではない。
    - 差分から分かるのは住所と、入居か空き家かが変わった時刻のおおよそだけで、誰が住み始めたか（名前・自己紹介）は分からない（D15。プロフィールはログインが要る）。

## 理由

- D1・D2 は OQ-054 の答え 1〜3 による。知り合いの家の印を M2 に置くのは、住所録（F-09）が M2 で、M1 には印にする住所がないから。入居の層は登録の画面に要る（答え 1「登録前」）ので M1 に置く。
- D3 は、OQ-044 の答えの「全ユーザーで共有して」と、印と入居の表示を、両方とも満たすため。土台を同じにし、層を本人の画面の上だけで重ねれば、共有する地図を崩さずに出せる。
- D4・D5 で家の一覧を C1 の静的なファイルに持たないのは、家の一覧と入居の 2 値を 1 つの応答から得れば、静的なファイルとプールの定義（C3）の 2 か所に同じ一覧を持たずに済むから（NFR-055）。
  位置は今までどおり番と号からの計算で求め、応答に座標を足さない。
- D7 で候補の印を押して選ぶのは、OQ-080 の答え「b」による。一覧を残すのは、地図だけにすると、画面を読み上げて使う人や細かい印を押しにくい人が選べず（NFR-041）、配置の定義にない住所の候補（D4 で印を付けない）を選べなくなるから。
  一覧と地図の選択を 1 つの状態にするのは、2 か所で違う候補が選ばれて見える状態を作らないため。押せる印を候補だけにするのは、答えが「候補の印を押して選ぶ形」で、空き家の印は答えにないから（OQ-089）。
  候補は候補の提示の中の住所なので、地図で選んでも登録で送るものは変わらず、経路を足さずに済む。
- D8 で入居を 2 つの形で示すのは、白黒の地図（ADR-0061 の D2）で、色に頼らずに見分けるため。押す処理を React のハンドラで付け、文字列のイベント属性を入れないのは、印の層に属性の文字列からコードを動かす道を作らないため（`security.md` §7 の T-07）。
- D9 で数を入れないのは、地図を住民の数の出る場所にしないため（P-2）。住所の一覧を数えれば分かることでも、画面と応答に数を出さない。
- D10 は答え 1 による。街のすべての家の入居の有無を見せると、名前がなくても人が住んでいる住所の一覧になる（`security.md` §7 の T-05）が、公開の範囲はマスターが決めることで、答え 1 で全員に見せると決まった。
  OQ-066 の答え（ADR-0049）で手紙は知り合いにしか出せないので、住所の一覧を手に入れても、知らない住民に手紙を出す相手の一覧には使えない。
- D13 は答え 2「休眠は空き家にしない」による。使われたことのない住所と退去のあとの住所を同じ `false` にするのは、答えの「boolean的に表示」と、退去の経緯を外に出さないため。
  転送中の旧住所を入居と示すのは、`addresses.status` が `active` のままで、今の状態の読み方を足さずに済むから（段階 3 で見直す、OQ-088）。
- D14 は、答え 1「いつでも確認が可能」を、要求を受けたときの状態で満たす最も小さい形だから。スナップショットを持つと、表とジョブが要る（NFR-055）。
- D15 で並びを番・号の順にし、登録の順に依らせないのは、1 回の応答の並びだけから住み始めた順を読み取らせないため。繰り返し取った差分から変わった時刻が分かることは、D18 で答え 1 の範囲として受け入れる。件数を返さないのは P-2 と ADR-0014（数を返さない）による。
  家の集合をプールの定義にするのは、候補に出る住所と地図に出る家を同じにし、どちらかにだけある住所を作らないため。
- D18 で差分を受け入れるのは、答え 1 が「いつでも」見せると決めており、いつ見ても今の状態が分かる以上、2 回見れば変わったことも分かるから。差分を隠すには、示す状態を遅らせるか丸めるしかなく、答え 1 の「いつでも確認が可能」を弱める。流量の制限は、認証なしの経路が街のすべての家を毎回返すので、負荷を抑えるために置く。
- D16 は、変えなくても答えを満たせ、変えると相手が自分を足したかの探り（ADR-0049 の D4・D5、OQ-081 (3)）が増えるから。

## 代わりの案（選ばなかった理由）

- **住民ごとに印を描き込んだ SVG を出す**: 土台が住民ごとに変わり、全住民で共有する画像（ADR-0061 の D1 (a)）と食い違う。
- **住所ごとの位置を DB の表に持ち、地図の API で返す**: 位置は計算で求められ、新しい表が要らない（ADR-0063 の D3）。
- **候補の一覧から選び、地図の印は押さない**: OQ-080 の答え「b」と食い違う。
- **候補の一覧をなくし、地図の候補の印だけで選ぶ**: 地図を見られない人・押しにくい人と、配置の定義にない住所の候補が選べなくなる（NFR-041、D4）。答えは地図の印で選べることを求めており、一覧をなくすことは求めていない。
- **空き家の印も押して選べるようにする**: 答えに書かれていない（OQ-089）。候補の提示（ADR-0001）の外の住所を選ぶ経路と、割り当ての規則が要る。
- **印に `onclick` などの文字列のイベント属性を書く**: 属性の文字列からコードが動く道ができ、`security.md` §7 の T-07 の守りと食い違う。React のハンドラで足りる。
- **表示の窓を自分の家を中心に切り取る（街の一部だけを見せる）**: 拡大・移動がないので、窓の外の家が見えなくなる。
- **知り合いを「互いに住所録に入れた住民」とする**: 地図の印から、相手が自分を住所録に入れたかを推し量れる（OQ-071 の答え、ADR-0051）。
- **入居の一覧をログインした住民だけに見せる**: 答え 1 の「登録前、後いつでも」と食い違う。
- **番ごと（区画ごと）にまとめて示す**: 答え（家ごとに「空き家か人がいるか」）と食い違い、まとめると数になる（P-2）。
- **休眠を空き家と示す**: 答え 2 と食い違う。
- **状態の種類（使われたことがない・退去のあと・休眠）を応答で分ける**: 答えの「boolean的に表示」を超え、退去の経緯が外に出る。
- **配達の時刻ごとに区切った状態を示す**: スナップショットの表とジョブが要り、答え 1「いつでも」に対して得るものがない。
- **短いキャッシュや状態の遅らせで差分の時刻をぼかす**: D14 の「要求を受けたときの状態」と食い違い、退去のすぐあとに空き家と示せない。ぼかしても、変わった日はおおよそ分かる。
- **自分の家・知り合いの家を入居の一覧の応答で区別する**: 応答が呼んだ人で変わり、キャッシュと確かめ方が複雑になる。印は D5 のほかの API で付けられる。
- **`GET /profiles/{address}` で空き家を 404 と分ける（例: 410）**: 入居の一覧で分かることを別の形で返すだけで、得るものがない。プロフィールの経路の形を変えずに済む。

## 決めていないこと

- 空き家の印も押して選べるようにするか: OQ-089（要回答）。暫定は押せず、選べるのは候補の印と一覧だけ（D7）。
- 休眠を空き家にするか・その閾値・転送中の旧住所を入居と示すか: OQ-088（持ち越し。段階 3 の F-16 の前にマスターに聞く）。暫定は、休眠を空き家にしない（ADR-0060 の D2・D3）ことと D13。
- 登録の画面のほかのログインの前の画面に地図を出すか: MVP では出さない `[assumed]`（ADR-0063 の D1）。
- 足した側が、相手もすでに自分を足していたと知れること（探り）を許すか: OQ-081 (3)（要回答）。
- ゲーム風の地図: OQ-055（持ち越し、ADR-0061 の D4）。
- 印の形・大きさ・見出しの置き方・選んだ候補の印の形と、代替テキストの文面: 実装で決める（D7〜D9 の範囲の中で）。アクセシビリティの水準は OQ-033（持ち越し）。
