## §1 分類と扱い

### 分類

| 分類 | 意味 |
|------|------|
| 不足 | 構想・要件・機能に記述がなく、設計・実装に進むと定義できないもの |
| 未確定 | 記述はあるが値・範囲・方針が確定していないもの |
| 矛盾 | 文書間または文書内で記述が食い違っているもの |
| リスク | 決定しないままにすると品質・安全性・体験に悪影響が出るもの |

### 扱い

| 扱い | 意味 |
|------|------|
| 要回答 | マスターの判断が必要。質問の形で記載し、暫定対応がある場合は添える |
| 決定 | 秘書が判断し ADR に記録した、またはマスターの答えで決まり ADR に記録した。理由（マスターの答えなら原文と日付）と ADR 番号を添える |
| 持ち越し | 後続の設計文書（architecture/db/api/async/security/roadmap/environment）で決定する |

### OQ-001 — マッチングは恋愛のためのものではない（未確定 → 決定）

**関連**: FR-061, FR-064, FR-069, FR-101, F-18  
**もとの質問**: 恋愛マッチングの利用を 18 歳以上に限定するか。年齢確認の手段も合わせて。  
**マスターの答え（2026-11-19）**: 「理想としては、恋愛ではない。あくまで、興味ある人同士が連絡を取れる手段。個別に連絡先の共有などは絶対禁止にする予定」  
**決定**: マッチングは恋愛のためのものではなく、恋愛のカテゴリは設けない。恋愛のための年齢条件・年齢確認は要らない。
マッチングは興味のある住民どうしが連絡を取れる手段で、成立後は街の中の手紙でやり取りする。
住民どうしが個別に連絡先を共有することは禁止する（FR-101）。マッチングの登録と提案に、街の外の連絡先の欄を設けない。
「連絡先」は街の外の連絡先だけで（OQ-041 → 決定、2026-11-19）、禁止は全ての書き込みに及ぶ（OQ-087 → 決定、2026-11-22、ADR-0071）。  
**決めていないこと**: マッチングの中での守り方の細部（OQ-050、持ち越し）。未成年とマッチングへの参加の年齢条件（OQ-004 → 決定、年齢条件なし、ADR-0027）。違反した住民への処置（OQ-037 → 決定、内容はマスターが後で決める、ADR-0032。残りは OQ-048、持ち越し）。  
**ADR**: [0024-matching-not-romance-no-contact-sharing](.ai/adr/0024-matching-not-romance-no-contact-sharing.md)

### OQ-002 — 配達完了の通知は送り、郵便の件数を含める（未確定 → 決定）

**関連**: FR-028, FR-102, F-05  
**もとの質問**: 朝便・夕便の配達完了時に住民へプッシュ通知を送るか。送る場合は通知の内容（「郵便が届いた」のみか、件数も含めるか）。  
**マスターの答え（2026-11-19）**: 「通知あり（内容：郵便の件数を含む）」  
**決定**: 配達回の公開のあとに、住民へ通知を 1 回送り、その住民に届いた郵便の件数を含める。

### OQ-042 — 新聞は全住民に定時に届けて通知し、手紙は午前・午後のランダムな時刻に届けて件数を通知する（未確定 → 決定）

**関連**: FR-028, FR-014, FR-022, FR-023, FR-030, FR-031, FR-032, FR-105, FR-106, F-05, F-06, ADR-0076  
**もとの質問**: OQ-002 の答えで「通知あり（内容：郵便の件数を含む）」と決まった。(1) 件数として数える「郵便」は手紙だけか。新聞（朝刊・夕刊）も 1 件として数えるか。
(2) その便で手紙が 0 通の住民にも通知を送るか。(3) 件数のほかに通知に載せたいもの（差出人の住所など）はあるか。  
**マスターの答え（2026-11-19）**: 「何も届かないのは悲しいね。何かしら送りたい。例えば、興味があることを回収して、ニュースを加工して新聞にする。とか。新聞も知り合いの数がいないと成り立たない可能性がある。何かしら新聞を送る方向で考え、通知についても送る。手紙の配達と新聞の配達は時間を分ける。手紙については、出した時間に応じて午前、午後にランダム、新聞は一定の時間。新聞が配達されました！手紙が配達されました！（３通）みたいな形かな。」  
**決定**: 新聞は手紙の有無にかかわらず全住民に届け、通知も送る（D1、答え）。新聞は一定の時刻（朝刊 07:00・夕刊 17:00）に届け、手紙とは時刻を分ける（D2、答え）。
手紙は出した時刻に応じて午前か午後に、ランダムな時刻で届く。振り分けは今の締め切り（01:00 / 14:00）で、朝便の手紙は午前 08:00〜12:00、夕便の手紙は午後 18:00〜21:00 に届く（D3、答え。時間帯は D8 [assumed]）。
通知は「新聞が配達されました！」（件数なし）と「手紙が配達されました！（N通）」の 2 つに分け、差出人・本文・住所は載せない（D4、答え）。
手紙が 0 通の住民には手紙の通知を送らない（D5、答えから読み取ったもの）。手紙の時刻は配達回ごと・住民ごとに 1 つで、同じ回の手紙はまとめて届く（D6）。
時刻は 10 分刻みの枠を `SHA-256(run_id:resident_id)` で決め、J4 が `mailbox_items.visible_at` に書く。公開（J5）と状態の確定は今のまま 07:00 / 17:00。
新聞の通知は J5 が、手紙の通知は J0 が枠ごとに積み、期限はそれぞれの時刻から 30 分（D9〜D12、秘書の判断）。  
**決めていないこと**: 知り合いが少なくても成り立つ新聞の中身（住民ごとに変えるか・興味を集めるか・ニュースの出どころ・加工に LLM を使うか。OQ-051）。答えの「興味があることを回収して、ニュースを加工して新聞にする」は例で、決定にしていない（OQ-051 → 決定、2026-11-20、ADR-0039。残りは OQ-058〜OQ-062。OQ-058 はのちに決定、2026-11-20、ADR-0044。OQ-059 ものちに決定、2026-11-20、ADR-0045。OQ-061 ものちに決定、2026-11-20、ADR-0046）。  
**ADR**: [0035-newspaper-for-all-letters-random-am-pm-separate-notifications](.ai/adr/0035-newspaper-for-all-letters-random-am-pm-separate-notifications.md)

### OQ-051 — 新聞は一人 1 枚にせず、知り合いの数で分けた組ごとの版にする。知り合いのない組は興味で分け、記事の文字は LLM が作り、組版はサーバーで行う（不足 → 決定）

**もとの質問**: OQ-042 の答えで、新聞は全住民に一定の時刻に届けると決まった（ADR-0035）。住民や投稿が少ないと紙面がほとんど空になる。

**マスターの答え（2026-11-20）**:  
「１：変えたいが、サーバー負荷考えると一人１枚はきつい。知り合いで埋まるグループ一部埋まらないグループ、知り合い0のグループで分けて、0のグループは趣味、興味でさらにグループして出し分ける」

「３：a,b」

住民が見られるのは自分の郵便受けに届いた版だけ（D11、秘書の判断）。MVP の M5 に入れる（D12）。FR-106 を直し、FR-108〜FR-111 を足した（D13）。  
**決めていないこと**: 知り合いで埋まる組・一部埋まらない組の紙面（OQ-058 → 決定、2026-11-20、ADR-0044。MVP は全住民を知り合い 0 の組とする。残りは OQ-070（持ち越し）・OQ-071（→ 決定、2026-11-20、ADR-0051））。検索などから興味を集めること（OQ-059 → 決定、2026-11-20、ADR-0045。自分に届いた過去の新聞の検索から集める。残りは OQ-072（→ 決定、2026-11-21、ADR-0053。住民は止められない））。外のニュースの配信元・利用の条件・費用（OQ-060、持ち越し）。
LLM が書いた文の示し方と、住民の投稿を LLM が書き換えてよいか（OQ-061 → 決定、2026-11-20、ADR-0046。投稿は書き換えず、LLM の文に印は付けない。残りは OQ-073（持ち越し）・OQ-074（→ 決定、2026-11-21、ADR-0054。投稿の記事は見出しだけ））。新聞の LLM のモデル・プロンプトと、記事と興味の結び付け方（OQ-062、持ち越し）。  
**ADR**: [0039-newspaper-editions-by-group-and-interest-llm-text-server-typesetting](.ai/adr/0039-newspaper-editions-by-group-and-interest-llm-text-server-typesetting.md)

### OQ-052 — 手紙は送るときにスパム・外部リンク・成人向けの言葉に当て、当たったら送った人が確認を頼むかを選び、頼んだ手紙をモデレーターが確かめる。年齢で守り方を変え、年齢は住民の設定をそのまま使う（未確定 → 決定）

照合は送るとき（`POST /api/v1/letters`）に、API が暗号化の前に行う。worker は手紙を照合しない（J1 は `moderation_queue` に手紙の行を入れず、J2 は手紙を扱わず、J4 は判定を見ずに準備する）（D2、答え 2）。

**決めていないこと**: 年齢で何を変えるか（止める項目・使える機能・年齢の区切り。OQ-063 → 決定、2026-11-20、ADR-0047。年齢による違いは作らない）。

「２：架空でOK。開いてる商店には入居者募集的な張り紙を導入したい。これもMVP時点では仮でOK。内容は、広さによって決定される、新聞への掲載頻度と記事の大きさ。金額についてはLPなどに問い合わせを設けて、そこから連絡をもらい資料内に記載する。入居者募集張り紙に具体的な金額は載せない」  
「３：お店の担当者。」  
「４：MVPで不要のため、改めて時期が来たら考えるが、広さと料金によって出せるものを変える。折込チラシはそのランクの中の最高」  
「５：商店は実在の情報を出してOK」  
**決定**（ADR-0043）: 実在の店とは契約を結び、利用料を場所の広さ・新聞に載る頻度・記事の大きさに比例させる考えを、メモとして残す。MVP では商店の具体的な仕組みを作らない（D1、答え 1）。
実在の店が来るまで架空の店を置いてよい（D2、答え 2「架空でOK」を問い (2) への答えと読むのは秘書の読み方）。
空いている商店の区画に入居者募集の張り紙を出し、中身は広さで決まる「新聞に載る頻度」と「記事の大きさ」とする（暫定）。具体的な金額は載せず、LP などの問い合わせから連絡を受けて資料の中で伝える。LP・問い合わせ・資料はアプリの外にあり、今は計画として書くだけ（D3、答え 2。「開いてる」を「空いている」と読むのは秘書の読み方）。
商店として発信するのはお店の担当者で、アカウントは運用者の CLI で作って担当者に渡し（ADR-0067 の D1・D2）、発信は配達の前に審査する（D4、答え 3）。
出せるものは広さと料金のランクで変え、折込チラシをランクの最高に置く。F-20 はこのフェーズの範囲外のまま（D5、答え 4）。
商店はお店の実在の情報（お店の名前など）を出してよい。`security.md` §2.2 の例外は、お店の実在の情報についての「実名・氏名」の項目だけで、ほかの項目（電話番号・顔写真・位置情報・決済情報など）は OQ-068・OQ-069 で決めるまで商店にも当てる。
担当者・経営者など個人の情報をどこまで出すかは答えに書かれておらず、公開の範囲にかかわるので決めない（OQ-069 (3) で S3-2 の前にマスターに聞く）。住民の実名を集めないことと、レポジトリ・テスト・シードに実在の名前を入れないこと（ADR-0038 の D5）は変えない（D6、答え 5）。
F-17 は段階 3 のままで、商店の部分は要回答では止まらない（D7）。FR-104・FR-047 を直し、FR-116・FR-117 を足した（D8）。  
**決めていないこと**: 架空の店と張り紙をいつ・どう出すか（MVP に入れるか・架空と示すか・架空の店が発信するか）は OQ-067（要回答 → 決定、2026-11-20、ADR-0050。広告をいつから出すかは OQ-083 → 決定（2026-11-21）、細部は OQ-084（持ち越し））。
契約・利用料・ランクの中身は OQ-068（持ち越し、マスターが決める）。担当者のログイン・主体・権限、区画の割り当てと広さ、実在の情報の項目、新聞への載せ方は OQ-069（持ち越し。担当者・経営者など個人の情報の公開の範囲はマスターに聞く）。

### OQ-058 — MVP は全住民を知り合い 0 の組とする。新聞の知り合いは互いに住所録に入れた住民で、載せるのは知り合いの掲示板の投稿（手紙は載せない）。組 1・2 は住民ごとに組み、足りない分は興味の版か共通の版の記事で埋める。アップロードした元の画像は持たない（不足 → 決定）

**関連**: FR-108, FR-118, F-06, F-11, ADR-0039, ADR-0042  
**もとの質問**: OQ-051 の答えで、新聞は一人 1 枚にせず、「知り合いで埋まるグループ」「一部埋まらないグループ」「知り合い0のグループ」に分け、知り合い 0 の組は趣味・興味で分けて出し分けると決まった（ADR-0039 の D1〜D3）。知り合いのいる 2 つの組について、次の 5 点を聞いた。
(1) 「知り合い」は誰か（(a) 自分の住所録に入れた住民、(b) 互いに住所録に入れた住民、(c) 手紙をやり取りしたことのある住民）。地図の印（ADR-0042 の D1 (c)、(a)）と同じ定義にするか。
(2) 知り合いの何を紙面に載せるか。手紙は載せない前提でよいか。知り合いの側の同意は要るか。
(3) 組 1・2 の紙面を組の中で共有するか、住民ごとに組むか（版の数が住民の数で増え、サーバーの負荷にかかわる）。
(4) 一部埋まらない組の足りない分を何で埋めるか。(5) 「埋まる」の境を秘書が決めてよいか。  
**マスターの答え（2026-11-20）**:  
「暫定通りで。全住民を「知り合い0の組」として扱う。」  
「(1) 知り合いの定義は b。新聞でも同じ定義」  
「(2) 一般的なSNSのツイートに当たる部分。手紙はDMなので新聞には載せない。」  
「(3) サーバー負荷は要検討だが、現時点では知り合いに合わせて構成したい。一般的なSNSと異なり、動画、画像を自由に無制限に上げることはできないので、割と軽量だと思ってる。アップロードした画像は新聞用に加工し、元データは保持しない方針」  
「(4) 共通の記事と興味の記事。」  
「(5) 秘書（システム）の設計で決めていい。手間をかけずに、シンプルに動く仕組みにすること。」  
**決定**（ADR-0044）: MVP（M5）では全住民を知り合い 0 の組として扱い、組 1・2 は作らない（D1、答えの冒頭）。
新聞の「知り合い」は互いに住所録に入れた住民で、互いの `address_book.registered_tenancy_id` が相手の今の居住記録を指すときだけとし、どちらかがブロックしていれば知り合いにしない（D2、答え (1)。ブロックは秘書の判断）。
組 1・2 の紙面に載せるのは、その配達回の承認済みの掲示板の投稿のうち知り合いが書いたものだけで、手紙は載せない（D3、答え (2)。「ツイートに当たる部分」を掲示板の投稿と読むのは秘書の読み方）。
組 1・2 の版は住民ごとに組み（`acquaintance:<resident_id>`）、本人だけが見られる。記事の文字は素材ごとに 1 回だけ作って使い回すので、LLM の費用は増えない（D4、答え (3)）。
アップロードした画像は新聞用に加工し、元の画像は加工が終わるか失敗した時点で消し、取りこぼしもアップロードから 24 時間 `[assumed]` を過ぎたあとの次の J14 が消す（最長で約 48 時間）（D5、答え (3)。段階 2）。
組 2 の足りない枠は、その住民が組 0 なら受け取る版（興味の版か共通の版）の記事で、その版の順に埋める（D6、答え (4)）。
組の境は、組を保存せず J3 が配達回ごとに計算する。記事の枠の数を S、知り合いの記事の件数を k として、k = 0 なら組 0、1 ≤ k < S なら組 2、k ≥ S なら組 1（D7、答え (5)、秘書の判断）。
FR-108 を直し、FR-118 を足した（D8）。  
**決めていないこと**: 組 1・2 をいつ作るか・負荷の見積もり・知り合いの側の同意（OQ-070、持ち越し）。
答えの「新聞でも同じ定義」が地図の決定（ADR-0042 の D1 (c)、(a)）と食い違うので、地図の知り合いの印も (b) にするか（OQ-071 → 決定、2026-11-20、ADR-0051。地図は (a) のままで、新聞と定義を分ける）。

### OQ-059 — 興味は、自分に届いた過去の新聞の検索から推し量って集める。検索語は残さず、当たった興味だけを持つ。住民には明るく開いた文で知らせ、個別の同意は取らない。推し量った興味を本人が見て消す仕組みは設けない（不足 → 決定）

**関連**: FR-109, FR-119, F-06, F-02, F-12, ADR-0039  
**もとの質問**: OQ-051 の答えで、興味は「登録の時と後から設定、検索などから収集しようかな」と決まり、登録のときとあとからの設定で集めることにした（ADR-0039 の D4）。
検索などから集めることは、住民の行いから興味を推し量ることになるので、次の 4 点を聞いた。
(1) どの検索から集めるか（今ある検索は住所録の検索 `?q=` だけで、自分のメモも検索する私的なもの）。(2) 「など」に入るものは何か（例: 読んだ記事・掲示板の投稿の中身）。
(3) 集めることを住民に知らせるか。同意を取るか。住民が止められるか。(4) 推し量った興味を、本人が見て消せるようにするか。  
**マスターの答え（2026-11-20）**:  
「1:過去の新聞」  
「2: などについては具体的に考えていない。設計詰めながら、利用できそうなところを秘書が検討、追加してOK」  
「3: 知らせるが、個別に同意は取らない。興味から新聞を届けます！と、ポジティブにオープンにする」  
「4: 設けない。」  
**決定**（ADR-0045）: 興味を集める検索は、自分に届いた過去の新聞（バックナンバー、F-12、段階 2 の S2-3）の検索（`GET /api/v1/newspapers?q=`、FR-119）だけとする（D1、答え 1。自分に届いた版に限るのは秘書の読み方、ADR-0039 の D11）。
住所録の検索からは今までどおり集めず、検索語を DB・ログに残さない。MVP（M5）には検索がないので、MVP の興味は登録と設定だけのまま。
「など」はこの変更では足さず、足すときは ADR を書き、知らせの文も同じ変更で直す。手紙・住所録とメモ・ブロック・通報・ログインや通知の記録からは集めない（D2、答え 2、秘書の判断）。
API が検索語を NFKC・小文字にそろえ、`active` な興味の `label` か `interest_categories.keywords` を含むかをメモリの中だけで調べる。LLM は使わない（D3、秘書の判断）。
当たった興味の ID だけを `inferred_interests` に書き、検索語はどこにも残さない（D4）。1 人 5 つまで、最後に当たってから 30 日で J14 が消し、退去の J7 では即時に消す（D5。5 つと 30 日は `[assumed]`）。
J4 で版を選ぶ候補は、選んだ興味と推し量った興味を合わせた集合にする（D6）。
同意の画面やチェックは置かず、検索の画面と利用の案内で、明るく開いた文（原文の「興味から新聞を届けます！」を入れる。文言は仮置き）で知らせる（D7、答え 3）。
推し量った興味を本人が見る・消す経路は作らない。`GET /api/v1/me/interests` もエクスポートも返さず、ほかの住民・モデレーター・LLM にも渡さない（D8、答え 4）。
M5 は変えず、S2-3 に検索と受け入れ条件 B-09 を足す（D9）。FR-109 を直し、FR-119 を足した（D10）。  
**決めていないこと**: 住民が推し量ることを止められるか（OQ-072 → 決定、2026-11-21、ADR-0053。止められない）。
知らせの文言・検索のしかた・`keywords` の中身（S2-3 で決める。`keywords` は OQ-062）。推し量った興味を本人に返さないことと、法令の開示の求めとの関係（OQ-032 で調べる）。

### OQ-061 — 新聞の LLM の文に「AI が書いた文」の印を付けない（規約は確かめる）。住民の掲示板の投稿の本文は書き換えずにそのまま載せ、LLM が書くのは生成部分だけにし、LLM の文を住民本人の文に見せない（未確定 → 決定）

**関連**: FR-111, F-06, ADR-0039  
**もとの質問**: OQ-051 の答えで、記事の文字は LLM が作ると決まった（ADR-0039 の D7）。答えには、LLM が書いた文の扱いが書かれていなかった。
住民の文を住民の知らないうちに LLM が書き換えることと、AI の文を人の文に見せることは倫理にかかわるので、次の 2 点を聞いた。
(1) LLM が書いた文（見出し・まとめ・外のニュースの記事）を、紙面でどう示すか（例: 記事ごとに「AI が書いた文」の印を付ける・紙面の欄外にまとめて書く・示さない）。
(2) 住民の掲示板の投稿の本文を、LLM が要約したり書き直したりして載せてよいか。よい場合、投稿した住民に知らせるか・断れるか。  
**マスターの答え（2026-11-20）**:  
「１：示さなくて良い。規約次第なので、要確認。」  
「２：住民の掲示板の投稿本文は、書き換えずにそのまま載せる。LLMが手を加えるのはあくまでニュース記事などの生成部分のみ。住民の生の声を勝手に加工して、あたかも本人が書いたように見せることはしない。」  
**決定**（ADR-0046）: 紙面は LLM が書いた見出し・まとめ・外のニュースの記事に「AI が書いた文」の印を付けず、欄外にまとめて書くこともしない（D1、答え 1）。
「規約次第なので、要確認」は OQ-073（持ち越し）にし、本番の文章アダプタを作る前に、秘書が J16 の LLM のサービスの規約（ADR-0086）と外のニュースの配信元の規約（OQ-060 と一緒に）を読んで結果をマスターに出す（D2。「規約」を外部のサービスの規約と読むのは秘書の読み方）。
`newspaper_articles.written_by` は見張りのために残し、紙面には出さない（D3）。
投稿の本文は書き換えずに `board_posts.body` をそのまま載せる（D4、答え 2）。LLM が書くのは生成部分（外のニュースの記事の文と見出し・まとめ）だけ（D5）。投稿の素材の見出しとまとめも「生成部分」と読んで LLM が書くのは秘書の読み方で暫定にし、書いてよいかは OQ-074（要回答）でマスターに聞いた
（OQ-074 → 決定、2026-11-21、ADR-0054・ADR-0055。見出しだけ書き、まとめは書かない。下の D6 の条件は見出しに当てる）。
投稿の本文は投稿の枠に入れ、その枠には `board_posts.body` だけを入れ、LLM の文は枠の外に新聞の文として置く。まとめを住民の言葉として書かせないことを、OQ-062 でプロンプトを決めるときの条件にする（D6、答え 2。のちに投稿の記事はまとめを書かないことになり、条件は見出しに当てた、ADR-0054 の D6）。
M5 の中身は変えず、A-17 (6) を直した（D7）。FR-111 を直した（D8）。  
**決めていないこと**: 規約が AI の文であることを示すよう求めるか、求めるならどう示すか（OQ-073、持ち越し）。住民の投稿を素材にした記事で LLM が見出しとまとめを書いてよいか（OQ-074 → 決定、2026-11-21、ADR-0054。見出しだけ書いてよい）。紙面に投稿者を出すか（今の文書のまま）。
外のニュースを LLM で書き直してよいか（OQ-060 のまま）。住民への説明（OQ-032 のまま）。プロンプトの中身（OQ-062）。

### OQ-063 — 年齢による違いは作らない。手紙と掲示板で止める基準・使える機能は全員に同じにし、詐欺と事件の防止も全員に同じ共通のルールで行う。年齢の区切りは置かない（不足 → 決定）

**関連**: FR-113, FR-094, FR-064, FR-112, FR-120, F-02, F-08, F-18, ADR-0041, ADR-0040, ADR-0027, ADR-0078  
**もとの質問**: OQ-052 の答え「３：変える。」で、住民の年齢で守り方を変えると決まった（ADR-0041 の D1）。何を変えるかと年齢の区切りは答えに書かれていなかったので、次の 3 点を聞いた。
(1) 年齢で、手紙と掲示板で止める項目を変えるか（例: 成人向けの言葉を、ある年齢より下の住民の手紙にだけ当てる・送る側か受け取る側のどちらの年齢で決めるか）。
(2) 年齢で、使える機能を変えるか（例: マッチングへの参加・知らない住民からの手紙を受け取るか・1 日の送信の上限。高齢の住民を詐欺から、若い住民を事件から守る守りを含む）。
(3) 年齢の区切りは何歳か。  
**マスターの答え（2026-11-20）**:  
「暫定の通り「年齢による違いは作らない」で進めて。」  
「(1) 手紙と掲示板のブロック対象は、年齢に関係なく全ユーザー共通の基準でフィルタリングする。特定の年齢層だけに別の言葉を出すような複雑なことはしない。一律、問題がある記載は一才許可しない」  
「(2) 機能の解放条件も年齢に紐付けない。詐欺防止や事件防止についても、年齢で制限するのではなく、システム全体の共通ルール（スパム検知や不審な挙動への対処）として実装すること。」  
「(3) 年齢による区切りは設けない。」  
「「年齢で守り方を変える」という言葉の意図は、将来的に「もし変えるとしたら」という拡張性や、データ構造として年齢を持っておくこと、あるいは年齢によって（属性として）表示が変わる可能性を含んでいるだけで、実装レベルで年齢ごとにフィルタリングロジックを分岐させるコストは払わない。シンプルに、全員に同じルールを適用する。」  
**決定**（ADR-0047）: 手紙と掲示板で止める基準は、送る人・受け取る人の年齢に関係なく全員に同じにし、ルール表に年齢の条件を持たせず、年齢層ごとに別の言葉の一覧を持たない（D1、答え 1）。
「一律、問題がある記載は一才許可しない」が、当たった手紙を送った人の確認とモデレーターの承認でも届けず一律に止めるという意味かは読み切れないので、OQ-076 で聞いた
（OQ-076 → 決定、2026-11-21、ADR-0069・ADR-0057。「1の方針」を土台に、照合を絶対NGと疑いの 2 段に分けた。「一律」は年齢で例外を作らないことと読む）。

### OQ-064 — 年齢は登録で必須にし、あとから変えられない。年は登録の日から 1 年ごとに進む。ほかの住民には、本人から手紙を受け取った住民にだけ見せる（不足 → 決定）

**関連**: FR-113, FR-094, FR-008, F-01, F-02, ADR-0041, ADR-0047, ADR-0027, ADR-0078  
**もとの質問**: OQ-052 の答えで、年齢は住民が設定した値をそのまま使い、架空の年齢も許すと決まった（ADR-0041 の D2）。OQ-063 の答えで、年齢による違いは作らないと決まった（ADR-0047）。
年齢の項目の扱いについて、次の 4 点を聞いた。
(1) 登録のときに年齢の入力を必須にするか、任意にするか。(2) 年齢をあとから変えられるか。
(3) 年齢を、ほかの住民に見せるか。見せるなら、年齢の属性で何の表示が変わるか。(4) 年齢は年とともに進むか。  
**マスターの答え（2026-11-20）**:  
「(1) 必須」  
「(2) 変更は不可」  
「(3) 一定条件で見せる。一定条件は安全性に基づき秘書が決定する」  
「(4) 進む。誕生日の情報も新聞に載せたら面白そう」  
**決定**（ADR-0048）: 登録（`POST /api/v1/registrations`）は `age`（整数）を必須で受け取る。ない・整数でない・0〜999（`[assumed]`）の外なら 400。既定値と「未設定」は置かず、登録の画面で「年齢はあとから変えられません」と示す（D1、答え 1）。
`PATCH /api/v1/me` は `age` を受け取らず、要求にあれば 400。モデレーター・運用者の CLI を含め、年齢を書き換える経路は作らない。直したい住民は退去して登録し直す（D2、答え 2）。
`residents` に `age_at_registration`（0〜999）と `age_base_date`（登録した日の JST の日付）を置き、今の年齢は基準の日から JST の日付で満了した年数を足して、C2 が読むときに計算する（2/29 はうるう年でない年は 3/1 に上がる。ジョブは持たない）（D3、答え 4）。
本人には `GET /api/v1/me` が今の年齢を返す。ほかの住民には、`GET /api/v1/profiles/{address}` が次をすべて満たすときだけ `age` を返す（D4、答え 3。条件は秘書が安全性に基づいて決めた）:
(a) 見る住民の郵便受けに、プロフィールの住民が送った手紙が `visible_at` を過ぎて 1 通以上ある（見る住民が削除した手紙は数えない）。(b) その手紙が、プロフィールの住民の今の居住記録の始まり以後に出された。(c) 見る住民が、プロフィールの住民をブロックしていない。
プロフィールの住民が見る住民をブロックしても、見え方は変えない（ブロックを気づかせない、security.md T-06・ADR-0015）。
住所録・地図・掲示板・新聞・マッチング・通知・検索・モデレーターと運用者の画面・LLM・ログ・ジョブのペイロードには出さず、見せるかの住民の設定も置かない。
年齢は平文で持ち、退去で行ごと即時に消す（D8）。ADR-0041 の D5・ADR-0047 の D5 のその部分・ADR-0027 の D3 の「年齢を集めない」を置き換えた（D7）。年齢で守りと権限を変えないこと（ADR-0047）は変わらない。FR-008・FR-113 を直した。  
**決めていないこと**: 誕生日を集めて新聞に載せるか（OQ-077 → 決定、2026-11-21、ADR-0093・ADR-0074。誕生日は必須で変えられず、年齢は誕生日に進み、知り合いの紙面にだけ載せる）。
年齢の属性で何の表示が変わるか（OQ-078、持ち越し。暫定は作らない）。適用法令が年齢の収集と表示について何を求めるか（OQ-032、持ち越し）。

### OQ-066 — 手紙は知り合いにだけ出せる。知り合いは互いに住所録に入れた住民（既定）か、掲示板で相手がオープンにした住民。足されたことは相手に知らせない（不足 → 決定）

**関連**: FR-115, FR-114, FR-012, FR-052, FR-053, FR-058, FR-121, FR-122, F-19, F-09, F-04, F-07, ADR-0042, ADR-0044, ADR-0048（OQ-040・OQ-071 にかかわる）  
**もとの質問**: OQ-054 の答えで、地図に自分の家・登録のときの候補・知り合い（自分の住所録に入れた住民）の家の印を付け、空き家か人がいるかを名前なしの 2 値で示すと決まった（ADR-0042）。範囲が答えになかったので、次の 4 点を聞いた。

掲示板で相手がオープンにしているときに知り合いになる経路を MVP の範囲で設ける（D7、答え「2 つ必要」）。中身は答えになく、答えが出るまで作らない。

### OQ-071 — 地図の知り合いの家の印は、自分の住所録のすべてのエントリに付ける。地図と新聞・手紙で「知り合い」の定義を分け、地図の印は `acquainted` で変えない（矛盾 → 決定）

### OQ-088 — 休眠を空き家にする判定と閾値、転送中の旧住所の地図の表示（未確定）

**関連**: FR-006, FR-071, FR-115, FR-072, F-16, F-19, ADR-0060, ADR-0062, ADR-0084, ADR-0091（OQ-010・OQ-023・OQ-024 にかかわる）

(1) 休眠を空き家にするか、するならその判定と閾値。OQ-079 の答え 2「休眠は空き家にしない。長くログインしていない判定に対する閾値などはMVP後に検討。いずれ空き家判定にする可能性はある」で、休眠（`dormant`）は入居と扱い、空き家にしないことが決まった（ADR-0060 の D2・D3）。
休眠からさらに空き家（`vacant_expired`）にする判定を作るか・閾値をいくつにするか、休眠にする閾値（今は暫定の 12 か月と通知）をどうするかは MVP の後に検討することになった。
(2) 転送中の旧住所（引っ越しのあと、転送期間 6 か月の間。ADR-0060 の D4）を、地図で入居と示すか空き家と示すか。答えはこの点に触れていない。今の `addresses.status` は転送期間が終わるまで `active` のまま。
