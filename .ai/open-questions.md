## §1 分類と扱い

### 分類

| 分類 | 意味 |
|------|------|
| 不足 | 構想・要件・機能に記述がなく、設計・実装に進むと定義できないもの |
| 未確定 | 記述はあるが値・範囲・方針が確定していないもの |
| 矛盾 | 文書間または文書内で記述が食い違っているもの |
| リスク | 決定しないままにすると品質・安全性・体験に悪影響が出るもの |

### 扱い

| 扱い | 意味 |
|------|------|
| 要回答 | マスターの判断が必要。質問の形で記載し、暫定対応がある場合は添える |
| 決定 | 秘書が判断し ADR に記録した、またはマスターの答えで決まり ADR に記録した。理由（マスターの答えなら原文と日付）と ADR 番号を添える |
| 持ち越し | 後続の設計文書（architecture/db/api/async/security/roadmap/environment）で決定する |

## §4 決定（ADR リンク付き）

### OQ-001 — マッチングは恋愛のためのものではない（未確定 → 決定）

**関連**: FR-061, FR-064, FR-069, FR-101, F-18  
**もとの質問**: 恋愛マッチングの利用を 18 歳以上に限定するか。年齢確認の手段も合わせて。  
**マスターの答え（2026-11-19）**: 「理想としては、恋愛ではない。あくまで、興味ある人同士が連絡を取れる手段。個別に連絡先の共有などは絶対禁止にする予定」  
**決定**: マッチングは恋愛のためのものではなく、恋愛のカテゴリは設けない。恋愛のための年齢条件・年齢確認は要らない。
マッチングは興味のある住民どうしが連絡を取れる手段で、成立後は街の中の手紙でやり取りする。
住民どうしが個別に連絡先を共有することは禁止する（FR-101）。マッチングの登録と提案に、街の外の連絡先の欄を設けない。  
**決めていないこと**: 「連絡先」と禁止の範囲（OQ-041、要回答）。未成年とマッチングへの参加の年齢条件（OQ-004 → 決定、年齢条件なし、ADR-0027）。違反した住民への処置（OQ-037）。  
**ADR**: [0024-matching-not-romance-no-contact-sharing](.ai/adr/0024-matching-not-romance-no-contact-sharing.md)

### OQ-002 — 配達完了の通知は送り、郵便の件数を含める（未確定 → 決定）

**関連**: FR-028, FR-102, F-05  
**もとの質問**: 朝便・夕便の配達完了時に住民へプッシュ通知を送るか。送る場合は通知の内容（「郵便が届いた」のみか、件数も含めるか）。  
**マスターの答え（2026-11-19）**: 「通知あり（内容：郵便の件数を含む）」  
**決定**: 配達回の公開のあとに、住民へ通知を 1 回送り、その住民に届いた郵便の件数を含める。
手段は Web Push で、住民が端末ごとに許可したときだけ届く。公開から 30 分を過ぎたら送らず、`skipped` の便では送らない（J15 `notify.delivery`）。
件数は通知の中身にだけ載せ、API の応答には載せない。  
**決めていないこと**: 何を「郵便」として数えるか・0 通の便で送るか・件数のほかの中身（OQ-042、要回答）。  
**ADR**: [0025-delivery-notification-web-push-with-count](.ai/adr/0025-delivery-notification-web-push-with-count.md)

### OQ-003 — クローズドな手紙も審査し、本文は LLM に渡さず、アクセスを厳しく限る（未確定 → 決定）

**関連**: FR-078, NFR-005, F-08  
**もとの質問**: 個人間・グループ間のクローズドな手紙を AI モデレーションの対象にするか。対象とする場合、プライバシー保護の措置（閲覧できる条件・範囲）も合わせて。  
**マスターの答え（2026-11-19）**: 「対象とする。ただし、LLMには渡さず、厳格なアクセス制御を行う」  
**決定**: 個人宛・グループ宛の手紙も配達の前に審査する。本文（一部や要約も）は LLM に渡さず、ルール表だけで照合する。
当たらなければ配達し、当たれば `blocked` にして配達しない（記録は当たった規則の ID と版だけ）。打ち切りまでに判定できない手紙は届けず、J5（公開できなければ J6）が次の便へ移す。
本文を復号してよいのは、(a) 送った人と受け取った人が読む (b) worker の中の J2 の照合 の 2 つと、暫定の (c) 通報された手紙をモデレーターが 1 通だけ確かめる（通報が `open`・当事者でない・二要素認証済み・毎回 `view_letter` を記録。YGO-007 からの暫定を続ける。OQ-043 (3)）に限る。
送った人には `blocked` を「届けられませんでした」と見せ、当たった規則は見せない。M4 で作る。  
**決めていないこと**: 手紙で止める内容と、モデレーターが手紙を見てよい場面（止めた手紙・通報された手紙。OQ-043、要回答）。  
**ADR**: [0026-closed-letters-rule-only-moderation](.ai/adr/0026-closed-letters-rule-only-moderation.md)

### OQ-004 — 未成年の利用を認め、年齢制限・特別な制限を置かない（不足 → 決定）

**関連**: FR-094, FR-064, F-02, F-18  
**もとの質問**: 未成年の利用を認めるか。認める場合は利用制限（マッチング（F-18）への参加の制限など）と保護者の同意の要否、認めない場合は年齢確認の方法（生年月日の入力だけか外部の確認か）。  
**マスターの答え（2026-11-19）**: 「年齢制限なし・特別な制限なし」  
**決定**: 未成年の利用を認め、登録に年齢制限を置かない（D1）。未成年だけに効く機能の制限・保護者の同意の手続き・年齢確認（生年月日の入力も外部の確認も）は設けず、
マッチング（F-18）への参加にも年齢条件を置かない（D2）。年齢を使う場面がないので、生年月日・年齢は集めない（D3、`security.md` §2.2）。
ブロック・通報・審査と連絡先の共有の禁止（FR-101）は、年齢に関係なくすべての住民に同じに効く。  
**決めていないこと**: 適用法令が未成年の利用について何かを求めるか（OQ-032、持ち越し）。  
**ADR**: [0027-minors-no-age-restriction](.ai/adr/0027-minors-no-age-restriction.md)

### OQ-005 — 架空の街の地図は静的な画像として MVP で作る（不足 → 決定）

**関連**: FR-103, F-19  
**もとの質問**: brief §2 の共通機能に「架空の街・地図・住所」が挙げられているが、地図の具体的な形（静的な画像か、インタラクティブか、住民が自分の住所の場所を見られるものか）と、どの段階で実装するか。  
**マスターの答え（2026-11-19）**: 「静的な画像として実装し、開発の初期段階で行う」  
**決定**: 地図は 1 枚の静的な画像（SVG を `<img>` で出す）とし、対話的な操作（拡大・移動・クリック）はしない（D1 (a)、答え）。
画像は全住民に同じにする（D1 (b)、秘書の判断と OQ-044 の暫定）。地図のための API・DB の表・ジオデータ・外部の地図サービスは持たない（D3・D5）。
ログインしていない人に地図の画面を出すかは決めない（D1。静的なファイルなのでセッションなしでも取れる、という技術上の結果だけを D3 に書いた）。段階は MVP（開発の初期段階）、マイルストーンは M1（住所・アカウント）で作る（D2。M1 は秘書の判断）。
画像には住民・入居・空き家・数を描かず、区画は「番」までにする（D4）。レポジトリの中で描いた架空の図で、代替テキストを付ける（D6）。  
**決めていないこと**: 地図の上で住所の場所を示すか（自分の住所・登録のときの候補。OQ-044、要回答）。  
**ADR**: [0028-town-map-static-image-in-mvp](.ai/adr/0028-town-map-static-image-in-mvp.md)

### OQ-006 — 商店・団体のアカウントは管理者が作る（不足 → 決定）

**関連**: FR-046, FR-047, FR-104, F-17  
**もとの質問**: 商店街に情報を発信する「商店・団体」のアカウントは、誰が作成・管理するか。一般の住民がお店を「開く」形式か、管理者が設定する形式か。

**決めていないこと**: 誰が商店・団体になるか・作ったあと誰が発信するか（OQ-045、要回答。答えの後半の問い返しへの説明も OQ-045 に書いた）。F-17 は OQ-045 の答えまで止まる。

### OQ-007 — 新規登録は開放式（未確定 → 決定）

**関連**: FR-091, F-02  
**もとの質問**: 新規住民の登録は、誰でも自由に登録できる開放式か、既存住民からの招待が必要な招待制か。  
**マスターの答え（2026-11-19）**: 「開放式」  
**決定**: 招待なしで誰でも新規登録できる。登録の API は招待トークン・紹介者を受け取らず、要求のスキーマにもその項目を置かない。招待トークンの管理は C2・C3 に加えない（D1、答え）。
登録の入り口は、すでにあるメールの確認・流量の制限（対象に登録の要求を明記、新しい数値は置かない）・手紙と掲示板の 1 日の上限・モデレーションで守り、新しい仕組みは足さない（D2、秘書の判断）。  
**決めていないこと**: メールの確認が済まないままの登録が住所を押さえ続ける期限と、期限が来た住所を候補に戻すか（OQ-046、持ち越し）。  
**ADR**: [0030-open-registration](.ai/adr/0030-open-registration.md)

### OQ-017 — LLM はラベルのみ返し、公開判断はルール表で決める（未確定）

**関連**: FR-079, NFR-011, NFR-012, F-08

### OQ-043 — 手紙で止める内容と、モデレーターが手紙を見てよい場面（未確定）【要回答】

**関連**: FR-078, NFR-005, F-08, ADR-0026（OQ-041・OQ-037 にかかわる）  
**質問**: OQ-003 の答えで「対象とする。ただし、LLMには渡さず、厳格なアクセス制御を行う」と決まりました。
手紙はルール表（決められた規則）だけで照合し、当たった手紙は配達しません。次の 3 点を教えてください。
(1) 手紙で止める内容は何ですか（ルール表のどの項目を手紙に当てますか）。掲示板と同じ項目にするか、手紙だけの項目にするか、
手紙では止めないものがあるか（例: 住民どうしの私的なやり取りとして許すもの）も教えてください。
(2) ルール表に当たって止めた手紙（通報されていないもの）を、モデレーターが見てよいですか。
見てよい場合は、どの目的（誤判定の確認・送った人の異議）で、どの条件で見てよいかも教えてください。
(3) 住民が通報した手紙を、モデレーターが本文を読んで確かめてよいですか。よい場合は、その条件
（例: 通報が処理中・当事者でない・二要素認証済み・1 回に 1 通だけ・読むたびに記録）も教えてください。
読ませない場合は、通報された手紙は本文を見ずに扱います（例: 通報した人のブロックだけで対応する）。

**暫定**: (1) 本番のルール表に手紙に当てる項目を置かない（仕組みはテスト用の偽の規則で確かめる）。
(2) 止めた手紙は人が見ない。送った人には「届けられませんでした」とだけ見せ、当たった規則は見せない。
(3) 通報された手紙は、モデレーターが 1 通だけ確かめる（YGO-007 からの暫定を続ける。条件は通報が `open`・当事者でない・二要素認証済み・1 回に 1 通、
読むたびに `view_letter` を記録、応答は `no-store`。ADR-0026 の D4 (c)）。
この暫定では、答えが出るまで本番で止まる手紙はない。
答えで変わる箇所: 本番のルール表の手紙の項目（`security.md` §5.1）、止めた手紙と通報された手紙の権限の行（`security.md` §4.2）・
復号してよい場面の (c)（`security.md` §2.3・§5.4、ADR-0026 の D4 (c)）・
`GET /api/v1/admin/reports/{id}/letter` の有無と条件（`api.md` §7 F-08）、止めた手紙の本文の保持期間（ADR-0013 の表にまだない）、

答えで変わる箇所: 発信する主体の認証（C2）とロール・主体の種類（ADR-0020、`security.md` §4）、F-20（FR-083）との境、

### OQ-046 — メールの確認が済まない登録が住所を押さえる期限（不足）
