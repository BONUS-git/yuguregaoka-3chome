## §1 分類と扱い

### 分類

| 分類 | 意味 |
|------|------|
| 不足 | 構想・要件・機能に記述がなく、設計・実装に進むと定義できないもの |
| 未確定 | 記述はあるが値・範囲・方針が確定していないもの |
| 矛盾 | 文書間または文書内で記述が食い違っているもの |
| リスク | 決定しないままにすると品質・安全性・体験に悪影響が出るもの |

### 扱い

| 扱い | 意味 |
|------|------|
| 要回答 | マスターの判断が必要。質問の形で記載し、暫定対応がある場合は添える |
| 決定 | 秘書が判断し ADR に記録した、またはマスターの答えで決まり ADR に記録した。理由（マスターの答えなら原文と日付）と ADR 番号を添える |
| 持ち越し | 後続の設計文書（architecture/db/api/async/security/roadmap/environment）で決定する |

### OQ-001 — マッチングは恋愛のためのものではない（未確定 → 決定）

**関連**: FR-061, FR-064, FR-069, FR-101, F-18  
**もとの質問**: 恋愛マッチングの利用を 18 歳以上に限定するか。年齢確認の手段も合わせて。  
**マスターの答え（2026-11-19）**: 「理想としては、恋愛ではない。あくまで、興味ある人同士が連絡を取れる手段。個別に連絡先の共有などは絶対禁止にする予定」  
**決定**: マッチングは恋愛のためのものではなく、恋愛のカテゴリは設けない。恋愛のための年齢条件・年齢確認は要らない。
マッチングは興味のある住民どうしが連絡を取れる手段で、成立後は街の中の手紙でやり取りする。
住民どうしが個別に連絡先を共有することは禁止する（FR-101）。マッチングの登録と提案に、街の外の連絡先の欄を設けない。
「連絡先」は街の外の連絡先だけで、禁止はマッチングの中だけ（OQ-041 → 決定、2026-11-19、ADR-0034）。  
**決めていないこと**: マッチングの中での守り方の細部（OQ-050、持ち越し）。未成年とマッチングへの参加の年齢条件（OQ-004 → 決定、年齢条件なし、ADR-0027）。違反した住民への処置（OQ-037 → 決定、内容はマスターが後で決める、ADR-0032。残りは OQ-048、持ち越し）。  
**ADR**: [0024-matching-not-romance-no-contact-sharing](.ai/adr/0024-matching-not-romance-no-contact-sharing.md)

### OQ-002 — 配達完了の通知は送り、郵便の件数を含める（未確定 → 決定）

**関連**: FR-028, FR-102, F-05  
**もとの質問**: 朝便・夕便の配達完了時に住民へプッシュ通知を送るか。送る場合は通知の内容（「郵便が届いた」のみか、件数も含めるか）。  
**マスターの答え（2026-11-19）**: 「通知あり（内容：郵便の件数を含む）」  
**決定**: 配達回の公開のあとに、住民へ通知を 1 回送り、その住民に届いた郵便の件数を含める。
手段は Web Push で、住民が端末ごとに許可したときだけ届く。公開から 30 分を過ぎたら送らず、`skipped` の便では送らない（J15 `notify.delivery`）。
件数は通知の中身にだけ載せ、API の応答には載せない。  
**決めていないこと**: 何を「郵便」として数えるか・0 通の便で送るか・件数のほかの中身（OQ-042 → 決定、2026-11-19、ADR-0035。新聞と手紙の通知を分け、配達の時刻も分けた）。
新聞の中身（知り合いが少なくても成り立つ紙面）は OQ-051（OQ-051 → 決定、2026-11-20、ADR-0039。残りは OQ-058〜OQ-062）。  
**ADR**: [0025-delivery-notification-web-push-with-count](.ai/adr/0025-delivery-notification-web-push-with-count.md)

### OQ-003 — クローズドな手紙も審査し、本文は LLM に渡さず、アクセスを厳しく限る（未確定 → 決定）

**関連**: FR-078, NFR-005, F-08  
**もとの質問**: 個人間・グループ間のクローズドな手紙を AI モデレーションの対象にするか。対象とする場合、プライバシー保護の措置（閲覧できる条件・範囲）も合わせて。  
**マスターの答え（2026-11-19）**: 「対象とする。ただし、LLMには渡さず、厳格なアクセス制御を行う」  
**決定**: 個人宛・グループ宛の手紙も配達の前に審査する。本文（一部や要約も）は LLM に渡さず、ルール表だけで照合する。
当たらなければ配達し、当たれば `blocked` にして配達しない（記録は当たった規則の ID と版だけ）。打ち切りまでに判定できない手紙は届けず、J5（公開できなければ J6）が次の便へ移す。
本文を復号してよいのは、(a) 送った人と受け取った人が読む (b) worker の中の J2 の照合 の 2 つと、(c) 通報された手紙をモデレーターが 1 通だけ確かめる（通報が `open`・当事者でない・二要素認証済み・毎回 `view_letter` を記録。もとは暫定で、OQ-043 → 決定、2026-11-19、ADR-0036）に限る。
送った人には `blocked` を「届けられませんでした」と見せ、当たった規則は見せない。M4 で作る。
（照合の時点と方法は OQ-052 → 決定、2026-11-20、ADR-0040 で置き換えた: 照合は送るときに API が暗号化の前に行い、(b) はなくなった。
当たったら送った人が y / n を選び、y の手紙（`held`）をモデレーターが (c) と同じ条件で確かめる (d) が加わった）  
**決めていないこと**: 手紙で止める内容と、モデレーターが手紙を見てよい場面（OQ-043 → 決定、2026-11-19、ADR-0036。通報された手紙は確かめてよい）。
手紙で止める内容と、止めた手紙の閲覧は OQ-052（→ 決定、2026-11-20、ADR-0040。スパム・外部リンク・成人向けの言葉。残りは OQ-065、持ち越し）。  
**ADR**: [0026-closed-letters-rule-only-moderation](.ai/adr/0026-closed-letters-rule-only-moderation.md)

### OQ-004 — 未成年の利用を認め、年齢制限・特別な制限を置かない（不足 → 決定）

**関連**: FR-094, FR-064, F-02, F-18  
**もとの質問**: 未成年の利用を認めるか。認める場合は利用制限（マッチング（F-18）への参加の制限など）と保護者の同意の要否、認めない場合は年齢確認の方法（生年月日の入力だけか外部の確認か）。  
**マスターの答え（2026-11-19）**: 「年齢制限なし・特別な制限なし」  
**決定**: 未成年の利用を認め、登録に年齢制限を置かない（D1）。未成年だけに効く機能の制限・保護者の同意の手続き・年齢確認（生年月日の入力も外部の確認も）は設けず、
マッチング（F-18）への参加にも年齢条件を置かない（D2）。年齢を使う場面がないので、生年月日・年齢は集めない（D3、`security.md` §2.2）。
ブロック・通報・審査と連絡先の共有の禁止（FR-101）は、OQ-063 の答えまでは、年齢に関係なくすべての住民に同じに効く（ADR-0041 の D1 で年齢で変えることにした）。  
**決めていないこと**: 適用法令が未成年の利用について何かを求めるか（OQ-032、持ち越し）。
OQ-043 の答え（2026-11-19）で、マスターが年齢や設定で守り方を変える案を問い返した。この決定とは食い違うので変えず、OQ-052 で聞いた（ADR-0027 の追記）。
OQ-052 → 決定（2026-11-20、ADR-0041）: 年齢で守り方を変える。年齢は住民の設定をそのまま使い、確かめない（年齢確認・保護者の同意は今までどおり設けない）。
D2 の「特別な制限を置かない」と D3 の「年齢を集めない」は ADR-0041 で置き換えた。生年月日は今までどおり集めない。
何を変えるかは OQ-063、年齢の扱いは OQ-064（どちらも要回答）。答えまで年齢による違いと年齢の項目は作らない。  
**ADR**: [0027-minors-no-age-restriction](.ai/adr/0027-minors-no-age-restriction.md)

### OQ-005 — 架空の街の地図は静的な画像として MVP で作る（不足 → 決定）

**マスターの答え（2026-11-19）**: 「静的な画像として実装し、開発の初期段階で行う」

画像は全住民で共有する 1 枚の画像にする（D1 (b)。もとは秘書の判断と OQ-044 の暫定で、OQ-044 → 決定、2026-11-19、ADR-0037 の D1 (a)。画像は白黒。住民ごとに中身を変えないことは OQ-054 の暫定）。地図のための API・DB の表・ジオデータ・外部の地図サービスは持たない（D3・D5）。

画像には住民・入居・空き家・数を描かず、区画は「番」までにする（D4）。レポジトリの中で描いた架空の図で、代替テキストを付ける（D6）。  
**決めていないこと**: 地図の上で住所の場所を示すか（OQ-044 → 決定、2026-11-19、ADR-0037。全住民で共有する 1 枚の白黒の画像）。
印（知り合いの家・自分の住所・登録のときの候補）は OQ-054（要回答）、ゲーム風の地図は OQ-055（持ち越し）。

### OQ-006 — 商店・団体のアカウントは管理者が作る（不足 → 決定）

### OQ-042 — 新聞は全住民に定時に届けて通知し、手紙は午前・午後のランダムな時刻に届けて件数を通知する（未確定 → 決定）

**もとの質問**: OQ-002 の答えで「通知あり（内容：郵便の件数を含む）」と決まった。(1) 件数として数える「郵便」は手紙だけか。新聞（朝刊・夕刊）も 1 件として数えるか。
(2) その便で手紙が 0 通の住民にも通知を送るか。(3) 件数のほかに通知に載せたいもの（差出人の住所など）はあるか。

**決定**: 新聞は手紙の有無にかかわらず全住民に届け、通知も送る（D1、答え）。新聞は一定の時刻（朝刊 07:00・夕刊 17:00）に届け、手紙とは時刻を分ける（D2、答え）。

通知は「新聞が配達されました！」（件数なし）と「手紙が配達されました！（N通）」の 2 つに分け、差出人・本文・住所は載せない（D4、答え）。
手紙が 0 通の住民には手紙の通知を送らない（D5、答えから読み取ったもの）。手紙の時刻は配達回ごと・住民ごとに 1 つで、同じ回の手紙はまとめて届く（D6）。
時刻は 10 分刻みの枠を `SHA-256(run_id:resident_id)` で決め、J4 が `mailbox_items.visible_at` に書く。公開（J5）と状態の確定は今のまま 07:00 / 17:00。
新聞の通知は J5 が、手紙の通知は J0 が枠ごとに積み、期限はそれぞれの時刻から 30 分（D9〜D12、秘書の判断）。  
**決めていないこと**: 知り合いが少なくても成り立つ新聞の中身（住民ごとに変えるか・興味を集めるか・ニュースの出どころ・加工に LLM を使うか。OQ-051）。答えの「興味があることを回収して、ニュースを加工して新聞にする」は例で、決定にしていない（OQ-051 → 決定、2026-11-20、ADR-0039。残りは OQ-058〜OQ-062）。  
**ADR**: [0035-newspaper-for-all-letters-random-am-pm-separate-notifications](.ai/adr/0035-newspaper-for-all-letters-random-am-pm-separate-notifications.md)

### OQ-051 — 新聞は一人 1 枚にせず、知り合いの数で分けた組ごとの版にする。知り合いのない組は興味で分け、記事の文字は LLM が作り、組版はサーバーで行う（不足 → 決定）

**関連**: FR-106, FR-035, FR-036, FR-108, FR-109, FR-110, FR-111, F-06, ADR-0007, ADR-0035  
**もとの質問**: OQ-042 の答えで、新聞は全住民に一定の時刻に届けると決まった（ADR-0035）。住民や投稿が少ないと紙面がほとんど空になる。
(1) 紙面を住民ごとに変えるか。(2) 住民の興味を集めるか、どう集めるか。(3) ニュースの出どころ（(a) 街の中だけ・(b) 実在の外のニュース・(c) 運営が書く架空の記事）。
(4) ニュースの加工に LLM を使うか、使うなら「組版は LLM を使わず決定的に組む」（ADR-0007・FR-037）との扱い。  
**マスターの答え（2026-11-20）**:  
「１：変えたいが、サーバー負荷考えると一人１枚はきつい。知り合いで埋まるグループ一部埋まらないグループ、知り合い0のグループで分けて、0のグループは趣味、興味でさらにグループして出し分ける」  
「２：登録の時と後から設定、検索などから収集しようかな」  
「３：a,b」  
「４：使う。モデルやプロンプトは要検討。文字だけLLMで作成し、新聞の生成部分はサーバーで行う想定」  
**決定**: 紙面は住民ごとに組まず、組ごとの版にし、版の数は住民の数によらない（D1、答え 1）。住民を「知り合いで埋まる組」「一部埋まらない組」「知り合い 0 の組」に分ける（D2、答え 1）。
知り合い 0 の組は興味で分け、興味のない住民には共通の版、興味が複数ある住民には `SHA-256(run_id:resident_id)` で配達回ごとに 1 つの版を届ける（D3、答え 1。共通の版とハッシュは秘書の判断）。
興味は登録のとき（任意）とあとからの設定で、運用者が保つ一覧から選んで集める（D4、答え 2。一覧から選ぶこと・1 人 5 つまでは秘書の判断）。
興味は個人情報として扱い、本人だけが見て変えられ、件数を返さず、退去で即時に消す（D5、秘書の判断）。
素材は街の中と実在の外のニュースで、運営の架空の記事は使わない。外のニュースは worker が許可した送り先からだけ取り込み、ルール表に当てる（D6、答え 3）。
記事の文字は LLM（J16）が作って保存し、組版はサーバー（J3・C6）が保存した文字からテンプレートで決定的に行い、やり直しで LLM を呼ばない（D7、答え 4）。
LLM には承認済みの投稿・外のニュース・版の興味の名前だけを渡し、手紙・住所・ID・ニックネーム・住民ごとの興味は渡さない。出力は検査し、外れたとき・失敗したときは決まった形で組み、休刊にしない（D8、秘書の判断）。
住民が見られるのは自分の郵便受けに届いた版だけ（D11、秘書の判断）。MVP の M5 に入れる（D12）。FR-106 を直し、FR-108〜FR-111 を足した（D13）。  
**決めていないこと**: 知り合いで埋まる組・一部埋まらない組の紙面（OQ-058、要回答）。検索などから興味を集めること（OQ-059、要回答）。外のニュースの配信元・利用の条件・費用（OQ-060、持ち越し）。
LLM が書いた文の示し方と、住民の投稿を LLM が書き換えてよいか（OQ-061、要回答）。新聞の LLM のモデル・プロンプトと、記事と興味の結び付け方（OQ-062、持ち越し）。  
**ADR**: [0039-newspaper-editions-by-group-and-interest-llm-text-server-typesetting](.ai/adr/0039-newspaper-editions-by-group-and-interest-llm-text-server-typesetting.md)

### OQ-052 — 手紙は送るときにスパム・外部リンク・成人向けの言葉に当て、当たったら送った人が確認を頼むかを選び、頼んだ手紙をモデレーターが確かめる。年齢で守り方を変え、年齢は住民の設定をそのまま使う（未確定 → 決定）

**関連**: FR-078, FR-080, NFR-005, FR-094, FR-064, FR-112, FR-113, F-02, F-08, ADR-0026, ADR-0027, ADR-0036  
**もとの質問**: OQ-043 の答えで、通報された手紙はモデレーターが条件付きで確かめてよいと決まった（ADR-0036）。
(1) 手紙で止める内容は何か（ルール表のどの項目を手紙に当てるか）。(2) ルール表に当たって止めた手紙（通報されていないもの）を、モデレーターが見てよいか（誤判定の確認・送った人の異議）。
(3) 住民の年齢で、守り方（止める内容・使える機能）を変えるか。変えるなら、年齢をどう確かめるか（生年月日の入力だけか、外部の年齢確認か）と年齢の区切り。  
**マスターの答え（2026-11-20）**:  
「20以上でも危険な機能は設けない想定なので、年齢はユーザーの入力信用すればいいと思う。理由としては、高齢者が若く設定や、若い人が高齢者として設定など、完全に架空の自分になることも許容したいから。設定と別々で持つ必要はなく、設定した年齢がそのままこの世界に反映される。」  
「１：手紙で止めるのは一般的なスパムや外部リンク、18禁ワード等」  
「２：送った人の異議は有用だね。ただ、配達に影響するので、送信時点でチェック、引っ掛かったらポップアップでy/n選んでもらって、モデレーター確認かな」  
「３：変える。」  
**決定**（手紙は ADR-0040、年齢は ADR-0041）:
手紙に当てる項目は、スパム（`spam`）・外部リンク（`external_link`）・成人向けの言葉（`adult_words`）の 3 種類にする（ADR-0040 の D1、答え 1）。
メールアドレスと電話番号は外部リンクに含めない（ADR-0034 とそろえる。偽の連絡先を含む手紙は今までどおり届く）。成人向けの言葉の一覧は公開レポジトリに置かず、テストは偽の規則で確かめる。
答えの「等」にあたる項目は、この変更では足さない。
照合は送るとき（`POST /api/v1/letters`）に、API が暗号化の前に行う。worker は手紙を照合しない（J1 は `moderation_queue` に手紙の行を入れず、J2 は手紙を扱わず、J4 は判定を見ずに準備する）（D2、答え 2）。
使ったルール表の版と当たった規則の ID は `letters.rule_version`・`matched_rule_id` に残す。送ったときに当たらなかった手紙は、配達の前に当て直さない（D3、秘書の判断）。
当たったら、何も保存せずに 422（`letter_needs_review`）を返し、当たった規則は返さない。送った人はポップアップで y / n を選ぶ。
n なら何も保存しない（秘書の判断）。y なら `request_review: true` で送り直し、`held`（確認待ち）で保存し、送信済みに「確認中」と見せる（D4、答え 2）。
モデレーターは `/api/v1/admin/held-letters` で、通報された手紙と同じ条件（当事者でない・二要素認証済み・1 通ずつ・毎回 `view_letter` を記録・`no-store`・外れたら 404）で確かめ、
`approve` なら次の配達回で届き、`reject` なら `blocked`（送った人には「届けられませんでした」）にする（D5、答え 2）。
`blocked` の本文は 30 日で消す（`[assumed]`）。退去すると、その住民の `held`・`blocked` の手紙を消す（D6）。422 には流量の制限を掛ける（D7）。M4 で作る（D8）。FR-112 を足した。  
年齢で守り方を変える（ADR-0041 の D1、答え 3）。何を変えるかが決まるまで、年齢による違いは作らない。
年齢は住民が設定した値をそのまま使い、確かめない。架空の年齢を許し、「本当の年齢」は別に持たない（D2、答えの冒頭）。どの年齢にも危険な機能は設けない（D3）。
集めるのは年齢で、生年月日は集めない（D4、秘書の判断）。年齢の項目と `residents` の列は、OQ-063・OQ-064 の答えが出るまで置かない（D5、秘書の判断。データ最小化）。
登録に年齢制限を置かないこと（ADR-0027 の D1）は変えない。FR-113 を足し、FR-094・FR-064 を直した。  
**決めていないこと**: 年齢で何を変えるか（止める項目・使える機能・年齢の区切り。OQ-063、要回答）。
年齢の扱い（登録で必須か・あとから変えられるか・ほかの住民に見せるか・年とともに進むか。OQ-064、要回答）。
スパムの決め方・外部リンクの形の細部・言葉の一覧の置き場・ポップアップの文言・流量の制限の値・長く確かめられない `held` の扱い・`reject` された手紙への異議（OQ-065、持ち越し）。  
**ADR**: [0040-letters-checked-at-send-sender-confirms-moderator-reviews](.ai/adr/0040-letters-checked-at-send-sender-confirms-moderator-reviews.md)・[0041-age-self-declared-protections-vary-by-age](.ai/adr/0041-age-self-declared-protections-vary-by-age.md)
