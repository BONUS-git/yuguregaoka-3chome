## 2026-11-22 — 退去の J7 が住民を指す行を残し、住民の行を消せなかった（R-005・R-008）

- **問題**

  - 居住記録が `is_current = true` のまま残り、J4 が退去した住民にも新聞の行を作り続ける設計だった。
  - 直しの 1 回目の案は、J14 の居住記録の起点を `ended_at` にしていた（前の引っ越しで終わった行が退去の直後に消える）。また、居住記録を指す住所録の列で J14 の削除が止まることを未確定に回していた（秘書の見直しの R1-F1・R1-F2）。
- **根本原因**
  - J7 の手順を ADR の退去の表から書き、`db.md` §2 の `residents` を指す外部キーの一覧から書かなかった。
  - 外部キーごとの ON DELETE を決めていなかった。`db.md` の列の説明に「退去済みは NULL」と書いても、J7 に手順がなかった。
- **気づけなかった理由**
  - R-005 の直し（YGO-015）は、指摘にある `credentials` と `sessions` だけを見て、`residents` を指すほかの外部キーを見直さなかった。
  - 実装とテストがまだなく、`sh scripts/check.sh` は文書の中身を確かめない。
- **再発防止**
  - `db.md` §2 の「住民を指す外部キー」の表に、`residents` を指す列ごとの ON DELETE と J7 の手順を書く。`residents` を指す列を足す変更は、同じ変更でこの表と `async.md` J7 の手順に行を足す。
  - 退去にかかわるチケットの受け入れ確認に、`grep -c "FK→residents" .ai/db.md` の数が、その表に書いた列のうち `sessions` を除いた数と同じであることを入れる（2026-11-22 は 16）。
  - 外部キーにかかわる指摘を直すときは、指摘にある列だけでなく、同じ表を指す外部キーをすべて見直す。
  - 行を消すジョブ（J7・J14）の条件を決めるときは、消す表を指す外部キー（ここでは `tenancies` を指す `registered_tenancy_id`）も同じ変更で決める。止まりうると気づいたら「未確定」に回さない。
  - 保持期間の起点の列は、その期間の言葉（「退去から」）と同じ出来事で書かれる列にする。対象の行が 1 つでないとき（今の行と前の行）は、どの行にも同じ起点が入るかを確かめる。

## 2026-11-23 — 配達回の終わりの時刻を書くジョブがなかった（R-009）

- **問題**
  - `delivery_runs.finished_at` は、J14 の通知の記録の保持（30 日）と J15 の新聞の通知の期限（30 分）の起点として読まれていた。

- **気づけなかった理由**

  - 実装とテストがまだなく、`sh scripts/check.sh` は文書の中身を確かめない。
- **再発防止**
  - `db.md` の列の説明に、その列をどのジョブのどの手順（か、どの API）が書くかを書く。時刻の列は、NULL になる状態も書く。
  - 列を起点や条件に使う決定をするときは、チケットの受け入れ確認に、その列を書く UPDATE があることを確かめる grep（例: `grep -n "finished_at" .ai/async.md` に書く箇所と読む箇所の両方が出る）を入れる。

## 2026-11-26 — YGO-062 の 1 回目が、ロックファイルがなく依存の準備で止まった

- **問題**
  - YGO-062（M1 のテストの土台）の実装の 1 回目で、`sh scripts/prepare.sh` が「package-lock.json がないため npm install で作る（できたファイルをコミットすること）」と出して失敗し、検証に進めなかった。
- **根本原因**
  - 今のレポジトリには `scripts/prepare.sh`・`package.json`・`package-lock.json` がどれもない（`scripts/` は `check.sh` だけ）。1 回目の変更は残っていないため、失敗したときの `prepare.sh` が、その回が書いたものか秘書の準備の段階のものかは確かめられない（推測: 1 回目が `package.json` を足し、ロックファイルを足さないまま準備の段階に入った）。
  - チケット `.ai/tickets/YGO-062-m1-test-harness.md` は、ロックファイルを「ない（範囲に入れる）」とし、受け入れ確認 7 で `package-lock.json` があることを求める。しかし、ロックファイルをどのコマンドで作るか、`package.json` と同じ変更でコミットするかの手順を範囲に書いていない。
  - チケットは `prepare.sh` を「`npm ci` だけを動かす」と決めている。`npm ci` はロックファイルがないと失敗するため、ロックファイルのない変更は準備で必ず止まる作りだった。ロックファイルがないときに `prepare.sh` が何を出して止まるかも、チケットに書いていない。
  - `.ai/environment.md` §3.1 は「依存を変えるときは `scripts/prepare.sh` とマニフェスト・ロックファイルを同じ変更で直す」とし、§3.2 の 1 と §5 は「ネットワークを使うのは `npm ci` だけ」とする。最初のロックファイルを作る `npm install`（ネットワークが要る）をいつ誰が動かすかを、どの文書も書いていない。
  - 実装のジョブの中では依存を入れられない（秘書が検証の前に `prepare.sh` で入れる）。そのジョブがネットワークを使ってロックファイルを作れたかは確かめられない（推測: 作れなかった）。
- **気づけなかった理由**
  - チケットを切った変更（a18faaa）は、受け入れ確認 7 の「ロックファイルがある」と範囲の「`prepare.sh` は `npm ci` だけ」を突き合わせず、ロックファイルを作る手順が抜けていることを確かめなかった。
  - `sh scripts/check.sh` は文書だけを確かめ、`package.json` があるのにロックファイルがない状態を見つけない。実装の変更の中で、終える前に `prepare.sh` を動かして確かめる手順もなかった。
- **再発防止**
  - 次の手順はどれも、次の YGO-062 の実装の変更で行う（この変更では実装しない）。
  - その変更の始めに、チケットの「範囲」と「受け入れ確認」に下の手順（ロックファイルの作り方・`prepare.sh` の動き・`check.sh` の確かめ）を足す。
  - ロックファイルの作り方は、ジョブがネットワークを使えるかで分ける。
    - (a) `package.json` を書いたあと、始めに `npm install --package-lock-only --ignore-scripts` を 1 回試す。作れたら、できた `package-lock.json` を `package.json` と同じ変更に入れる。終える前に `sh scripts/prepare.sh` と `sh scripts/check.sh` を動かし、どちらも終了コード 0 であることを確かめる。
    - (b) 作れなかったら、ロックファイルを手で書かない。ジョブの中で次の 2 つだけを行う: (1) 止まった段（ロックファイルの作成）と、出たエラーの行をそのままチケットの「確かめた事実」に書く。(2) それまでの段のファイルを変更として出す（2 回目の再発防止の「変更 0 件で終えない」と同じ）。秘書の準備の段階がロックファイルを作ってくれることは当てにしない。1 回目に観測した準備の段階の出力は、ロックファイルを作らずに失敗し、変更の側がコミットすることを求めていた。準備の段階が作ってくれるというのは、この出力と合わない推測である。
  - 同じ変更で `.ai/environment.md` §3.1・§3.2 の 1・§5 を書き直す: 「ネットワークを使うのは `npm ci` だけ」に、例外として「最初のロックファイルを作る `npm install --package-lock-only`（依存を足す変更の中で (a) のとおり動かす）」を足し、できたロックファイルは `package.json` と同じ変更でコミットすることを書く。作れなかったときは (b) のとおりにする、と書く（準備の段階が作るとは書かない）。
  - `scripts/prepare.sh` は、`package.json` があり `package-lock.json` がないときはロックファイルを作らず、「依存を変える変更の中でロックファイルを作ってコミットする」と出して終了コード 1 で止まる。ロックファイルがあるときは `npm ci` だけを動かす。
  - YGO-062 の実装の変更で `scripts/check.sh` に、`package.json` があるのに `package-lock.json` がないとき、または `package.json` の依存の名前がロックファイルにないときに失敗する確かめを足す（ネットワークを使わない）。
  - 受け入れ確認に、ロックファイルを消した状態で `sh scripts/prepare.sh` と `sh scripts/check.sh` がどちらも終了コード 0 以外で終わることを足す。
