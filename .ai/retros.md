# 失敗の記録

失敗ごとに、問題・根本原因・気づけなかった理由・再発防止を書く。

## 2026-11-22 — 他の文書への提案の節にそろえ直しを積み残した（R-007）

- **問題**
  - `api.md`・`architecture.md`・`async.md`・`db.md`・`security.md`・`open-questions.md` の 6 文書に、他の文書の直しを後の変更に回す提案の節が残っていた。
  - どの提案が済んだかの印がそろっておらず、どの文書が正本か読めなかった。
  - これが `reviews/0001-design-review.md` の R-001・R-002・R-005・R-006・R-010・R-013・R-025・R-026・R-029 の原因になった。
- **根本原因**
  - YGO-001〜009 で文書を 1 つずつ書き、範囲の外の文書を直さずに提案の節に積んだ。
  - 後の変更が、提案の節を見直す手順を持っていなかった。
- **気づけなかった理由**
  - チケットの受け入れ確認が、その文書の中だけを見ていた。
  - `sh scripts/check.sh` は、文書が空でないことしか確かめない。
- **再発防止**
  - 提案の節を作らず、食い違う文書を同じ変更で直す。
  - 範囲の外の指摘が持つものは、その文書の未確定の箇所に、指摘か OQ の ID と一緒に書く。
  - チケットの受け入れ確認に、次の grep の結果を入れる（この行に当たらないよう、1 文字を `[]` で囲む）: `grep -rn "変更[提]案\|別[チ]ケット" .ai --exclude-dir=reviews --exclude-dir=tickets`

## 2026-11-22 — 退去の J7 が住民を指す行を残し、住民の行を消せなかった（R-005・R-008）

- **問題**
  - J7 の手順に、住民を指す行の扱いが抜けていた。R-005 は認証情報とセッション、R-008 は差出人・投稿者・居住記録（ほかに通報者・モデレーター・画像を上げた住民の列）。
  - そのため J7 の最後の `residents` の削除が外部キーで失敗し、再試行しても通らない設計だった。
  - 居住記録が `is_current = true` のまま残り、J4 が退去した住民にも新聞の行を作り続ける設計だった。
  - 直しの 1 回目の案は、J14 の居住記録の起点を `ended_at` にしていた（前の引っ越しで終わった行が退去の直後に消える）。また、居住記録を指す住所録の列で J14 の削除が止まることを未確定に回していた（秘書の見直しの R1-F1・R1-F2）。
- **根本原因**
  - J7 の手順を ADR の退去の表から書き、`db.md` §2 の `residents` を指す外部キーの一覧から書かなかった。
  - 外部キーごとの ON DELETE を決めていなかった。`db.md` の列の説明に「退去済みは NULL」と書いても、J7 に手順がなかった。
- **気づけなかった理由**
  - R-005 の直し（YGO-015）は、指摘にある `credentials` と `sessions` だけを見て、`residents` を指すほかの外部キーを見直さなかった。
  - 実装とテストがまだなく、`sh scripts/check.sh` は文書の中身を確かめない。
- **再発防止**
  - `db.md` §2 の「住民を指す外部キー」の表に、`residents` を指す列ごとの ON DELETE と J7 の手順を書く。`residents` を指す列を足す変更は、同じ変更でこの表と `async.md` J7 の手順に行を足す。
  - 退去にかかわるチケットの受け入れ確認に、`grep -c "FK→residents" .ai/db.md` の数が、その表に書いた列のうち `sessions` を除いた数と同じであることを入れる（2026-11-22 は 16）。
  - 外部キーにかかわる指摘を直すときは、指摘にある列だけでなく、同じ表を指す外部キーをすべて見直す。
  - 行を消すジョブ（J7・J14）の条件を決めるときは、消す表を指す外部キー（ここでは `tenancies` を指す `registered_tenancy_id`）も同じ変更で決める。止まりうると気づいたら「未確定」に回さない。
  - 保持期間の起点の列は、その期間の言葉（「退去から」）と同じ出来事で書かれる列にする。対象の行が 1 つでないとき（今の行と前の行）は、どの行にも同じ起点が入るかを確かめる。

## 2026-11-23 — 配達回の終わりの時刻を書くジョブがなかった（R-009）

- **問題**
  - `delivery_runs.finished_at` は、J14 の通知の記録の保持（30 日）と J15 の新聞の通知の期限（30 分）の起点として読まれていた。
  - しかし、どのジョブ（J1・J5・J6）にも書く手順がなく、NULL のままで起点が決まらない設計だった。
- **根本原因**
  - 列を `db.md` に足したとき、どのジョブのどの手順が書くかを決めなかった（列の説明が「—」だった）。
  - ADR-0025・ADR-0076 で起点を `finished_at` に決めたとき、書く側を確かめなかった。
- **気づけなかった理由**
  - 列を読む箇所と書く箇所を突き合わせる確認がなかった。
  - 実装とテストがまだなく、`sh scripts/check.sh` は文書の中身を確かめない。
- **再発防止**
  - `db.md` の列の説明に、その列をどのジョブのどの手順（か、どの API）が書くかを書く。時刻の列は、NULL になる状態も書く。
  - 列を起点や条件に使う決定をするときは、チケットの受け入れ確認に、その列を書く UPDATE があることを確かめる grep（例: `grep -n "finished_at" .ai/async.md` に書く箇所と読む箇所の両方が出る）を入れる。

## 2026-11-23 — 準備が終わらないと持ち越しに進まない分岐の順だった（R-010）

- **問題**
  - J0 の擬似コードで、「新聞の行があり準備が済んでいない → J4」が、最後の「持ち越しの打ち切りを過ぎた → J6」より先に当たっていた。J4 が失敗し続けると J0 は J4 を積み直すだけで、持ち越しも公開も起きなかった。J5 の枝と休刊の J3 の枝も、打ち切りのあとに先に当たっていた。
  - 準備の完了を判断する列（`delivery_runs.prepared_at`）が `db.md` になく、J4 にも書く手順がなかった。
- **根本原因**
  - 打ち切りで別の工程に移る分岐を、工程の順に並べた `elif` の最後に置いた。前の枝が当たり続ける場合を考えなかった。
  - J0 の条件（「準備が済んだ」）を書いたとき、その条件に使う列と、それを書く手順を決めなかった。
- **気づけなかった理由**
  - 擬似コードを、ふつうに進む場合の順にだけ読み、工程が失敗し続ける場合にどの枝に当たるかを確かめなかった。
  - 実装とテストがまだなく、`sh scripts/check.sh` は文書の中身を確かめない。
- **再発防止**
  - 打ち切りで別の工程に移る分岐は、その配達回の枝の先頭に置く（どの工程で止まっていても当たるように）。
  - 条件に使う列は、その列を書く手順と同じ変更で決める（`db.md` の列と、書くジョブの出力・冪等性を同じ変更で書く）。
